# 第 13 章 部署与验证：从零到 `/demo` 跑通

前十二章都在讲"代码为什么这样写"。这一章讲的是另一件事：**这些假设怎么在一台干净的机器上被重新验证一遍**。

部署代码只有六个文件——`Dockerfile`、`compose.yaml`、`.env.example`、`.dockerignore`、`alembic.ini`、`pyproject.toml`，加起来 316 行。但它们承载的判断密度不低于任何一个 Agent 模块，因为部署期的错误有一个共同特征：**症状是"看起来正常"**。依赖版本漂移不会报错，只会让某个 Provider 行为微妙不同；`.env` 里一个空串不会报错，只会让一个本该受保护的端口对外敞开；迁移和种子之间用 `;` 而不是 `&&` 不会报错，只会让 API 带着一张空的知识图启动，然后每次检索都返回零条结果——而零条结果在 Agent 系统里长得很像"这个问题确实没有相关知识"。

这一章的读法和前面一致：先看实测输出，再逐文件读源码，最后给一份可以照着敲的验证清单。

这里要说清楚一件事，因为它是本项目评测诚实性规则的同一条原则（见 CLAUDE.md 的"评测数字的诚实性要求"）：`docker compose config` 能在守护进程未启动时成功，是因为它只做 YAML 解析和变量插值，完全不联系 Docker Engine。所以它证明的是"Compose 文件本身合法、`.env` 里该有的变量都有"，**不能**证明"镜像能构建成功"或"容器能跑起来"。本章后面凡是写"实测"的地方，都指上面这四条；凡是写"预期"的地方，都指需要守护进程才能确认的部分。区分这两者不是谦虚，是因为把"配置能解析"当成"部署验证通过"写进简历，是一句会在面试现场被拆穿的话。

## 13.2 Dockerfile：三个决定，每个都不是格式问题

26 行，全文：

```dockerfile
# 镜像先安装可复现的运行期 lock，再拷贝源码，这样应用模块改动不会让依赖层缓存失效。
# 最后一步的包安装使用 --no-deps，因为 requirements.lock 已经为这个 Linux 环境解析并安装了
# 完整依赖图；再解析一次只会引入与 lock 不一致的版本。
FROM python:3.11-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /workspace

COPY requirements.lock ./requirements.lock
RUN python -m pip install --no-cache-dir --upgrade pip \
    && python -m pip install --no-cache-dir -r requirements.lock

COPY pyproject.toml README.md alembic.ini ./
COPY app ./app
COPY mcp_server ./mcp_server
COPY data ./data

# 安装项目 wheel 是为了验证 app/ 与 mcp_server/ 都真的进入了可分发包：只依赖工作目录运行的话，
# 打包遗漏要等到部署时才暴露，而 MCP 子进程正是用 `python -m mcp_server.server` 启动的。
RUN python -m pip install --no-cache-dir --no-deps .

EXPOSE 8000

CMD ["uvicorn", "app.api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### 13.2.1 为什么 `COPY requirements.lock` 单独一行

Docker 镜像是分层的，每条 `RUN`/`COPY` 产生一层，缓存的失效是**级联**的：某一层的输入变了，它和它之后所有层都要重建。

依赖安装是这个镜像里最慢的一步（`requirements.lock` 有 alembic、asyncpg、fastapi、langgraph、mcp、openai、pgvector、pydantic、sqlalchemy、sse-starlette、uvicorn 及其全部传递依赖）。如果写成常见的偷懒版本：

```dockerfile
COPY . .
RUN pip install -r requirements.lock
```

那么改一行 `app/api/main.py` 的注释就会让 `COPY . .` 这一层的哈希变化，`pip install` 整层跟着重建。开发期每次改代码都要重新解析安装几十个包——这不是"慢一点"，这是让人放弃使用 Docker 验证，从而让"容器里能不能跑"这个问题一直没人回答。

先拷 lock、装完、再拷源码，就把"依赖变了"和"代码变了"分成了两个独立的缓存边界。改代码只重建后三条 `COPY` 和最后那次 `--no-deps` 安装，都是秒级。

`COPY pyproject.toml README.md alembic.ini ./` 放在源码之前也是同一逻辑，只是这三个文件变动频率介于 lock 和源码之间。`README.md` 出现在这里不是装饰：`pyproject.toml` 声明了 `readme = "README.md"`，构建 wheel 时 setuptools 会读它，少这一个文件最后那步 `pip install .` 直接失败。

### 13.2.2 `--no-deps` 不是省时间，是防止依赖图被重新解析

最后一步 `pip install --no-deps .` 很容易被误读成"优化"。它实际上是一道**一致性锁**。

`requirements.lock` 是 pip-compile 产物，头部记录了生成方式：

```text
#    pip-compile --output-file=requirements.lock --strip-extras pyproject.toml
```

也就是说 lock 里每个版本号都是针对这套 `pyproject.toml` 依赖声明**解析过一次的结果**，包括所有传递依赖。此时再运行一次不带 `--no-deps` 的 `pip install .`，pip 会按 `pyproject.toml` 里的范围约束（`fastapi>=0.116,<1` 这种）**重新解析一遍**。重新解析在绝大多数情况下会得到相同结果，但"绝大多数"在部署里不够用：只要上游发布了一个 lock 生成之后的新版本，pip 就会装上它，而镜像里的版本从此和 `requirements.lock` 不一致。

后果的形态是最难查的那一类：本地 venv 按 lock 装，容器按范围装，两边跑同一份代码得到不同行为，而两边的 `pip list` 你不会主动去比。

`--no-deps` 让这一步只做一件事：把 `app/` 和 `mcp_server/` 打成 wheel 装进 site-packages，一个依赖都不碰。

### 13.2.3 为什么要装 wheel，而不是直接在工作目录里跑

`WORKDIR /workspace` 里已经有 `app/` 和 `mcp_server/`，`uvicorn app.api.main:app` 靠当前目录就能 import。那为什么还要多一次安装？

因为 MCP 是真协议边界。回看第 3 章：`app/mcp/client.py` 用 `sys.executable -m mcp_server.server` 起 stdio 子进程。子进程的模块解析依赖的是 `sys.path`，而不是"我记得工作目录里有这个文件夹"。只要 `pyproject.toml` 的 `[tool.setuptools.packages.find]` 漏配了：

```toml
[tool.setuptools.packages.find]
include = ["app*", "mcp_server*"]
```

——比如只写了 `include = ["app*"]`——那么在工作目录里跑一切正常，但换任何一种以安装包方式分发的部署形态，`python -m mcp_server.server` 就会 `ModuleNotFoundError`。而这个错误的暴露时机是**第一次真正调用工具的时候**，也就是用户已经提了一个故障描述、Planner 已经决定要查 LTS 状态之后。

`RUN python -m pip install --no-cache-dir --no-deps .` 把这个检查提前到了**镜像构建期**：打包配置漏了包，`docker build` 当场失败，而不是等到有人在演示时点了"开始诊断"。

这是本项目反复出现的一个模式：**把只能在运行期发现的错误，改造成构建期或启动期发现的错误**。第 12 章的 lifespan 契约 ID 逐项比对是同一件事的另一个位置。

### 13.2.4 两个 `ENV` 与单阶段的选择

`PYTHONDONTWRITEBYTECODE=1` 避免在容器里生成 `.pyc`——镜像层里的 `__pycache__` 纯属体积浪费，容器生命周期内不会有第二次进程复用它带来的收益。`PYTHONUNBUFFERED=1` 是关键那个：Python 的 stdout 在非 tty 环境下默认全缓冲，不设这个变量的话，`docker compose logs` 里的启动日志会成块延迟出现，而 lifespan 的契约校验失败信息恰恰是你最想立刻看到的东西。容器崩得足够快时，缓冲区里的日志可能根本没有被 flush 出来——症状就是"容器退出了，日志是空的"。

这个 Dockerfile 是**单阶段**的。多阶段构建（builder 阶段编译、runtime 阶段只拷产物）能显著减小镜像，前提是有需要编译的原生扩展。本项目的依赖里 asyncpg、pydantic-core 都提供 manylinux wheel，`python:3.11-slim` 直接装二进制，builder 阶段没有产物可以丢弃。为了一个学习型演示项目引入多阶段，收益是几十 MB，成本是构建逻辑复杂一倍——这个权衡不成立，所以没做。

## 13.3 compose.yaml：两个服务，以及一条三段启动命令

文件名是 `compose.yaml`，不是 `docker-compose.yml`。这是 Compose V2 的规范文件名，`docker compose`（子命令形式，非独立的 `docker-compose` 二进制）优先读它。

先看 `database` 服务：

```yaml
services:
  # PostgreSQL 是本项目唯一的状态服务。pgvector 镜像把向量存储、全文检索、图边和长期案例记忆
  # 收在同一个基础设施边界内，而不是再引入独立的图数据库或向量库——多一个有状态组件就多一份
  # 备份、迁移和一致性成本，而本项目的检索规模完全用不上。
  database:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_DB: dataops
      POSTGRES_USER: dataops
      POSTGRES_PASSWORD: ${DATAOPS_DB_AUTH:?set DATAOPS_DB_AUTH in .env}
    ports:
      - "127.0.0.1:${DATAOPS_DB_PORT:-15432}:5432"
    healthcheck:
      test:
        - CMD-SHELL
        - "pg_isready -U dataops -d dataops"
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 5s
    volumes:
      - dataops-postgres:/var/lib/postgresql/data
```

镜像是 `pgvector/pgvector:pg16` 而不是官方 `postgres:16`，因为 pgvector 扩展需要预装。这条注释里的判断值得展开一句：一个"标准"的生产多 Agent 系统在这里通常是三个组件——PostgreSQL 存业务数据、Neo4j 存图、Qdrant/Milvus 存向量。本项目把三者收进一个 PostgreSQL，代价是图查询要手写递归 CTE（第 4 章）、向量检索受 pgvector 的索引能力限制；收益是**只有一个有状态组件**，也就是只有一套备份策略、一条迁移链、一处一致性边界。对于一个知识图规模在几百节点、案例记忆在几十条的项目，这个取舍是明显的。规模上去之后它会翻转，那时该换的是存储而不是这一章的结论。

### 13.3.1 `${VAR:?message}`：让缺配置在第一秒失败

```yaml
POSTGRES_PASSWORD: ${DATAOPS_DB_AUTH:?set DATAOPS_DB_AUTH in .env}
```

Compose 的变量插值有四种写法，区别不是风格：

| 写法 | 变量未设置时的行为 |
| --- | --- |
| `${VAR}` | 替换成空字符串，静默继续 |
| `${VAR:-default}` | 用 `default`，静默继续 |
| `${VAR:?message}` | **报错退出**，打印 `message` |
| `${VAR:+alt}` | 变量非空时才用 `alt` |

数据库口令用 `:?`，端口用 `:-`（`${DATAOPS_DB_PORT:-15432}`）。这个区分是刻意的：端口缺省有一个合理的默认值，口令没有。

如果这里写成 `${DATAOPS_DB_AUTH}`，`DATAOPS_DB_AUTH` 未设置时会插值成空串。而 `POSTGRES_PASSWORD` 为空串时，官方 PostgreSQL 镜像的行为是——**容器起得来**，因为它把空密码理解为"允许无密码连接"（配合 `POSTGRES_HOST_AUTH_METHOD` 的默认逻辑）。于是你得到一个能连、能读写、能演示的数据库，和一个完全没有口令保护的 5432 端口。

`:?` 让这种情况在 `docker compose up` 打印第一行日志之前就终止。前面 §13.1 那句 `compose config: OK` 之所以有意义，正是因为这条约束：它同时证明了当前 `.env` 里 `DATAOPS_DB_AUTH` 确实有值——如果没有，`docker compose config` 会直接失败，而不是输出一份带空密码的配置。**一个能同时验证语法和必需配置存在性的命令，比只验证语法的命令有用得多。**

### 13.3.2 两个端口都绑 `127.0.0.1`，因为默认鉴权是关的

```yaml
ports:
  - "127.0.0.1:${DATAOPS_DB_PORT:-15432}:5432"
```

```yaml
    # 端口只绑定回环地址：默认部署的鉴权是关闭的，绑到 0.0.0.0 等于把可触发付费模型调用的接口
    # 暴露到同网段。需要对外演示时应显式配置 bearer 令牌并放在反向代理之后。
    ports:
      - "127.0.0.1:${DATAOPS_API_PORT:-18000}:8000"
```

`ports: - "18000:8000"` 这种常见写法，宿主侧监听的是 `0.0.0.0`，也就是所有网卡。在咖啡厅 Wi-Fi 或公司内网里，这等于把服务开放给同网段的每一台机器。

对本项目来说这个风险有一个具体的形状。回看第 12 章：`api-auth:v1` 的默认模式是 `DATAOPS_API_AUTH_MODE=disabled`，这个默认值本身是刻意的——它让 `docker compose up --build` 之后能直接打开 `/demo` 演示，不需要先生成令牌、配请求头。但"默认无鉴权"和"绑定所有网卡"这两个决定**不能同时成立**，因为 `/api/v1/sessions/{id}/messages` 会触发 Planner 和 Auditor 的模型调用，而那是花钱的。一个开放的、无鉴权的、能触发付费 API 调用的端点，是一个可以被人当矿机用的东西。

所以两个默认值必须成对：鉴权默认关 → 端口默认只绑回环。想对外暴露，就得同时改两个地方（`DATAOPS_API_AUTH_MODE=bearer` 加 32 位令牌，以及改 `ports` 或者放到反向代理后面），而"必须同时改两处"本身就是一道刻意设置的摩擦——它让"不小心暴露"变成"明确决定暴露"。

宿主端口用 `15432` / `18000` 而不是 `5432` / `8000`，是为了不和本机已有的 PostgreSQL 或其它开发服务冲突。容器内部端口保持 `5432` / `8000` 不变，因为容器网络里的服务名寻址（`database:5432`）和宿主映射是两套独立的地址空间。

### 13.3.3 `env_file` 与 `environment`：一个容易漏的语义差别

```yaml
    # `.env` 里的 DATAOPS_* 配置（Provider、维度、鉴权模式、限流配额）需要真正进入容器，否则
    # 宿主上改完 .env 只影响 Compose 变量插值，容器内仍在跑仓库默认值。缺省的键保持未设置而不是
    # 空字符串，这一点对 DATAOPS_API_AUTH_TOKEN 尤其重要：空串会被解析成"已配置的空令牌"。
    env_file:
      - .env
    environment:
      DATAOPS_ENVIRONMENT: docker
      DATAOPS_DATABASE_URL: "postgresql+asyncpg://dataops:${DATAOPS_DB_AUTH}@database:5432/dataops"
```

这是新手最常踩的一处。Compose 会自动读取项目根目录的 `.env` 用于**变量插值**——也就是把 `compose.yaml` 里的 `${DATAOPS_DB_AUTH}` 替换掉。很多人由此以为 `.env` 的内容会自动成为容器的环境变量。**不会。**

插值发生在 Compose 解析文件的时候，在宿主上；容器环境变量的注入是另一回事，必须用 `env_file` 或 `environment` 显式声明。

漏了 `env_file: - .env` 的后果特别隐蔽：容器起得来，`/health` 返回 200，一切正常，只不过里面跑的是 `app/core/settings.py` 的仓库默认值。你在 `.env` 里配好的 `DATAOPS_CHAT_PROVIDER=openai-compatible`、`DATAOPS_EMBEDDING_PROVIDER=bge-m3:v1`、`DATAOPS_API_AUTH_MODE=bearer` 全部没生效——模型是 disabled、Embedding 回落到确定性哈希、端口没有鉴权。而这三件事的表现分别是"资源 API 返回 503"、"检索结果质量莫名偏低"、"看起来一切正常"。第三个是最坏的。

`environment` 里那两个键为什么不放在 `.env` 里：

- `DATAOPS_ENVIRONMENT: docker` 是**部署形态**而非用户配置。`.env.example` 里它是 `development`，容器里必须是 `docker`，这不该由使用者维护。
- `DATAOPS_DATABASE_URL` 里的主机名是 `database`——Compose 服务名，只在容器网络内可解析。宿主上跑本地 venv 时这个地址是无效的（宿主要用 `localhost:15432`）。把它写进 `.env` 会导致同一份 `.env` 无法同时服务两种运行方式。

注意 `environment` 的优先级高于 `env_file`，所以即使有人在 `.env` 里写了 `DATAOPS_DATABASE_URL`，容器里生效的仍是这条容器网络地址。这个覆盖方向是对的：容器不该被一个指向宿主 localhost 的 URL 带偏。

### 13.3.4 `depends_on: condition: service_healthy` 与两个 healthcheck

```yaml
    depends_on:
      database:
        condition: service_healthy
```

`depends_on` 的短语法（`depends_on: [database]`）只保证**启动顺序**：Compose 先启动 `database` 容器，再启动 `api`。它不保证 PostgreSQL 已经准备好接受连接。而 PostgreSQL 容器第一次启动时要初始化数据目录（`initdb`）、创建数据库和用户、执行 `/docker-entrypoint-initdb.d` 里的脚本——这个过程要几秒到十几秒。

`api` 服务的第一条命令是 `alembic upgrade head`，它会立刻尝试连库。短语法下这必然失败，而失败之后整条 `&&` 链断掉，容器退出。你会看到 `api` 容器反复重启（如果配了 restart policy）或者干脆退出码非零，日志里是 `ConnectionRefusedError`。

`condition: service_healthy` 把等待条件从"容器启动了"改成"容器的 healthcheck 通过了"：

```yaml
    healthcheck:
      test:
        - CMD-SHELL
        - "pg_isready -U dataops -d dataops"
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 5s
```

`pg_isready -U dataops -d dataops` 带上用户和库名很重要。不带参数的 `pg_isready` 只检测"服务器在监听端口"，而初始化期间 PostgreSQL 会先用临时配置启动一次（用于执行 initdb 脚本）再重启——那一瞬间端口是通的但业务库还不存在。指定 `-d dataops` 让健康判定包含"目标库可连接"这个条件。

`start_period: 5s` 的作用是：这 5 秒内的失败**不计入 `retries`**。没有它，初始化期间必然失败的前几次探测会消耗重试预算。`interval: 5s` × `retries: 10` 给了约 50 秒的初始化窗口，对 pg16 的首次 initdb 是充裕的。

`api` 自己也有 healthcheck：

```yaml
    healthcheck:
      test:
        - CMD
        - python
        - -c
        - "import urllib.request; urllib.request.urlopen('http://localhost:8000/health', timeout=2)"
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 5s
```

两个细节：

第一，用 `python -c urllib.request` 而不是 `curl`。`python:3.11-slim` 里**没有 curl**（slim 镜像剥掉了它）。写 `curl -f http://localhost:8000/health` 会让 healthcheck 永久失败——而且失败原因是 `executable file not found`，和"服务真的不健康"在 `docker inspect` 的输出里长得不太一样但很容易看漏。用解释器自带的 `urllib` 就不需要往镜像里装额外的包。

第二，探的是 `/health` 而不是某个 `/api/v1` 端点。这直接对应第 12 章 `api-auth:v1` 的前缀设计：`PROTECTED_PATH_PREFIXES = ("/api/v1", "/metrics")`，`/health` 刻意留在保护范围之外。如果健康探针必须带令牌，那令牌就得写进 `compose.yaml`——而 `compose.yaml` 是提交进版本控制的文件。"健康检查不需要凭据"不是偷懒，是为了让凭据不必出现在一个会被提交的文件里。

`urlopen` 在 4xx/5xx 时抛 `HTTPError`，进程非零退出，healthcheck 判定失败——所以这条探针同时覆盖了"服务没起来"和"服务起来了但 `/health` 返回错误"两种情况。而 `/health` 本身按第 12 章的设计是零 I/O 的（所有值都由 lifespan 缓存），所以 5 秒一次的高频探测不会给数据库添压力。

`volumes: - dataops-postgres:/var/lib/postgresql/data` 用具名卷而不是 bind mount。具名卷由 Docker 管理，跨 `docker compose down`（不带 `-v`）保留，所以案例记忆和知识图不会因为重启演示环境而丢；同时它避免了 Windows 上 bind mount 的文件权限问题——PostgreSQL 要求数据目录属主是 postgres 用户，而 Windows 文件系统映射进容器后的权限模型对不上，这会让 initdb 直接失败。

### 13.3.5 那个 `&&` 为什么必须是 `&&`

```yaml
    command:
      - sh
      - -c
      - "alembic upgrade head && python -m app.persistence.seed && uvicorn app.api.main:app --host 0.0.0.0 --port 8000"
```

三段命令，两个 `&&`。这是本章最值得单独讲的一行。

`&&` 是短路与：前一条命令退出码为 0 才执行下一条。换成 `;`（顺序执行，不管成败）会发生什么，分两种情况看：

**情况一：`alembic upgrade head` 失败。** 迁移失败的原因可能是数据库连不上、某个迁移里有语法错误、或者线性链断了（出现两个 head）。用 `;` 的话，seed 会接着跑——它会因为表不存在而失败——然后 `uvicorn` 照样启动。此时 API 进程活着，`/health` 会返回什么？回看第 12 章的 lifespan：数据库是**可选**依赖，连不上时 `memory_runtime` 和 `diagnosis_runtime` 都是 `None`，资源 API 返回 503。所以你得到的是一个 `/health` 200、`/api/v1/*` 全 503 的服务。这个状态和"我故意没配数据库"完全一样，于是你会去检查配置，而真正的原因是一条迁移写错了。

**情况二（更糟）：`alembic upgrade head` 成功，`python -m app.persistence.seed` 失败。** 表都建好了，但知识图和文档语料是空的。这时数据库连接是正常的，lifespan 的可选依赖检查全部通过，`diagnosis_runtime` 正常装配（假设模型也配了），资源 API 全部返回 200。用户提一个故障描述，Planner 正常跑 ReAct，MCP 工具正常返回 Observation，GraphRAG 检索——**返回零条知识节点**。

零条知识节点在这个系统里意味着什么？意味着 Evidence Bundle 里没有因果链、没有 Runbook 切片、没有根因锚点。Planner 只能基于工具 Observation 硬推，报告的引用会稀疏，Auditor 的确定性规则（第 9 章 `app/reporting/policy.py`）大概率判出"缺引用"类问题，报告被打回返工，返工预算耗尽后转 `degraded`。

于是最终症状是：**"这个 Agent 的诊断质量很差"**。而真实原因是种子脚本在启动时失败了，日志在几百行 uvicorn 请求日志上面。

`&&` 让这两种情况都变成同一个明确的结果：容器以非零码退出，`docker compose up` 打印种子脚本的 traceback，服务不启动。

这正好和 `app/persistence/seed.py` 的 `main()` 对上：

```python
def main() -> None:
    """把异步种子流程桥接为 `python -m app.persistence.seed` 命令行入口。

    `asyncio.run` 为短生命周期脚本创建并关闭事件循环；任何异常保持非零退出，让 Docker 启动链
    在迁移或种子失败时停止，而不是继续启动一个知识图不完整的 API。
    """

    asyncio.run(seed_database())
```

注意它**没有** `try/except`。一个"友好"的 CLI 入口通常会捕获异常、打印一行人类可读的错误、`sys.exit(1)`。这里刻意不做：`&&` 需要的只是非零退出码，而未捕获异常自动给出非零退出码**加上完整 traceback**。加一层 `except Exception as exc: print(f"seed failed: {exc}")` 反而会丢掉栈——而种子失败的原因往往在栈深处（某个节点的 `KnowledgeNodeType` 拼错、某条边引用了不存在的节点 ID、embedding Provider 的维度和数据库列不匹配）。

这一条串起了本项目的一个总体原则，前面几章反复出现过：**"少了一条通道"必须和"这条通道返回空"可区分**。第 12 章的 §12.18 把它总结为"空、零和不存在必须可区分"。`&&` 是这条原则在部署层的实现——它不让系统进入"通道缺失但接口正常"的中间状态。

## 13.4 Alembic：单 head 线性链，与一个编码陷阱

迁移链当前是十步，单 head（§13.1 实测 `20260716_0010 (head)`）：

```text
0001 → 0002 → 0003 → 0004 → 20260716_0005(session_checkpoints)
     → 20260716_0006(diagnosis_worker) → 20260716_0007
     → 20260716_0008(documents) → 20260716_0009(run_trace_spans)
     → 20260716_0010(remediation_risk_level)
```

有一个坑必须记住：**`20260716_0005_diagnosis_worker.py` 这个文件里的 `revision` 值是 `"20260716_0006"`**。文件名和 revision 不一致。Alembic 只认 `revision` / `down_revision` 变量，完全不看文件名，所以判断顺序永远看 revision 值。这是历史遗留的命名错位，改文件名会破坏已部署环境的 `alembic_version` 记录对应关系，所以留着并在文档里显式说明——修一个纯装饰性的不一致，代价是让所有已有部署的迁移历史需要人工干预，不值得。

"单 head"这个约束为什么重要：Alembic 允许分叉（两个迁移都以同一个迁移为 `down_revision`），此时 `alembic upgrade head` 会因为"有多个 head"报错。这在团队协作里很常见——两个人各自加了一条迁移。本项目的启动链里 `alembic upgrade head` 是第一段，所以链一分叉，容器就起不来。`alembic heads` 只输出一行是这个约束的验证方式，值得在合并任何带迁移的改动前跑一次。

### 13.4.1 `alembic.ini` 为什么必须是纯 ASCII

`alembic.ini` 41 行，本项目里唯一一个**注释必须写英文**的人工文件。文件头自己解释了原因：

```ini
[alembic]
# ASCII-only on purpose: Alembic and logging.fileConfig both read this file with the
# process locale encoding, so any CJK byte here breaks "alembic upgrade head" on a
# GBK/Shift-JIS Windows shell. The Chinese rationale (including why no database URL is
# stored here) lives in app/persistence/migrations/env.py, which is always read as UTF-8.
script_location = app/persistence/migrations
prepend_sys_path = .
```

这条约束和全局的"所有注释用中文"规则冲突，冲突的解决方式值得学：**不是破例，而是把中文说明搬到一个编码行为可控的文件里**。`app/persistence/migrations/env.py` 的模块 docstring 承接了完整中文解释：

```python
"""Alembic 异步迁移运行环境。

迁移 URL 只从 pydantic-settings 的 SecretStr 获取，不写入 alembic.ini。在线模式通过
异步引擎运行迁移，离线模式保留生成 SQL 的能力，两种模式共享 ORM metadata。

两条约束记录在这里而不是 alembic.ini：
1. 数据库 URL 刻意不写进 ini。凭据只经 `DATAOPS_DATABASE_URL` 进入进程，因此不会被提交进
   版本控制，也不会出现在迁移日志或 `alembic history` 输出里。
2. alembic.ini 必须保持纯 ASCII。Alembic 自身用 `encoding="locale"` 读取该文件，`fileConfig`
   也再读一遍，所以在中文 Windows（cp936）终端下，ini 里任何 CJK 字节都会让
   `alembic upgrade head` 在连接数据库之前就抛 UnicodeDecodeError；本文件是 Python 源码，
   永远按 UTF-8 解码，才是放中文说明的正确位置。
"""
```

技术细节：Python 的 `configparser` 默认用 `locale.getpreferredencoding()` 读文件，Alembic 内部还额外用 `encoding="locale"` 读一遍，`logging.config.fileConfig` 又读第三遍。在中文 Windows 上这个编码是 cp936（GBK）。UTF-8 编码的中文注释在 GBK 解码下就是无效字节序列，抛 `UnicodeDecodeError`。

失败点在**连接数据库之前**——`configparser` 解析 ini 是 Alembic 启动的第一步。所以症状是 `alembic upgrade head` 立刻崩，报的是编码错误而不是任何和迁移有关的信息。在 Linux 容器里（`LANG` 通常是 UTF-8 或 C.UTF-8）一切正常，在中文 Windows 开发机上必崩——一个只在部分环境出现的失败，最耗时。

Python 源码文件没有这个问题：PEP 263 规定 `.py` 默认按 UTF-8 解码，与 locale 无关。所以"中文说明放 `.py`，ini 保持 ASCII"是唯一正确的分工。

### 13.4.2 数据库 URL 刻意不写进 ini

Alembic 生成的默认 `alembic.ini` 有一行 `sqlalchemy.url = driver://user:pass@localhost/dbname`。本项目**删掉了它**。

URL 从 `env.py` 里通过 pydantic-settings 的 `SecretStr` 读取：

```python
settings = get_settings()
if settings.database_url is None:
    raise RuntimeError("DATAOPS_DATABASE_URL is required for migrations")
```

三个收益：

1. `alembic.ini` 是提交进版本控制的文件，不含 URL 就不可能提交凭据。
2. `SecretStr` 的 `__repr__` 是 `SecretStr('**********')`，所以即使某个异常把 settings 对象打进日志，口令也不会出现。取值必须显式调 `.get_secret_value()`——一个必须主动写出来的动作，比"默认就是明文"安全得多。
3. `alembic history`、`alembic current` 这类命令的输出不含 URL。这些命令的输出经常被贴进 issue 或聊天窗口。

`if settings.database_url is None: raise RuntimeError(...)` 这个显式检查也值得一提：不检查的话，`None` 会一路传到 SQLAlchemy 的 `create_async_engine`，抛出的错误是 `ArgumentError` 之类的底层信息，而不是"你需要设置 `DATAOPS_DATABASE_URL`"。**在边界上把缺配置翻译成人类可读的要求**，是本项目在每个入口重复做的事。

## 13.5 seed：幂等 upsert 与一个不该存在的中间状态

`app/persistence/seed.py` 90 行，是启动链的第二段。它的模块 docstring 说明了两个设计判断：

```python
"""人工知识种子与运维文档语料的幂等数据库写入入口。

容器在迁移后、API 启动前执行本模块。节点、边和文档使用 upsert，因此重复启动不会生成重复
记录；任何 Schema 或外键错误都会中止启动，而不是静默跳过坏数据。知识图与文档语料在同一个
事务里提交，避免出现"图已就绪但文档缺失"的中间状态——那种状态下检索仍会返回结果，只是永远
少了一条通道，而这在演示时几乎不可能被发现。
"""
```

**幂等是部署的硬要求。** `docker compose up` 会被反复执行——改了代码重新构建、机器重启、`docker compose restart`。每次都跑一遍 seed，如果用 `INSERT` 就会主键冲突（启动失败）或者生成重复节点（图被污染，一条边指向哪个副本变成随机的）。用 upsert（`ON CONFLICT DO UPDATE`）让"跑第一次"和"跑第 N 次"结果相同。

**"图已就绪但文档缺失"这个中间状态**是这个文件真正想防的东西。看提交时机：

```python
        async with factory() as session:
            repository = PostgresGraphRepository(session)
            document_repository = PostgresDocumentRepository(session)

            # 节点必须先于边写入，整个 Bundle 只提交一次以保证图结构原子可见。
            await repository.upsert_seed_bundle(embedded_bundle)
            await document_repository.upsert_document_library(embedded_library)
            await session.commit()
```

一次 `commit()`，覆盖知识图和文档语料两条通道。如果写成两次 commit，那么文档写入失败时，数据库里会留下一张完整的知识图和一个空的文档表。此后 API 正常启动、GraphRAG 正常返回节点和路径、`document-retrieval:v1` 永远返回零个切片。报告里会有引用，只是从来没有 Runbook 引用——**而"这个案例恰好没有相关 Runbook"是一个完全合理的解释**，所以没人会去查。

第 6 章讲文档 RAG 时提到过它是"第二条知识通道"，这里是那句话的部署侧后果：两条通道的可用性必须是原子的，否则系统会以"一条通道"的能力运行并且看不出异常。

还有两个次要但有代表性的细节：

```python
    # 在连接数据库前完成文件与图引用校验，让坏种子以更清晰、低成本的错误提前失败。
    bundle = load_knowledge_seed(settings.knowledge_seed_file)
    library = load_document_library(settings.document_manifest_file)
```

文件解析和图引用校验在建立数据库连接**之前**完成。一个 JSON 拼写错误不该表现为"连上库、开了事务、写了一半、回滚"，那样的错误信息里混着 SQLAlchemy 的事务栈。顺序换一下，错误就只有"这个 JSON 的第 N 个节点缺字段"。

```python
    # 远程 Provider 持有 httpx 连接池；种子是短进程，向量生成完成后立刻释放而不是等解释器退出。
    if hasattr(embedding_provider, "aclose"):
        await embedding_provider.aclose()
```

`hasattr` 鸭子类型判断，和第 12 章 lifespan 关闭 reranker 时用的是同一模式——确定性哈希 Provider 没有 `aclose`（它不持有任何连接），远程 Provider 有。写成 `isinstance` 检查会把 Provider 的具体类型泄漏到 seed 脚本里，而 Provider 的可替换性是第 5 章的核心边界。

## 13.6 .dockerignore：排除什么，以及刻意保留什么

11 行：

```text
# Exclude local development state and documents that are not required to run the
# API image. Application source, MCP server, migrations, and synthetic data remain
# in the build context because startup validation depends on them.
.venv
__pycache__
.pytest_cache
.ruff_cache
.git
.env
docs
tests
```

`.dockerignore` 的作用范围是**构建上下文**——`docker build` 开始时会把整个上下文目录打包发给守护进程。没有 `.dockerignore` 时 `.venv`（几百 MB）和 `.git`（含全部历史）都会被打包传输，即使 Dockerfile 里从来没 `COPY` 它们。这不只是慢：上下文的内容会参与缓存键计算，`.git` 每次提交都变，于是缓存永远失效。

两条排除项有安全含义：

- **`.env`** 必须排除。它含本机 API key 和数据库口令。这个 Dockerfile 没有 `COPY .env`，所以理论上不会进镜像——但 `.dockerignore` 是**结构性**防线：任何时候有人往 Dockerfile 里加了一条 `COPY . .`（一个很自然的偷懒动作），`.env` 就会被烤进镜像层，而且**删不掉**——镜像分层是只写的，后续 `RUN rm .env` 只是在新层里标记删除，前一层里的文件仍然可以被 `docker save` 导出。凭据一旦进了镜像层就等于泄漏。容器的配置由 `env_file` 在**运行时**注入，这是唯一正确的通道。
- **`.git`** 排除同理。它含完整历史，任何曾被误提交又被删除的凭据都还在 reflog 里。

`docs` 和 `tests` 排除是体积和职责考虑：运行 API 不需要它们，`pyproject.toml` 也把 pytest/ruff 隔离在 `[project.optional-dependencies].dev` 里，所以镜像里没有测试运行器，放测试代码进去也跑不了。

反过来看**刻意保留的**，注释里点了名：

- `app/` 和 `mcp_server/` —— 应用与 MCP 服务端，显然。
- `app/persistence/migrations/` —— 启动链第一段要用。
- **`data/`** —— 这个最容易被当成"测试数据"顺手排掉。它含 `data/fixtures/scenarios`（MCP 工具的 Fixture）、`data/fixtures/golden_cases.json`（28 条 Golden Case）、`data/knowledge/cross_chain_graph.json`（知识图种子）、`data/knowledge/documents/`（Runbook 语料）。前两个是 lifespan 启动校验的输入（第 12 章：Golden Case 必须引用已知场景、根因锚点必须是真实的 `ROOT_CAUSE` 节点 ID），后两个是 seed 的输入。少了 `data/`，容器在启动校验阶段就失败——这次是好事，因为 `&&` 和 lifespan 的 fail-fast 让它明确报错而不是静默降级。

`__pycache__` / `.pytest_cache` / `.ruff_cache` 是纯本地状态。`__pycache__` 还有一层：宿主上的 `.pyc` 是用宿主的 Python 编译的，混进 Linux 容器可能被误用（尽管有 magic number 校验），排掉更干净——这也是 Dockerfile 里 `PYTHONDONTWRITEBYTECODE=1` 的对称面。

## 13.7 .env：117 行里，79 行是边界说明

`.env.example` 是这套部署里信息密度最高的文件。它不是"默认值清单"，而是**每个旋钮的可调范围与调错的后果**。这里不逐行重复（前面各章已经讲过大部分参数的原理），只挑三组讲部署视角特有的东西。

### 13.7.1 三类凭据，三种处理方式

文件里有四个凭据位，全部以注释形式存在：

```text
# DATAOPS_API_AUTH_TOKEN=在此填入本机专用的至少32位随机令牌
# DATAOPS_CHAT_API_KEY=在此填入只存本机的密钥
# DATAOPS_EMBEDDING_API_KEY=在此填入只存本机的密钥
# DATAOPS_RERANK_API_KEY=在此填入只存本机的密钥
```

加上一个有占位值的：

```text
DATAOPS_DB_AUTH=在此填入本机专用的数据库口令
```

区别在于 `DATAOPS_DB_AUTH` 是**必填**（`compose.yaml` 用 `${DATAOPS_DB_AUTH:?...}` 强制），所以它在示例文件里必须是一个可见的、写着"请替换"的占位串——注释掉它会让复制完 `.env` 的人得到一个"变量缺失"错误，而不是一个"这里要填东西"的提示。另外四个是**选填**（不配就走 disabled / 确定性 Provider 路径），所以保持注释状态。

`.env.example` 开头那两行是整个文件的前提：

```text
# API 与确定性运行预算。使用 Docker 前先把本文件复制成 .env；生成的 .env 绝不能提交，
# 因为它会包含只存在于本机的凭据。所有键都带 DATAOPS_ 前缀，由 pydantic-settings 统一校验。
```

"`DATAOPS_` 前缀由 pydantic-settings 统一校验"这句在部署时有个具体好处：`app/core/settings.py` 的 `Settings` 用 `env_prefix="DATAOPS_"`，所以配置项和宿主环境里其它变量（`PATH`、`LANG`、别的项目的 `DATABASE_URL`）**不可能碰撞**。容器里 `env_file: .env` 会把 `.env` 全部注入，前缀让"哪些变量是这个应用的"一目了然。

### 13.7.2 为什么注释掉一行，比留空更安全

```text
# 令牌行请保持注释而不是留空：空串会被解析成"已配置的空令牌"。
```

这是本项目里"空、零和不存在必须可区分"这条原则最短的一个例子，也是最容易做错的一个。

`DATAOPS_API_AUTH_TOKEN=`（等号后面什么都没有）和把整行注释掉，在 shell 语义里完全不同：

- 整行注释 → 环境变量**不存在** → pydantic 的 `api_auth_token` 是 `None` → 第 12 章的启动校验判定"未配置令牌"。
- `KEY=` → 环境变量**存在且值为空串** → pydantic 拿到 `""`，这是一个 `str` 而不是 `None`。

如果 `security.py` 的校验写成 `if settings.api_auth_token is None: raise ...`，那么空串会通过这个检查。`MINIMUM_API_TOKEN_CHARS = 32` 那道校验会拦住它（`len("") < 32`），所以本项目实际上是安全的——但这份安全依赖于**第二道**校验，而不是第一道。`.env` 里保持注释状态，是不去考验第二道防线。

同样的逻辑适用于三个模型 Provider 的 key。`DATAOPS_CHAT_API_KEY=` 空串的话，Provider 工厂会认为"key 已提供"，然后带着一个空 Authorization 头去打端点，得到 401——而 `model-transient-retry:v1` 的规则是**认证失败不重试**（第 5 章），所以它会立刻上抛。这个结果是对的，但错误信息是"上游 401"，而不是"你没配 key"。

### 13.7.3 半配置：`bearer` 缺令牌 vs `disabled` 却配了令牌

```text
# 资源 API 的鉴权与限流（api-auth:v1）。默认关闭鉴权，让 `docker compose up` 之后就能直接演示，
# 因此 Compose 只把 API 端口绑定到 127.0.0.1。要保护 /api/v1 与 /metrics，必须同时把模式切成
# bearer 并设置至少 32 个可见 ASCII 字符的令牌；只设其中一个会拒绝启动——"配了令牌但模式是
# disabled"会让部署者误以为接口已受保护。
```

第 12 章讲过这两个方向都在启动期被拒。从部署视角补一句为什么**第二个方向更危险**：

- `bearer` 模式 + 无令牌：如果不拦，服务要么把所有请求都拒（没有令牌可比对），要么把所有请求都放（无从判定）。前者症状明显（一切 401），后者是灾难。
- `disabled` 模式 + 有令牌：这是一个人**做了保护工作**的现场——他生成了令牌、写进了 `.env`、可能还配了客户端。只是忘了改模式那一行。此时服务完全正常运行，`/demo` 能用，`/api/v1` 也能用（因为不校验），**没有任何异常症状**。他会认为端口已受保护，可能因此把 `ports` 改成 `0.0.0.0`。

第二种的症状是"一切看起来都对"，所以它必须在启动期被拒。这是本章开头那句话的又一个实例：部署期错误的共同特征是症状为"看起来正常"，所以防线只能设在启动之前。

`app/core/settings.py` 的 `_validate_api_security` 覆盖前两个条件（模式与令牌的存在性配对），`MINIMUM_API_TOKEN_CHARS = 32` 这个常量只活在 `app/api/security.py` 里——不在两处各写一遍 `32`，是为了它不会漂移。这个分工在第 12 章 §12.4.1 讲过，这里是它在 `.env` 侧的表现：`.env.example` 的注释写"至少 32 个"，但这个数字的**唯一权威定义**在 `security.py`。

### 13.7.4 三组时间预算的偏序，在 `.env` 里长什么样

第 7 章讲过 `_validate_react_budget`，第 12 章讲过 `_validate_run_stream`。这两组跨模块的偏序约束在 `.env.example` 里是以注释形式解释的，因为**它们是使用者最可能去调的旋钮，也是最容易调出隐性 bug 的地方**：

```text
# 这是覆盖 Planner 决策、LangGraph 调度和 MCP 调用的总墙钟预算，与单个工具超时相互独立；
# 它的作用是防止一串"每步都合法"的调用把整个 run 无限拖住。实测 Planner 单次 8–15s，8 步预算
# 本身需要约 150s，再加上一次瞬时重试的最坏开销（跑满 30s 超时 + 1s 退避）因此定在 240s；
# 配得太紧会让"时间不够"伪装成"步数用完"，也会让重试在退避途中被掐断。
DATAOPS_REACT_TOTAL_TIMEOUT_SECONDS=240
```

"配得太紧会让'时间不够'伪装成'步数用完'"——这句话描述的是一个**归因错误**：run 以 `react_budget_exhausted` 结束，你去调大 `DATAOPS_MAX_REACT_STEPS`，然而真正的瓶颈是墙钟。调完之后现象不变，你会以为"这个模型就是找不到根因"。

```text
DATAOPS_RUN_STREAM_POLL_SECONDS=0.5
DATAOPS_RUN_STREAM_KEEPALIVE_SECONDS=15
DATAOPS_RUN_STREAM_MAX_SECONDS=300
```

前面注释里那句"最长存活时间要大于 ReAct 总超时"是**跨模块**约束：`300 > 240`。这两个数字分属两个完全不同的子系统（推流和 ReAct 循环），如果有人只把 `DATAOPS_REACT_TOTAL_TIMEOUT_SECONDS` 调到 360 而不动推流，那么一个跑满 300 秒还没结束的正常 run 会被推流在 `stream_timeout` 处截断，浏览器上的表现是"流断了"。而这个 run 其实还在跑，60 秒后会正常完成——只是用户已经刷新页面了。启动期校验拦住这个组合，正是因为它的症状（流断）指向的模块（推流）不是真正需要改的模块（ReAct 预算）。

另外两组值得注意的独立性：

```text
DATAOPS_MAX_REACT_STEPS=8
DATAOPS_MAX_PARALLEL_TOOL_ACTIONS=3
```

```text
# 并行度与步数预算是两个独立旋钮：同一轮最多提交这么多个互不依赖的只读 Action，但一批 N 个 Action
# 仍然消耗 N 个步数。因此调大它只压缩 P95 等待时间，不会让 Planner 获得更多取证机会。
```

这是第 8 章"并行只买延迟，不买预算"的配置侧说明。为什么必须写在 `.env` 里：因为看到"并行度 3"最自然的联想是"能多查东西了"。如果一个使用者按这个错误理解把并行度调到 6 期待覆盖率提升，结果只会是覆盖率不变而单轮 token 消耗上升。

```text
DATAOPS_CHAT_TRANSIENT_RETRY_ATTEMPTS=2
DATAOPS_PLANNER_SCHEMA_REPAIR_COUNT=1
DATAOPS_AUDITOR_SCHEMA_REPAIR_COUNT=1
```

```text
# 瞬时重试与上面两个 Schema 修复预算是两套预算：修复处理"模型输出格式不对"，重试处理"请求根本
# 没打到模型"（429/5xx/超时/连接失败）。认证失败不重试。放大 ATTEMPTS 必须同时放宽
# DATAOPS_REACT_TOTAL_TIMEOUT_SECONDS，否则启动校验会直接拒绝——重试跑不完等于没加重试。
```

"重试跑不完等于没加重试"是这里的关键判断。把 `ATTEMPTS` 从 2 调到 4 而不放宽总超时，得到的不是"更强的容错"，而是"在退避途中被墙钟掐断"——比不重试更糟，因为你付了等待的时间成本却没拿到重试的收益。启动校验强制这个偏序，所以这种半配置无法上线。

### 13.7.5 Auditor 超时为什么单列

```text
DATAOPS_CHAT_TIMEOUT_SECONDS=30
# Auditor 超时单列：它要读完整草稿并逐条核对引用，实测耗时是 Planner 的两到三倍。共用 30s 会让
# 审计频繁超时，而超时按"审计不可用"直接降级，等于把审计路径整条关掉。
DATAOPS_AUDITOR_TIMEOUT_SECONDS=90
```

这条配置的后果链值得完整走一遍，因为它把第 9 章的四级降级阶梯和部署配置连起来了：

Auditor 超时 → 抛 `AuditorAgentError` → 工作流立即转 `degraded`，**且不消耗返工预算、不重跑报告**（因为"审计不可用"不等于"审计通过"）→ `degraded` 报告永远不会进入长期记忆（第 10 章 `stage_case_memory` 只接受 accepted 且含根因的报告）。

所以如果 Auditor 超时被配成和 Planner 一样的 30 秒，而实测 Auditor 需要 60–90 秒，那么**每一次诊断都会降级**。表现是：报告出得来（degraded 也是一份报告）、有内容、只是标着降级，而且长期记忆永远是空的。一个"审计路径整条关掉"的系统，从外部看和"审计路径存在但经常判降级"几乎无法区分。

两个超时分开，是因为它们衡量的工作量在**结构上**不同：Planner 每一步只看当前 Evidence Bundle 加已有 Observation，输出一个 Action；Auditor 要读完整草稿并对每一条引用回查证据。这不是"Auditor 慢一点"，是"Auditor 的输入长度和检查项数量都是另一个量级"。

## 13.8 pyproject.toml：三处配置，各自防一件事

```toml
[project.optional-dependencies]
# 开发依赖与运行容器的 lock 隔离，因此镜像里不会出现 pytest 与 ruff。
dev = [
  "httpx>=0.28,<1",
  "pip-tools>=7.5,<8",
  "pytest>=8.4,<9",
  "pytest-asyncio>=1.1,<2",
  "ruff>=0.12,<1",
]
```

运行依赖在 `[project].dependencies`，开发依赖在 `optional-dependencies.dev`。两个 lock 文件对应两个集合：`requirements.lock`（Dockerfile 装这个）和 `requirements-dev.lock`（本地开发装这个）。

隔离的收益不只是镜像小 20 MB。pytest 和 ruff 是**开发期工具**，它们出现在生产镜像里意味着容器内可以执行任意测试代码——而 `.dockerignore` 已经排掉了 `tests/`，所以镜像里有测试运行器但没有测试，这是一个纯粹的攻击面增量。httpx 是测试用的 HTTP 客户端（FastAPI 的 `TestClient` 依赖它），运行期完全不需要。

`pip-tools` 在 dev 里，因为 lock 文件是它生成的：

```text
#    pip-compile --output-file=requirements.lock --strip-extras pyproject.toml
```

`--strip-extras` 让 lock 里不出现 `uvicorn[standard]` 这种带 extra 的写法，而是把 extra 展开成具体的包（`httptools`、`uvloop`、`watchfiles` 等）。这让 lock 成为一份**完全展开的、无需再解析的**清单——正好是 Dockerfile 里 `--no-deps` 成立的前提。

```toml
[tool.pytest.ini_options]
# PostgreSQL 集成测试必须显式选择 marker，因为它们需要真实数据库；默认套件因此在没有基础设施的
# 面试环境里也能完整跑通，不会用 skip 把失败伪装成通过。
addopts = "-ra -m 'not postgres'"
testpaths = ["tests"]
markers = [
  "postgres: requires a running PostgreSQL/pgvector integration database",
]
```

"不会用 skip 把失败伪装成通过"是这里的核心判断。有两种排除数据库测试的方式：

1. 用 `pytest.mark.skipif(no_db)` —— 测试会跑，然后 skip。输出是 `418 passed, 12 skipped`。
2. 用 `-m 'not postgres'` deselect —— 测试根本不被收集。输出是 `430 passed, 12 deselected`。

区别在于**"skipped"和"deselected"读起来意思不同**。`12 skipped` 的自然读法是"有 12 个测试没通过但我们放过它了"，而且一个真正坏掉的测试如果 skip 条件写错也会显示为 skipped——于是坏测试藏在一堆 skip 里。`12 deselected` 明确说的是"这 12 个不在本次选择范围内"，是一个关于**选择**的陈述而不是关于**结果**的陈述。

§13.1 那条 `430 passed, 12 deselected in 221.54s` 因此是一句可以直接对外说的话：430 个测试全部通过，另有 12 个需要数据库、本次未选。没有任何一个测试处于"我们不知道它是好是坏"的状态。

```toml
[tool.ruff]
target-version = "py311"
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "ASYNC"]
```

六个规则集，其中 `ASYNC` 是这个项目特别需要的：它检测异步函数里的阻塞调用。第 12 章提过 `_resolve_demo_asset` 和 `_demo_index_available` 被刻意写成同步函数，正是为了让 `ASYNC` 能验证事件循环没被文件 I/O 阻塞——如果它们是 `async def` 里直接调 `Path.exists()`，`ASYNC` 会报出来。一个 Agent 系统里满是 `await`，阻塞调用混进去的后果是整个事件循环卡住（所有并发的 MCP 子进程调用一起变慢），而这种性能问题在小样本测试里根本看不出来。

`UP`（pyupgrade）保证代码用 3.11 的现代写法，`B`（bugbear）抓可变默认参数这类陷阱，`I`（isort）统一 import 顺序减少 diff 噪音。`line-length = 100` 而不是 black 默认的 88：本项目的中文注释信息密度高，88 列会让大量注释被迫折行，而折行的注释比长一点的注释更难读。

## 13.9 从零到 `/demo`：四条验证路径

这一节是可以照着敲的。四条路径按依赖递增排列，每条都有明确的"应该看到什么"——包括**哪些接口应该返回 503**。

先说清楚为什么 503 是正确行为而不是失败。`app/api/main.py` 有两个集中的守卫函数：

```python
def _require_memory_runtime(request: Request) -> PostgresMemoryRuntime:
    """读取 lifespan 发布的 memory runtime，未配置 PostgreSQL 时抛出 HTTP 503。

    该检查集中两个路由的降级语义，避免 AttributeError 或把禁用存储误报为空搜索；测试可注入满足
    相同方法的 runtime 替身验证 HTTP Schema。
    """

    runtime = request.app.state.memory_runtime
    if runtime is None:
        raise HTTPException(
            status_code=503,
            detail="case memory requires configured PostgreSQL",
        )
    return runtime


def _require_diagnosis_runtime(request: Request) -> DiagnosisApplicationRuntime:
    """读取 lifespan 发布的资源化诊断 runtime，依赖不完整时抛出 HTTP 503。

    runtime 只有在 PostgreSQL、Planner 和 Auditor 都配置后存在；集中检查防止四个路由分别产生
    AttributeError 或把 disabled 模式误报为未知 session/run。测试可注入满足同一方法的替身。
    """

    runtime = request.app.state.diagnosis_runtime
    if runtime is None:
        raise HTTPException(
            status_code=503,
            detail="diagnosis resources require PostgreSQL and configured Planner/Auditor",
        )
    return runtime
```

两个守卫的**依赖集合不同**，这是验证清单的关键：

| 守卫 | 依赖 | 覆盖的路由 |
| --- | --- | --- |
| `_require_memory_runtime` | 仅 PostgreSQL | `POST /api/v1/memories/{id}/confirm`、`DELETE /api/v1/memories/{id}`、`GET /api/v1/memories/search` |
| `_require_diagnosis_runtime` | PostgreSQL **且** Planner **且** Auditor | `/metrics`、`POST /api/v1/sessions`、`POST .../messages`、`GET /api/v1/runs/{id}`、`.../events`、`.../stream`、`.../trace`、`.../cancel`、`.../resume` |

所以"只配了数据库、没配模型"是一个**部分可用**状态：记忆搜索能用，诊断不能用。这个粒度是刻意的——它让"我的数据库配好了吗"和"我的模型配好了吗"两个问题可以分别验证。

`/metrics` 用的是诊断守卫（不是记忆守卫），因为它的数据来自 `run_trace_spans` 聚合，而没有诊断 runtime 就不会有 run。它返回 503 而不是全零文本的理由在第 12 章讲过：Prometheus 抓到 503 会把这次抓取记为失败（`up=0`），抓到全零文本会记为一次健康的零错误采样。**"未部署"和"零错误"必须可区分。**

### 13.9.1 路径 A：本地 venv，零凭据（最小可运行）

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements-dev.lock
.venv/Scripts/python -m uvicorn app.api.main:app --reload
```

不需要 `.env`，不需要数据库，不需要任何 API key。`app/core/settings.py` 的默认值让 Provider 全部处于 disabled / 确定性哈希状态。

预期结果：

| 请求 | 预期 | 说明 |
| --- | --- | --- |
| `GET /health` | 200 | `chat.status` 为 `disabled`、`database` 为未配置、`stream.available_under_auth` 为 `true`（因为鉴权是 disabled） |
| `GET /demo` | 200 | 前端页面能打开；健康卡会显示 disabled 状态 |
| `GET /metrics` | **503** | `detail` 为 `diagnosis resources require PostgreSQL and configured Planner/Auditor` |
| `POST /api/v1/sessions` | **503** | 同上 |
| `GET /api/v1/memories/search?query=lts` | **503** | `detail` 为 `case memory requires configured PostgreSQL` |

**这五行全部符合预期，才算路径 A 通过。** 特别是那三个 503：如果 `POST /api/v1/sessions` 返回了 201，说明有什么东西被静默地装配起来了，那比 503 严重得多。

这条路径最重要的作用是**离线套件能完整跑通**：

```bash

```

实测 `All checks passed!` 和 `430 passed, 12 deselected in 221.54s (0:03:41)`。注意这 430 个测试里包含真正的 MCP stdio 子进程握手（第 3 章）——协议边界是真的，只有模型和数据库是缺的。

### 13.9.2 路径 B：Docker Compose 全栈（含 PostgreSQL，不含模型）

```bash
cp .env.example .env
# 编辑 .env，把 DATAOPS_DB_AUTH 改成本机专用口令
docker compose config      # 先验证配置能解析、必需变量都在
docker compose up --build
```

`docker compose config` 这一步不要跳。它同时验证两件事：YAML 合法，以及 `${DATAOPS_DB_AUTH:?...}` 有值。跳过它的话，缺 `DATAOPS_DB_AUTH` 的错误会混在 `docker compose up` 的构建输出里——而构建输出有几百行。

预期的启动日志顺序（这个顺序本身是验证项）：

1. `database` 容器启动，initdb，healthcheck 从失败转 healthy（约 5–15 秒）。
2. `api` 容器启动（`depends_on` 等到上一步才放行）。
3. `alembic upgrade head` 输出十条 `Running upgrade` 直到 `20260716_0010`。
4. `python -m app.persistence.seed` 无输出正常退出（它返回计数但不打印知识正文）。
5. uvicorn 的 lifespan 校验依次通过，最后 `Application startup complete`。

第 3 步和第 4 步之间不该有任何间隔性的失败重试——如果看到 `alembic` 报连接错误，说明 healthcheck 的判定条件太松（回看 §13.3.4 为什么 `pg_isready` 要带 `-d dataops`）。

预期结果（宿主端口 18000）：

| 请求 | 预期 |
| --- | --- |
| `GET http://127.0.0.1:18000/health` | 200，`database` 已配置，`chat.status` 仍是 `disabled` |
| `GET .../api/v1/memories/search?query=lts` | **200**，返回空列表或已有候选 |
| `POST .../api/v1/sessions` | **503**（Planner/Auditor 未配置） |
| `GET .../metrics` | **503**（同一守卫） |
| `GET http://<局域网IP>:18000/health` | **连接被拒**（端口只绑 `127.0.0.1`） |

第二行从 503 变成 200，是"数据库这一层配好了"的直接证据。第五行是 §13.3.2 那条安全边界的验证方式——它应该**失败**，而这次失败是通过。

数据落地验证（口令只经 `PGPASSWORD` 传入，不写进命令行参数，也不回显）：

```bash
set -a && . ./.env && set +a
PGPASSWORD="$DATAOPS_DB_AUTH" docker compose exec -T database \
  psql -U dataops -d dataops -c 'select count(*) from knowledge_nodes;'
```

节点数非零，就证明启动链第二段真的跑了。这一步是 §13.3.5 那个 `&&` 的事后确认：`&&` 保证 seed 失败时容器不启动，这条查询保证 seed 成功时数据真的在。

### 13.9.3 路径 C：加上真实模型（诊断闭环）

在 `.env` 里补三组配置（值只存本机，不进版本控制）：

```text
DATAOPS_CHAT_PROVIDER=openai-compatible
DATAOPS_CHAT_MODEL=<模型名>
DATAOPS_CHAT_BASE_URL=<OpenAI 兼容端点>
DATAOPS_CHAT_API_KEY=<只存本机的密钥>
```

重启后预期：

| 请求 | 预期 |
| --- | --- |
| `GET /health` | 200，`chat.status` 为 `configured`，只暴露 `endpoint_host` 而非完整 URL |
| `POST /api/v1/sessions` | **201** |
| `POST /api/v1/sessions/{id}/messages` | **202**，`status=queued` |
| `GET /api/v1/runs/{run_id}` | 200，状态在 `queued → running → completed` 之间推进 |
| `GET /api/v1/runs/{run_id}/events` | 200，公开 Action/Observation 时间线 |
| `GET /api/v1/runs/{run_id}/trace` | 200，单根时间轴，七类 span |
| `GET /metrics` | **200**，五组指标 |
| `GET /demo` | 完整闭环：提交、状态推进、审计裁决卡、记忆确认 |

`/health` 只暴露 `endpoint_host` 这一点值得在验证时亲自确认一次：`GET /health` 的输出里**不该出现完整 URL**。完整 URL 可能带 userinfo（`https://user:pass@host/v1`），而 `/health` 是公开接口。

202 而不是 200 也是验证项。第 11 章讲过 run 由 PostgreSQL Worker 执行，POST message 只入队。如果这里返回 200 并附带完整报告，说明诊断是在请求线程里同步跑的——那是一个完全不同的（且会在 30 秒后被网关超时切断的）架构。

再验一次同 session 并发约束：连续提交两条 message，第二条应该返回 **409**，`detail` 里带 `active_run_id`，前端据此直接去轮询那个 run。

### 13.9.4 路径 D：开启鉴权（对外暴露前必做）

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

把结果写进 `.env` 的 `DATAOPS_API_AUTH_TOKEN`，同时把 `DATAOPS_API_AUTH_MODE` 改成 `bearer`。**两个都改**——只改一个会拒绝启动，这本身是第一个验证项：

| 配置 | 预期 |
| --- | --- |
| `bearer` + 无令牌 | 启动失败（lifespan 阶段拒绝） |
| `disabled` + 有令牌 | 启动失败（同上） |
| `bearer` + 令牌 < 32 字符 | 启动失败 |
| `bearer` + 32 位以上令牌 | 正常启动 |

启动成功后：

| 请求 | 预期 |
| --- | --- |
| `GET /health` | **200**，无需令牌（刻意公开） |
| `GET /health` 的 `stream.available_under_auth` | **`false`** |
| `GET /demo` | 200，无需令牌 |
| `GET /api/v1/runs/x` 无 Authorization 头 | **401** |
| `GET /api/v1/runs/x` 带 `Authorization: Basic xxx` | **401**，响应体与上一行**逐字相同** |
| `GET /api/v1/runs/x` 带错误 Bearer 令牌 | **401**，响应体与上两行**逐字相同** |
| `GET /api/v1/runs/x` 带正确令牌 | 200 / 404（取决于 run 是否存在） |
| `GET /metrics` 无令牌 | **401**（`/metrics` 在保护前缀内） |
| 快速发 121 次请求（默认配额 120/60s） | 第 121 次 **429**，带 `Retry-After` |

那三个"逐字相同"的 401 值得亲手 diff 一次。第 12 章 §12.4 讲过理由：如果"缺头"和"错令牌"的响应有任何差异，攻击者就能探测出"这个实例配了令牌吗"——而那是一个关于配置的事实，不是关于数据的事实，同样不该泄漏。

`stream.available_under_auth` 从 `true` 变 `false` 是另一个必看项。浏览器的 `EventSource` 无法携带请求头，所以 bearer 模式下 SSE 推流必然 401。这个限制既没被隐藏，也没被"修复"成 query-string 传令牌（那会让令牌进浏览器历史、代理日志和 Referer），而是变成了一个**机器可读的事实**：前端读到 `false` 就直接走轮询，不去尝试建流然后困惑于 401。

429 那一行还有一个容易漏的验证：**被限流之后等一分钟，应该能恢复**。第 12 章 §12.3.2 讲过，超限时刻意不追加时间戳，否则自动重试的客户端会把窗口起点一直往后推，形成永久封禁——"限流应该是减速带而不是路障"。手动验证方式就是超限后等待窗口过去再请求一次。

### 13.9.5 补上那 12 个 deselected 的测试

路径 B 之后数据库已经就绪，可以把 §13.1 里被 deselect 的 12 个用例补跑。注意**必须用一个独立的测试库**，而不是演示库——集成测试会建表、写数据、清数据：

```bash
DATAOPS_TEST_DATABASE_URL='postgresql+asyncpg://...' .venv/Scripts/python -m pytest -m postgres
```

`-m postgres` 是 `select`，不是在默认套件上追加：`pyproject.toml` 的 `addopts` 里已有 `-m 'not postgres'`，命令行的 `-m` 覆盖它，所以这条命令只跑那 12 个。想跑全部 442 个，用 `-m ''` 清空表达式。

`DATAOPS_TEST_DATABASE_URL` 和 `DATAOPS_DATABASE_URL` 是两个不同的键，这个分离本身是防护：如果集成测试读的是 `DATAOPS_DATABASE_URL`，那么在配好演示环境的机器上跑一次 `pytest -m postgres` 就会清掉演示数据——而这种事只有在演示前一分钟才会被发现。

同一批基础设施还能跑五层作品集评测（第 14 章的主题，这里只给命令）：

```bash
DATAOPS_TEST_DATABASE_URL='postgresql+asyncpg://...' .venv/Scripts/python -m app.evaluation
```

无库时的快速反馈是 `--skip-postgres`，但它的 JSON 报告会明确标 `complete=false`——这个标记的作用和 `deselected` / `skipped` 那组区分完全一致：**一份不完整的评测必须自己声明不完整**，不能靠读者记得自己当时加了哪个参数。

如果密钥也配好了，可以跑真实模型 Golden 冒烟：

```bash
.venv/Scripts/python -m app.evaluation.live_golden --code-revision <git-sha> --output live-golden.json
```

三件事在这一步必须注意，前两件是安全的，第三件是诚实性的：

1. 生成的 `live-golden*.json` 在 `.gitignore` 里，因为原始报告含本机端点配置。提交前扫一遍再说。
2. 密钥只经环境变量进入进程，不作为命令行参数（命令行参数会进 shell 历史和 `ps` 输出）。
3. `--code-revision` 是必填的。一份不知道对应哪个 commit 的评测报告，在几天之后就无法解释——尤其当 Prompt 版本变过（`planner-react:v7` → `v8` 那次实测差异很大）。

## 13.10 本章的取舍清单

| 决定 | 替代方案 | 为什么选当前这个 | 出处 |
| --- | --- | --- | --- |
| 单阶段 Dockerfile | 多阶段（builder + runtime） | 依赖全是 manylinux wheel，builder 阶段无产物可丢；收益几十 MB，成本是构建逻辑复杂一倍 | §13.2.4 |
| `COPY requirements.lock` 单独一层 | `COPY . .` 后统一安装 | 把"依赖变了"和"代码变了"分成两个缓存边界；否则改一行注释就重装全部依赖，直接导致没人用 Docker 验证 | §13.2.1 |
| 最后一步 `pip install --no-deps .` | 不装 wheel，靠工作目录 import | 打包漏配（如 `include` 少写 `mcp_server*`）在构建期暴露，而不是等到第一次 MCP 子进程调用 | §13.2.3 |
| `--no-deps` | 允许 pip 重新解析 | lock 已为该 Linux 环境解析过完整依赖图；重解析会引入 lock 之后发布的新版本，导致容器与本地行为不一致 | §13.2.2 |
| `pgvector/pgvector:pg16` 一个有状态组件 | PostgreSQL + Neo4j + 向量库 | 一套备份、一条迁移链、一处一致性边界；代价是手写递归 CTE 和受限的向量索引，在当前规模下明显划算 | §13.3 |
| `${DATAOPS_DB_AUTH:?...}` | `${DATAOPS_DB_AUTH}` | 空串会让官方镜像启动一个无口令数据库，且完全能用；`:?` 让缺配置在第一行日志前终止 | §13.3.1 |
| 端口只绑 `127.0.0.1` | `"18000:8000"`（绑 0.0.0.0） | 默认鉴权是 disabled，绑全网卡等于把可触发付费模型调用的端点开放给同网段 | §13.3.2 |
| 显式 `env_file: .env` | 依赖 Compose 自动读 `.env` | 自动读只做变量插值，不注入容器环境；漏掉它会让容器静默跑仓库默认值而 `/health` 仍是 200 | §13.3.3 |
| `DATAOPS_DATABASE_URL` 写在 `environment` | 写进 `.env` | 主机名 `database` 只在容器网络可解析；写进 `.env` 会让同一份文件无法同时服务本地 venv | §13.3.3 |
| `condition: service_healthy` | `depends_on: [database]` 短语法 | 短语法只保证启动顺序，不保证可连接；启动链第一段 `alembic upgrade head` 会立刻失败 | §13.3.4 |

| healthcheck 探 `/health` | 探某个 `/api/v1` 端点 | `/health` 在保护前缀之外，探针无需令牌；否则令牌要写进提交进版本控制的 `compose.yaml` | §13.3.4 |
| 具名卷 | bind mount | 跨 `docker compose down` 保留记忆与知识图；同时避开 Windows 下 PostgreSQL 数据目录属主不匹配导致 initdb 失败 | §13.3.4 |
| 启动链用 `&&` | 用 `;` | 迁移或种子失败时若继续启动，会得到"接口全 200、检索永远返回空"的状态，最终被误读为"Agent 诊断质量差" | §13.3.5 |
| `seed.main()` 不捕获异常 | `try/except` + 友好错误 | `&&` 只需要非零退出码，未捕获异常同时给出 traceback；种子失败的真因常在栈深处 | §13.3.5 |
| 知识图与文档语料一次 commit | 分两次提交 | 防"图已就绪、文档缺失"——那个状态下检索仍有结果，只是永远少一条通道，演示时不可能发现 | §13.5 |

| ini 不含数据库 URL | Alembic 默认的 `sqlalchemy.url` | ini 会被提交；`SecretStr` 让口令不进 repr、不进 `alembic history` 输出 | §13.4.2 |
| 文件名与 revision 不一致保持原样 | 重命名 `20260716_0005_diagnosis_worker.py` | 改名会破坏已部署环境 `alembic_version` 的对应关系，为一个装饰性一致付出人工干预代价 | §13.4 |
| `.env` 凭据行保持注释 | 留空（`KEY=`） | 空串是"已配置的空值"而非"未配置"；它会通过 `is None` 检查，只被第二道长度校验拦住 | §13.7.2 |
| `disabled` + 有令牌也拒绝启动 | 只拦 `bearer` 缺令牌 | 后者症状明显，前者"一切看起来正常"却端口无保护，是更危险的半配置 | §13.7.3 |
| Auditor 超时单列 90s | 与 Planner 共用 30s | Auditor 实测耗时 2–3 倍；共用会让每次诊断都因超时降级，等于把审计路径整条关掉且从外部难以区分 | §13.7.5 |

| dev 依赖与运行 lock 隔离 | 单一 lock | 镜像里没有 pytest/ruff/httpx；`tests/` 已被 `.dockerignore` 排除，留下运行器是纯攻击面增量 | §13.8 |
| ruff 启用 `ASYNC` | 只用 E/F/I | 阻塞调用混进 `async def` 会卡住整个事件循环（所有并发 MCP 子进程一起变慢），小样本测试看不出来 | §13.8 |
| `.dockerignore` 排 `.env` / `.git` | 只靠 Dockerfile 不 COPY 它们 | 结构性防线：任何人加一条 `COPY . .` 就会把凭据烤进镜像层，而镜像层里的文件删不掉 | §13.6 |

## 13.11 遗留问题

按"离生产还差多远"排序，不含前十二章已列过的项。

1. **`docker compose up --build` 在本次会话没有实测**。Docker 守护进程未运行（§13.1 的 npipe 连接错误）。已实测的只有 `docker compose config`，它不联系 Engine，所以证明的是配置合法性而非可运行性。§13.9.2 那条启动日志顺序是**预期**而非实测记录。

2. **单实例限流器在 Compose 扩容后失效**。`api` 服务如果 `--scale api=2`，每个实例各自持有一份滑动窗口，实际配额变成 2 倍。修法是把窗口移到共享存储，但项目约束是"PostgreSQL 是唯一状态服务"，用数据库做每请求的限流计数意味着每次请求多一次往返——对一个默认配额 120/60s 的演示服务，这个成本不划算。这条和第 12 章 §12.17 的第一项是同一个问题的部署侧表述。

3. **没有反向代理配置示例**。`.env.example` 的注释说"需要对外演示时应显式配置 bearer 令牌并放在反向代理之后"，但仓库里没有那份 nginx / Caddy 配置。而 SSE 推流对代理配置**敏感**：默认开启响应缓冲的代理会把 `text/event-stream` 攒成一个响应，表现是"浏览器一直转圈直到 run 结束才一次性出全部事件"——推流的全部价值消失，且看起来像后端慢。这条需要 `proxy_buffering off` 之类的显式配置，没写出来就等于把一个已知陷阱留给使用者。

4. **健康检查没有区分 liveness 与 readiness**。`/health` 同时承担两个角色。Compose 只需要一个，但换成 Kubernetes 就需要分开：liveness 失败会**重启容器**，readiness 失败只是**摘掉流量**。以当前的 `/health` 做 liveness，一个"数据库暂时连不上"的状态会导致容器被反复重启，而它本该只是暂时不接流量。

5. **迁移是启动链的一部分，多实例会竞争**。`alembic upgrade head` 在每个 `api` 实例启动时都会执行。Alembic 用 `alembic_version` 表加锁，所以并发执行不会损坏数据，但会有实例在等锁——单实例部署下这不是问题，扩容或滚动更新时就是。生产做法是把迁移拆成独立的一次性 Job，而不是塞进应用启动命令。

6. **没有镜像体积和构建耗时的实测数字**。所以 §13.2.4 那句"多阶段收益是几十 MB"是估算而非测量。这个判断的方向应该是对的（slim 基础镜像 + 纯 wheel 依赖），但数字没测过就不该写成实测。

7. **没有 `docker compose down` 之后的数据保留验证**。具名卷理论上跨 down 保留（不带 `-v`），但这件事没有在真实环境走过一遍——包括"卷里的数据是旧 schema，代码是新版本"这个更实际的场景（`alembic upgrade head` 应该能处理，但没验过）。

8. **`.env` 没有 schema 校验的独立入口**。配置错误全部靠 lifespan 在启动时发现，而 lifespan 要等到镜像构建完、数据库起来之后才跑。一个 `python -m app.core.settings --check` 之类的离线校验命令能把"我的 `.env` 写对了吗"这个问题的反馈时间从几分钟压到一秒。

9. **P95 ≤ 30s 仍未达标**，实测每案例 58–125s。这个目标值写在设计文档里，部署配置（`DATAOPS_REACT_TOTAL_TIMEOUT_SECONDS=240`）反映的是实测现实而不是目标。`DATAOPS_MAX_PARALLEL_TOOL_ACTIONS=3` 是为这个目标准备的旋钮，但它压缩的只是工具调用的等待时间，而实测耗时的主要构成是 Planner 与 Auditor 的模型往返——那部分并行度帮不上。这条和第 12 章 §12.17 的最后一项是同一个未达标项。

## 13.12 小结

部署的六个文件没有一行是"配置格式"层面的东西。每一处都在回答同一类问题：**这个错误会不会以"看起来正常"的形态出现，如果会，怎么把它挪到启动之前**。

三条贯穿本章的判断：

**第一，`&&` 和 `:?` 是同一类工具。** 它们都在把"部分成功"这个状态从可能的世界里删掉。启动链用 `;` 会得到一个接口全 200、检索永远空的服务；`${VAR}` 而不是 `${VAR:?}` 会得到一个能连、能写、无口令的数据库。这两个字符各自阻止了一个"完全可用但完全错误"的部署。

**第二，安全边界是成对的默认值。** 鉴权默认 disabled 是为了 `docker compose up` 之后能直接演示，这个便利只有在端口绑 `127.0.0.1` 的前提下才可接受。同理，`.env` 凭据行保持注释而不是留空，是为了不让"已配置的空值"通过第一道 `is None` 检查。任何单独看都成立的默认值，配错另一半就是漏洞。

**第三，验证清单的价值在于它列出了应该失败的项。** §13.9 四条路径里最重要的行是那些期望 503、401、429 和"连接被拒"的行。一份只检查"该通的都通了"的清单会漏掉最危险的那类问题——因为无鉴权的端口、静默降级的 runtime、被忽略的 `env_file`，症状全都是"该通的都通了"。

**第 14 章转向评测**：五层作品集评测的 20 个指标怎么分层、GraphRAG 消融与记忆召回消融各自控制什么变量、`portfolio-eval-run:v23` 的报告结构、`app/evaluation/live_golden.py` 如何在真实模型上跑 Golden 集，以及那些实测数字——必要 Action 覆盖 1.0000、必要因果链完整率 0.6667、`root_cause_top1_hit_rate` 仍为 0——各自的口径、分母和限制。最后一项尤其重要：把 0 解释成"模型找不到根因"是错的，把它悄悄改口径后当成提升更错，第 14 章会讲这两个陷阱之间那条唯一诚实的路。
