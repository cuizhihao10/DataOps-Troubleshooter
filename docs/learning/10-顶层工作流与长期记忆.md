# 第 10 章 顶层工作流与长期记忆

第 8 章讲了内层的 `BoundedReactLoop`：它把用户问题变成一批实时 Observation。第 9 章讲了中层的
`AuditedReportWorkflow`：它把 Observation 变成一份两层门禁都放行的报告。本章讲最外层的
`AuditedDiagnosisWorkflow`，它要回答两个新问题：

1. **历史案例什么时候查、查回来的东西算什么？** 一个"记得住昨天"的排障系统很有吸引力，但它同时
   是最容易出事的地方：一旦历史结论能直接变成今天的结论，系统就从"证据驱动"退化成"经验复读"。
2. **什么样的诊断结果值得被记住？** 写记忆是唯一一个会影响**未来所有 run** 的写操作。它必须发生在
   审计之后，而且默认不生效。

这两个问题的答案都是同一句话：**实时 Observation 永远优先于历史案例，历史只能作参考证据**。本章要
看的是这句话怎么变成代码里的门禁，而不是 Prompt 里的一句叮嘱。

## 10.2 为什么最外层是一条直线

第 8 章的循环有条件边（继续调工具还是停），第 9 章的报告图有条件边（返工、降级还是放行）。最外层
一个条件边都没有：

```python
# app/orchestration/diagnosis_workflow.py:204
graph.add_edge(START, "recall_case_memories")
graph.add_edge("recall_case_memories", "run_react")
graph.add_edge("run_react", "explain_case_matches")
graph.add_edge("explain_case_matches", "run_report")
graph.add_edge("run_report", "stage_case_memory")
graph.add_edge("stage_case_memory", END)
```

模块里给出的理由是一句话：

> 每个节点只有一条后继边，因为 accepted/degraded 分支已在报告子图内部收敛；顶层始终执行
> `stage_case_memory`，由记忆服务根据审计 outcome 产生写入或 skipped 结果。

这句话值得展开，因为它是本章最容易写错的设计。

### 10.2.1 顶层如果自己分支，会坏在哪

一个很自然的写法是在顶层加条件边：

```python
# 反面写法
graph.add_conditional_edges("run_report", _route_after_report, {
    "stage": "stage_case_memory",
    "skip": END,
})
```

看着更"高效"——降级报告反正不写记忆，何必再进一个节点？问题有三个：

1. **判断逻辑被复制了。** "什么算 accepted"的规则现在有两份：一份在 `CaseMemoryService.stage_from_report`
   里，一份在顶层的路由函数里。两份规则只要有一天不同步，就会出现"顶层认为该写、Service 认为
   不该写"或者反过来。第 9 章 §9.6.3 讲过路由函数只读 `AuditStatus` 的原因，这里是同一条原则的
   延伸：**资格判断必须只有一个所有者**。
2. **`memory_stage` 会变成可空字段。** 走 skip 分支时顶层拿不到 `MemoryStageResult`，
   `DiagnosisRunResult.memory_stage` 就得允许 `None`，于是 API 和评测又要面对"None 是没写、还是
   还没跑到、还是写失败了"这种猜谜。现在的写法让**每次诊断都有一个明确的记忆结论**，四个取值
   （`staged` / `merged` / `skipped_no_root_cause` / `skipped_not_accepted`）本身就是解释。
3. **测试会失去一条断言。** `test_diagnosis_workflow_skips_unrequested_history_and_records_degraded_skip`
   里有一行 `assert len(memory.stage_calls) == 1`——降级路径下 staging **仍然被调用**。这行断言正是
   在防止有人日后"优化"出一个提前 return。

### 10.2.2 `recursion_limit=8`

```python
raw_state = await self._graph.ainvoke(
    initial,
    context=self._runtime,
    config={"recursion_limit": 8},
)
```

第 8 章的循环用的是 `max_steps * 2 + 6` 这种按预算算出来的上限，因为它真的会循环。这里的 8 是硬
编码的字面量，理由和第 9 章 §9.6 的 `recursion_limit=10` 一样：**路径可以穷举**。五个节点、五条边、
无分支，一次运行恰好 5 个 super-step，写 8 留两步余量，足够让"图被改成六个节点却忘了改上限"这类
错误暴露成明确的 `GraphRecursionError`，而不是变成一次静默的截断。

值得注意的是这里用的是 `ainvoke` 而不是第 8 章的 `astream`。原因也在拓扑：顶层节点之间没有需要
逐步观察的中间态，事件流是由两个子图各自产出的 `ReactPublicEvent` / `ReportPublicEvent` 携带的，
顶层只负责把它们原样带出去。

### 10.2.3 顶层不是第三个 Agent

`AuditedDiagnosisWorkflow` 的构造函数只接四个东西：

```python
self._runtime = DiagnosisGraphRuntime(
    react=react,
    report=report,
    memory=memory,
    config=config,
)
```

三个依赖全是 `Protocol`，不是具体类：

| Protocol | 生产实现 | 暴露的方法 |
|---|---|---|
| `ReactWorkflow` | `BoundedReactLoop` | `run(ReactRunRequest) -> ReactRunResult` |
| `ReportWorkflow` | `AuditedReportWorkflow` | `run(ReportRunRequest) -> ReportRunResult` |
| `CaseMemoryWorkflow` | `PostgresMemoryRuntime` | `search(...)`、`stage(...)` |

模块 docstring 把边界说得很直接：

> 本模块只做确定性编排：两个 LLM Agent 仍分别位于既有 ReAct/报告子图，案例查询与写入仍由记忆
> runtime 执行。任何数据库或子图异常都会传播，不能静默伪装为空历史或成功报告。

也就是说：顶层没有 LLM 客户端、没有 MCP 客户端、没有 AsyncSession。它能做的事只有"按顺序调用"和
"把结果拼成契约"。这是本项目里"三层嵌套但只有两个 Agent"的结构保证——**层数不等于 Agent 数**。

### 10.2.4 `CaseMemoryWorkflow` 故意不暴露 confirm/reject

`PostgresMemoryRuntime` 实际上有四个公开方法：`stage`、`decide`、`delete`、`search`（还有 `counts`）。
但顶层 Protocol 只声明了两个：

```python
class CaseMemoryWorkflow(Protocol):
    """声明顶层编排需要的 confirmed 搜索和审计后暂存接口。

    生产 ``PostgresMemoryRuntime`` 为每次调用创建独立会话/事务；协议不暴露 confirm/reject，避免
    自动诊断擅自代替用户改变确认状态。搜索和 staging 错误必须显式传播。
    """
```

这是一个"用类型系统表达权限"的例子。Python 是鸭子类型，`PostgresMemoryRuntime` 传进来以后
**运行时**当然能调 `.decide()`。但节点代码只能看到 `runtime.context.memory`，其静态类型是
`CaseMemoryWorkflow`；任何在节点里写 `await runtime.context.memory.decide(...)` 的代码都过不了
类型检查，也过不了代码评审——因为读者会立刻发现节点在调用协议里不存在的方法。

为什么值得这样防？因为"自动确认"是这个系统里最诱人的捷径。一次 accepted 的诊断，看起来完全可以
顺手把记忆直接写成 `confirmed`，这样下一次就能召回了，演示效果立竿见影。但那意味着：**一个模型
产出的结论，在没有任何人看过的情况下，成为了未来所有诊断的"已确认历史事实"**。错一次，错误就
开始自我复制。这条路必须堵死在结构上，不能靠"我们记得不要那样做"。

对应的用户路径在第 12 章：`POST /api/v1/memories/{memory_id}/decision` 由人显式调用。

## 10.3 recall：历史查询是"按需"的

第一个节点：

```python
async def _recall_case_memories(
    graph_state: DiagnosisGraphState,
    runtime: Runtime[DiagnosisGraphRuntime],
) -> DiagnosisGraphState:
    if graph_state.capability_request.history_trigger is HistoryTrigger.NOT_REQUESTED:
        return graph_state.model_copy(update={"memory_query": None, "recalled_memories": ()})

    query = _build_memory_query(
        graph_state.initial_state,
        max_chars=runtime.context.config.memory_query_max_chars,
    )
    matches = await runtime.context.memory.search(
        query,
        limit=runtime.context.config.memory_search_limit,
    )
    return graph_state.model_copy(
        update={
            "memory_query": query,
            "recalled_memories": tuple(matches),
        }
    )
```

十几行，四个决定。

### 10.3.1 `NOT_REQUESTED` 直接短路数据库

`HistoryTrigger` 来自第 4 章的能力配置层（`app/capabilities/`）。它有三个值，`not_requested` 是其中
一个：既没有用户显式要求参考历史，Planner 也没有在校验阶段要求对比先例。

这个分支**在任何 I/O 之前**返回，连查询文本都不构造。收益不是省一次 SQL，而是三件事：

1. **省一次 embedding 调用。** 记忆搜索必须先把查询文本嵌入成向量（`CaseMemoryService.search_confirmed`
   里的 `embed_texts`）。这是一次真实的远端 HTTP 请求，在 SiliconFlow `BAAI/bge-m3` 上是几十到
   几百毫秒，还要花钱。每一次诊断都固定付这笔钱，只为了大概率返回空列表，不划算。
2. **让"没有历史"和"没查历史"可区分。** 结果模型里 `memory_query` 是 `str | None`，
   `not_requested` 时是 `None`，其余触发时必须是非空串。第 10.10 节会看到结果契约把这条对应关系
   校验成了硬约束。
3. **测试能直接断言零调用。** `assert memory.search_calls == []` 是一条比"返回了空列表"强得多的
   断言，它证明的是路径没被走，而不是走了但没找到。

### 10.3.2 `_build_memory_query`：优先级就是截断顺序

```python
def _build_memory_query(state: AgentState, *, max_chars: int) -> str:
    segments = [f"用户问题: {state.user_query.strip()}"]
    for evidence in state.evidence:
        if evidence.source_type is EvidenceSourceType.CASE_MEMORY:
            continue
        segments.append(f"实时观察: {evidence.content.strip()}")
    for hypothesis in state.hypotheses:
        components = ",".join(component.value for component in hypothesis.components)
        segments.append(
            "当前假设: "
            f"症状={hypothesis.symptom.strip()}; "
            f"根因={hypothesis.candidate_root_cause.strip()}; "
            f"组件={components}"
        )

    # 统一在组合后截断，保证同一状态稳定生成同一查询，同时让高优先级实时事实位于预算前部。
    query = "\n".join(segment for segment in segments if segment.strip())[:max_chars].rstrip()
    if not query:
        raise ValueError("memory recall query must not be blank")
    return query
```

三段的顺序不是随手排的，它等价于一份优先级声明：

| 顺序 | 内容 | 为什么在这个位置 |
|---|---|---|
| 1 | 用户问题 | 唯一一定存在的输入；任何情况下都不该被预算挤掉 |
| 2 | 实时 Evidence 正文 | 本次观察，检索相关性最高的信号 |
| 3 | 当前假设（症状 / 根因 / 组件） | 推断产物，可靠性最低，最该被截掉 |

注意截断发生在 `"\n".join(...)` **之后**，而不是逐段判断"还剩多少额度"。这是一个刻意的选择：先拼后
截，同一个 `AgentState` 永远生成逐字节相同的查询字符串，于是同一个状态永远得到同一批召回结果。
如果改成逐段预算，"某段刚好卡在边界"这种情形会让查询在不同 Python 版本、不同字典顺序下产生细微
差异，Golden 回放就不再可重现了。

测试锁的正是这份顺序：

```python
assert len(query) <= 512
assert "请检查 LTS 上游未就绪" in query
assert "实时工具显示任务仍等待上游数据" in query
assert "当前假设" in query
assert "旧案例文本" not in query
```

配置来自 `DiagnosisWorkflowConfig`，测试里传的是 `memory_query_max_chars=512`；生产默认值在
`app/core/settings.py` 是 `memory_query_max_chars: int = Field(default=4000, ge=256, le=20_000)`。

### 10.3.3 排除 `CASE_MEMORY`：不让历史递归强化自己

`continue` 那一行是本节最重要的三个词：

```python
if evidence.source_type is EvidenceSourceType.CASE_MEMORY:
    continue
```

配套注释：

> CASE_MEMORY 来源不会再次进入查询，避免历史案例递归强化自身。

这个陷阱在会话恢复（第 11 章）时才真正显形。设想一次多轮会话：

1. 第一轮召回了案例 A，A 的内容作为一条 `EvidenceSourceType.CASE_MEMORY` 的 Evidence 进了
   `AgentState`。
2. 会话继续，第二轮又触发历史召回。如果查询文本里包含 A 的正文，那么这次查询和 A 的向量距离
   会**因为 A 自己的文本**而变近。
3. A 于是几乎必然再次排在第一，相似度还更高。第三轮更高。

这就是一个正反馈回路：一个案例被召回过一次，就会越来越难被别的案例挤掉，而这份"越来越确信"完全
来自它自己。同样的模式在 `app/memory/matcher.py` 里也出现了一次：

```python
segments.extend(
    evidence.content
    for evidence in state.evidence
    if evidence.source_type is not EvidenceSourceType.CASE_MEMORY
)
```

那里排除它的理由略有不同——不是为了检索分数，而是为了不让"历史案例的文本"被当成"当前上下文复现
了历史症状"的证据（§10.5.3）。两处都是同一句话的不同侧面：**历史不能证明历史**。

### 10.3.4 查询失败必须传播

`search` 的异常没有被 `try` 包住。这是刻意的，测试专门证明了后果：

```python
memory = RecordingMemoryWorkflow(
    matches=[],
    stage_result=_pending_stage_result(),
    search_error=RuntimeError("synthetic memory search failure"),
)
...
with pytest.raises(RuntimeError, match="synthetic memory search failure"):
    await workflow.run(...)

assert react.requests == []
assert report.requests == []
assert memory.stage_calls == []
```

这条测试的 docstring 说明了理由：

> 该语义防止数据库或 Embedding Provider 故障被伪装为"没有历史案例"；异常原样返回调用方，空调用
> 记录证明尚未产生模型成本、MCP 副作用或不完整诊断结果。

对比一下"友好降级"的写法会发生什么：

```python
# 反面写法
try:
    matches = await runtime.context.memory.search(query, limit=...)
except Exception:
    matches = []          # "至少能跑完"
```

诊断会正常完成，报告会正常产出，`similar_cases` 是空的，一切看起来都很好。而真相是数据库连不上，
或者 embedding Provider 返回了 500。用户看到的是一份"没有找到相似历史案例"的诊断——这是一句**假话**。
更糟的是它可复现地假：只要故障持续，每一份报告都会这么说，而且没有任何地方记录过异常。

顺带值得注意的是三条 `assert ... == []`。它们证明失败发生在**花钱之前**：没有 Planner 调用（没有
token 消耗）、没有 MCP 子进程、没有 staging 写库。第 7 章讲 Provider 边界时说过"失败要早、要明确"，
这里是同一原则在编排层的体现：顺序上把最可能失败的依赖放在最前面，故障成本就最低。

## 10.4 一份不可变快照，两个 Agent

`recalled_memories` 在 recall 节点写入之后，后续节点**只读不写**。这一节讲为什么这条不变量比它看起来
更重要。

### 10.4.1 只投影 `.memory`，similarity 留在顶层

```python
memories = tuple(match.memory for match in graph_state.recalled_memories)
```

`CaseMemoryMatch` 有六个字段：`memory`、`similarity`、`retrieval_channels`、`direct_similarity`、
`graph_score`、`graph_edge_refs`。进入 `ReactRunRequest.confirmed_case_memories` 的只有第一个。

为什么不把整个 match 交给 Planner？因为 `similarity=0.94` 这种数字对模型是**有害输入**。它天然读起来
像"94% 可能是同一个问题"，而它实际上只是 cosine 距离换算出来的检索分数。模型看到高分会倾向于直接
采信历史根因，而这正是整章都在防的事。

那 similarity 去哪了？两个地方：

1. 留在 `DiagnosisGraphState.recalled_memories`，最终作为 `DiagnosisRunResult.recalled_memories`
   返回给 API 与评测——**人和评测脚本可以看到分数**，因为他们知道分数是什么。
2. 通过 matcher 变成一句带明确免责声明的自然语言（§10.5.2）：
   `f"历史候选最终排序分为 {match.similarity:.3f}，该分数不等于事实置信度。"`

同一个数字，给人看时是原始值，给模型看时必须带着"这不是置信度"一起出现。

### 10.4.2 confirmed 门禁在 Pydantic 层，不在 Prompt 层

`ReactRunRequest` 有这个校验器：

```python
@model_validator(mode="after")
def validate_confirmed_memories(self) -> ReactRunRequest:
    """拒绝把 pending/rejected 案例作为 Planner 已确认历史上下文。

    运行请求是长期记忆与 Planner 之间的确定性边界；任何非 confirmed 案例都会产生 Pydantic
    ValidationError，而不是依赖 Prompt 提醒模型忽略，从结构上降低记忆污染风险。
    """

    if any(
        memory.status is not MemoryStatus.CONFIRMED for memory in self.confirmed_case_memories
    ):
        raise ValueError("React runs can include only confirmed case memories")
    if [item.memory_id for item in self.confirmed_case_memories] != [
        item.case_id for item in self.history_case_matches
    ]:
        raise ValueError("React history explanations must match confirmed memory order")
    return self
```

这里有**三层**同样的门禁，全都在做"只有 confirmed 能进"：

| 层 | 位置 | 形式 |
|---|---|---|
| SQL | `PostgresCaseMemoryRepository.search_confirmed` | `WHERE status = 'confirmed'` |
| 领域模型 | `CaseMemoryMatch.validate_confirmed_memory` | `if self.memory.status is not MemoryStatus.CONFIRMED: raise` |
| 请求契约 | `ReactRunRequest` / `ReportRunRequest` | 上面这段 |

三层重复是不是冗余？在别的地方也许是，在这里不是。理由：这三层各自防的是不同的失效模式。SQL 防
正常路径；`CaseMemoryMatch` 防"仓储返回了脏数据"或"测试替身漂移"；请求契约防"编排层从别的来源
（比如会话恢复出来的旧快照、API 直接注入）拼出了案例集合"。第三层是唯一能防住最后这种情况的，因为
那条路径根本不经过 SQL。

`DiagnosisRunRequest` 的 docstring 直接点了这件事：

> `state` 可以携带会话恢复得到的实时 Evidence/假设，但用户问题必须含非空白字符。历史是否查询由
> `capability_request.history_trigger` 决定，调用方不能直接注入未确认案例绕过仓储。

第二条校验（列表顺序逐项相等）是另一件事：它保证 `confirmed_case_memories[i]` 和
`history_case_matches[i]` 说的是同一个案例。如果两个列表可以错位，Planner 看到的"案例 A 的解释"
可能配着"案例 B 的正文"，而这种错误在自然语言里几乎不可能被发现。用**列表顺序相等**而不是"集合
相同"来校验，是因为顺序本身承载信息——它是检索排序。

### 10.4.3 为什么 report 节点不重新搜索

```python
async def _run_report(...):
    if graph_state.react_result is None:
        raise RuntimeError("report node requires completed React result")
    # 复用 recall 节点的同一不可变快照，避免 ReAct 与 Auditor 之间再次查询导致确认状态或排序漂移。
    memories = tuple(match.memory for match in graph_state.recalled_memories)
```

ReAct 循环可能跑几十秒。这段时间里数据库不是冻结的：另一个用户可能刚 confirm 了一个新案例，也可能
刚 reject 了 Planner 正在参考的那个。如果 report 节点重新查一次，会出现两类事故：

- **Auditor 看不到 Planner 看过的案例。** Planner 基于案例 A 写了一条假设，Auditor 手上没有 A，于是
  这条假设"引用了不存在的历史来源"。第 9 章 §9.5.4 的 `_case_issues` 会把它判成
  `unconfirmed_case` 或 `evidence_conflict`，报告白白返工一次——而且返工也修不好，因为问题不在报告里。
- **排序漂移。** 即使案例集合没变，向量索引的近邻顺序也可能因为新插入的行而微调。两个 Agent 看到
  同一批案例但顺序不同，`validate_post_react_boundary` 的列表顺序校验会直接失败。

所以顶层的规则是：**一次诊断只查一次历史**。这也是 `test_diagnosis_workflow_recalls_once_reuses_context_and_stages_accepted`
名字里 "recalls_once" 的含义，对应断言 `assert len(memory.search_calls) == 1`，以及：

```python
assert react.requests[0].confirmed_case_memories == (_confirmed_match().memory,)
assert report.requests[0].confirmed_case_memories == (_confirmed_match().memory,)
assert report.requests[0].history_case_matches == result.history_case_matches
```

## 10.5 `explain_case_matches` 为什么跑两次

这是本章最容易看漏的一处设计。`explain_case_matches` 在顶层被调用了两次，一次在 `_run_react` 里面，
一次作为独立节点 `_explain_case_matches`。

### 10.5.1 两次调用，同一批候选，不同的当前状态

```python
# _run_react 里：ReAct 之前
preliminary_matches = explain_case_matches(
    graph_state.recalled_memories,
    graph_state.initial_state,                      # ← 初始状态
    current_components=graph_state.capability_request.components,
)

# _explain_case_matches 节点：ReAct 之后
matches = explain_case_matches(
    graph_state.recalled_memories,                  # ← 同一批候选
    graph_state.react_result.state,                 # ← ReAct 终态
    current_components=graph_state.capability_request.components,
)
```

第一个参数完全一样，第二个参数不一样。节点 docstring 解释得很清楚：

> 候选集合、顺序和 similarity 仍来自 recall 节点；本节点只更新解释字段，不重新访问数据库。这样
> Planner 先看到基于输入/旧状态的初步对比，Auditor 与最终报告再看到工具执行后的差异，同时避免第二次
> 搜索造成确认状态或排序漂移。

用一张表说明两次解释的差别：

| | 第一次（Planner 侧） | 第二次（Auditor / 报告侧） |
|---|---|---|
| 候选集合 | recall 节点的快照 | **同一个快照** |
| 相似度 | 原值 | **原值** |
| 当前组件 | capability 请求 | capability 请求 |
| 当前假设 | 用户输入 / 恢复出来的旧假设 | ReAct 投影出的假设 |
| 实时 Evidence | 恢复出来的（通常为空） | 本轮所有 TOOL Observation |
| 用途 | 给 Planner 一份"历史说过什么"的初步对照 | 给 Auditor 一份"历史与本次实测差在哪"的最终对照 |

这就是"实时优先"落到实处的地方：Planner 开工前拿到的历史对照只能基于输入，它没有资格宣称"历史结论
和本次观察一致"——因为本次还没观察。只有工具跑完之后，第二次解释才有权说"当前上下文复现了历史症状"
或者"当前根因与历史根因不一致"。

代价是同一段确定性逻辑跑了两遍。它是纯函数、纯字符串比较，没有 I/O，成本可以忽略。

### 10.5.2 matcher 是规则，不是第三个 Agent

`app/memory/matcher.py` 的模块 docstring 划的边界很干净：

> 向量直接分与 SIMILAR_TO 图传播分都只说明检索相关，不能证明两次故障等价。本模块比较当前组件、
> 问题、假设、实时 Evidence 和历史结构，生成可审计 `SimilarCaseReference`；它不调用第三个 Agent，
> 也不改变候选集合或分数，保持"检索决定候选、规则解释边界、实时事实优先"的职责分离。

它为每个候选生成五类字段。逐个看它们是怎么算出来的。

**共同点 `common_points`** — 第一条永远是免责声明，其后按可确认程度递减追加：

```python
common_points = [f"历史候选最终排序分为 {match.similarity:.3f}，该分数不等于事实置信度。"]
if MemoryRetrievalChannel.VECTOR in match.retrieval_channels:
    common_points.append(f"案例直接 pgvector cosine 相似度为 {match.direct_similarity:.3f}。")
if MemoryRetrievalChannel.GRAPH in match.retrieval_channels:
    common_points.append(
        "案例由已确认先例沿 SIMILAR_TO 关系扩展，"
        f"查询相关度与边权相乘后的图传播分为 {match.graph_score:.3f}；"
        f"关系引用：{', '.join(match.graph_edge_refs)}。"
    )
if overlap:
    common_points.append(f"本次与历史案例共同涉及组件：{', '.join(overlap)}。")
```

注意第一条的位置：它在**任何**具体共同点之前。Prompt 里这批解释是按顺序渲染的，把"这不是置信度"
放在最前面，模型读到具体的相似度数字时已经先读过限制条件。这不是万能的，但方向是对的。

组件重合用的是精确集合运算：

```python
current_component_values = {item.value for item in current_components}
memory_component_values = {item.value for item in memory.components}
overlap = sorted(current_component_values & memory_component_values)
current_only = sorted(current_component_values - memory_component_values)
memory_only = sorted(memory_component_values - current_component_values)
```

`Component` 是三值枚举（`lts` / `bds` / `flashsync`），集合运算在这里是**完全可靠**的——不存在歧义、
不需要分词、不需要模型。`sorted` 保证输出稳定，这样同一状态生成逐字相同的解释文本，报告层才能用
整对象相等来校验（§10.5.7）。

根因比较也是精确的，只是先做了规范化：

```python
current_roots = {
    _normalize_text(hypothesis.candidate_root_cause)
    for hypothesis in state.hypotheses
    if hypothesis.status is not HypothesisStatus.REJECTED
}
memory_root = _normalize_text(memory.root_cause)
if memory_root in current_roots:
    common_points.append("当前候选假设与历史根因一致，但仍需本次实时证据独立支持。")
```

两个细节：`REJECTED` 的假设被排除（已经被否掉的猜测不该参与"和历史一致"的判断）；即使一致，句子也
带上了"但仍需本次实时证据独立支持"。这句话不是客套，它对应第 9 章 §9.5.3 的那条规则——报告里的根因
必须有本次的 supporting evidence，历史一致不构成支持。

### 10.5.3 保守的双向包含：宁可漏报共同点

症状比较是唯一不能做精确匹配的地方，因为症状是自由文本。实现是这样：

```python
def _texts_overlap(left: str, normalized_right: str) -> bool:
    """用规范化双向包含判断两个非空短文本是否存在保守重叠。

    不使用字符集合比例，避免中文常见字造成伪相似；短于两个字符的片段不参与，降低"失败"等
    单字/短词误命中。该规则宁可漏报共同点，也不编造语义等价。
    """

    normalized_left = _normalize_text(left)
    if len(normalized_left) < 2 or len(normalized_right) < 2:
        return False
    return normalized_left in normalized_right or normalized_right in normalized_left
```

三个刻意的取舍：

1. **不用字符集合重合比例。** 这是中文文本相似度最常见的土办法：把两句话切成字符集合算 Jaccard。
   在中文上它会灾难性地误报——"任务调度失败"和"资源配额失败"共享"失败"，还共享很多常用字，
   比例算下来相当可观，但两者说的完全是两件事。
2. **不用分词或同义词表。** 那意味着引入一个新依赖（jieba 之类）和一份需要维护的词表，而它带来的
   收益不确定，带来的不确定性倒是确定的。`docs/reference-adoption.md` 定的规矩是调整依赖前先读那份
   文档，这里的结论是不引入。
3. **短于两字符不参与。** 防的是"失败"这种两字词被包含进任何一段长文本就算命中。注意条件写成
   `len(normalized_left) < 2 or len(normalized_right) < 2`，两侧都查——右侧是整段上下文，几乎不可能
   短于两字符，但校验成本为零，写上就不用推理"它一定不会"。

漏报的后果是什么？`common_points` 少一条，`differences` 多一条：

```python
if not matched_symptoms:
    differences.append("当前结构化上下文尚未明确复现历史症状，需要继续核对实时 Observation。")
```

也就是说：**漏报导向"需要继续核对"，误报导向"已经确认相似"**。前者让人多看一眼，后者让模型少想
一步。在这个系统里方向很明确。

### 10.5.4 `differences` 永远非空

`SimilarCaseReference` 的 Schema 要求 `differences: list[str] = Field(min_length=1)`。matcher 的最后
一道兜底保证它一定能满足：

```python
if not differences:
    differences.append("当前结构化字段未发现明确差异，仍不能把语义相似度当作事实等价。")
```

这一行是整个 matcher 的态度：**空的差异列表不等于"完全一致"，它只等于"我们的规则没能发现差异"**。
这两件事在语义上差得很远，而 `min_length=1` 的 Schema 约束逼实现必须表态。这是第 9 章 §9.2.2 讲的
"Schema 约束反过来促成好实现"的又一例。

`pitfall_warnings` 用同样的方式构造，第一条是常驻的：

```python
pitfall_warnings = [
    "历史方案只用于人工参考；执行前必须以本次实时 Observation 重新验证前置条件。"
]
if current_roots and memory_root not in current_roots:
    pitfall_warnings.append("根因存在结构化冲突，禁止直接复用历史修复方案。")
if current_only or memory_only:
    pitfall_warnings.append("组件范围不同，需逐项检查方案是否会影响本次未覆盖链路。")
```

`reference_actions` 则处理"历史案例没记方案"的情况：

```python
reference_actions = list(memory.solution_steps) or [
    "历史案例未记录可复用处置步骤，本次不得据此生成生产写操作。"
]
```

`or` 的短路在这里承担了 Schema 的 `min_length=1`：空列表是 falsy，于是退回那句显式声明。它比抛异常
好，因为"历史案例没有 solution_steps"是完全合法的数据（`CaseMemory.solution_steps` 允许为空）。

测试锁的是冲突路径：

```python
result = explain_case_matches(
    (_raw_match(),),
    _state(root_cause="BDS 资源不足", components=[Component.LTS, Component.BDS]),
    current_components=(Component.LTS, Component.BDS),
)[0]

assert any("本次额外涉及组件：bds" in item for item in result.differences)
assert any("当前候选根因与历史根因不一致" in item for item in result.differences)
assert any("禁止直接复用" in item for item in result.pitfall_warnings)
assert any("组件范围不同" in item for item in result.pitfall_warnings)
```

历史案例是 LTS 的"上游数据未按时就绪"，本次是 LTS+BDS 的"BDS 资源不足"，similarity 仍是 0.91。
0.91 是很高的分数，而输出里有两条差异和两条禁止复用的警告。这就是"相似不等于相同"从一个原则变成
四条可断言字符串的样子。

### 10.5.5 引用里必须有 case_id，但 edge ID 不是 Evidence

```python
# 案例 ID 是历史来源；本次 TOOL Evidence 放在其后，供报告同时展示旧先例与实时事实。
realtime_refs = [
    evidence.evidence_id
    for evidence in state.evidence
    if evidence.source_type is EvidenceSourceType.TOOL
]
evidence_refs = _stable_unique([memory.memory_id, *realtime_refs[:7]])
```

`memory_id` 在第一位，而且是强制的——`SimilarCaseReference` 的校验器写着：

```python
if self.case_id not in self.evidence_refs:
    raise ValueError("similar case evidence_refs must include case_id")
```

为什么要强制？因为一条"历史匹配"如果只引用本次的 Evidence，读者就无法回答"这个相似度是拿哪个案例
算出来的"。测试专门锁了这条：

```python
with pytest.raises(ValidationError, match="must include case_id"):
    SimilarCaseReference.model_validate(
        {**base, "confirmed": True, "evidence_refs": ["ev_current_tool_001"]}
    )
```

而同一个测试的前半段锁的是另一件事：

```python
with pytest.raises(ValidationError, match="must be confirmed"):
    SimilarCaseReference.model_validate({**base, "confirmed": False})
```

`confirmed` 是个 bool 字段，但它只能取 `True`。这看起来很怪——为什么留一个只能填一个值的字段？校验器
的 docstring 回答了：

> 相似案例进入 Planner/报告前必须经过 confirmed-only 搜索，因此 `confirmed=False` 不是可展示的降级
> 值，而是上游污染。

字段存在的意义是**让下游能看到这个事实**（API 响应和 `/demo` 前端都会显示它），而校验器存在的意义是
**让上游不可能填错**。如果去掉字段，前端就得靠"我们知道这里只有 confirmed"的默契来渲染；如果去掉
校验器，那这个字段就变成了一个可以撒谎的地方。

`realtime_refs[:7]` 的 7 是个预算：加上 `memory_id` 一共 8 条，对应 `SimilarCaseReference.evidence_refs`
在 Prompt 里的合理长度。只取 `TOOL` 来源是因为**只有工具 Observation 算本次实测事实**，
`KNOWLEDGE_GRAPH` / `DOCUMENT` / `CASE_MEMORY` 都不是。

现在看那条 graph-only 的测试断言：

```python
assert result.history_case_matches[0].evidence_refs[0] == "mem_graph_history_001"
assert "edge_case_similar_0123456789abcdef" not in result.history_case_matches[0].evidence_refs
```

这个候选是纯图召回的，它带着一个 `graph_edge_refs=["edge_case_similar_0123456789abcdef"]`。edge ID
**出现在 `common_points` 的解释文本里**（"关系引用：..."），但**不出现在 `evidence_refs` 里**。区别是
本质性的：

- `common_points` 是解释，说的是"这个候选为什么会被召回"。
- `evidence_refs` 是引用，说的是"这个说法由什么支撑"。第 9 章 §9.2.3 讲过可引用宇宙
  （`app/reporting/evidence.py`）只包含四类 ID：Evidence、知识节点、图路径、confirmed case_id。
  一条案例相似边不在其中。

如果 edge ID 混进 `evidence_refs`，报告层的 `_invalid_reference_issues` 会立刻把它判成
`unsupported_claim`——可引用宇宙不认它。所以这条断言其实也是在保护第 9 章的规则不被绕过。

### 10.5.6 `del runtime` 是怎么来的

```python
async def _explain_case_matches(
    graph_state: DiagnosisGraphState,
    runtime: Runtime[DiagnosisGraphRuntime],
) -> DiagnosisGraphState:
    """...保留名为 ``runtime`` 的注解参数是 LangGraph context 注入约定；本确定性节点不读取其中
    依赖，但不能改名成普通未识别参数。
    """

    del runtime  # LangGraph 依赖该命名注入 context；节点本身不读取外部依赖。
```

这两行是给未来的读者（和 linter）的说明。LangGraph 通过**参数名**决定要不要注入 context：一个签名为
`(state)` 的节点只拿状态，签名为 `(state, runtime)` 的节点会拿到 `Runtime[ContextT]`。这个节点确实
不需要任何外部依赖——它是纯函数——但如果把参数删掉或改名，签名就变了。

那为什么不干脆删掉？因为五个节点的签名保持一致本身有价值：`_build_diagnosis_graph` 里五个
`traced_node(...)` 包装是同构的，读者不需要逐个确认"这个节点拿不拿 runtime"。而 `del runtime` 让
ruff 的未使用参数检查通过，同时**在代码里留下一句解释**，比 `# noqa` 信息量大得多。

这是本项目里反复出现的一种注释风格：不解释代码在做什么（`del` 显然是删名字），而解释**为什么这行必须
存在**。`AGENTS.md` 和 `tests/unit/test_documentation_policy.py` 对内联注释的要求就是这个。

### 10.5.7 报告层会把 matcher 输出逐字段钉住

matcher 输出的 `SimilarCaseReference` 进了 `DiagnosisReport.similar_cases`。第 9 章 §9.5.4 提过
`_case_issues` 用的是整对象相等：

```python
if item != expected:
    # → AuditIssueCode.EVIDENCE_CONFLICT
```

`test_report_policy_rejects_similarity_or_explanation_drift` 演示了这条规则的威力：

```python
report = builder.build(state, confirmed_case_memories=(raw.memory,), history_case_matches=(match,))
validator = ReportPolicyValidator()
assert validator.validate(report, state, ...) == ()          # 干净报告零问题

drifted = DiagnosisReport.model_validate(
    {**report.model_dump(), "similar_cases": [match.model_copy(update={"similarity": 0.99})]}
)
issues = validator.validate(drifted, state, ...)

assert [issue.code.value for issue in issues] == ["evidence_conflict"]
assert issues[0].claim_path == "similar_cases[0]"
```

唯一的改动是把 similarity 从 0.91 改成 0.99。`case_id` 还对，`confirmed` 还是 True，`evidence_refs`
还合法，五类解释一字未动。规则照样否决。

这就把一整类攻击面关掉了：任何环节（模型、后续节点、手工修补、反序列化）想把 0.91 说成 0.99、想删掉
一条不利的 `differences`、想给 `reference_actions` 加一句"可以直接执行"，都会被判成
`evidence_conflict` 并触发返工。**确定性 matcher 的输出是唯一合法值，报告只能原样搬运。**

由此也能理解为什么 matcher 的每一处都用 `sorted` 和 `_stable_unique`：整对象相等的校验要求输出是
**逐字节确定的**。任何依赖 `set` 迭代顺序的地方都会让这条规则变成随机失败。

## 10.6 检索侧：向量 + SIMILAR_TO 图怎么合并

到这里为止，`recalled_memories` 是从哪来的还没讲。它来自
`CaseMemoryService.search_confirmed` → `PostgresCaseMemoryRepository.search_confirmed`，而后者的核心
是一个纯函数 `merge_case_memory_matches`（`app/memory/repository.py:453`）。SQL 部分留给第 11 章，这一节
只看合并逻辑，因为它是"图关系到底有没有用"这个问题的答案所在。

### 10.6.1 两个通道，一个融合

召回分两步走：

1. **直接命中。** 查询向量在 `case_memories.embedding` 上做 pgvector cosine，取 top-k。这些是
   `MemoryRetrievalChannel.VECTOR`。
2. **图扩展。** 拿第 1 步的结果作为**种子**，沿已审计的 `SIMILAR_TO` 边走一跳，得到邻居案例。这些是
   `MemoryRetrievalChannel.GRAPH`。邻居的分数不是它自己和查询的相似度，而是
   **种子相似度 × 边权**（`CaseMemoryMatch` 的 docstring：`图传播分由直接种子相似度乘 SIMILAR_TO 边权得到`）。

第 2 步的评分方式很关键。一个纯图邻居没有直接和查询比过，所以它的分数必须**继承自种子并被边权衰减**。
乘法保证了两个性质：种子越相关，邻居越有资格；边越弱，衰减越多。docstring 里那句"避免仅凭历史关系
无条件提高候选"说的就是这个——如果邻居直接拿边权当分数，一条 0.95 的边就能让任意案例挤进 top-k，
哪怕种子本身只有 0.3 的相关性。

然后是合并：

```python
candidates: dict[str, dict[str, object]] = {}
for match in direct_matches:
    candidates[match.memory.memory_id] = {
        "memory": match.memory,
        "direct_similarity": match.direct_similarity,
        "graph_score": None,
        "graph_edge_refs": [],
    }
```

先放直接命中。注释说明了顺序的理由：

> 中间字典只保存生成最终强类型模型所需的最小分量；先放直接命中，保证同 ID 的公开案例快照与查询 SQL
> 一致，图查询只为缺失候选补充 memory。

也就是说同一个案例的 `CaseMemory` 快照以直接查询那份为准。两份数据理论上应该一样（同一张表），但
两次查询之间可能有并发更新，选一个明确的赢家比"看哪个先写"好。

### 10.6.2 图邻居可以真的挤掉直接命中

这是本项目敢说"GraphRAG"而不是"向量检索 + 图装饰"的分界线。测试：

```python
merged = merge_case_memory_matches(
    [_vector_match("mem_aaaaaaaaaaaaaaaa", 0.86), _vector_match("mem_bbbbbbbbbbbbbbbb", 0.70)],
    [(_memory("mem_cccccccccccccccc"), 0.75, "edge_case_similar_1111111111111111")],
    limit=2,
)

assert [match.memory.memory_id for match in merged] == [
    "mem_aaaaaaaaaaaaaaaa",
    "mem_cccccccccccccccc",
]
graph_match = merged[1]
assert graph_match.retrieval_channels == [MemoryRetrievalChannel.GRAPH]
assert graph_match.direct_similarity is None
assert graph_match.graph_score == 0.75
assert graph_match.graph_edge_refs == ["edge_case_similar_1111111111111111"]
```

A（0.86）和 B（0.70）是直接 top-2。C 从来没直接命中过，它只是 A 的 `SIMILAR_TO` 邻居，图传播分 0.75。
`limit=2` 时最终返回的是 **A 和 C**——B 被踢出去了。

测试 docstring 把意义写明了：

> 结果保留 C 的 graph-only 通道和 edge 引用，证明图关系改变候选而非只作为旁路展示。

很多号称用了知识图的系统里，图只是"顺带展示一下相关实体"，最终喂给模型的候选还是纯向量 top-k。那种
做法的图是可以整块删掉而不影响任何输出的。这里不是：删掉图扩展，C 就进不来，Planner 就看不到那个
先例。这也是第 14 章消融实验能测出增益的前提——`MemoryRetrievalMode.VECTOR_ONLY` 关掉图扩展后，
召回结果**真的会变**。

顶层测试 `test_diagnosis_workflow_passes_graph_only_match_to_both_agents` 验的是同一件事在编排层的
延续：

```python
assert result.recalled_memories == (_graph_confirmed_match(),)
assert react.requests[0].confirmed_case_memories == (_graph_confirmed_match().memory,)
assert report.requests[0].confirmed_case_memories == (_graph_confirmed_match().memory,)
assert any(
    "SIMILAR_TO" in point for point in react.requests[0].history_case_matches[0].common_points
)
```

纯图召回的候选**不会**在编排层被过滤掉（一个很容易写出的"只保留直接命中更可靠"的优化会毁掉整个图
通道），而且它的来源会被 matcher 明确解释给两个 Agent 看。

### 10.6.3 同一个案例不能占两个坑

一个案例可能既直接命中，又被好几条边指到。合并逻辑：

```python
candidate = candidates.setdefault(memory.memory_id, {...})
current_graph_score = candidate["graph_score"]
if current_graph_score is None or graph_score > float(current_graph_score):
    candidate["graph_score"] = graph_score
    candidate["graph_edge_refs"] = [edge_id]
elif abs(graph_score - float(current_graph_score)) <= 1e-9:
    edge_refs = candidate["graph_edge_refs"]
    if not isinstance(edge_refs, list):  # pragma: no cover - internal invariant.
        raise TypeError("graph edge accumulator must be a list")
    if edge_id not in edge_refs:
        edge_refs.append(edge_id)
```

三分支：更高分则**替换**（连 edge 引用一起换掉）；分数并列（浮点容差 `1e-9`）则**追加** edge 引用；
更低分则丢弃。测试：

```python
merged = merge_case_memory_matches(
    [CaseMemoryMatch(memory=memory, similarity=0.80,
                     retrieval_channels=[MemoryRetrievalChannel.VECTOR], direct_similarity=0.80)],
    [
        (memory, 0.70, "edge_case_similar_3333333333333333"),
        (memory, 0.82, "edge_case_similar_2222222222222222"),
        (memory, 0.82, "edge_case_similar_1111111111111111"),
    ],
    limit=5,
)

assert len(merged) == 1
assert merged[0].similarity == 0.82
assert merged[0].retrieval_channels == [MemoryRetrievalChannel.VECTOR, MemoryRetrievalChannel.GRAPH]
assert merged[0].direct_similarity == 0.80
assert merged[0].graph_score == 0.82
assert merged[0].graph_edge_refs == [
    "edge_case_similar_1111111111111111",
    "edge_case_similar_2222222222222222",
]
```

一个案例，一次直接命中（0.80）和三条边（0.70 / 0.82 / 0.82）。结果：

- 只返回**一次**。这是核心——`limit` 是给 Planner 的上下文预算，一个案例占三个名额意味着其他两个
  案例的信息被白白挤掉了，而重复的三份内容对模型没有任何增量。
- 最终分 0.82，`retrieval_channels` 两个都有，两个分量都保留。这样 API 和评测能回答"这个案例是怎么
  被找到的"。
- 0.70 那条边被丢弃，两条并列的 0.82 都保留并按 edge ID 排序。**排序**是为了输出稳定：数据库返回边的
  顺序不保证，`sorted(...)` 让同样的输入永远得到同样的 `graph_edge_refs` 列表。这一点在 §10.5.7 说过
  为什么重要——报告层用整对象相等校验。

为什么并列时保留全部而不是随便留一条？因为 edge 引用是**可审计来源**。"这个案例通过两条不同的先例
关系都能到达"是有信息量的（说明它和当前问题的关联更结构化），随手扔掉一条就是在丢证据。

### 10.6.4 `CaseMemoryMatch` 的联合校验

最终分怎么算？

```python
component_scores = [
    score for score in (self.direct_similarity, self.graph_score) if score is not None
]
expected = max(component_scores)
if abs(self.similarity - expected) > 1e-9:
    raise ValueError("memory match similarity must equal the strongest retrieval score")
```

**取最大值，不是加权求和。** 这个选择值得说清楚。加权融合（比如 `0.7*direct + 0.3*graph`）是检索系统
里更常见的做法，这里没用，理由是可解释性：`max` 的语义是"这个案例最强的一条召回路径有多强"，而加权和
的语义是"我们调出来的一个复合分数"。前者能对用户解释，后者只能对调参日志解释。而且加权和有个反直觉
后果——一个只有直接命中 0.9 的案例会输给一个直接 0.7 + 图 0.7 的案例，虽然后者没有任何一条路径比
0.9 更强。

四条联合校验把通道声明和分量绑死：

```python
if has_vector != (self.direct_similarity is not None):
    raise ValueError("vector retrieval channel must match direct_similarity")
if has_graph != (self.graph_score is not None):
    raise ValueError("graph retrieval channel must match graph_score")
if has_graph != bool(self.graph_edge_refs):
    raise ValueError("graph retrieval channel must match graph edge refs")
if any(not reference.startswith("edge_case_similar_") for reference in self.graph_edge_refs):
    raise ValueError("memory graph edge refs must use stable case similarity IDs")
```

注意用的是 `!=` 而不是单向的 `if has_graph and score is None`。`!=` 双向校验：声明了图通道就必须有
分数，**没声明图通道也不许残留分数**。后半句防的是"改了通道列表忘了清分量"这类半改动。

最后那条前缀校验有个具体目标：`graph_edge_refs` 最终会出现在 `common_points` 的解释文本里，而那段
文本会进 Prompt、进 API 响应、进 `/demo` 前端。如果任意数据库字符串能进来，它就成了一个注入点。要求
`edge_case_similar_` 前缀意味着**只有 `case_similarity_edge()` 生成的 ID 能通过**（§10.9.3 会看到那个
函数怎么造 ID）。测试锁了这三条：

```python
with pytest.raises(ValidationError, match="graph retrieval channel must match graph_score"): ...
with pytest.raises(ValidationError, match="stable case similarity IDs"): ...      # edge_untrusted
with pytest.raises(ValidationError, match="strongest retrieval score"): ...        # 0.9 vs 0.7
```

而 `merge_case_memory_matches` 在纯函数层还有一道 confirmed 防线：

```python
for memory, graph_score, edge_id in graph_neighbors:
    if memory.status is not MemoryStatus.CONFIRMED:
        raise ValueError("graph memory neighbors must be confirmed")
```

对应测试的 docstring 解释了为什么 SQL 已经过滤了还要再查一次：

> SQL 会先过滤状态，本纯函数仍提供第二道领域防线；若数据库快照或测试替身漂移，合并直接失败而不是
> 静默泄漏已取消确认案例。

"泄漏已取消确认的案例"是这里最坏的结果：用户明确 reject 过一个错误案例，它却因为图扩展路径的 SQL
少写了一个 `WHERE` 又回到了 Planner 面前。图扩展的 SQL 是个 join，状态过滤要在**邻居侧**写一遍，很容易
漏——所以纯函数这道防线不是形式主义。

### 10.6.5 五级排序键

```python
# 最终分优先；分数相同时直接命中优先于纯图扩展，再比较图分、新鲜度和稳定 ID，保证分页/测试
# 不依赖 PostgreSQL 未声明的行顺序。
return sorted(
    merged,
    key=lambda match: (
        -match.similarity,
        -(match.direct_similarity if match.direct_similarity is not None else -1),
        -(match.graph_score if match.graph_score is not None else -1),
        -match.memory.updated_at.timestamp(),
        match.memory.memory_id,
    ),
)[:limit]
```

| 级 | 键 | 语义 |
|---|---|---|
| 1 | `-similarity` | 最终分降序 |
| 2 | `-direct_similarity`（缺失记 `-1`） | 同分时直接命中优先于纯图扩展 |
| 3 | `-graph_score`（缺失记 `-1`） | 再比图分 |
| 4 | `-updated_at` | 新鲜度 |
| 5 | `memory_id` | 字典序兜底 |

第 2 级的 `else -1` 是个小技巧：缺失分量映射成 `-(-1) = 1`，排在所有真实分量（映射成 `-0.x ≤ 0`）之后。
效果是"有直接命中的排前面"，符合注释里的说法。

第 5 级是**保证全序**的那一级。前四级理论上仍可能全部相等（同分、同通道、同一微秒更新），而
`memory_id` 是主键，一定唯一。这一级存在的意义完全是可重现性：如果排序不是全序，`[:limit]` 的结果就
取决于 Python `sorted` 的稳定性 + 输入顺序 + PostgreSQL 未声明的行顺序，Golden 回放会随机失败，而且
是那种"重跑一次就好了"的假失败——最消耗信任的一类 bug。

### 10.6.6 `MemoryRetrievalMode` 为什么不进公开 API

```python
class MemoryRetrievalMode(StrEnum):
    """定义长期记忆召回评测允许的向量基线与生产向量+图模式。

    ``vector_only`` 只返回 pgvector 直接 top-k；``vector_graph`` 继续沿 ``SIMILAR_TO`` 扩展并是
    runtime/API 默认值。显式枚举让消融实验可重放，避免用隐藏布尔开关改变检索条件；公开 API
    不接受该参数，普通用户不能关闭生产图召回。
    """
```

这个枚举只为第 14 章的消融实验存在。两个设计点：

1. **用枚举而不是布尔开关。** `enable_graph: bool = True` 这种参数在半年后没人知道 `False` 到底关掉了
   什么。`MemoryRetrievalMode.VECTOR_ONLY` 是个可以写进评测报告的名字，第 14 章的消融结果表里直接
   用它当行名。
2. **不透传到公开 API。** `PostgresMemoryRuntime.search` 签名里有 `mode` 参数，但
   `CaseMemoryWorkflow` 协议里没有——顶层工作流拿不到它，于是诊断路径永远走
   `VECTOR_GRAPH`。这跟 §10.2.4 不暴露 `decide` 是同一手法：**能力存在，但在这条路径上不可达**。

## 10.7 stage：写记忆的四道门

最后一个节点：

```python
async def _stage_case_memory(
    graph_state: DiagnosisGraphState,
    runtime: Runtime[DiagnosisGraphRuntime],
) -> DiagnosisGraphState:
    if graph_state.report_result is None:
        raise RuntimeError("memory stage node requires completed report result")
    stage = await runtime.context.memory.stage(graph_state.report_result)
    # staging 是当前 run 的最终确定性投影；重新验证完整 ReportRunResult，可清除恢复状态中的旧候选，
    # 也让后续 checkpoint/API 从 AgentState 与外层 memory_stage 读取到完全一致的对象。
    report_state = graph_state.report_result.state.model_copy(
        update={"memory_candidate": stage.memory}
    )
    report_result = ReportRunResult.model_validate(
        {
            **graph_state.report_result.model_dump(),
            "state": report_state,
        }
    )
    return graph_state.model_copy(
        update={
            "report_result": report_result,
            "memory_stage": stage,
            "status": DiagnosisWorkflowStatus.COMPLETED,
        }
    )
```

### 10.7.1 顶层不判断资格，只调用一次

节点 docstring：

> 节点对 accepted 与 degraded 使用同一调用路径，避免顶层复制审计资格判断；记忆服务分别返回
> staged/merged、skipped_no_root_cause 或 skipped_not_accepted。异常会阻止 completed，保证 API 不会
> 在持久化未知时宣称诊断收尾成功。

最后一句是 `status = COMPLETED` 放在这个节点末尾的理由。`stage` 抛异常 → 状态永远不会变成
`COMPLETED` → `run()` 里的 `if final_state.status is not DiagnosisWorkflowStatus.COMPLETED: raise
RuntimeError("diagnosis graph ended without completed status")` 触发（实际上异常会先原样冒出来）。
无论哪条路，调用方都得到一个错误，而不是一份"诊断完成了，记忆状态未知"的结果。

### 10.7.2 `stage_from_report` 的两道 skip

真正的资格判断在 `CaseMemoryService`：

```python
if (
    result.outcome is not ReportWorkflowOutcome.ACCEPTED
    or result.state.audit_result is None
    or result.state.audit_result.status.value != "accept"
):
    return MemoryStageResult(status=MemoryStageStatus.SKIPPED_NOT_ACCEPTED)
report = result.state.draft_report
if report is None or not report.root_causes:
    return MemoryStageResult(status=MemoryStageStatus.SKIPPED_NO_ROOT_CAUSE)
```

第一道门查了**三个条件**，而它们理论上应该是同一件事：工作流 outcome 是 accepted、审计结果存在、审计
状态是 accept。第 9 章 §9.10 讲过 `ReportRunResult.validate_terminal_result` 已经把 outcome 和
`AuditStatus` 双向绑定了，所以这三个条件在合法数据上必然同时成立。

为什么还要全查？因为这是**写操作的最后一道门**，而且写下去的东西会影响未来所有 run。第 9 章的报告可以
返工，这里写错了只能靠人去 reject。在这种位置上，把三个应该等价的条件都查一遍的成本是三个 `or`，收益
是"任何一层契约被改坏都不会导致误写"。这跟 §10.4.2 三层 confirmed 门禁是同一种判断。

第二道门查根因。`ACCEPTED` 但没有 `root_causes` 是完全可能的——第 9 章 §9.4.1 的三道过滤会把没有
supporting evidence 的假设全部拦掉，产出一份"证据不足"的报告，而这份报告是**合法的、可以通过审计的**。
它只是没什么可记的：一条没有根因的案例记忆，症状有了、方案没有、根因没有，召回它对未来毫无帮助，
还会占据 top-k 名额。所以 `skipped_no_root_cause` 是个正常出口，不是错误。

注意两个 skip 的顺序和位置：**都在任何 I/O 之前**。测试直接断言这一点：

```python
result = await service.stage_from_report(_degraded_result())

assert result.status is MemoryStageStatus.SKIPPED_NOT_ACCEPTED
assert repository.lock_scopes == []
assert repository.records == {}
```

`lock_scopes == []` 意味着连 advisory lock 都没取。这不只是省资源——advisory lock 是按组件范围加的
（§10.8.1），一次不必要的加锁会阻塞同组件的其他 staging。降级报告在生产里不算罕见，如果每次都要排队
拿锁再发现自己没资格，那就是白白引入了一个串行点。

### 10.7.3 `_candidate_from_result`：根因必须精确匹配假设

从报告投影成 `CaseMemory` 的逻辑值得整段看：

```python
conclusion = sorted(
    report.root_causes,
    key=lambda item: (-item.confidence, item.root_cause),
)[0]
hypotheses = [
    hypothesis
    for hypothesis in result.state.hypotheses
    if hypothesis.candidate_root_cause == conclusion.root_cause
]
if not hypotheses:
    raise ValueError("accepted memory root cause must match an AgentState hypothesis")
```

选"最高置信度那一条"用的是 `(-confidence, root_cause)` 两级排序，不是 `max(...)`。原因和 §10.6.5 的
五级排序键一样：置信度并列时必须有确定性的次级键，否则同一份报告在不同 Python 版本、不同列表构造顺序
下可能记下不同的根因，Golden 回放就不可复现。

真正值得停下来想的是那个 `raise ValueError`。它检查的是：报告里写的根因，必须**逐字**等于 `AgentState`
里某个假设的 `candidate_root_cause`。为什么要有这道检查？

因为 `CaseMemory` 是给未来用的**事实断言**，而报告里的 `root_causes[].root_cause` 只是一段
模型写的文本。第 9 章 §9.4 里，报告草稿的根因条目要求 `supporting_evidence` 非空且引用可citable ID，
但**没有要求它必须来自某个假设**——报告 Agent 完全可以在 `claim` 里换一种说法总结根因，那在报告语境下
是可接受的润色。

一旦这段文本要变成长期记忆，情况就变了。案例记忆的签名（§10.8.2）是 `sorted(components) + 归一化根因`
的 SHA-256；召回时匹配器判断"根因一致"也是归一化精确比较（§10.5.3）。如果记下来的根因是一段报告独有的
润色文本，那它跟 ReAct 阶段真正验证过的那个假设就**对不上**了：签名会分裂（同一个故障产出两条记忆）、
未来的根因一致性判断会失效。

所以这道检查的本质是：**只有经过 ReAct 循环、被证据检验过的假设，才有资格进入长期记忆**。报告可以润色，
记忆不行。检查失败时抛 `ValueError` 而不是 skip，因为这不是"这份报告不值得记"，而是"上游契约坏了"——
一份 accepted 报告的根因不在假设列表里，说明第 8 章的假设更新或第 9 章的草稿生成有 bug，应该炸出来。

### 10.7.4 候选不能引用被召回的历史案例

`evidence_refs` 的构造里有一行过滤和一段注释：

```python
historical_ids = {match.memory.memory_id for match in result.state.history_case_matches}
evidence_refs = [
    ref
    for ref in _stable_unique(raw_refs)
    if ref not in historical_ids
]
```

测试断言的是一个很干净的结果：

```python
assert staged.memory.evidence_refs == ["ev_memory_unit_001"]
```

输入里明明还有历史案例的 `memory_id`，输出只剩一条实时证据。这是在阻止**递归自引用**。

设想不过滤会怎样。第一次诊断产出案例 A，引用了三条实时证据。第二次遇到相似故障，召回了 A，报告引用了
A 作为参考证据，于是新案例 B 的 `evidence_refs` 里含 A。第三次召回 B，案例 C 引用 B……几轮之后，一条
案例的证据链全是"其他案例说的"，而最初那三条真实工具输出早就不在引用里了。这时候如果案例 A 被 reject
删掉了（§10.9.6），B、C、D 的证据引用就全成了悬空 ID。

更根本的是 §10.3.3 那条同源约束：**历史不能证明历史**。`_build_memory_query` 排除 CASE_MEMORY 证据，
`matcher._normalized_context_text` 排除 CASE_MEMORY 证据，这里排除历史案例 ID——三处都在切断同一个反馈
回路。区别只是这一处切的是"写"，前两处切的是"读"。

### 10.7.5 新候选默认 `pending`

`_candidate_from_result` 的收尾：

```python
memory_id = f"mem_{signature[:16]}"
return CaseMemory(
    memory_id=memory_id,
    ...
    status=MemoryStatus.PENDING,
    occurrence_count=1,
)
```

`status=MemoryStatus.PENDING` 是硬编码的，不是参数。整条 staging 路径上没有任何地方能写出
`CONFIRMED`——`CaseMemoryService.decide` 才能，而 §10.2.4 已经讲过 `decide` 不在
`CaseMemoryWorkflow` 协议里，所以诊断图**在类型层面**碰不到它。

这个默认值决定了系统的整体可信度模型。`search_confirmed` 的 SQL 里有 `WHERE status='confirmed'`
（§10.4.2），图注册也只处理 confirmed 案例（§10.9.1）。所以一条新写入的 pending 记忆：不会被召回、不会
进图、不会影响任何后续诊断。它就是一条等人看的候选。

为什么不敢自动 confirm？因为审计通过（第 9 章）只保证**这份报告的每条结论都有实时证据支撑、且引用格式
合法**。它不保证根因判断是对的。审计器看不到真实世界的修复结果，它只能核对"你说的话有没有证据"。一条
错误但引用规范的根因完全可以通过审计——比如把"上游同步延迟"误判成"调度器资源不足"，如果证据里恰好有
一条资源使用率偏高的观测，这个判断在证据链上是自洽的。

自动 confirm 的后果是这个错误会被**放大**：它进入向量库和图，被后续相似故障召回，成为 Planner 和
Auditor 共享的"历史参考"，甚至通过 §10.8 的去重合并把 `occurrence_count` 累加成"这个问题出现过 5 次"，
看上去更可信了。人工 confirm 这一步的成本是一次点击，收益是系统不会自己把错误结论沉淀成知识。

### 10.7.6 重新校验完整的 `ReportRunResult`

回到 `_stage_case_memory` 节点，它调 Service 之前和之后各做一件事：

```python
report_result = ReportRunResult.model_validate(
    {**state.report_result.model_dump(), "state": staged_state}
)
```

节点把 `memory_candidate` 写回 `AgentState`，然后**重新构造并校验整个 `ReportRunResult`**，而不是
`model_copy(update=...)`。这跟 §10.8.4 `_merge_duplicate` 里用 `model_validate` 重建而非
`model_copy` 是同一个决定：`model_copy` 绕过所有 validator。

这里绕过的具体是什么？是 `ReportRunResult.validate_terminal_result`（第 9 章 §9.10）那一整套 outcome
与 `AuditStatus` 的双向绑定检查。写回 `memory_candidate` 理论上不会破坏它们，但"理论上不会破坏"和
"重新验证一遍确认没破坏"之间的差别，就是一次几十微秒的 Pydantic 校验。这是全书反复出现的取舍：在状态
跨阶段传递的接缝处，重新校验的成本远低于让不一致状态流到下游。

最后一行才是关键：

```python
status = DiagnosisWorkflowStatus.COMPLETED
```

`COMPLETED` 在这个节点**最后**才写。如果 staging 抛异常——`_candidate_from_result` 的 `ValueError`、
数据库连接断开、embedding provider 超时——status 停在 `RUNNING`，而 `DiagnosisGraph.run()` 的守卫
（§10.2.1）会把它变成 `RuntimeError("diagnosis graph ended without completed status")`。

这排除的是一种特别难查的结果：**"诊断完成，但记忆状态未知"**。如果 status 先写 COMPLETED 再 staging，
一次 staging 失败会返回一份看起来完整的诊断结果，`memory_stage` 却是 `None` 或半成品。调用方（API、
评测脚本）拿到 `COMPLETED` 就认为一切正常，几天后才发现某些案例没被记录，且没有任何日志说明是哪几条。

## 10.8 去重：两级判定与幂等合并

一个故障不会只发生一次。同一个 LTS 调度积压可能每周复现，如果每次诊断都插入一条新记忆，向量库很快会被
近似重复项填满，top-k 召回全是同一个案例的五个副本，其他有用的案例被挤出去。所以 staging 必须去重。

### 10.8.1 advisory lock 的范围是组件集合

```python
async with self._repository.lock_dedup_scope("|".join(candidate.components)):
```

去重是"先查再写"，天然有竞态：两个 run 同时诊断同一个故障，都查不到重复项，都插入，结果两条一样的记忆。
PostgreSQL advisory lock 解决这个问题，但**锁的粒度选择本身是个设计决定**。

锁全局？那所有 staging 串行，并发诊断的吞吐直接归一。锁 `memory_id`（即签名）？那只能防住精确签名重复，
防不住 §10.8.3 的向量近似重复——两条根因文本不同但语义相同的记忆签名不同，会各自拿到自己的锁然后同时
插入。

锁**组件集合**正好覆盖需要的范围：向量相似判定只在同组件范围内进行（`find_similar` 的查询条件），所以
所有可能互相判定为重复的候选必然共享同一个锁范围。而不同组件的故障（LTS 的和 BDS 的）完全可以并发
staging，因为它们之间不可能被判定为重复。锁的粒度和去重判定的作用域**精确对齐**，这是这类锁设计的一般
原则。

`"|".join(components)` 之前 components 已被 `_sorted_components` 排序，所以 `["lts","bds"]` 和
`["bds","lts"]` 拿到的是同一个锁——否则组件顺序不同的两个候选会绕过锁。

### 10.8.2 精确签名先查，向量后算

```python
signature = memory_signature(candidate.components, candidate.root_cause)
existing = await self._repository.find_by_signature(signature)
if existing is not None:
    return await self._merge_duplicate(...)

embedding = await self._embedding_client.embed_one(text)
similar = await self._repository.find_similar(...)
```

源码里的注释直说了原因：

> 精确签名无需先生成向量，避免重复记录每次 staging 都支付不必要的 Provider 成本。

签名是纯本地计算——`sorted(components)` 加归一化根因文本，SHA-256。embedding 是一次远程 HTTP 调用，
有延迟、有费用、有失败可能。而"同一个故障重复出现"这个最常见的情况恰好是精确签名能命中的：同样的组件、
同样的根因文本。把免费的确定性判定放在收费的语义判定前面，常见路径上一次 Provider 调用都不花。

顺序反过来会怎样？功能上完全一样，但每次重复 staging 都多一次 embedding 调用。在一个每天诊断几十次、
其中一半是复现故障的系统上，这是一半的 embedding 预算白花。

`memory_signature` 的实现值得看一眼：

```python
payload = "|".join([*_sorted_components(components), _normalize_text(root_cause)])
return hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

`_normalize_text` 做 casefold + 空白折叠。所以"LTS 调度器线程池耗尽"和"lts 调度器线程池耗尽"
（以及中间多一个空格的版本）签名相同。这是**故意保守**的归一化：不做同义词、不做分词，只处理确定不会
改变语义的差异。跟 §10.5.3 匹配器的保守策略同源——宁可漏判成"新案例"（多一条记忆，可人工合并），
不能误判成"重复"（丢掉一次真实的独立故障记录）。

### 10.8.3 向量近似重复用的是独立阈值

```python
similar = await self._repository.find_similar(
    embedding=embedding,
    components=candidate.components,
    threshold=self._dedup_similarity_threshold,
)
```

`dedup_similarity_threshold` 默认 `0.92`（`app/core/settings.py:134`）。这个数字比召回用的任何阈值都
高得多——§10.6 的图扩展阈值是 `0.75`，而召回本身根本不设阈值（取 top-k）。

三个数字的关系不是随手定的，`Settings` 里有一条启动期跨字段守卫：

```python
if self.case_graph_similarity_threshold > self.memory_dedup_similarity_threshold:
    raise ValueError("case_graph_similarity_threshold must not exceed memory dedup threshold")
```

为什么必须 `graph ≤ dedup`？因为如果图阈值比去重阈值还高，那任何满足"可以连边"的两条案例都已经先被
判定为重复合并掉了——图里永远不会有 `SIMILAR_TO` 边，整个 §10.6 的图扩展通道结构性失效。这条守卫把
一个"配置改了以后某个功能静默变成死代码"的问题变成了启动失败。

`0.92` 这个具体数值的含义：在 `bge-m3` 的向量空间里，两段中文技术描述要到 0.92 余弦相似度，基本是
同一件事的不同措辞。留出 `0.75–0.92` 这个区间给"相关但不同"的案例——它们连边、互相召回，但保持独立
身份。

### 10.8.4 合并的四条不变量

`_merge_duplicate` 是这一节最密集的地方，四件事各解决一个具体问题。

**（一）同 run 幂等。**

```python
if existing.has_source_run(candidate.source_run_id):
    return MemoryStageResult(status=MemoryStageStatus.MERGED, memory=existing, ...)
```

同一个 run 重复 staging 必须不累加。什么时候会重复？第 11 章要讲的 Worker 租约机制里，一个 run 可能
在 heartbeat 超时后被另一个 Worker 接管重跑；`resume` 也会重放节点。测试锁死了这个行为：

```python
assert repository.insert_calls == 1
assert repository.update_calls == 1
assert stored.occurrence_count == 2
```

两次 staging（不同 run）产生 1 次 insert + 1 次 update，`occurrence_count` 是 2 而不是 3。第三次用
已记录的 run_id 再来一遍，两个计数都不变。

`occurrence_count` 会出现在召回的案例文本里，人看到"该问题出现过 5 次"会据此判断严重程度。如果 Worker
重试能把它刷高，这个数字就变成了基础设施抖动的度量而不是故障频率的度量。

**（二）`model_validate` 重建，不用 `model_copy`。**

```python
merged = StoredCaseMemory.model_validate({**existing.model_dump(), ...})
```

`model_copy(update=...)` 完全跳过 validator。而 `StoredCaseMemory` 的 validator 里有
`validate_embedding_space`——检查向量长度与声明的 dimensions 一致、无 NaN/Inf、非全零。合并要重新
embed（见下面第四条），如果 provider 返回了一个维度不对的向量，`model_copy` 会让它静默进库，然后在
未来某次 `cosine_distance` 查询时以一个完全不相关的 SQL 错误炸出来。

**（三）无变化不写库。**

```python
if merged_without_time == existing:
    return MemoryStageResult(status=MemoryStageStatus.MERGED, memory=existing, ...)
```

比较时排除 `updated_at`，因为那个字段必然变。如果除时间戳外一切相同，就不发 UPDATE。这不只是省一次写：
`updated_at` 是排序和运维排查用的字段，一次纯粹的重复 staging 把它刷新，会让"这条记忆最近被更新过"
这个信号失去意义。

**（四）时间戳取 max，重新 embed。**

```python
updated_at=max(now, existing.updated_at)
```

`max` 而不是直接赋 `now`，防止时钟回拨或乱序重放让 `updated_at` 倒退。

合并后要重新生成 embedding，因为合并可能改变了案例文本——新 run 带来了新的 symptoms、新的
solution_steps。文本变了向量不变，等于让这条记忆的语义位置停留在第一次的措辞上，后续召回会越来越不准。

有一点**不会**被合并改掉：canonical 案例的 `root_cause` 和 `status`。合并只做增量累积（
occurrence_count、source_run_ids、evidence_refs、symptoms），根因保持首次写入时的版本，状态保持人工
决定的结果。所以一条已 confirmed 的案例被重复命中后仍是 confirmed，不会退回 pending 要求重新确认；
一条 pending 的也不会因为"又出现了一次"就自动升级。

## 10.9 图注册：让案例成为 GraphRAG 的一等节点

第 5 章讲过知识图谱：节点是组件、故障模式、处置动作，边是 `DEPENDS_ON` / `CAUSES` / `MITIGATES`。案例
记忆确认后，会以**同样的节点/边表**注册进这张图，而不是单独建一套案例关系表。`app/memory/graph_registration.py`
（421 行）做这件事。

三个模块常量定义了它的边界：

```python
CASE_GRAPH_SOURCE_ID = "case-memory-graph:v1"
CASE_GRAPH_NODE_RELIABILITY = 0.9
CASE_GRAPH_MAX_NEIGHBORS = 20
```

`source_id` 是所有权标记。图表里同时住着 seed 知识（第 5 章）和案例节点，所有写和删都带
`source_id == CASE_GRAPH_SOURCE_ID` 条件——案例注册器**结构上无法**改动或删除 seed 知识节点。这比
"约定不要动别人的数据"强得多。

`reliability=0.9` 而不是 1.0：案例来自一次真实诊断且经过人工确认，比模型推测可信，但仍不如 seed 里
手写的组件依赖关系确定（那些是系统架构事实）。这个值参与第 5 章的检索加权。

### 10.9.1 复用已审计过的向量，不重新 embed

```python
def case_graph_node(memory: StoredCaseMemory) -> GraphNode:
    return GraphNode(
        node_id=case_graph_node_id(memory.memory_id),
        ...
        embedding=list(memory.embedding),
```

节点直接用 `StoredCaseMemory` 里存着的那个向量。这省掉一次 Provider 调用，但更重要的是**一致性**：
§10.6 的图扩展是"用查询向量找到种子案例，再沿边走到邻居"，而边的权重是案例间的余弦相似度。如果图节点
用一个新生成的向量，而 `search_confirmed` 用库里存的那个，两者在极小的数值差异下会给出不同的邻居排序，
`CaseMemoryMatch` 的四条双向一致性校验（§10.6.4）就会随机失败。同一个向量服务两条检索通道，是这些
校验能成立的前提。

节点的 `aliases` 由 components 和 tags 拼成，`name` 加 `"历史案例："` 前缀——在 `/demo` 的图谱视图里
一眼能区分案例节点和知识节点。`source_span` 里写着"不包含模型原始思维链"，这是 §10.13 会展开的那条
全局约束在数据层的落点。

`_bounded_case_content` 把节点正文截到 4000 字符，**根因和症状排在最前面**。截断在长案例上必然发生，
排序决定了截掉的是什么：留下根因和症状（检索和判断都靠它们），截掉的是靠后的处置步骤细节。

### 10.9.2 先删干净再重建

`register_confirmed` 的中段是这一节最容易被质疑的设计：

```python
# 先删除本注册器拥有的全部 SIMILAR_TO 边，再按当前阈值重建。
# 否则历史上曾超过阈值、现在已低于阈值的边会永久残留。
await self._delete_owned_similarity_edges(session, node_id)
...
for neighbor in neighbors:
    await self._upsert_edge(session, case_similarity_edge(node_id, neighbor_id, similarity))
    await self._upsert_edge(session, case_similarity_edge(neighbor_id, node_id, similarity))
```

为什么不做增量 upsert？因为**阈值和邻居集合都会变**。案例文本被合并更新过（§10.8.4 第四条）会导致向量
移动，原来 0.80 的邻居可能掉到 0.70；`case_graph_similarity_threshold` 也可能被调高。纯 upsert 只会
写入新满足条件的边，永远不会删除已不满足条件的边，于是图里逐渐积累"历史上曾经相似过"的陈旧边。

这些陈旧边不是无害的：§10.6.2 讲过图扩展会让一个纯图邻居挤掉直接命中。一条不该存在的边会把不相关的
案例推进召回结果，而且因为它有合法的 `edge_case_similar_` ID 和 source_span，从 API 输出上看不出问题。
删除范围严格限定在 `source_id == CASE_GRAPH_SOURCE_ID` 且触及该节点的 `SIMILAR_TO` 边，所以重建的代价
只是这个节点的邻居数（≤20）。

**两个方向的边都写。** 相似性是对称的，但图查询不是——SQL 里沿边走要么按 `from_node_id` 要么按
`to_node_id`，写两条有向边让"从任一端出发都能到达对面"变成数据事实，而不需要在每个查询里写
`OR` 条件。代价是边数翻倍，在 ≤20 邻居的规模下无关紧要。

### 10.9.3 ID 生成是纯函数且格式严格

```python
def case_graph_node_id(memory_id: str) -> str:
    if not _CASE_MEMORY_ID_PATTERN.fullmatch(memory_id):
        raise ValueError("case graph node id requires a mem_<16 hex> memory id")
    return f"case_{memory_id[4:]}"
```

`mem_0123456789abcdef` → `case_0123456789abcdef`。纯函数、无状态、不查库。所以从案例 ID 推节点 ID 和
反推都不需要一张映射表，任何地方（API、评测、`/demo`）都能自己算。

格式检查用 `fullmatch` 且只接受小写十六进制。为什么这么严？因为 `memory_id` 是
`f"mem_{signature[:16]}"`（§10.7.5），signature 是 SHA-256 的 hexdigest——所以合法输入必然是 16 位
小写 hex。任何不符合的输入意味着有人手工造了一个 memory_id，或者签名算法被改了。这时候生成一个格式古怪
但能用的节点 ID，只会让问题在几层之后以"图里找不到这个节点"的形式出现。

边 ID 同样是确定性的：

```python
digest = hashlib.sha256(f"{CASE_GRAPH_SOURCE_ID}|{from_node_id}|{to_node_id}").hexdigest()
edge_id = f"edge_case_similar_{digest[:16]}"
```

把 `source_id` 放进哈希输入，是为了让案例边的 ID 空间和其他来源的边不可能碰撞。前缀
`edge_case_similar_` 就是 §10.6.4 那条前缀校验检查的东西——边 ID 会进 Prompt、API 响应和 `/demo`，
所以只有由 `case_similarity_edge()` 生成的 ID 才允许通过。这个函数还挡了两种非法输入：自环
（`from == to`）和 `0 < similarity <= 1` 范围外的分数。

### 10.9.4 节点 upsert 的双重所有权保护

`_upsert_owned_node` 看起来过度设计，实际每一层都有具体作用：

```python
existing = await session.execute(
    select(GraphNodeRecord).where(...).with_for_update()
)
...
statement = insert(GraphNodeRecord).values(...).on_conflict_do_update(
    index_elements=["node_id"],
    set_={...},
    where=and_(
        GraphNodeRecord.node_type == GraphNodeType.CASE,
        GraphNodeRecord.source_id == CASE_GRAPH_SOURCE_ID,
    ),
)
result = await session.execute(statement)
if result.rowcount != 1:
    raise ValueError(...)
```

`with_for_update()` 的预检负责**并发**：两个 confirm 决策同时落到同一个案例时，第二个会等第一个的事务
提交。`on_conflict_do_update` 的 `where` 负责**所有权**：如果 `case_xxx` 这个 node_id 已经被一个
seed 节点占用（不同 node_type 或不同 source_id），冲突分支的 `where` 不成立，UPDATE 不执行。

而 `rowcount != 1` 检查负责把上面那种"什么都没发生"变成异常。这是关键——`on_conflict_do_update` 带
`where` 时，条件不满足不会报错，语句成功执行影响 0 行。没有 rowcount 检查的话，一次被所有权守卫拦下的
写入会**静默成功**，`register_confirmed` 返回一个声称注册完成的结果，而图里那个节点还是别人的。

### 10.9.5 阈值配置与 seed 边界

`PostgresCaseGraphRegistrar.__init__` 校验两个参数：`threshold` 在 `[0, 1]`，`max_neighbors` 在
`[1, 100]`。默认阈值从 `Settings.case_graph_similarity_threshold`（`0.75`）来，上限由 §10.8.3 那条
`graph ≤ dedup` 启动守卫锁住。

`_find_similar_confirmed` 的查询条件值得逐条看：

- `cosine_distance` 排序，`limit(max_neighbors)`；
- 排除自身；
- **要求同 provider 同 dimensions**——不同 embedding 模型的向量之间算余弦相似度是没有意义的数字，
  这个条件保证换模型后新旧向量不会混着比。第 6 章讲过同样的约束出现在文档检索里；
- 只查 `status == confirmed`；
- Python 侧再过滤 `similarity <= 0` 或低于阈值的结果。

注册器**不自己 commit**：`session` 由 `PostgresMemoryRuntime` 传入，事务边界属于调用方（§10.11）。
一个会自己提交的注册器无法和"确认案例状态"这个写操作放进同一个事务，就会出现"状态已 confirmed 但图里
没节点"的中间态。

### 10.9.6 reject 靠外键级联

```python
async def remove(self, session: AsyncSession, memory_id: str) -> bool:
```

`remove` 只删节点，不删边——边由 `ON DELETE CASCADE` 自动清理。这依赖第 5 章建表时给
`graph_edges.from_node_id` / `to_node_id` 加的外键约束。手工删边的版本需要两条 DELETE 且必须覆盖两个
方向，漏一个方向就留下悬空边；级联把这个正确性交给数据库。

删除前先 `_assert_owned_case_node`，同样是所有权检查。节点不存在时返回 `False` 而不是抛异常——reject
一条从未 confirmed 过的候选是完全正常的操作（它本来就不在图里）。

整条生命周期由一个集成测试锁住：`search_visibility_tracks_confirm_reject_and_reconfirm_decisions`。
pending 时搜不到；confirm 后搜得到且图里有节点；reject 后搜不到且节点连边一起消失；再 confirm 又完整
恢复。这个测试要真数据库（`-m postgres`），因为它验证的正是级联删除和 pgvector 查询这些数据库行为。

## 10.10 `DiagnosisRunResult`：五组跨阶段一致性检查

顶层结果对象自己带一个 `model_validator`，把三个子结果之间的关系全部检查一遍。它的价值在于：这些关系
**任何单个阶段都无法验证**——ReAct 不知道报告的 outcome，报告不知道记忆是否写成功。

```python
if self.history_trigger is HistoryTrigger.NOT_REQUESTED:
    if self.memory_query is not None or self.recalled_memories or self.history_case_matches:
        raise ValueError("unrequested history cannot contain a query, memories, or explanations")
elif self.memory_query is None or not self.memory_query.strip():
    raise ValueError("requested history requires a recorded memory query")
```

**第一组：触发状态与内容双向绑定。** NOT_REQUESTED 必须三样都空，其余 trigger 必须有非空查询。这让
"没有相似案例"和"根本没查"在结果对象上永远可区分（§10.3.1）。少了后半句，一个"查了但 query 字段没
记录"的结果会看起来像正常的空召回，事后无法判断是检索没命中还是节点有 bug。

```python
raw_ids = [match.memory.memory_id for match in self.recalled_memories]
explained_ids = [match.case_id for match in self.history_case_matches]
if raw_ids != explained_ids:
    raise ValueError("history explanations must preserve recalled memory order and identity")
```

**第二组：召回快照与解释逐位对齐。** 用列表相等而不是集合相等——顺序携带检索排名信息（§10.6.5 那个
五级排序键的结果），乱序等于丢掉排名。相似度列表也要逐位相等。这两条一起把 §10.5.1 那个"同一份不可变
快照跑两遍匹配器"的约定变成运行时保证：任何在两次之间偷偷重新检索、过滤或重排的实现都会在这里失败。

```python
if self.react.state.run_id != self.report.state.run_id:
    raise ValueError("React and report results must share run_id")
if self.react.state.session_id != self.report.state.session_id:
    raise ValueError("React and report results must share session_id")
```

**第三组：身份同源。** 挡的是调用方（尤其是评测脚本和 resume 逻辑）把不同诊断的中间结果拼在一起。

```python
if self.report.state.memory_candidate != self.memory_stage.memory:
    raise ValueError("report state memory_candidate must match memory stage result")
```

**第四组：`memory_candidate` 与 staging 结果同一对象。** §10.7.6 那次写回如果写错了或漏了，这里炸。

```python
if self.report.outcome is ReportWorkflowOutcome.DEGRADED:
    if self.memory_stage.status is not MemoryStageStatus.SKIPPED_NOT_ACCEPTED:
        raise ValueError("degraded report must skip memory as not accepted")
elif self.memory_stage.status is MemoryStageStatus.SKIPPED_NOT_ACCEPTED:
    raise ValueError("accepted report cannot use not-accepted memory skip status")
```

**第五组：降级与跳过状态双向等价。** 两个方向都查：degraded 必须跳过；反过来，非 degraded 的报告不许
用 `SKIPPED_NOT_ACCEPTED` 这个理由。后半句挡的是一种很隐蔽的错误——如果某天有人在 staging 里加了
try/except 把数据库失败也归到 `SKIPPED_NOT_ACCEPTED`，那一次真实的写库故障就会伪装成"审计没通过所以
不记"，而报告本身是 accepted。这正是第 9 章 §9.9 那条原则的延伸：**"不可用"不等于"不通过"**。

### 10.10.1 一个字段缺失如何把评测指标结构性归零

`evidence_bundle` 字段上的注释记录了一次真实事故，值得完整引用：

> Bundle 随结果一起返回，而不是只在运行时传给两个 Agent：报告层允许引用 `path_*`，因此任何事后核对
> （评测打分、离线重放、人工复查"这条 fault_chain 依据哪条图路径"）都必须能拿到本次真正进入上下文的
> 路径集合。缺这个字段时，评测只能退回 `AgentState.retrieved_paths`，而生产路径从不填充该字段，于是
> "报告引用了图路径"这件事在实测里恒为 0——首次真实模型评测的 `fault_path_completeness` 就是这样被
> 结构性归零的，与模型表现无关。

拆开看这个 bug 链：报告可以引用 `path_*` ID（第 5 章的图路径）；这些路径来自 `GraphEvidenceBundle`，
运行时传给两个 Agent；但结果对象最初没有把 bundle 带出来。评测要算 `fault_path_completeness`（报告的
故障链覆盖了多少检索到的路径），只能去读 `AgentState.retrieved_paths`——一个生产代码路径从不写入的字段。
于是分母恒为空，指标恒为 0。

这个 bug 的危险性在于它**看起来像模型能力问题**。第一次真实模型评测报出 `fault_path_completeness=0`，
最自然的解读是"模型不会用图路径证据"，接下来可能去改 Prompt、加 few-shot、调图检索——全都在治一个不存在
的病。而实际原因是评测读错了字段。

这就是 CLAUDE.md 那条"评测数字的诚实性要求"和 `docs/live-golden-eval-results.md` 里那句"不能把
`root_cause_top1_hit_rate=0` 说成'模型找不到根因'"想防的东西。**一个为 0 的指标，第一步永远是确认
分母不为空。** 第 14 章会讲评测层怎么处理这类"指标本身不可信"的情况。

## 10.11 事务边界：`PostgresMemoryRuntime` 的写事务与读会话

`app/memory/runtime.py`（196 行）是记忆层唯一持有 session factory 的地方。Service 和 Registrar 都
只接收 session、不自己 commit，事务边界全部在这里。五个方法分成两类：写路径（`stage` / `decide` /
`delete`）用显式事务，读路径（`search` / `counts`）用短只读会话。

**写路径用 `begin()`（显式事务）：**

```python
async with self._session_factory.begin() as session:
    repository = PostgresCaseMemoryRepository(session)
    service = self._service(session, repository=repository)
    stage_result = await service.stage_from_report(result)
```

注释说明了为什么必须共享一个 begin：

> staging 会同时改主表、出现次数和 Evidence 关联，因此必须共享一个 begin 上下文；任何一步失败都由
> SQLAlchemy 回滚，避免产生"案例已增加但审计来源缺失"的状态。

advisory lock 也在这个事务里。PostgreSQL 的事务级 advisory lock 在提交或回滚时自动释放，所以
§10.8.1 那把锁不需要 try/finally——异常路径下的释放由事务边界保证。

**读路径用普通会话，不 commit：**

```python
async with self._session_factory() as session:
    service = self._service(session)
    return await service.search_confirmed(query, limit=selected_limit, mode=mode)
```

> 搜索只需要事务一致性快照，不需要显式 commit；短会话在上下文退出时归还连接，避免 FastAPI 并发请求
> 复用同一个非线程安全 AsyncSession。

后半句是实际会咬人的部分：`AsyncSession` 不是并发安全的。如果 runtime 持有一个长生命周期 session
给所有请求用，两个并发搜索会在同一个连接上交错发 SQL。每次调用开一个短会话，代价是从连接池取一次
连接。

### 10.11.1 合并到已 confirmed 案例时必须同事务重建图

`stage` 里那段容易被认为多余的分支：

```python
if (
    stage_result.memory is not None
    and stage_result.memory.status is MemoryStatus.CONFIRMED
):
    stored = await repository.get_stored(stage_result.memory.memory_id, for_update=True)
    if stored is None:
        raise LookupError(f"confirmed case memory disappeared: {...}")
    await self._graph_registrar(session).register_confirmed(stored)
```

注释解释得很清楚：

> 新候选默认 pending，不进入图；若重复报告合并到已 confirmed 的 canonical 案例，正文和 embedding
> 已变化，必须在同一事务立即重建节点/边，避免长期记忆与 GraphRAG 分叉。

推理链是这样的：staging 通常产出 pending 候选，pending 不进图，所以 staging 通常不该碰图。但
§10.8.4 说合并会**重新 embed** 且累积 symptoms——如果合并目标恰好是一条已 confirmed 的案例，那么
库里的向量和正文变了，而图节点里的向量和正文还是旧的。

§10.9.1 讲过图扩展的正确性依赖"同一个向量服务两条检索通道"。一旦分叉，`CaseMemoryMatch` 的四条双向
一致性校验（§10.6.4）会开始随机失败——而且是在下一次**检索**时失败，离真正的原因（上一次 staging）
已经隔了很远。所以必须在同一事务立即重建。

`for_update=True` 重读一次而不直接用 `stage_result.memory`，是因为 `CaseMemory` 是对外投影，**不带
embedding**（§10.4.1 的同一个决定）。图节点需要真实向量，只能从 `StoredCaseMemory` 拿。`decide` 里
同样的重读还有一条注释补充了另一层理由：

> set_status 已锁定并 flush 当前行；再次读取内部快照不会跨事务，且能保证图节点复用与最终持久化内容
> 完全相同的 embedding/provider/dimensions。

### 10.11.2 `decide` 与 `delete`：状态与图共享事务

`decide` 的两个分支——confirm 注册、reject 删除——都在状态更新的**同一个事务**里。注释点明了后果：

> 状态与图共享事务，任一图写入异常都会回滚状态。

如果分成两个事务，一次图写入失败会留下"状态 confirmed 但图里没节点"的记忆：它能被向量通道召回，但
永远不会作为图种子的邻居出现，也不会给别人当邻居。这种不一致没有任何报错，只表现为召回结果比预期差
一点。

`delete` 的顺序是先删图节点再删主记录，注释解释了为什么反过来不行的方向：

> 先锁定并读取 embedding 所在的持久化行，再调用图注册器清理节点，最后删除主记录；任一步失败都会
> 回滚，避免出现"数据库已删但图仍可召回"的分裂状态。

同一段注释还标了一个能力边界：**"该能力只用于用户明确请求的清理，不会被诊断流程自动调用。"** 这和
§10.2.4 是同一件事——`delete` 不在 `CaseMemoryWorkflow` 协议里，诊断图碰不到它。

## 10.12 本章的设计取舍

| 决定 | 放弃了什么 | 换到了什么 | 出处 |
| --- | --- | --- | --- |
| 顶层图零条件边 | 无法在顶层按 accepted/degraded 分流 | 资格规则只有一份（在 Service 里）；`memory_stage` 非空；`assert len(stage_calls) == 1` 可成立 | §10.2.1 |
| `recursion_limit=8` 硬编码 | 配置灵活性 | 路径可穷举（5 节点 5 边无分支），任何意外循环立即暴露 | §10.2.1 |
| `CaseMemoryWorkflow` 不含 `decide`/`delete` | 诊断流程无法自动确认或清理记忆 | 类型系统层面保证不会自动沉淀错误结论 | §10.2.4 / §10.7.5 |
| NOT_REQUESTED 提前 return | 少一条统一代码路径 | 省一次远程 embedding；"没查"与"查了没命中"可区分 | §10.3.1 |
| 排除 CASE_MEMORY 证据（三处） | 历史文本无法参与查询构造和相似判定 | 切断历史自证的反馈回路，避免悬空引用 | §10.3.3 / §10.7.4 |
| 检索失败直接向上传播 | 没有"友好降级" | 不产出可复现的假报告（"未找到相似案例"） | §10.3.4 |
| 三层 confirmed 门禁 | 三份重复校验代码 | 各覆盖不同失败模式；契约层是注入/恢复快照的唯一防线 | §10.4.2 |
| 匹配器是确定性规则 | 语义理解能力 | 可复现、可测试、零模型成本；不会自己编造相似点 | §10.5.2 |
| 保守双向子串判症状 | 会漏判语义相似的症状 | 不误判（中文常用字导致的假阳性）；漏判导向"需继续核对" | §10.5.3 |
| `differences` `min_length=1` | 不能表达"完全一致" | 强制写出保守兜底句，空列表不会被读成"等价" | §10.5.4 |
| edge ID 不进 `evidence_refs` | 无法直接引用图边作为证据 | citable ID 宇宙只有 4 类，报告引用校验可穷举 | §10.5.5 |
| 融合取 `max` 而非加权和 | 多通道命中不额外加分 | 可解释为"最强单一检索路径"；0.7+0.7 不会打败 0.9 | §10.6.3 |
| 五级排序键 | 排序代码变长 | 全序，`[:limit]` 不依赖 Python 排序稳定性和 PostgreSQL 行顺序 | §10.6.5 |
| 资格门禁在任何 I/O 之前 | 代码结构上门禁与主流程分离 | 降级报告不加锁、不查库、不调 Provider | §10.7.2 |
| 根因必须精确匹配假设 | 报告的润色措辞不能直接入库 | 只有被证据检验过的假设能沉淀；签名不分裂 | §10.7.3 |
| 精确签名先于向量判重 | 判重逻辑分两级 | 最常见的复现故障路径上零 Provider 调用 | §10.8.2 |
| advisory lock 锁组件集合 | 同组件 staging 串行 | 锁粒度与判重作用域精确对齐；跨组件并发不受影响 | §10.8.1 |
| 合并只增量、不改根因/状态 | 无法用新报告纠正旧根因 | 人工确认结果不会被自动流程推翻 | §10.8.4 |
| 图注册删干净再重建 | 每次多 ≤20 次删除 | 阈值或向量变化后不残留陈旧边 | §10.9.2 |
| `rowcount != 1` 检查 | 多一行断言 | 被所有权守卫拦下的写入不会静默"成功" | §10.9.4 |
| 边由外键级联删除 | 依赖建表时的约束 | 不会漏删反向边 | §10.9.6 |
| 合并到 confirmed 时同事务重建图 | staging 路径偶尔要碰图 | 长期记忆与 GraphRAG 不分叉 | §10.11.1 |
| `COMPLETED` 最后才写 | 无 | 排除"诊断完成、记忆状态未知"的结果 | §10.7.6 |

## 10.13 本章尚未解决的问题

**（一）图注册的邻居上限是 20，且没有告警。** `CASE_GRAPH_MAX_NEIGHBORS = 20` 在案例库小的时候
绰绰有余。但当同一类故障积累到几十条 confirmed 案例时，一个节点的真实相似邻居会超过 20，
`_find_similar_confirmed` 按相似度截断，被截掉的边**静默消失**。结果是图扩展在案例密集区域的召回
能力反而下降，而没有任何指标反映这件事。合理的做法是在截断发生时记一个 metric，目前没有。

**（二）`occurrence_count` 只能增不能减。** 合并会累加，但如果一条案例被误合并（两个不同故障的根因
文本恰好归一化后相同），除了人工 `delete` 重建，没有拆分机制。考虑到根因文本要**逐字**相同才会走精确
签名合并，误合并概率很低，但向量通道的 0.92 阈值合并是有可能误判的。

**（三）`similarity` 的语义没有校准。** §10.5.1 的匹配器文本明确写了"该分数不等于事实置信度"，这是
诚实的表述，但也意味着 `0.94` 和 `0.78` 之间的差距对使用者没有可操作含义。要让它有含义需要一批
人工标注的相似/不相似案例对，目前没有这个数据集，所以文档和 Prompt 都只能强调"不要把它当置信度"。

**（四）pending 候选没有过期或容量管理。** 一条永远没人 confirm 也没人 reject 的候选会一直留在库里。
它不影响召回（`WHERE status='confirmed'`），但会让 `MemoryCounts.pending` 持续增长，最终变成一个
没人看的待办堆。生产系统通常会给这类队列加 TTL 或提醒，目前没有。

**（五）合并后的重新 embed 没有失败重试。** `_merge_duplicate` 里的 embedding 调用失败会让整个
staging 事务回滚。对一次成功的诊断来说，这意味着"报告出了但记忆没记"，而 §10.7.6 的 status 守卫会把
它变成 `RuntimeError`，整个诊断结果被丢弃。更合理的行为是让 staging 失败降级为一个带失败原因的
`MemoryStageResult`，而不是废掉整份报告——但那需要新增一个 stage status 并同步修改 §10.10 第五组
校验，属于契约变更，本章范围内没有做。

## 10.14 小结

这一章走完了系统的最外层。三层嵌套 LangGraph 的顶层只做五件事，且刻意做得**没有分支**：召回历史、
跑 ReAct、解释匹配、出报告、暂存记忆。所有真正的决策都在下层——工具调用在第 8 章的有界循环里，
放行与否在第 9 章的四级审计阶梯里，而记忆的资格判断在 `CaseMemoryService` 里。

长期记忆这条链上有三个反复出现的原则值得记住：

- **实时证据永远优先于历史。** 历史只能作参考证据，冲突时报告要突出差异（§10.5）。
- **历史不能证明历史。** 查询构造、相似判定、证据引用三处都切断了自引用回路（§10.3.3 / §10.7.4）。
- **系统不会自己把结论沉淀成知识。** 审计通过只保证引用合法，不保证判断正确，所以新候选默认
  `pending`，`decide` 在类型上对诊断流程不可见（§10.7.5 / §10.2.4）。

**第 11 章转向持久化层**：`app/persistence/` 的表结构和仓储实现、`diagnosis_worker.py` 怎么用
`FOR UPDATE SKIP LOCKED` + 租约 heartbeat 领取 run、`session_checkpoints` 如何支撑 cancel/resume、
以及本章反复提到但没展开的那些 SQL（`search_confirmed` 的 pgvector 查询、
`merge_case_memory_matches` 的图 join）到底长什么样。
