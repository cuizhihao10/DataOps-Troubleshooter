# 第 2 章 配置与启动门禁：为什么这个服务宁可拒绝启动

## 2.1 你会验证什么

```bash
.venv/Scripts/python -m pytest -q tests/unit/test_settings.py tests/integration/test_health.py
```

本章的核心命题：**半配置的实例比完全没配置的实例更危险。** 你会看到 `app/core/settings.py` 和
`app/api/main.py` 的 lifespan 如何把这句话变成三十多条启动期校验。

## 2.2 `pydantic-settings` 的基本机制

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_prefix="DATAOPS_",
        extra="ignore",
    )
```

`BaseSettings` 会按"环境变量 → `.env` 文件 → 字段默认值"的优先级填充字段，前缀 `DATAOPS_` 意味着
`max_react_steps` 读的是 `DATAOPS_MAX_REACT_STEPS`。类型转换和范围校验都由 Pydantic 完成，所以业务代码
拿到的一定是合法值，不需要 `int(os.environ.get(...))` 这种到处散落的解析。

Java 读者可以对照 Spring Boot 的 `@ConfigurationProperties` + `@Validated`，区别在于 Pydantic 的校验
失败发生在**对象构造时**，也就是进程启动的最早期。

`extra="ignore"` 和第 1 章领域模型的 `extra="forbid"` 相反，这个不对称是刻意的：领域模型里出现未知
字段说明契约漂移，必须炸；而部署环境里有一堆别的 `DATAOPS_*` 之外的环境变量是正常的，容器平台会
注入大量自己的变量。

## 2.3 `SecretStr`：让凭据无法被意外打印

```python
    database_url: SecretStr | None = None
    chat_api_key: SecretStr | None = None
    embedding_api_key: SecretStr | None = None
    rerank_api_key: SecretStr | None = None
    api_auth_token: SecretStr | None = None
```

`SecretStr` 的 `__repr__` 和 `__str__` 返回 `**********`，取真值必须显式调用 `.get_secret_value()`。
这条防线针对的是最常见的泄漏路径：异常栈里格式化了一个对象、日志打了一整份配置、健康检查返回了
配置快照。

代码里唯一取值的地方是构造引擎：

```python
database_engine = create_database_engine(settings.database_url.get_secret_value())
```

一次调用、一个地方，审计成本极低。而如果 URL 是普通 `str`，你就得审计所有可能格式化它的路径。

对应地，`/health` 只公开 `endpoint_host`（主机名）而不是完整 URL：

```python
class PlannerConfiguration(BaseModel):
    status: Literal["disabled", "configured"]
    provider: str
    model: str
    endpoint_host: str
    timeout_seconds: float
    schema_repair_count: int
```

docstring 里那句"configured 表示本地配置可构造，不冒充远端连接已经探测成功"也很重要——健康检查
**不发送付费探测请求**，所以它只能承诺"配置合法"，不能承诺"模型可用"。诚实地缩小承诺范围，比给出
一个可能骗人的 `ok` 更有用。

## 2.4 每个预算旋钮背后都有一次实测事故

这是本章最值得慢读的部分。`Settings` 里的注释密度极高，因为每个默认值都是被实测逼出来的。

### 2.4.1 步数预算必须有余量

```python
    max_react_steps: int = Field(default=8, ge=1, le=20)
```

注释：

> 步数预算必须严格大于 Golden 集里最长的必需工具集（跨组件案例 required_tools 最多 6 个），否则
> 系统被设计成必然拿不到满覆盖：真实模型总要花一到两步试探，零余量下每次试探都直接换掉一个必需
> 取证。首次真实模型评测就撞上了这一点——跨组件案例执行满 6 步后以 react_budget_exhausted 结束，
> 却漏掉 bds.get_table_info。

这是一个典型的"看起来合理的配置其实设计上不可能达标"的例子。预算 = 需求量时，容错为零。

### 2.4.2 墙钟预算必须容得下重试

```python
    react_total_timeout_seconds: float = Field(default=240, gt=0, le=600)
```

从 60s 放宽到 240s 的理由链条：实测 Planner 单次 8–18s → 8 步最坏要四次决策 → 加上工具与检索时间 →
60s 会把"预算够但时间不够"伪装成正常终止。

而且它和重试预算是耦合的，所以有一条专门的联合校验：

```python
    def _validate_transient_retry(self) -> None:
        policy = self.transient_retry_policy()
        worst_case = self.chat_timeout_seconds + policy.worst_case_added_seconds(
            self.chat_timeout_seconds
        )
        if self.react_total_timeout_seconds < worst_case:
            raise ValueError(
                "react_total_timeout_seconds must cover one planner call plus its transient retries"
            )
```

docstring 一句话说穿了这条校验的价值：

> 只加重试而不留预算是自欺欺人：Planner 跑在 `react_total_timeout_seconds` 内，若预算连"一次跑满
> 超时的首次尝试 + 全部重试与退避"都装不下，一个本可恢复的 429 会被外层 `asyncio.timeout` 截断成
> total_timeout，指标上看不出重试曾经生效。

**两个独立正确的配置组合起来可以是错的**，这类跨字段约束是配置校验最有价值的部分。注意它用 Planner
超时而不是 Auditor 超时，因为 Auditor 不在这个预算内——见下一条。

### 2.4.3 Auditor 需要独立超时：一次审计路径整条失效的事故

```python
    chat_timeout_seconds: float = Field(default=30, gt=0, le=300)
    auditor_timeout_seconds: float = Field(default=90, gt=0, le=300)
```

注释记录的事故非常完整：

> 首次真实模型评测里两个角色的延迟分布差一个量级（Planner 实测 8–15s，Auditor 实测 22–30s，因为它
> 要读完整草稿并逐条判定引用，输出也接近 1100 token）。共用 30s 的后果被实测抓到：四次 Auditor 调用
> 有三次超时，而超时按 AuditorAgentError 直接降级且不消耗返工预算，于是三个案例的
> accepted_report_rate 全是 0——审计路径整条失效。

这段话串起了三个子系统：配置（一个超时旋钮）、审计阶梯（`AuditorAgentError` → 直接降级）、评测
（接受率归零）。一个共享超时值让整条审计链路静默失效，而指标上看起来像是"模型质量差"。

分成两个旋钮之后还有一条推理：Planner 必须保持紧超时（它在 ReAct 预算内，一次挂死吃掉整轮），
Auditor 可以放宽（不在该预算内，放宽不会拖长循环）。**同一个参数在不同位置有不同的最优值，说明它
本来就该是两个参数。**

### 2.4.4 重试预算与 Schema 修复预算故意分开

```python
    planner_schema_repair_count: int = Field(default=1, ge=0, le=1)
    auditor_schema_repair_count: int = Field(default=1, ge=0, le=1)
    chat_transient_retry_attempts: int = Field(default=2, ge=1, le=3)
    chat_transient_retry_backoff_seconds: float = Field(default=1.0, gt=0, le=30)
    chat_transient_retry_max_backoff_seconds: float = Field(default=8.0, gt=0, le=60)
```

注释：

> 修复预算处理"模型输出格式不对"，重试预算处理"请求根本没打到模型"。第二次真实模型评测实测到必须
> 有它——新端点在约 92s 内成功 6 次调用后连续 4 次返回 HTTP 错误（每次 250–630ms 即被驳回），两个
> 案例因此以 planner_provider_error 终结。

"每次 250–630ms 即被驳回"是判断依据：成功调用要 8–23s，失败调用只要 0.3s，**响应时间差两个数量级
说明请求根本没到模型**。这是一种非常实用的运维判断法。

默认只重试一次的理由也是实测的：那种配额窗口打满的形态重试更多次也救不回来，只会把单次决策的最坏
耗时推出墙钟预算。

### 2.4.5 并行度是延迟旋钮，不是预算旋钮

```python
    max_parallel_tool_actions: int = Field(default=3, ge=1, le=MAX_PARALLEL_TOOL_ACTIONS)
```

注释里有一句必须记住的话：

> 并行只把"状态 + 日志 + 拓扑"这类互不依赖的取证压进同一段等待时间，一批 N 个 Action 仍然消耗 N 个
> 步数。因此调大这个值只会降低 P95 延迟，不会让模型获得更多取证机会。

这直接回答了一个常见误解："加了并行是不是等于放宽了预算？"不是。这个设计选择让并行成为一个**纯
性能优化**，不影响任何质量指标的可比性——Run D 和 Run G 的并行度不同但步数预算相同，所以覆盖率
仍然可比。

上限用的是第 1 章那个领域常量 `MAX_PARALLEL_TOOL_ACTIONS`，而不是又写一个 3。配置的上界和契约的
上界是同一个数字，这就是"唯一定义"手法。

还有一条联合校验：

```python
        if self.max_parallel_tool_actions > self.max_react_steps:
            raise ValueError("max_parallel_tool_actions must not exceed max_react_steps")
```

注释：宁可启动失败也不要留下"看起来配了 3 实际只能 1"的误导性配置。

### 2.4.6 Worker 心跳必须短于租约的一半

```python
        if self.diagnosis_worker_heartbeat_seconds >= self.diagnosis_worker_lease_seconds / 2:
            raise ValueError(
                "diagnosis_worker_heartbeat_seconds must be less than half the worker lease"
            )
```

这是分布式租约的经典约束：如果心跳周期 ≥ 租约的一半，那么**丢一次心跳就会掉租约**，正在执行的 run
会被另一个 Worker 抢走并重复执行。除以 2 是最低限度的容错余量（允许丢一次）。第 11 章会看到租约
机制的实现。

### 2.4.7 推流三个时间必须有序

```python
    def _validate_run_stream(self) -> None:
        if self.run_stream_poll_seconds >= self.run_stream_keepalive_seconds:
            raise ValueError("run_stream_poll_seconds must be shorter than the keepalive period")
        if self.run_stream_keepalive_seconds >= self.run_stream_max_seconds:
            raise ValueError("run_stream_keepalive_seconds must be shorter than the max lifetime")
        if self.run_stream_max_seconds <= self.react_total_timeout_seconds:
            raise ValueError("run_stream_max_seconds must exceed react_total_timeout_seconds")
```

前两条是内部有序性（轮询 < 心跳 < 寿命），第三条是**跨子系统**约束：推流寿命必须超过 ReAct 总超时，
否则一个完全正常、只是跑满预算的 run 会在结束前被推流截断，演示者看到的是"流断了"而不是"诊断完成"。

## 2.5 安全配置的双向校验

```python
    def _validate_api_security(self) -> None:
        if self.api_auth_mode == "bearer" and self.api_auth_token is None:
            raise ValueError("api_auth_token is required when api_auth_mode is bearer")
        if self.api_auth_mode == "disabled" and self.api_auth_token is not None:
            raise ValueError("api_auth_token must be unset when api_auth_mode is disabled")
```

两个方向都拦，理由不对称：

- `bearer` 缺令牌 → 每个请求都 401 → 服务等于不可用（可用性问题，会被立刻发现）。
- `disabled` 却配了令牌 → 部署者以为接口受保护、把端口暴露出去（**安全问题，不会被发现**）。

第二条才是这条校验存在的真正理由。字段注释直接写着："配了令牌却没启用"比"完全没配"更危险。

同样的双向思路出现在检索 Provider 校验里：

```python
    def _validate_retrieval_providers(self) -> None:
        remote_embedding = self.embedding_provider != DETERMINISTIC_HASH_PROVIDER_ID
        if self.embedding_base_url.username or self.embedding_base_url.password:
            raise ValueError("embedding_base_url must not include user information")
        if remote_embedding and self.embedding_api_key is None:
            raise ValueError("embedding_api_key is required for remote embedding providers")
        # bge-m3 固定 1024 维；配置漂移只有在此处硬校验才能避免整库写入错误维度后再回滚。
        if self.embedding_provider == BGE_M3_PROVIDER_ID:
            if self.embedding_dimensions != BGE_M3_DIMENSIONS:
                raise ValueError(f"{BGE_M3_PROVIDER_ID} requires {BGE_M3_DIMENSIONS} dimensions")
```

三条各针对一种真实后患：

1. **URL 里禁止内嵌凭据**（`https://user:pass@host/v1`）。这种 URL 会出现在异常消息、trace 属性和
   日志里，而 `SecretStr` 保护不到它——凭据藏在一个非 secret 字段里。
2. **远程 Provider 缺 key 要在启动时失败**，否则检索会在首次查询时才失败并返回空结果，而那时部署者
   已经以为语义检索生效了。空结果是最坏的失败模式：它看起来像"没有相关知识"。
3. **维度必须匹配模型**。bge-m3 固定 1024 维，配错维度会把整库向量写进另一个空间，发现时只能重写全库。

## 2.6 权重不做隐式归一化

```python
    def hybrid_scoring_weights(self) -> HybridScoringWeights:
        return HybridScoringWeights(
            semantic=self.retrieval_semantic_weight,
            lexical=self.retrieval_lexical_weight,
            path=self.retrieval_path_weight,
            reliability=self.retrieval_reliability_weight,
            freshness=self.retrieval_freshness_weight,
        )
```

docstring：**若权重和不为一，本方法抛出 ValidationError 而不进行隐式归一化。**

隐式归一化很"友好"，但会掩盖配置错误：你以为自己把语义权重从 0.45 调到 0.9，实际上归一化后所有
权重都被缩放了，排序变化和你的预期不一致，而且没有任何提示。宁可失败。

`document_scoring_weights()` 的 docstring 还解释了为什么文档通道只有三因子：

> 文档通道不使用 path/freshness：切片之间没有关系边，静态文档也没有可信的时效性，硬凑五因子只会让
> 公式看起来复杂而不更准确。

这是很好的克制。很多项目会为了"统一"强行让两条通道用同一个公式，结果是两个恒为常量的因子。

注意这三个方法在 `validate_runtime_configuration` 里被**调用但不使用返回值**：

```python
        self.hybrid_scoring_weights()
        self.evidence_bundle_budget()
        self.document_scoring_weights()
```

这是故意的：调用它们是为了触发内部的 Pydantic 校验，让权重和不为一这类错误在启动时就暴露，而不是
等到第一次检索。

## 2.7 `get_settings` 为什么要缓存

```python
@lru_cache
def get_settings() -> Settings:
    return Settings()
```

docstring 给了两个理由，第二个更重要：

> 缓存可避免每个请求重复 I/O，也防止运行中环境变量变化造成同一诊断使用不同预算。

一次诊断跨多个节点、多次异步调用。如果每个节点自己读环境变量，理论上可以出现"第 3 步用 8 步预算、
第 5 步用 6 步预算"的诡异状态。缓存把配置变成进程级不变量。

测试需要切换配置时必须 `get_settings.cache_clear()` 后重建，而不是修改已有对象——修改已有对象会
绕过 `model_validator`，得到一个从未通过校验的配置。

## 2.8 lifespan：开放端口前的完整审计

`app/api/main.py` 的 `lifespan` 是一个异步上下文管理器，`yield` 之前是启动、之后是停机：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = get_settings()

    # 先验证完全本地且成本最低的资产，让路径或 Schema 错误在启动早期给出清晰反馈。
    fixture_registry = FixtureRegistry.from_directory(settings.fixture_directory)
    golden_cases = load_golden_cases(settings.golden_case_file)
    scenario_ids = set(fixture_registry.scenario_ids)
    missing_scenarios = sorted({case.scenario_id for case in golden_cases} - scenario_ids)
    if missing_scenarios:
        raise ValueError(f"golden cases reference unknown scenarios: {missing_scenarios}")
```

**检查顺序按成本递增**：本地文件 → 契约 ID 字符串比较 → Provider 工厂构造 → MCP 子进程握手 →
数据库连接 → 模型 runtime。路径写错这种最常见的错误在第一步就报出来，不用等三十秒的连接超时。

### 2.8.1 一条防止"假指标"的校验

```python
    # 根因锚点必须真的是知识图里的 root_cause 节点：锚点一旦拼错就永远不可能被任何报告引用命中，
    # 于是 `root_cause_anchor_hit_rate` 会静默退化成恒为 0 的假指标——那正是这条契约要修掉的毛病。
    root_cause_node_ids = {
        node.node_id
        for node in load_knowledge_seed(settings.knowledge_seed_file).nodes
        if node.node_type is KnowledgeNodeType.ROOT_CAUSE
    }
    unknown_anchors = sorted(
        {
            anchor
            for case in golden_cases
            for anchor in case.allowed_root_cause_anchors
            if anchor not in root_cause_node_ids
        }
    )
    if unknown_anchors:
        raise ValueError(f"golden cases reference unknown root cause anchors: {unknown_anchors}")
```

这条校验保护的是**评测指标本身的有效性**。锚点命中率的判定是"报告引用的 `kn_root_cause_*` 是否命中
案例声明的锚点"。如果案例声明了一个不存在的锚点，判定永远为假，指标恒为 0，而你会以为模型定位
能力差。第 14 章会详细讲这个指标为什么要和 `root_cause_top1_hit_rate` 并列发布。

### 2.8.2 十九条契约 ID 逐项比对

```python
    if settings.planner_prompt_id != PLANNER_PROMPT_ID:
        raise ValueError("configured planner prompt ID does not match the packaged prompt")
    if not load_planner_prompt().strip():
        raise ValueError("planner prompt must not be empty")
    if settings.planner_provider_contract_id != PLANNER_PROVIDER_CONTRACT_ID:
        raise ValueError("configured Planner provider contract ID does not match the package")
    ...
    if settings.run_stream_contract_id != RUN_STREAM_CONTRACT_ID:
        raise ValueError("configured run stream contract ID does not match the package")
```

模式是统一的：**Settings 里有一份期望值，模块里有一份常量，lifespan 逐项比对。** 加上第三处（文档）
和第四处（`tests/unit/test_documentation_policy.py` 的字面量断言），升一个版本要同时改四个地方。

看起来繁琐，但它解决的是一个真实问题：**评测报告里记录的 Prompt 版本必须真的是执行时用的版本。**
如果 Settings 写 `planner-react:v8` 而包里的 Prompt 实际是 v7，你的所有实测数字都标错了版本，
无法复现，也无法对比。注释写得很直接：Prompt 文本和 ID 必须成对校验，否则评测记录的版本无法代表
实际执行内容。

`load_planner_prompt().strip()` 那条空检查是补充：ID 对了但文件是空的，同样会让"v8 的成绩"变成
假数据。

### 2.8.3 安全守卫排在最前面

```python
    # 守卫在任何 Provider、MCP 子进程和数据库连接之前构造：弱令牌或非法配额必须让进程拒绝开放
    # 端口，而不是等第一个请求到达时才发现"鉴权其实没生效"。
    api_security = ApiSecurityGuard(
        mode=settings.api_auth_mode,
        token=settings.api_auth_token,
        max_requests=settings.api_rate_limit_requests,
        window_seconds=settings.api_rate_limit_window_seconds,
    )
```

`Settings._validate_api_security` 只查"模式与令牌是否配套"，令牌强度、字符集和限流器参数由
`ApiSecurityGuard` 校验。为什么分两处？`Settings` 的 docstring 解释了：守卫持有唯一的策略常量，
避免最小长度被写成两份而漂移。**校验规则应该住在拥有该规则的对象里**，配置层只做它能判断的部分。

### 2.8.4 MCP 工具发现必须走真协议

```python
    # 工具发现必须跨真实 stdio MCP 握手；直接比较本地枚举会掩盖服务进程注册失败。
    mcp_client = StdioMcpClient(timeout_seconds=settings.tool_timeout_seconds)
    mcp_tools_available = await mcp_client.list_tools()
    required_mcp_tools = {tool.value for tool in ToolName}
    missing_mcp_tools = sorted(required_mcp_tools - set(mcp_tools_available))
    if missing_mcp_tools:
        raise ValueError(f"required MCP tools are unavailable: {missing_mcp_tools}")
```

这段代码真的启动了一个子进程、真的做了 MCP 握手、真的调用了 `tools/list`。断言的是"服务端注册的
工具集合 ⊇ 本地枚举"。

如果只写 `assert set(ToolName) == set(ToolName)`（比较本地枚举和自己），那什么都没验证。这里的
关键是**两个独立来源**：本地的 `ToolName` 枚举 vs 服务进程实际注册的工具。第 3 章会看到服务端如何
注册它们。

### 2.8.5 向量空间的"全有或全无"

```python
                knowledge_nodes_embedded = await repository.count_embedded_nodes(
                    provider_id=embedding_provider.provider_id,
                    dimensions=embedding_provider.dimensions,
                )
                if knowledge_nodes_embedded != knowledge_nodes_loaded:
                    raise ValueError(
                        "all knowledge nodes must be embedded in the configured provider space"
                    )
```

计数是**带 provider_id 和维度条件的**，所以这条校验实际在说："当前配置的向量空间里，每个知识节点都
必须有向量。"如果你把 embedding provider 从 `deterministic-hash:v1` 切到 `bge-m3:v1` 而没有重新
生成向量，节点数会对不上，服务拒绝启动。

文档切片有同样的校验，注释解释了为什么不能容忍部分缺失：

> 与知识节点同样是全有或全无：部分切片缺向量时语义通道只会少召回而不报错，那种"看起来正常但永远
> 查不到某份 Runbook"的状态在演示中几乎不可能被发现。

这也解释了 CLAUDE.md 里那条运维提示：跑完 `-m postgres` 集成测试后必须重新 `python -m
app.persistence.seed`，因为集成测试会把节点向量重写成确定性 hash 向量。**它不是缺陷，是这条校验
在起作用。**

## 2.9 三者齐备才发布 runtime，否则明确 503

```python
        if (
            session_factory is not None
            and memory_runtime is not None
            and planner_runtime is not None
            and auditor_runtime is not None
        ):
            # 资源 runtime 只在数据库和两个模型角色都可构造时发布；构造本身不发送模型请求。
            retriever = PostgresGraphContextRetriever(...)
            diagnosis_workflow = AuditedDiagnosisWorkflow(...)
            diagnosis_runtime = DiagnosisApplicationRuntime(...)
            diagnosis_worker = DiagnosisRunWorker(...)
```

这是整个 lifespan 最重要的一个设计决定：**依赖不全时不静默降级，而是让 `diagnosis_runtime` 保持
`None`，API 明确返回 503。**

常见的反面做法是"模型不可用就退化成规则引擎"。那样的系统在演示时看起来永远正常，但你无法区分
"这份报告是双 Agent 产出的"还是"这份报告是兜底规则拼的"。对一个以"证据驱动"为卖点的系统，这种
含糊是致命的。

同时注意这里的组装是**依赖注入**：`AuditedDiagnosisWorkflow` 收到的是已构造好的 `BoundedReactLoop`
和 `AuditedReportWorkflow`，而后者又收到 `planner_runtime.agent` / `auditor_runtime.agent` 和配置对象。
三层嵌套 LangGraph 的组装全在这一处完成，没有任何一层自己 `get_settings()`。这让每一层都可以在单测
里用替身注入——第 8、9 章的测试就是这么写的。

## 2.10 发布顺序与停机顺序

```python
        # 只有全部检查完成后才发布共享状态，避免路由观察到半初始化的依赖集合。
        app.state.settings = settings
        app.state.api_security = api_security
        ...
        if diagnosis_worker is not None:
            # Worker 在所有 app.state 依赖发布后再启动，避免后台 task 观察到半初始化的 runtime。
            diagnosis_worker.start()
        yield
    finally:
        # 先按角色关闭模型 HTTP 池，再释放数据库池；均不吞异常，避免测试重启后遗留资源。
        if diagnosis_worker is not None:
            # 先停止领取新任务；未完成 run 的 lease 会自然过期并由新 Worker 接管。
            await diagnosis_worker.stop()
        if auditor_runtime is not None:
            await auditor_runtime.aclose()
        if planner_runtime is not None:
            ...
```

三条顺序纪律：

1. **`app.state` 一次性发布**。如果边检查边发布，某个路由可能在启动中途读到 `memory_runtime` 已设置
   但 `diagnosis_runtime` 未设置的状态。
2. **Worker 最后启动**。它是后台 task，会立刻开始领取任务；早启动一行就可能读到半初始化的 runtime。
3. **停机反序**：先停 Worker（不再领新活）→ 关模型 HTTP 池 → 关数据库池。反过来会让正在执行的 run
   在数据库连接已关闭时试图写结果。

`finally` 里的注释"均不吞异常"也值得注意：关闭失败要报出来，否则测试反复重启进程时会积累泄漏的
连接和子进程，表现为莫名的超时。

Worker 停止时"未完成 run 的 lease 会自然过期并由新 Worker 接管"——这是租约机制带来的好处：优雅停机
不需要等待正在执行的 run 完成。

## 2.11 本章小结

启动门禁的设计原则可以概括成四句话：

| 原则 | 例子 |
|---|---|
| 半配置比未配置更危险 | `disabled` + 令牌 → 拒绝启动 |
| 校验顺序按成本递增 | 本地文件 → 契约字符串 → 子进程 → 数据库 |
| 跨字段约束才是重点 | 重试预算 vs 墙钟预算；心跳 vs 租约 |
| 不静默降级 | 依赖不全 → runtime 为 None → 明确 503 |

另外记住"唯一定义 + 多处比对"这个手法：契约 ID 在 Settings、模块常量、lifespan、文档、测试五处
出现，但只有一处是定义，其余四处都是比对。这让"改了实现忘了改文档"变成一个会失败的测试，而不是
一个未来某天被发现的不一致。
