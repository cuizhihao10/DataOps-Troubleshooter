# 第 11 章 持久化、任务队列与会话检查点

前面十章的所有编排都活在一个进程里。本章要回答的是那个更朴素的问题：**进程重启之后呢？**

这个项目的答案很激进：**PostgreSQL 是唯一状态服务**。队列在里面、租约在里面、向量在里面、图在里面、
调用链 span 在里面、会话检查点也在里面。没有 Redis、没有 Celery、没有 Neo4j、没有独立向量库。

选一个数据库承担全部状态不是偷懒，它是一个有代价也有收益的决定：

- **收益**：任何两件事只要需要"要么都发生、要么都不发生"，就能放进同一个事务。第 10 章那些"状态改了
  但图没改"的分裂状态，在这个架构下是可以用一行 `async with begin()` 排除的。
- **代价**：所有并发正确性都压在 SQL 上。行锁、`SKIP LOCKED`、部分唯一索引、advisory lock、
  CheckConstraint——本章大半篇幅都在讲这些机制各自挡住了什么。

## 11.2 一张表就是一份契约

`app/persistence/models.py` 里九张表的共同特点是：**数据库约束几乎完整重复了 Pydantic 契约**。
`case_memories` 的 status 枚举在 `MemoryStatus` 里有一份，在 `CheckConstraint` 里又有一份；
`agent_runs` 的状态载荷规则在 `AgentRunSnapshot.validate_run_state` 里有一份，在
`ck_agent_runs_terminal_payload` 里又有一份。

这看起来是重复劳动，但两者防的不是同一件事。Pydantic 挡的是**应用代码写错**；数据库约束挡的是
**绕过应用代码的写入**——手工 psql、临时脚本、迁移里的 UPDATE、以及未来某个新加的仓储方法。模块
docstring 把这句话说得很直接：

> 表级约束重复验证领域枚举、向量空间、状态和计数，形成数据库最后一道防线。

### 11.2.1 `eager_defaults=True` 是异步栈的正确性开关

`Base` 的 docstring 有一段比表结构本身更值得读的内容：

```python
class Base(DeclarativeBase):
    __mapper_args__ = {"eager_defaults": True}
```

> `eager_defaults=True` 是异步栈的正确性要求而不是性能开关：带 `server_default` / `onupdate` 的列在
> flush 之后会被标记为过期，下一次读取会触发一次隐式 SELECT。同步代码里这只是多一次查询，但在
> asyncio 下属性读取无法 await，SQLAlchemy 只能抛 `MissingGreenlet`，于是"先写后读同一行"的仓储方法
> （例如领取 run 后立刻把 ORM 行转成公开快照）会在真实 PostgreSQL 上直接崩。

这个坑值得完整理解，因为它是异步 ORM 最典型的陷阱之一：

1. `created_at` 有 `server_default=func.now()`。SQLAlchemy 不知道数据库会填什么值，所以 INSERT 之后
   把这个属性标记为 expired。
2. `claim_next_run` 领取一行后立刻调 `_run_from_record(record)`，其中要读 `record.created_at`。
3. 同步栈下，读一个 expired 属性会自动发一条 `SELECT` 去刷新——慢一点，但能跑。
4. 异步栈下，属性访问是**同步的 Python 语法**（`record.created_at`），没有 `await` 可以插进去。
   SQLAlchemy 检测到需要 I/O 但不在 greenlet 上下文里，只能抛 `MissingGreenlet`。

关键在于**这个 bug 在测试替身上完全不会出现**。用内存 fake repository 的单元测试全绿，只有连真
PostgreSQL 才炸。开启 `eager_defaults` 后，PostgreSQL 用 `RETURNING` 在同一条 INSERT 里把生成值带回来，
属性永不过期，也不多一次往返。

### 11.2.2 为什么所有 `updated_at` 都刻意不用 `onupdate`

同一段 docstring 的后半部分：

> 与之配套，所有 `updated_at` 只保留 `server_default` 而**不使用** `onupdate=func.now()`：写入方全部
> 显式传入注入的 `now`，而 `onupdate` 只在该列没有净变化时才触发，届时数据库事务时钟会悄悄覆盖应用
> 时间戳。这既让"租约必须晚于本次更新"这类跨字段校验随机失败，也让 checkpoint 的 `updated_at`
> 一致性比对无法复现。审计时间戳的真相应由注入时钟决定，不由数据库时钟决定。

`onupdate=func.now()` 是 SQLAlchemy 里几乎所有人都会顺手加的东西。这里不加，是因为系统有两处逻辑
依赖 `updated_at` 的**精确值**：

- `ClaimedDiagnosisRun.validate_claim` 要求 `lease_expires_at > run.updated_at`。如果 `updated_at`
  被数据库时钟覆盖成一个比应用时钟稍晚的值，而 `lease_expires_at` 是应用算的
  `now + lease_seconds`，那么在时钟偏差接近租约长度时这个校验会**随机失败**。
- `_checkpoint_from_record` 逐字段比对 JSONB 快照与关系列，包括 `updated_at`（§11.6.7）。JSONB 里的值
  是应用写的，列上的值如果被 `onupdate` 改了，两者永远对不上。

所以整个仓储层的写法是统一的：**每个写方法都接一个 `now: datetime` 参数**，由调用方（Worker、
runtime、测试）注入。测试因此可以用一个合成的单调时钟验证租约过期接管，而不需要 `sleep` 或改系统
时钟——`_utc_now` 被包装成有名字的 callable 正是为此。

### 11.2.3 `ck_agent_runs_terminal_payload`：把状态机写进 SQL

这是全项目最长的一条约束。它列举了五个状态各自允许的完整字段组合：

```sql
(status = 'queued' AND result IS NULL AND error_code IS NULL
  AND error_message IS NULL AND started_at IS NULL AND completed_at IS NULL
  AND attempt_count = 0 AND lease_owner IS NULL AND lease_expires_at IS NULL) OR
(status = 'running' AND result IS NULL AND ... AND started_at IS NOT NULL
  AND attempt_count >= 1 AND lease_owner IS NOT NULL AND lease_expires_at IS NOT NULL) OR
(status = 'completed' AND result IS NOT NULL AND error_code IS NULL ... ) OR
(status = 'failed' AND result IS NULL AND error_code IS NOT NULL ... ) OR
(status = 'cancelled' AND result IS NULL AND error_code IS NOT NULL
  AND ((started_at IS NULL AND attempt_count = 0) OR
       (started_at IS NOT NULL AND attempt_count >= 1)))
```

每一行都对应 `AgentRunSnapshot.validate_run_state` 里的一段 Python。值得注意的是它**不是**在检查
"字段合法"，而是在检查"状态与字段的组合合法"。单看 `result IS NULL` 没有意义，
`status='completed' AND result IS NULL` 才是错误。

这条约束排除的具体故障是：**一个既声称完成又没有结果的 run**。API 的 `GET /runs/{id}` 会把
`status=completed` 的行反序列化成 `DiagnosisRunResult`，如果 result 是 NULL，那就是一个 `None` 被
当成结果返回给前端。有了约束，这一行根本写不进去；写入方在 flush 时就会拿到
`IntegrityError`，而不是让前端渲染出一个空报告。

`cancelled` 那一支是唯一有内部分支的：取消可以发生在 queued（没 started_at、attempt_count=0）也可以
发生在 running（有 started_at、attempt_count≥1）。这正是 §11.7.2 要展开的地方。

### 11.2.4 部分唯一索引：同 session 活跃 run 唯一

```python
Index(
    "uq_agent_runs_active_session",
    "session_id",
    unique=True,
    postgresql_where=sa.text("status IN ('queued','running')"),
),
```

一个 session 在任意时刻最多有一个未终结的 run。这条规则在 `create_run` 里有一份 Python 检查
（查 active、抛 `ActiveRunConflictError`），但**Python 检查挡不住并发**：两个请求同时查、都没查到、
都插入。

部分唯一索引（partial unique index）把这条规则变成数据库事实。它只对 `status IN ('queued','running')`
的行生效，所以同一个 session 可以有几十条 completed/failed/cancelled 历史 run，但只能有一条活跃的。

`create_run` 里那句 `with_for_update()` 锁 session 行是第二层保护，注释说明了它的另一个作用：

> 锁定 session 可把"刷新最后问题摘要"和"创建 run"绑定为同一活动更新，避免并发消息互相覆盖。

为什么要串行化一个 session？注释在 `ActiveRunConflictError` 里给了答案：

> 单 session 串行化保护 checkpoint 的单调版本和追问顺序。

checkpoint 的版本必须**恰好加一**（§11.6.6）。如果两个 run 并发跑完，两个都想写 version 2，一个会
失败——但那时它已经调完模型、跑完工具，成本已经付了。在入队时就拒绝，成本是一次 409。

### 11.2.5 `remediation_risk_level` 的条件性非空

第 5 章讲过处置动作要声明风险等级。数据库这边的表达方式值得学：

```sql
(node_type IN ('solution','sop') AND remediation_risk_level IN ('low','medium','high')) OR
(node_type NOT IN ('solution','sop') AND remediation_risk_level IS NULL)
```

配套注释：

> 只有 solution/sop 行允许非空：CheckConstraint 让"方案缺风险声明"和"事实节点夹带风险"两种污染都
> 无法进入表，即使有人绕过 Pydantic 直接写库。

一个 `nullable=True` 的列通常意味着"可以没有"。这条约束把它变成"在特定行上必须有，在其他行上必须
没有"。第二个方向同样重要：一个 `component` 类型的节点带着 `risk_level='high'`，会让报告层的风险
汇总把一个组件事实当成处置建议。

## 11.3 队列：用一张表和一条 SQL 做任务分发

POST 一条消息返回 `202 queued`，不等诊断跑完。这是必须的：一次真实模型诊断实测 58–125 秒
（`docs/live-golden-eval-results.md`），任何 HTTP 客户端都会先超时。

生产系统通常上 Celery + Redis 或 SQS。这里用一张 `agent_runs` 表加一条 SQL：

```python
eligible = or_(
    AgentRunRecord.status == AgentRunStatus.QUEUED.value,
    and_(
        AgentRunRecord.status == AgentRunStatus.RUNNING.value,
        AgentRunRecord.lease_expires_at.is_not(None),
        AgentRunRecord.lease_expires_at <= now,
        AgentRunRecord.attempt_count < max_attempts,
    ),
)
record = await self._session.scalar(
    select(AgentRunRecord)
    .where(eligible)
    .order_by(AgentRunRecord.created_at, AgentRunRecord.run_id)
    .with_for_update(skip_locked=True)
)
```

### 11.3.1 `FOR UPDATE SKIP LOCKED` 到底做了什么

`SELECT ... FOR UPDATE` 给选中的行加排他行锁，直到事务结束。加上 `SKIP LOCKED` 后，语义变成：
**跳过所有已被其他事务锁住的行，返回第一行没被锁的**。

这一个修饰符就把"多消费者竞争同一个队列"解决了。三个 Worker 同时执行这条 SQL：

- Worker A 锁住最早的 run，其他两个看不到它；
- Worker B 拿到第二早的；
- Worker C 拿到第三早的。

没有 `SKIP LOCKED` 会怎样？B 和 C 会**阻塞等待** A 的事务提交，然后发现那行已经是 running 了，再重新
查。这不只是慢——在高并发下会形成一个惊群，所有 Worker 排队等同一行。

这也是为什么不需要 Redis：`SKIP LOCKED` 是 PostgreSQL 9.5 起的原生能力，而这个项目的规模（单机演示、
最多几个 API 副本）离需要专用队列中间件的量级还很远。用数据库队列换来的是**事务性**：入队和更新
session 摘要在同一事务，终态和事件在同一事务——这是外部队列做不到的。

排序键是 `(created_at, run_id)` 而不是只有 `created_at`。同一毫秒创建的两条 run 需要一个确定性的
次级键，否则领取顺序取决于 PostgreSQL 的物理行顺序。这跟第 10 章 §10.6.5 的五级排序键是同一个考虑。

### 11.3.2 领取事务与执行严格分离

`run_once` 的结构值得逐行读：

```python
now = self._now_factory()
async with self._session_factory.begin() as session:
    repository = PostgresDiagnosisRunRepository(session)
    await repository.fail_exhausted_runs(now=now, max_attempts=self._max_attempts)
    claim = await repository.claim_next_run(...)
if claim is None:
    return False
await self._execute_with_heartbeat(claim)
return True
```

注意 `async with` 在 `_execute_with_heartbeat` **之前**就结束了。领取事务只做三件事：清理耗尽的 run、
选一行、改状态和租约。然后提交、释放行锁。真正的诊断（GraphRAG 检索、LangGraph、MCP 子进程、模型
调用）全在事务外。

如果反过来——把整个执行包在领取事务里——会同时踩三个坑：

1. **一个数据库连接被占用 2 分钟**。连接池很快耗尽，API 的读请求开始等待。
2. **行锁持有 2 分钟**。任何想 `FOR UPDATE` 这一行的操作（比如用户点取消）全部阻塞。
3. **PostgreSQL 的 idle-in-transaction 超时会杀掉连接**，诊断结果在提交前丢失。

`claim_next_run` 的 docstring 把这条边界写成了规则：

> 领取事务只更新状态、attempt_count 和短租约，随后立即提交并释放行锁；真正 GraphRAG/模型/MCP 执行
> 发生在事务外。

### 11.3.3 过期的 running 也可以被领取

`eligible` 的第二支允许领取一个状态已经是 `running` 的 run，条件是租约过期且尝试次数没用完。这是
**崩溃恢复**：

Worker 进程被 `docker stop` 杀掉、容器 OOM、机器重启——这些情况下那条 run 停在 `running`，
`lease_owner` 还指着一个已经不存在的 Worker。没有这一支，它会永远卡在 running：
`uq_agent_runs_active_session` 会让这个 session 再也无法提交新消息（409），而用户完全不知道为什么。

`attempt_count < max_attempts`（默认 2）限制了重试次数。为什么要限制？因为**导致崩溃的原因可能是这个
run 本身**。一个能让 Worker 进程死掉的输入（极端长的用户文本、某个触发无限递归的边界情况）会被无限
接管、无限崩溃，把整个队列变成一个死循环。两次机会：一次可能是基础设施抖动，两次就该认定是任务本身
有问题。

### 11.3.4 `started_at` 只在首次领取时写

```python
if record.status == AgentRunStatus.QUEUED.value:
    record.started_at = now
record.status = AgentRunStatus.RUNNING.value
record.attempt_count += 1
```

接管一个过期 running run 时，`started_at` **保持不变**，只有 `attempt_count` 增加。所以
`started_at` 的语义是"第一次被 Worker 拿起的时间"，而不是"当前这次尝试开始的时间"。

这个选择让 `completed_at - started_at` 表示用户视角的**端到端等待时间**（包括崩溃和重新接管的那段），
而不是最后一次尝试的耗时。对 P95 延迟这类指标来说，用户等的是前者。`attempt_count` 单独记录了尝试
次数，两个信息都没丢。

## 11.4 Worker：租约与心跳

`DiagnosisRunWorker`（208 行）不创建 Agent、不复制 workflow。它的 docstring 把定位说得很清楚：

> 进程内 task 只是唤醒器，队列事实、租约和终态都在 PostgreSQL；因此容器重启不丢任务，多个 API 副本
> 也能依靠行锁分工。

### 11.4.1 构造期就拒绝不安全的心跳配置

```python
if heartbeat_seconds >= lease_seconds / 2:
    raise ValueError("worker heartbeat must be less than half the lease")
```

默认值是 `lease_seconds=180`、`heartbeat_seconds=30`，比例 1:6。为什么必须小于一半？

租约的作用是"我还活着，别抢我的任务"。心跳的作用是在租约过期前续租。如果心跳间隔 ≥ 租约的一半，
那么**一次心跳失败（网络抖动、数据库短暂不可用）就足以让租约过期**——因为下一次心跳要等一个完整
间隔，而那时租约已经没了。小于一半意味着至少有两次续租机会覆盖同一个租约周期，单次失败可以由下一次
补救。

这类"两个时间参数之间的关系"是分布式租约里最容易配错的地方，而错误的表现是**偶发的重复执行**——
最难查的一类 bug。把它变成构造期的 `ValueError`，等于让错误配置在进程启动时就死掉。

### 11.4.2 `asyncio.wait` 只等待，不取消

```python
while True:
    done, _ = await asyncio.wait({execution}, timeout=self._heartbeat_seconds)
    if done:
        execution.result()
        return
    renewed = await self._renew_claim(claim.run.run_id)
    if not renewed:
        execution.cancel()
        with suppress(asyncio.CancelledError):
            await execution
        return
```

这里的关键是 `asyncio.wait` 与 `asyncio.wait_for` 的区别：**`wait_for` 超时会取消任务，`wait` 只是
超时返回**。用 `wait` 意味着诊断可以跑任意长时间，心跳只是每 30 秒醒来看一眼、续一次租。

`execution.result()` 那一行有条注释：

> 传播 DiagnosisExecutionFailed，让 worker loop 记录为已处理而继续消费下一条。

`result()` 会把子 task 里的异常重新抛出来。这是故意的——异常需要冒泡到 `_run_loop` 的
`except Exception`，才能被记为"这一轮处理完了"。如果这里静默吞掉，Worker 会认为一切正常，但那条
run 的终态从没被提交。

### 11.4.3 续租失败必须取消执行

`renewed` 为 False 的分支是本节最重要的地方。`renew_lease` 的 SQL 是条件 UPDATE：

```python
update(AgentRunRecord).where(
    AgentRunRecord.run_id == run_id,
    AgentRunRecord.status == AgentRunStatus.RUNNING.value,
    AgentRunRecord.lease_owner == worker_id,
    AgentRunRecord.lease_expires_at > now,
).values(lease_expires_at=now + timedelta(seconds=lease_seconds), updated_at=now)
return result.rowcount == 1
```

四个 WHERE 条件，`rowcount == 1` 才算成功。任何一个不成立都返回 False：

- 状态不再是 running → 任务已被取消或已终结；
- `lease_owner != worker_id` → 别的 Worker 接管了；
- `lease_expires_at <= now` → 自己的租约已经过期。

docstring 说明了为什么用条件 UPDATE 而不是"先读后写"：

> 条件更新而非先读后写避免两个 Worker 之间的竞态；rowcount 为零表示任务已被别的 Worker 接管或已终态，
> 执行方必须停止继续提交结果。

"先读后写"的版本是：SELECT 确认 owner 是我 → UPDATE 延长。两步之间另一个 Worker 完全可以抢走这行。
条件 UPDATE 把检查和写入合成一个原子操作。

失败后立刻 `execution.cancel()`，防止**双写**：如果两个 Worker 都在跑同一个 run，两个都会尝试
`complete_run`。虽然 `_lock_owned_running_run`（§11.5.1）会拦住失去租约的那个，但继续跑下去纯属浪费
模型预算和 MCP 子进程。

顺便注意 `renew_lease` 的最后一句 docstring：**"该方法不保存 heartbeat 事件，避免时间线噪声。"**
心跳是基础设施细节，一次两分钟的诊断会产生四次心跳，写进 `run_events` 只会把用户要看的四五条业务
事件淹掉。

### 11.4.4 reaper：谁来终结彻底没救的 run

`fail_exhausted_runs` 处理的是 `attempt_count >= max_attempts` 且租约已过期的 run。它们**不满足**
`claim_next_run` 的领取条件，所以如果没人管，会永远停在 running。

```python
record.status = AgentRunStatus.FAILED.value
record.error_code = "worker_attempts_exhausted"
record.error_message = "诊断 Worker 重试次数已耗尽；请重新提交问题。"
```

同时写一条 system 事件，序号接在现有事件之后：

```python
last_sequence = await self._session.scalar(
    select(func.max(RunEventRecord.sequence)).where(RunEventRecord.run_id == record.run_id)
)
sequence = (last_sequence or 0) + 1
```

用 `MAX(sequence) + 1` 而不是硬编码，因为一个被接管过的 run 可能已经写了部分事件。
`uq_run_events_run_sequence` 会让序号冲突直接失败，所以这里必须先查。

reaper 放在 `run_once` 的**开头**而不是单独的定时任务，注释解释了原因：

> 先终结无法再接管的任务，避免它们长期占用 running 状态而阻塞 session 新消息。

一个卡住的 running run 会通过 `uq_agent_runs_active_session` 阻塞整个 session。把清理放在每次轮询
开头，意味着 Worker 一活着就会持续修复这类状态，不需要额外的调度器。

### 11.4.5 `_run_loop`：吞掉异常，但绝不吞 `CancelledError`

```python
try:
    claimed = await self.run_once()
except asyncio.CancelledError:
    raise
except Exception:
    claimed = False
```

`except asyncio.CancelledError: raise` 必须写在 `except Exception` 前面。Python 3.8 起
`CancelledError` 继承自 `BaseException` 而非 `Exception`，所以理论上不会被后面那个捕获——但显式写出来
是一种防御：任何人把它改成 `except BaseException` 时，这一行还在。

吞掉其余异常的理由：一次数据库连接故障不应该杀掉整个 Worker。注释写了两层：

> 详细异常留在受控进程日志；公共 run 状态由 runtime/租约机制保证，不把 traceback 写入 API。
> 进入一次短暂 poll 退避，避免数据库故障或租约竞争造成忙等。

`claimed = False` 会让循环进入 `wait_for(stop_event.wait(), timeout=poll_interval)` 分支，也就是退避
0.25 秒再试。没有这个退避，数据库不可用时 Worker 会以最快速度重试，把 CPU 打满。

停机路径用 `stop_event` + `task.cancel()` 双重机制：`stop_event` 让空闲等待自然退出，`cancel()` 立刻
打断正在执行的一轮。`stop` 的 docstring 强调了一个语义边界：

> 取消只作用于 Worker task，不把浏览器或进程停机伪装成业务 cancelled；未完成 run 的租约会在
> lease_expires_at 后由新 Worker 接管。

**进程停机不是用户取消。** 一个正在跑的 run 在 Worker 停止后保持 running，等租约过期被接管——用户
看到的是"还在跑"，而不是"被取消了"。只有用户显式调 cancel 才会产生 `cancelled` 终态。

### 11.4.6 `worker_id` 也有格式校验

```python
self._worker_id = worker_id or f"worker_{uuid4().hex[:16]}"
if re.fullmatch(r"worker_[a-f0-9]{16}", self._worker_id) is None:
    raise ValueError("worker_id must contain worker_ plus 16 hexadecimal characters")
```

`ClaimedDiagnosisRun.worker_id` 有同样的 pattern 约束。为什么一个纯内部标识需要格式检查？因为它是
**所有权凭证**：`renew_lease` 和 `_lock_owned_running_run` 都用它做相等比较。测试可以注入固定
worker_id，如果注入了一个空字符串或 `None`，那么 `lease_owner == worker_id` 的比较语义会漂移
（比如 SQL 里 `NULL = NULL` 为 NULL 而非 True）。定长十六进制让这类比较永远是明确的。

## 11.5 终态：四件事一起提交

诊断跑完后要写的东西不止一条：run 的终态、给用户看的事件时间线、下一轮追问要用的 checkpoint、
可回放的 trace span。`complete_run` 把它们放进**同一个事务**。

### 11.5.1 `_lock_owned_running_run`：三重身份检查

每个终态方法的第一行都是它：

```python
record = await self._session.scalar(
    select(AgentRunRecord).where(AgentRunRecord.run_id == run_id).with_for_update()
)
if record is None:
    raise LookupError(f"agent run not found: {run_id}")
if (
    record.status != AgentRunStatus.RUNNING.value
    or record.lease_owner != worker_id
    or record.lease_expires_at is None
    or record.lease_expires_at <= now
):
    raise LookupError(f"agent run lease is no longer owned: {run_id}")
```

docstring 点出了它挡住的那个具体场景：

> 行锁把完成/失败竞争串行化；租约过期后旧 Worker 即使完成模型调用也不能覆盖新 Worker 的结果。

这是 §11.4.3 那条防线的另一半。假设 Worker A 的租约过期了（数据库卡了 3 分钟），Worker B 接管并跑
完了。此时 A 的模型调用终于返回，它拿着一份完整报告来提交。如果只检查 `status == running`，A 会成功
覆盖 B 的结果——用户看到的是一份用**过期上下文**算出来的报告。

`lease_owner != worker_id` 这一条挡住它。注意它检查的不只是"我曾经拥有"，还包括
`lease_expires_at > now`：即使 owner 字段还是 A（B 还没来得及领取），一个过期租约也不允许提交。
**过期就是失去授权**，跟有没有人接管无关。

注意这里抛的是 `LookupError` 而不是自定义异常。"找不到"和"不再拥有"用同一种异常，因为对调用方来说
处理方式一样：放弃这次提交，让循环去消费下一条。

### 11.5.2 四件事的原子性

```python
record.status = AgentRunStatus.COMPLETED.value
record.result = result.model_dump(mode="json")
record.completed_at = now
record.updated_at = now
record.lease_owner = None
record.lease_expires_at = None
self._session.add_all([_event_record(event) for event in events])
self._add_trace_spans(run_id, trace)
await self._save_checkpoint(checkpoint)
await self._session.flush()
```

docstring 用一句话说明了为什么必须同事务：

> 四者和 run 终态共用外层事务，因而轮询者不会看到 completed 但缺少时间线或 trace。

设想分成两个事务：先提交终态，再提交事件。中间那个瞬间，一个前端正在轮询
`GET /runs/{id}`，看到 `status=completed`，于是停止轮询、去拉 `GET /runs/{id}/events`——拿到空数组。
用户看到一份没有任何过程记录的报告，而且**永远不会再看到**，因为轮询已经停了。

第 12 章讲推流时这条约束会再出现一次：`run-stream:v1` 的每一跳必须**先读 run 快照再读增量事件**。
如果反过来（先读事件、再读快照），在这两次读之间发生的 `complete_run` 会让流看到终态却漏掉最后一批
事件。这不是同一个 bug，但根源是同一个：终态和事件是一起变的，读的顺序决定了你会不会踩到它。

顺便注意终态会把 `lease_owner` 和 `lease_expires_at` 置 `None`。这不只是清理——
`ck_agent_runs_terminal_payload`（§11.2.3）里 completed 那一支要求它们为 NULL，不清就直接
`IntegrityError`。约束在这里起到了"提醒你别忘了收尾"的作用。

最后一个细节在调用方：`_execute_traced_run` 里根 span 是在这次 `complete_run` 提交**之前**关闭的。
这意味着 trace 里记录的总耗时**不包含最后那次事务提交**。这是一次刻意的交换——如果反过来（先提交、
再关根 span、再写 span），span 就必须走第二个事务，于是出现"终态提交成功、span 提交失败"的可能，
也就是 §11.5.4 想避免的那种事后无法分辨的污染。用一点时间精度换严格的原子性，代价记在 §11.16 的
遗留问题里。

### 11.5.3 `fail_run` 要求一条 `sequence=1` 的 system 事件

```python
if not error_code.strip() or not error_message.strip():
    raise ValueError("failed run requires public error code and message")
if event.run_id != run_id or event.sequence != 1 or event.phase is not RunEventPhase.SYSTEM:
    raise ValueError("failed run requires a first system event for the same run")
```

`sequence != 1` 这个条件第一眼很怪：为什么失败的 run 只能有第一条事件？docstring 给了答案：

> 事件必须为目标 run 的 sequence=1 system 事件，防止部分成功时间线被伪造成失败。

失败路径是**整体回滚**的。`_execute_traced_run` 出异常时，那个事务里所有已 `add` 的事件都没提交。
所以进入 `fail_run` 时，这条 run 在数据库里**一条事件都没有**，新写的必然是 1 号。

如果允许 `sequence=5`，意味着有人在声称"前面 4 条已经存在"。要么那 4 条真的存在（说明失败发生在一个
已经部分提交的事务之后，架构上不该出现），要么不存在（时间线出现 1–4 号缺口，`RunEventList` 的连续
性校验会在读取时炸）。两种都是缺陷，所以直接在写入口拒绝。

另一半是 `error_code` / `error_message` 非空。docstring：

> 只接受非空稳定错误码/公开摘要；原异常通过 Python exception chaining 留给调用日志，不进入数据库。

`message_failure_returns_safe_run_id_without_internal_exception_text` 这个测试守的就是它：API 失败时
返回 run_id 加一个稳定错误码，不返回 `str(exc)`。原始异常文本可能包含数据库连接串、Provider 的原始
响应、Prompt 片段——任何一样泄露出去都是事故。异常链留在进程日志里，那是受控环境。

### 11.5.4 `_add_trace_spans`：外键证明不了归属

```python
if trace is None:
    return
if trace.run_id != run_id:
    raise ValueError("trace must belong to the persisted run")
self._session.add_all([_trace_span_record(span) for span in trace.spans])
```

注释是本章我最喜欢的一条：

> 归属校验放在这里而不是依赖数据库外键，是因为外键只能证明 run 存在，无法阻止把 A run 的 span 写到
> B run 名下——那种错误会让两次诊断的耗时混在一张火焰图上，且事后完全无法分辨。

这是对"数据库约束是最后防线"的一个精确补充。`run_trace_spans.run_id` 上的外键能保证那个 run 存在，
但 A 和 B 都存在，所以把 A 的 span 挂到 B 名下**完全合法**。数据库无法表达"这批 span 必须属于当前
正在提交的那个 run"，因为它不知道"当前正在提交的"是哪个。这个知识只存在于 Python 调用栈里。

后果为什么严重？trace 是用来算 P95 和定位慢节点的。两次 run 的 span 混在一起，一个 3 秒的检索和一个
90 秒的模型调用会出现在同一棵树上，你会以为检索和推理有依赖关系。而且**无法事后修复**：span 记录里
没有任何字段能告诉你它原本属于谁。

`trace is None` 直接 return 也是设计：

> 缺省 trace 视为"本次未开启采集"而不是错误。

离线评测和旧测试不绑定采集器。把"没采集"当成错误，会让评测脚本必须假装装配一个观测器。

### 11.5.5 `list_trace_spans`：区分"run 不存在"和"没有 span"

```python
exists = await self._session.scalar(
    select(AgentRunRecord.run_id).where(AgentRunRecord.run_id == run_id)
)
if exists is None:
    return None
```

多一次查询只为了区分两种空结果。docstring：

> "run 存在但没有 span"与"run 不存在"必须区分：前者说明该 run 在未开启采集的部署下执行，后者是调用方
> 用错了 ID。

对应到 API：`None` → 404，空 `RunTrace` → 200 加一个空 spans 数组。如果合并成一种，用户拿着一个打错的
run_id 会收到 200 和空 trace，然后开始怀疑是采集器坏了。

## 11.6 会话 checkpoint：追问怎么继承上下文

用户问"LTS 任务卡住了"，拿到一份报告。接着问"这个风险高吗"。第二句话里没有任何组件名、没有任何
故障描述——它必须依赖上一轮的上下文才能理解。

`app/memory/checkpoint.py`（246 行）就是这件事的全部实现。模块 docstring 先划了一条边界：

> checkpoint 与跨会话 `case_memories` 完全分离：它只服务一个 session 的追问，保存公开 AgentState 子集
> 和上一轮报告，并在新 run 开始时重建新的瞬态状态。

第 10 章的 `case_memories` 是**跨会话**的长期记忆，要经过审计、要用户 confirm、要算向量相似度。
checkpoint 是**单会话**的短期状态，无条件保存、不需要审批、只在这个 session 内可见。两者放在一起会
出现"用户随便问一句，就被当成一个案例沉淀下来"的荒谬后果。

### 11.6.1 六个上限：滚动窗口而不是无限 transcript

```python
CHECKPOINT_MAX_PLAN_ITEMS = 16
CHECKPOINT_MAX_HYPOTHESES = 16
CHECKPOINT_MAX_EVIDENCE = 64
CHECKPOINT_MAX_TOOL_EVENTS = 64
CHECKPOINT_MAX_PATHS = 32
CHECKPOINT_MAX_OBSERVATION_REFS = 128
```

注释说明了为什么必须有上限：

> 检查点是"滚动窗口"而不是无限 transcript。保留最近公开状态可以让追问继续使用最新证据，同时给
> JSONB、检索查询和恢复 Pydantic 校验设定确定上限。

一个 session 可以有几十轮追问。如果每轮都把上一轮的全部证据累积进去，`Evidence` 数量会线性增长：
JSONB 行越来越大、恢复时的 Pydantic 校验越来越慢、`build_checkpoint_retrieval_query` 拼出来的文本
越来越长。**有界性是不用测就知道会需要的东西**，只是通常等到线上出问题才加。

取尾部而不是头部：

```python
return tuple(values[-limit:])
```

`_bounded_tail` 的 docstring 解释了这个方向：

> 诊断循环按时间追加 plan、Evidence 和 ToolEvent，因此尾部代表最新上下文。

这也是为什么 `tool_events` 值得保留 64 条——`restore_agent_state` 的 docstring 提到它有个额外用途：
**"保留 ToolEvent 让 ReAct 从历史 Action 重建跨 run 去重指纹。"** 第 8 章的指纹去重是防止 Planner
反复调同一个工具，这条防线要跨追问生效，就必须把历史 Action 带过来。

### 11.6.2 显式字段清单是一道门禁

`build_session_checkpoint` 里最重要的是那条注释：

> 只复制恢复所需集合；显式字段清单是防止未来 AgentState 新增敏感字段后被自动持久化的门禁。

对比两种写法。偷懒版：`SessionCheckpoint(**state.model_dump())`，或者干脆把整个 `AgentState` 序列化
存进 JSONB。省事版：逐个字段列出来。

`SessionCheckpoint` 的 docstring 把排除清单也写明了：

> 明确排除 next_action、stop_reason、audit_result、memory_candidate 与旧 react_step。

这条清单里的每一项都有具体理由（§11.6.3 展开）。但更关键的是**未来**：半年后有人给 `AgentState` 加
一个 `raw_provider_response` 或 `planner_thought` 字段来调试。用 `model_dump()` 的版本会立刻把推理
过程写进数据库，而且是静默的——没有任何测试会失败，因为没人写过"checkpoint 不许包含 thought"的断言。
显式清单的版本什么都不会发生：新字段不在列表里，就不会被复制。

`model_config = ConfigDict(extra="forbid", frozen=True)` 是同一件事的另一半。`extra="forbid"` 让
"多传一个字段"变成 `ValidationError` 而不是被静默接受。

### 11.6.3 恢复时归零：预算不能继承

`restore_agent_state` 的返回值里有一串显式的零值：

```python
react_step=0,
next_action=None,
stop_reason=None,
draft_report=None,
audit_result=None,
retry_count=0,
memory_candidate=None,
```

这些字段在 `SessionCheckpoint` 里根本不存在，所以这里的 `=0` / `=None` 其实是在写"新 run 从头开始"。
但显式写出来有意义——它让读代码的人一眼看到七个瞬态字段各自被重置了。docstring：

> 本轮 `react_step` 从零开始，旧 next_action/stop_reason/audit/memory 不恢复，因此单轮预算与终态不会
> 污染追问。

逐个看后果：

- **`react_step`**：上一轮用了 6 步（预算 8）。如果继承，追问只剩 2 步——用户会发现"第二个问题模型
  明显变笨了"，而且是随机的，取决于上一轮用了多少步。
- **`stop_reason`**：上一轮是 `react_budget_exhausted`。继承的话新 run 一开始就带着终止信号。
- **`audit_result`**：上一轮的审计裁决。继承会让新报告**跳过审计**——`audit_report` 节点看到已有
  裁决就不再调 Auditor。这是四级审计阶梯（第 9 章）被绕过的最短路径。
- **`memory_candidate`**：上一轮的记忆候选。继承会让这个候选被**再暂存一次**，`occurrence_count`
  凭空加一。第 10 章说过那个数字是人类当严重度读的。
- **`retry_count`**：上一轮的返工次数。继承会让追问的返工预算（`max_audit_revisions ≤ 1`）已经用完。

`restore_creates_new_run_and_resets_transient_fields` 这个测试守的就是整组。

还有一条容易被忽略的细节：

```python
# 所有列表都重新分配，防止新 run 的节点原地修改 checkpoint 所持有的集合引用。
return AgentState(
    ...
    plan=list(checkpoint.plan),
    hypotheses=list(checkpoint.hypotheses),
```

`checkpoint.plan` 是 tuple，`AgentState.plan` 是 list。`list(...)` 不只是类型转换——它切断了共享。
如果 checkpoint 里存的是 list 而直接传引用，ReAct 循环 `state.plan.append(...)` 会**同时改掉那个
"不可变"快照**。`frozen=True` 只冻结属性绑定，不冻结容器内容，这是 Pydantic 一个常见误解。

### 11.6.4 跨会话恢复直接抛异常

```python
if checkpoint.session_id != session_id:
    raise ValueError("checkpoint cannot be restored into a different session")
```

两行代码，但它是这个模块里唯一的**安全**校验（其余都是正确性校验）。会话 A 诊断出"FlashSync 主键
冲突"，会话 B 属于另一个用户。如果 B 能恢复 A 的 checkpoint，B 的报告里会出现 A 的根因、A 的证据引用、
A 的报告摘要——一次完整的跨用户数据泄露。

`restore_rejects_cross_session_checkpoint` 是 §11.1 表里那条。为什么这个错误有可能发生？因为
`get_checkpoint(session_id)` 和 `restore_agent_state(checkpoint, session_id=...)` 是**两次传参**。
中间任何一次改动（比如某天加个缓存层、或者 resume 路径复用了错的变量）都可能让它们不一致。校验放在
消费点，无论上游怎么错都拦得住。

### 11.6.5 `_bounded_unique_tail`：去重之后还要保时序

```python
unique_reversed: list[str] = []
seen: set[str] = set()
for value in reversed(values):
    if value not in seen:
        unique_reversed.append(value)
        seen.add(value)
    if len(unique_reversed) == limit:
        break
return tuple(reversed(unique_reversed))
```

反向遍历去重、再反转。docstring：

> 从后向前去重能保留最近一次出现的位置；随后反转恢复时间顺序。

为什么不用 `tuple(dict.fromkeys(values))[-limit:]`？那个写法保留的是**首次**出现的位置，然后取尾部。
考虑 `["ev_1", "ev_2", "ev_1"]`，limit=2：

- 正向去重 → `["ev_1", "ev_2"]` → 取尾 2 → `("ev_1", "ev_2")`；
- 反向去重 → `["ev_1", "ev_2"]`（反序收集）→ 反转 → `("ev_2", "ev_1")`。

第二个才对：`ev_1` 最后一次出现在 `ev_2` 之后，说明它是更近的引用。当引用数超过 128 需要丢弃时，
这个差别决定了丢掉的是不是真正最旧的那些。

`checkpoint_rolling_window_bounds_latest_items_and_deduplicates_refs` 用
`assert refs == ("ev_0", "ev_1", "ev_2")` 和 `assert evidence[0] == 5` 两条断言同时守住"去重后仍保
时序"和"超限时丢最旧"。

顺便，`SessionCheckpoint.validate_identity_and_timestamps` 里有一条对应的校验：

```python
if len(self.observation_refs) != len(set(self.observation_refs)):
    raise ValueError("checkpoint observation_refs must not contain duplicates")
```

构造函数不会替你去重，它只会告诉你没去重。这个方向是对的——静默去重会掩盖上游的重复来源。

### 11.6.6 版本必须恰好加一

`_save_checkpoint` 的三条规则：

```python
if current is None:
    if checkpoint.checkpoint_version != 1:
        raise ValueError("first session checkpoint must use version one")
    ...
if checkpoint.checkpoint_version != current.checkpoint_version + 1:
    raise ValueError("session checkpoint version must increase by exactly one")
if checkpoint.created_at != current.created_at:
    raise ValueError("session checkpoint created_at must remain stable across updates")
```

docstring 说明了它防的是什么：

> 现有行使用 `FOR UPDATE` 串行化并发完成；新版本必须恰好加一，created_at 必须保持不变。这会让基于旧
> 快照完成的并发 run 明确失败，而不是倒退 source_run 或覆盖更新的上下文。

`+1` 而不是 `>`。为什么？因为 run 计算新版本号的方式是
`checkpoint_version = 1 if checkpoint is None else checkpoint.checkpoint_version + 1`——它读的是
**开始执行时**的版本。假设 run X 读到版本 2、跑了 90 秒；期间 run Y 读到版本 2、跑完写了版本 3。X 写
版本 3 时如果只要求"大于当前"，会失败（3 不大于 3），这倒是对的。但如果 X 读到版本 2 而 Y 已经写到
版本 4，X 的版本 3 在 `>` 规则下同样失败。用 `+1` 的好处是**错误信息精确**：版本不连续本身就是
"你基于一个过期快照在写"的证明。

`created_at` 必须稳定这一条更微妙。checkpoint 表用 `session_id` 做主键，所以它是**原地更新**的：
`created_at` 是"这个 session 第一次有 checkpoint 的时间"，`updated_at` 是最后一次。`_execute_traced_run`
里对应的代码是把旧 `created_at` 传下去。如果某次写入把它改了，你就永远无法知道这个会话是什么时候
开始有上下文的——而这条校验让"改了"变成一次显式失败。

§11.2.4 的部分唯一索引在这里闭环：单 session 活跃 run 唯一，意味着**正常情况下根本不会有两个 run
并发写同一个 checkpoint**。这三条校验是第二层——防的是索引失效、手工插入、或者未来某个"允许并行
run"的改动。

### 11.6.7 JSONB 与关系列交叉校验

`_checkpoint_from_record` 读回时做四组比对：

```python
checkpoint = SessionCheckpoint.model_validate(record.snapshot)
if checkpoint.session_id != record.session_id:
    raise ValueError("checkpoint snapshot session_id does not match its row")
if checkpoint.source_run_id != record.source_run_id:
    raise ValueError("checkpoint snapshot source_run_id does not match its row")
if checkpoint.checkpoint_version != record.checkpoint_version:
    raise ValueError("checkpoint snapshot version does not match its row")
if checkpoint.created_at != record.created_at or checkpoint.updated_at != record.updated_at:
    raise ValueError("checkpoint snapshot timestamps do not match its row")
```

同一份信息存了两遍：JSONB 里一份，关系列上一份。为什么要冗余？docstring：

> snapshot 自带身份、版本和时间；关系列是数据库索引/外键事实。两者任何漂移都抛 ValueError，防止只
> 修改 JSONB 或只修改列后把错误上下文恢复到下一条用户消息。

关系列的存在是为了让数据库能**索引和约束**它们：`uq_session_checkpoints_source_run`、
`checkpoint_version >= 1` 这些约束都作用在列上，JSONB 内部的字段数据库管不到。而 JSONB 里那一份是
`SessionCheckpoint` 的完整自描述形式。

冗余的代价是可能不一致，所以每次读都比对。这也是 §11.2.2 那条"不用 `onupdate`"的直接原因——
`updated_at` 有两份，一份是应用写进 JSONB 的，一份在列上。如果 `onupdate=func.now()` 悄悄把列改成
数据库时钟的值，这条比对**永远失败**，而且只在真 PostgreSQL 上失败。

### 11.6.8 检索查询：当前问题永远排第一

```python
segments = [f"当前问题: {normalized_query}"]
if checkpoint is not None:
    segments.extend(
        [
            f"上一问题: {checkpoint.source_user_query}",
            f"上一报告摘要: {checkpoint.report.summary}",
        ]
    )
    segments.extend(
        f"上一轮根因: {root_cause.root_cause}"
        for root_cause in checkpoint.report.root_causes
    )
return "\n".join(segments)[:max_chars].rstrip()
```

顺序是刻意的。`[:max_chars]` 从**尾部**截断，所以排在前面的内容永远不会被裁掉。当前问题排第一，
意味着无论上一轮的报告有多长，用户刚问的那句话一定完整进入检索查询。

`checkpoint_retrieval_query_prioritizes_followup_and_adds_report_context` 就是这条断言。如果顺序反过来
（历史在前），一个上一轮产出了 8 条根因的长报告会把当前问题挤出 4000 字预算——检索会退化成"重新
检索上一个问题"，返回一模一样的证据，而用户新问的东西完全没被看见。

docstring 还划了一条内容边界：

> 函数只组合公开文本并按字符截断，不加入工具原始响应或高维向量。

`checkpoint.report.summary` 和 `root_cause.root_cause` 都是已经过审计的公开文本。工具原始响应可能
包含未净化的内容，embedding 是数字噪声——两者都不该进检索查询。

## 11.7 取消与恢复

用户点了"取消"。这个动作看起来简单，但它要和一个正在跑的 Worker 竞争同一行数据。

### 11.7.1 `FOR UPDATE` 让取消与提交互斥

`cancel_run` 的 docstring 把两种竞争顺序都写清楚了：

> `FOR UPDATE` 让取消与 Worker 的完成/失败提交互斥：如果 Worker 已先提交，调用返回 completed/failed
> 快照，API 再把它解释为不可取消；如果取消先提交，Worker 后续的 lease 校验会失败，因此不会覆盖
> cancelled 结果。

这是两个方向都安全的设计，值得拆开看：

**取消先拿到锁**：`cancel_run` 把 status 改成 `cancelled`、清空 `lease_owner`、提交。Worker 稍后调
`complete_run`，`_lock_owned_running_run` 发现 `status != running` 且 `lease_owner != worker_id`，抛
`LookupError`。Worker 那一轮被记为"已处理"，继续消费下一条。用户的取消是终态。

**Worker 先拿到锁**：`complete_run` 在事务里把 status 改成 `completed`。`cancel_run` 阻塞在
`FOR UPDATE` 上，等 Worker 提交后拿到锁，看到 status 已经是 `completed`：

```python
if record.status not in {
    AgentRunStatus.QUEUED.value,
    AgentRunStatus.RUNNING.value,
}:
    return _run_from_record(record)
```

**直接返回，不报错。** 返回的是那个 completed 快照，API 层看到终态不是 cancelled，把它解释为"取消
失败，任务已完成"。这个设计比抛异常好：用户拿到的是一份可用的报告，而不是一条"取消失败"的错误提示。

重复取消也是同一个分支的前一条：

```python
if record.status == AgentRunStatus.CANCELLED.value:
    return _run_from_record(record)
```

幂等。用户狂点三次取消按钮，第二三次是无副作用的读。没有这一条，第二次调用会试图再写一遍
`completed_at` 和一条新的 `run_cancelled` 事件——时间线上出现三条"已取消"。

### 11.7.2 两种 cancelled 的字段形态

docstring 里这句对应 §11.2.3 的 SQL：

> 该方法保持 queued 的 `attempt_count=0` 和 running 的已开始信息，满足数据库与领域模型的双重状态约束。

注意 `cancel_run` **没有**碰 `started_at` 和 `attempt_count`，它只写 status / error / completed_at /
updated_at / 清租约。这个"不做什么"正是关键：

- 取消一个 queued run：`started_at` 还是 NULL、`attempt_count` 还是 0 → 命中约束里
  `(started_at IS NULL AND attempt_count = 0)` 那一支；
- 取消一个 running run：两个字段都已经被 `claim_next_run` 填过 → 命中
  `(started_at IS NOT NULL AND attempt_count >= 1)` 那一支。

如果 `cancel_run` 顺手把 `attempt_count` 归零"清理干净"，那么取消一个 running run 会写出
`started_at IS NOT NULL AND attempt_count = 0`——两支都不满足，`IntegrityError`。约束在这里起的作用是
**阻止一次善意的过度清理**。

同时它保留了审计价值：一条被取消的 run 仍然记着"它跑到过第几次尝试、什么时候开始跑的"。
`cancel_and_resume_routes_keep_cancelled_run_auditable` 守的就是这个——取消不是删除。

`error_code = "user_cancelled"` 而不是 NULL：约束里 cancelled 那一支要求 `error_code IS NOT NULL`。
取消在数据模型上被当成一种"失败原因已知"的终态，而不是一种成功。错误消息
`"诊断任务已由用户取消，可从会话检查点恢复。"` 直接告诉用户下一步能干什么。

事件序号同样用 `MAX(sequence) + 1`（跟 §11.4.4 的 reaper 一样），因为一个被取消的 running run 可能
已经写过部分事件——比如它被接管过一次。

### 11.7.3 resume 是 run 级，不是节点级

`resume_run` 的 docstring 有一句很诚实的自我限定：

> 这是可靠的 run-level resume：它复用同一 session 的最新 checkpoint，而不是声称实现 LangGraph 内部
> 节点级恢复。

```python
source = await repository.lock_run(run_id)
if source is None:
    return None
if source.status is not AgentRunStatus.CANCELLED:
    raise RunResumeConflictError(run_id, source.status)
return await repository.create_run(
    run_id=new_run_id,
    session_id=source.session_id,
    message=DiagnosisMessage(
        content=source.user_query,
        intent=source.intent,
        components=source.components,
        history_trigger=source.history_trigger,
    ),
    now=now,
)
```

恢复做的事情是：读出被取消 run 的原始输入，用它创建一个**新的 queued run**。被取消的那条 run 保持
cancelled 不变。新 run 会被 Worker 领取，读到 session 的最新 checkpoint（那是**上一次成功完成**的
run 留下的），然后从头跑一遍。

为什么不做节点级恢复？LangGraph 确实有 checkpointer 机制可以从中断的节点继续。但那要求把
`AgentState` 的**每个中间态**都持久化——包括 `next_action`、`audit_result` 这些 §11.6.3 特意排除的字段，
还包括 MCP 子进程的状态（根本没法序列化）。这个项目选择的边界是：**只在 run 边界上恢复**，代价是
被取消的那部分工作真的白做了，收益是恢复语义完全确定、没有"半个状态被恢复"的可能。

把这个限制写进 docstring 而不是含糊地叫"resume"，是这个项目一贯的做法：能力边界要能被读代码的人
看见。

`lock_run` 的 `FOR UPDATE` 加上 `uq_agent_runs_active_session` 是双重防线，docstring 讲了分工：

> 行锁与 session 的 active 唯一索引共同防止两个请求同时恢复同一个会话。

用户双击"恢复"：两个请求都要 `lock_run` 同一行，第二个阻塞。第一个创建了新 queued run 并提交；第二个
拿到锁后看到源 run 还是 cancelled（源 run 不会因为恢复而改变状态），于是它**也**会尝试
`create_run`——这时 `ActiveRunConflictError` 或部分唯一索引拦住它。两层缺一不可：行锁串行化了检查，
索引保证了结果。

## 11.8 事件时间线：三层连续性校验

`run_events` 是用户在 `/demo` 上看到的那条进度条：检索了多少节点、ReAct 走了几步、报告是否被返工、
记忆是否暂存。它的核心不变式只有一条——**序号从 1 开始严格连续**。这条不变式被检查了三次。

### 11.8.1 为什么同一件事要检查三遍

| 层 | 位置 | 检查什么 |
|---|---|---|
| 写入前 | `_validate_events`（Python） | 非空、run_id 一致、`[1..N]` 严格连续 |
| 写入时 | `uq_run_events_run_sequence`（数据库） | `(run_id, sequence)` 唯一 |
| 读出后 | `RunEventList.validate_event_sequence`（Pydantic） | 不混 run_id、序号 `1..N` |

三层各自能挡住不同的东西，去掉任何一层都会漏。

**为什么不能只靠唯一约束？** `_validate_events` 的 docstring 回答了：

> 该校验在插入数据库前执行，避免依赖唯一约束逐条失败后才发现时间线缺口；不自动重排，因为顺序错误
> 表示投影逻辑或调用链发生真实漂移。

唯一约束只能发现**重复**，发现不了**缺口**。事件序号是 `[1, 2, 4]` 时三条都唯一，插入成功。缺口要等
到读的时候才被 `RunEventList` 发现——那时候数据已经在库里了，而且这条 run 的 events 接口从此永久 500。

**为什么不能只靠 Python 前置校验？** 因为它只看这一批。一个被接管过的 run 可能已经写了 1、2 号事件，
新 Worker 提交的批次又从 1 开始——两批各自内部连续，合起来重复。这时候唯一约束是唯一能拦住的东西。

**为什么读出来还要再校验一遍？** `RunEventList` 的 docstring：

> 仓储按 sequence 排序，但响应模型再次验证，避免 SQL 或测试替身漂移导致前端时间线错乱；失败显式暴露，
> 不静默重排或丢弃重复事件。

"测试替身漂移"是关键词。单元测试用的内存 fake repository 完全可以返回一个乱序列表——如果响应模型不
校验，那些测试会全绿，而真实前端会拿到错序的时间线。响应模型的校验对**替身和真库同时生效**。

"不静默重排"这个选择要专门说一下。既然能检测出乱序，为什么不顺手 `sorted()` 一下？因为乱序的成因
不是"顺序坏了"，而是**投影逻辑坏了**。`_project_run_events` 负责把 `AgentState` 投影成事件序列；如果
它漏了一个阶段或算错了序号，排序只会把这个 bug 藏起来，让"少了一个 ReAct 事件"变成"时间线看起来
挺正常"。

### 11.8.2 `list_events_after` 为什么返回裸元组

`list_events` 返回 `tuple[RunPublicEvent, ...] | None`，`list_events_after` 也是。但注意它们**没有**
返回 `RunEventList`——那个包装是在 API 层做的。docstring 解释了增量场景为什么必须这样：

> 推流需要的是切片而不是全量：领域 `RunEventList` 要求 sequence 恰好覆盖 1..N，无法承载增量结果，
> 因此这里直接返回元组而不包装成列表模型。

一个推流连接第二次轮询时，游标是 5，拿到的是 6、7、8 号事件。这三条塞进 `RunEventList` 会立刻
`ValidationError`——`[6, 7, 8] != [1, 2, 3]`。

这是一个很典型的建模张力：`RunEventList` 的"1..N 连续"是**为全量视图设计的正确性契约**，而增量视图
的正确性契约是"严格大于游标且递增"。硬把两者塞进一个模型，只能放松成"递增"，那么全量接口就失去了
缺口检测。这里的处理方式是**让增量路径不使用那个模型**，各自保留自己最强的约束。

docstring 的后半句是性能考虑：

> 过滤放在 SQL 层，一条长连接的每次轮询只取真正的新增行，而不是每次都把整条时间线搬进内存再切。

`sequence > after_sequence` 命中 `ix_run_events_run_sequence` 这个 `(run_id, sequence)` 复合索引。
一条推流连接活 5 分钟、轮询几十次，如果每次都拉全量，第 40 次要搬 40 遍同样的行。

推流本身是第 12 章的内容（`run-stream:v1`、`Last-Event-ID` 续传、`end_reason` 区分 run 级终态和连接级
终止），这里只看它在数据库这一端要的两个方法：读 run 快照、读增量事件。`iter_run_stream` 结构上只
持有这两个只读方法——它**没有办法**推进或修改一个 run。

### 11.8.3 存在性检查：区分"未知 run"和"暂无事件"

`list_events` 和 `list_events_after` 都先做一次主键查询：

```python
exists = await self._session.get(AgentRunRecord, run_id)
if exists is None:
    return None
```

跟 §11.5.5 的 `list_trace_spans` 是同一个模式。docstring：

> 先做轻量主键存在性检查可区分"已知 run 暂无事件"和"未知 run"。

`RunEventList` 允许空列表，但只在一种情况下合理——它的 docstring 说得很具体：

> 空列表仅允许 running run 尚未写入首个事件的瞬间。

一个刚被领取、还没走到第一个节点的 run 确实没有事件。这时返回 `200 + []` 是对的。而一个打错的 run_id
必须是 404。合并成一种的后果是前端开始轮询一个不存在的 run，永远等一个不会出现的事件。

注意这里用 `self._session.get()` 而不是 `select()`。`get()` 会先查身份映射（identity map），如果这一行
在当前事务里已经加载过就不发 SQL。`complete_run` 之后紧跟一次 `list_events` 的路径上，这次检查是免费的。

## 11.9 ORM 行不是领域对象

仓储层最后 150 行是八个 `_xxx_from_record` / `_xxx_record` 函数。它们看起来像纯样板——逐字段抄一遍。
但这些函数是**信任边界**，值得单独一节。

### 11.9.1 每次读都重新过一遍 Pydantic

```python
result = DiagnosisRunResult.model_validate(record.result) if record.result is not None else None
return AgentRunSnapshot(
    run_id=record.run_id,
    ...
    status=AgentRunStatus(record.status),
    components=tuple(Component(value) for value in record.components),
    history_trigger=HistoryTrigger(record.history_trigger),
```

`_run_from_record` 的 docstring：

> completed JSON 必须重新通过 DiagnosisRunResult 校验，防止代码升级后旧或损坏 payload 未经检查直接
> 进入 API。

"代码升级后旧 payload"是这里的真实场景。`DiagnosisRunResult` 是一个版本化契约。今天写进 JSONB 的
结构，三个月后如果契约加了一个必填字段，那些旧行就**不再满足新契约**。两种处理方式：

- 不校验：旧 payload 直接被当成 `DiagnosisRunResult` 用，缺的字段在下游某处变成 `AttributeError`，
  或者更糟——被 `.get()` 静默当成空值，用户看到一份缺了一半的报告。
- 校验：那一行的 `GET /runs/{id}` 立刻 500，错误信息明确指出哪个字段不满足。

后者显然更好。500 是一个可以被监控发现、可以被迁移修复的问题；静默的空报告不是。

三个枚举转换 `AgentRunStatus(...)`、`Component(...)`、`HistoryTrigger(...)` 是同一件事的轻量版。
数据库里 status 是 `String`，`CheckConstraint` 限制了取值——但那条约束是 §11.2 说的"最后一道防线"，
它挡的是绕过应用的写入。如果有人用 psql 在约束创建**之前**写了一行 `status='pending'`，枚举转换会抛
`ValueError`。

`_event_from_record` 的 docstring 把这个态度说得最直接：

> 数据库未知 phase 或无时区时间会显式失败，**不静默转成 system**。

"静默转成 system"是那种看起来很贴心的容错。它的后果是：一个本该是 `react` 阶段的事件出现在系统消息
里，前端把它渲染成灰色的基础设施提示，用户永远看不到那一步推理发生过。

### 11.9.2 `dict(...)` 浅复制切断共享引用

四个转换函数里都有 `payload=dict(...)` 或 `attributes=dict(...)`。`_event_record` 的 docstring 解释了
写入方向：

> payload 复制为普通 dict，防止调用方后续修改共享引用。

场景：`_project_run_events` 构造了一批 `RunPublicEvent`，`_event_record` 把它们转成 ORM 行。如果直接
`payload=event.payload`，那个 dict 现在被两个对象共享。ORM 行在 flush 之前一直是可变的，任何对原
`event.payload` 的修改都会改变即将写入数据库的内容——一个跨对象的隐式耦合。

读出方向也一样。`_event_from_record` 的 docstring 补了一句为什么**浅**复制就够：

> payload 只做浅复制，因为 JSONB 已由驱动返回普通可序列化对象。

asyncpg 把 JSONB 反序列化成全新的 Python 原生对象，不存在跟别处共享的嵌套结构。所以不需要
`copy.deepcopy`——那会在每次读事件时白付一次递归开销。

`_trace_span_record` 的注释把这个论证做得更完整：

> 属性做浅复制后写入 JSONB：值已在遥测层被限制为标量与 ASCII 标识符，因此不存在需要深拷贝的嵌套
> 结构，也不可能夹带 Prompt、Thought 或凭据正文。

这里出现了第 12 章那条"span 名称与属性值被正则限制为 ASCII 标识符"的约束在持久化层的回报：因为遥测层
已经保证了 attributes 是扁平的标量映射，这里的浅复制是**可证明安全的**，而不是"大概够用"。

### 11.9.3 枚举以字符串值落库，为了 SQL 能聚合

`_trace_span_record` 里 `kind=span.kind.value`、`status=span.status.value`，docstring 说明了理由：

> 枚举以字符串值落库以便 SQL 直接聚合。

如果用 PostgreSQL 原生 ENUM 类型，`GROUP BY kind` 一样能跑，但每次给枚举加一个成员都需要一次
`ALTER TYPE ... ADD VALUE` 迁移，而且那个语句在旧版本 PostgreSQL 里不能在事务里执行。用 `String` +
`CheckConstraint` 的组合：加成员只需要一次 drop-and-recreate 约束（§11.12 里迁移 0007 做的正是这件
事），而且 §11.11 的 `aggregate_metrics` 可以直接 `GROUP BY kind, name`。

### 11.9.4 `get_run` 刻意不加载事件

```python
record = await self._session.get(AgentRunRecord, run_id)
return _run_from_record(record) if record is not None else None
```

docstring 最后一句：

> 方法不加载事件，GET run 和 GET events 保持独立预算。

`AgentRunRecord` 上有到 `run_events` 的外键关系，SQLAlchemy 完全可以配 `lazy="selectin"` 让每次读 run
自动带上全部事件。这里不这么做，因为轮询接口 `GET /runs/{id}` 的调用频率是所有接口里最高的——前端每
两秒一次。带上事件意味着每次轮询都多搬几十行，而客户端**只想知道 status 变了没有**。

拆成两个接口的另一个好处是失败面独立：一条损坏的事件行会让 `GET events` 500，但 `GET run` 照常返回
报告。合并的话，一条坏事件会让用户连结果都拿不到。

## 11.10 补上第 10 章欠的账：pgvector 与图 join 的真实 SQL

第 10 章讲长期记忆时反复提到"向量去重"、"图扩展"、"advisory lock"，但都停在语义层面。这一节把那些
SQL 摊开。

### 11.10.1 `pg_advisory_xact_lock(hashtext(...))`

```python
if not scope.strip():
    raise ValueError("memory dedup scope must not be blank")
# 事务级 advisory lock 无需显式 unlock，commit/rollback 都会由 PostgreSQL 自动释放。
await self._session.execute(
    text("SELECT pg_advisory_xact_lock(hashtext(:scope))"),
    {"scope": f"case_memory:{scope}"},
)
```

advisory lock 是 PostgreSQL 提供的"应用自定义锁"：它不锁任何一行，只锁一个你自己定义的 64 位整数。
用在这里的原因是**要锁的东西还不存在**——查重是为了决定"要不要插入一行新案例"，那行还没有，没有行
可以 `FOR UPDATE`。

三个细节：

- **`_xact_` 变体**：对应的是 `pg_advisory_lock`（会话级）。会话级锁必须显式 `pg_advisory_unlock`，
  一次异常没解锁就永久泄漏，而且连接池会把这个连接还给下一个请求，锁跟着漂移。事务级版本在
  commit/rollback 时由 PostgreSQL 自动释放，注释写明了这一点。
- **`hashtext`**：advisory lock 只接受整数，`hashtext` 把字符串映射成 int4。docstring 特意声明
  **"`hashtext` 只生成锁键，不用于安全签名"**——它是非加密哈希，会碰撞。碰撞的后果是两个不同 scope
  偶然共享一把锁，也就是多一点串行，不影响正确性。把这句写出来是为了防止后来者以为它有安全语义。
- **`case_memory:` 前缀**：整个数据库共享同一个 advisory lock 命名空间。如果将来有另一个模块也用
  advisory lock，加前缀能避免两个语义完全无关的东西抢同一把锁。

scope 本身是**排序后的组件集合**。第 10 章解释过为什么锁粒度是组件：向量相似度只在组件完全相同的
案例之间比较，所以锁的范围和去重的范围**恰好重合**。锁大了（比如全局锁）会让不同组件的 staging 互相
排队；锁小了（比如按 signature）根本挡不住相似度去重的竞态。

### 11.10.2 `find_exact` 在 `find_similar` 之前

`find_exact` 只有一条 `WHERE signature = :sig` 加 `FOR UPDATE`。它的价值全在**调用顺序**上：精确签名
是本地 SHA-256，免费；向量相似度需要先调远程 embedding API，付费且有延迟。

而最常见的情况恰恰是精确命中——同一个故障反复出现，`sorted(components) + 规范化根因` 算出来的签名
一模一样。所以先查签名等于让高频路径完全不碰 embedding。

`if len(signature) != 64` 这个前置校验是为了让"传了个错东西"立刻失败。一个 32 位的 MD5 或者一个
未 hex 化的 bytes 传进来，SQL 会正常执行并返回 0 行——看起来就是"没有重复"，于是插入一条新案例。
**去重功能静默失效**是这里最坏的结果，长度检查让它变成一次显式异常。

### 11.10.3 `find_similar`：三个相等条件加一个 `<=>`

```python
distance = CaseMemoryRecord.embedding.cosine_distance(embedding)
row = (
    await self._session.execute(
        select(CaseMemoryRecord, distance.label("cosine_distance"))
        .where(
            CaseMemoryRecord.embedding_provider == provider_id,
            CaseMemoryRecord.embedding_dimensions == len(embedding),
            CaseMemoryRecord.components == component_values,
        )
        .order_by(distance, CaseMemoryRecord.updated_at.desc(), CaseMemoryRecord.memory_id)
        .limit(1)
        .with_for_update()
    )
).first()
```

`cosine_distance` 就是 pgvector 的 `<=>` 运算符。三个相等条件各挡一件事，注释一句话总结：
**"只比较 Provider、维度和组件完全相同的记录，避免数学空间或故障范围混合。"**

- **`embedding_provider`**：`bge-m3` 和另一个模型算出的向量即使维度相同，也处在完全不同的语义空间里。
  它们之间的 cosine 距离是个没有意义的数字——但它是个**看起来很正常**的数字（0 到 2 之间），不会
  报错。
- **`embedding_dimensions`**：pgvector 对不同维度的向量做 `<=>` 会直接报错，所以这一条更像是双重
  保险（表上还有 `vector_dims(embedding) = embedding_dimensions` 的 CheckConstraint）。
- **`components == component_values`**：JSONB 精确相等。docstring 举了例子：
  **"避免 LTS 与跨组件案例因文本相似被误合并。"** 一个"LTS 调度延迟"和一个"LTS+BDS 级联延迟"的文本
  描述可能相似到 0.93，但它们是两个不同的故障——后者的根因在跨组件依赖上。

`order_by(distance, updated_at.desc(), memory_id)`：三级排序键。距离相同时（合成数据里完全可能）取
更新更近的，再相同时取 ID 序。这跟第 10 章 §10.6.5 的五级排序键是同一个动机——**确定性**。没有次级键
的 `LIMIT 1` 在两行距离相等时返回哪一行取决于执行计划，同一份数据两次运行可能合并到不同案例上。

`.limit(1).with_for_update()`：只锁真正要合并的那一行。

### 11.10.4 `search_confirmed` 的两个阶段

第一阶段是纯向量 top-k，`status='confirmed'` 写在 WHERE 里：

```python
.where(
    CaseMemoryRecord.status == MemoryStatus.CONFIRMED.value,
    CaseMemoryRecord.embedding_provider == provider_id,
    CaseMemoryRecord.embedding_dimensions == len(embedding),
)
```

注意跟 `find_similar` 的差别：**这里没有组件相等条件**。去重要求组件完全一致（否则会错误合并），但
检索不要求——一个 BDS 的问题完全可能从一个 LTS 的历史案例里学到东西。同一张表、同一个向量列，两个
用途用不同的过滤强度。

`status == CONFIRMED` 是第 10 章那条"pending 候选不能影响诊断"的实现。docstring 强调
**"pending/rejected 在两条 SQL 路径均被排除"**——两条，意味着图扩展那条也要独立检查一次，因为一条
合法的 `SIMILAR_TO` 边完全可以指向一个 pending 邻居。

第二阶段只在 `VECTOR_GRAPH` 模式下执行。这个 mode 参数是给消融评测用的（第 14 章）：把它设成
`VECTOR` 就得到"没有图扩展"的对照组，同一份代码路径产出两组数字。

### 11.10.5 三个 `aliased`：一条 join 走完边、两端节点、邻居案例

```python
seed_node = aliased(KnowledgeNodeRecord)
neighbor_node = aliased(KnowledgeNodeRecord)
neighbor_memory = aliased(CaseMemoryRecord)
result = await self._session.execute(
    select(
        neighbor_memory,
        KnowledgeEdgeRecord.edge_id,
        KnowledgeEdgeRecord.weight,
        seed_node.source_id.label("seed_memory_id"),
    )
    .join(seed_node, KnowledgeEdgeRecord.from_node_id == seed_node.node_id)
    .join(neighbor_node, KnowledgeEdgeRecord.to_node_id == neighbor_node.node_id)
    .join(neighbor_memory, neighbor_node.source_id == neighbor_memory.memory_id)
```

`knowledge_nodes` 在这条查询里出现两次——一次作为边的起点、一次作为终点。SQL 层面必须给它们两个不同的
别名，否则 `from_node_id = node_id AND to_node_id = node_id` 会要求边的两端是同一个节点（而
`from_node_id <> to_node_id` 的约束保证了那永远查不到东西）。`aliased()` 就是 SQLAlchemy 生成
`AS anon_1` / `AS anon_2` 的方式。

第三个 join 从邻居节点回到 `case_memories`：图节点只存 `source_id`（指向案例 ID），真正的案例内容
（根因、证据、`occurrence_count`）在案例表里。

WHERE 里七个条件构成一条完整的信任链，docstring 说是
**"同时校验边来源/类型、两端 case 节点、邻居状态及向量空间"**：

```python
KnowledgeEdgeRecord.relation_type == KnowledgeRelationType.SIMILAR_TO.value,
KnowledgeEdgeRecord.source_id == CASE_GRAPH_SOURCE_ID,
seed_node.node_type == KnowledgeNodeType.CASE.value,
seed_node.source_id.in_(list(seed_scores)),
neighbor_node.node_type == KnowledgeNodeType.CASE.value,
neighbor_memory.status == MemoryStatus.CONFIRMED.value,
neighbor_memory.embedding_provider == provider_id,
neighbor_memory.embedding_dimensions == dimensions,
```

`source_id == CASE_GRAPH_SOURCE_ID` 这一条是第 10 章讲的**所有权隔离**在读路径上的另一半：只走本模块
自己注册的动态边，不会顺着种子知识图谱的 `CAUSES` / `DEPENDS_ON` 边乱爬。写路径靠它防止改到种子节点，
读路径靠它防止把种子拓扑当成案例相似度用。

### 11.10.6 边权必须乘种子相似度

```python
# 边权只描述两个历史案例的接近程度，必须乘当前查询对种子的直接相似度，防止与本次
# 问题无关但彼此相似的旧案例仅凭图结构获得高排名。
graph_score = seed_scores[str(seed_memory_id)] * float(edge_weight)
if graph_score <= 0:
    continue
```

这是整个图扩展里唯一真正需要想清楚的地方。`edge_weight` 是**两个历史案例之间**的相似度，跟当前用户
问的问题毫无关系。假设库里有两个互相 0.99 相似的旧案例 X 和 Y，而当前查询对 X 的直接相似度只有 0.31
（勉强进了 top-k 的尾部）。如果图分数直接取 `edge_weight = 0.99`，Y 会以 0.99 排到第一名——**一个跟
当前问题几乎无关的案例，凭借"它和另一个弱相关案例很像"拿到最高分**。

乘法把这件事修正成 `0.31 × 0.99 = 0.307`：Y 的分数不可能超过它的种子。图扩展只能**补充**候选，不能
凭结构逆转排序。这是一个乘法就能表达的性质，但如果没想到，bug 的表现是"检索偶尔返回莫名其妙的案例"，
而且很难归因。

`graph_score <= 0` 被丢弃，docstring 说明理由：**"零传播分被排除，因为它不能提供排序增益。"**
`weight > 0 AND weight <= 1` 的约束让 `edge_weight` 不可能是 0，所以这一条实际拦的是
`direct_similarity == 0` 的种子——一个跟查询正交的种子，它的所有邻居都不该出现。

`max(0.0, min(1.0, graph_score))` 是最后的钳位。两个 [0,1] 的数相乘不可能越界，但浮点乘法加上未来
可能改成"加权求和"的公式变更，让这个钳位成为一个便宜的不变式保证——它同时也是 `CaseMemoryMatch` 的
字段约束要求的。

`order_by(seed_node.source_id, weight.desc(), edge_id)` 还是确定性排序。这条查询没有 `LIMIT`，
截断发生在 `merge_case_memory_matches` 里（第 10 章 §10.6 讲过合并规则和四条一致性校验），但排序稳定
意味着**同一份数据每次产出同样的候选顺序**——评测数字可复现的前提。

## 11.11 指标聚合为什么必须放在数据库

`/metrics` 曝光五组指标，全部由 `aggregate_metrics` 的两条 GROUP BY 算出来：

```python
run_rows = (
    await self._session.execute(
        select(AgentRunRecord.status, func.count()).group_by(AgentRunRecord.status)
    )
).all()
span_rows = (
    await self._session.execute(
        select(
            RunTraceSpanRecord.kind,
            RunTraceSpanRecord.name,
            func.count(),
            func.sum(RunTraceSpanRecord.duration_ms),
            func.max(RunTraceSpanRecord.duration_ms),
            func.count().filter(RunTraceSpanRecord.status != TraceSpanStatus.ERROR.value),
        ).group_by(RunTraceSpanRecord.kind, RunTraceSpanRecord.name)
    )
).all()
```

docstring 里那句话是本章最值得抄进自己项目的一条：

> 聚合放在数据库而不是进程内计数器，是因为 Worker 与 API 可以是不同进程、还会重启：进程内计数器在
> 重启后归零，会让"**错误率突然下降**"这种最危险的假象出现在监控面板上。

进程内计数器（Prometheus client 的 `Counter` 那种）在单进程长驻服务里没问题。但这个系统有两个进程会
产生指标：Worker 执行 run，API 服务读请求。而且它们都会重启——部署、OOM、`docker compose up --build`。

"错误率突然下降"为什么比"归零"更危险？因为归零看起来像故障，会被人注意到。而错误率下降看起来像
**修复生效了**。一次重启之后面板显示错误率从 12% 掉到 0%，团队会以为上一个补丁起作用了，而实际情况是
计数器忘了过去。数据库里的行不会忘。

第二个理由是 span 聚合的索引：

> span 聚合按 `kind` + `name` 分组，正好命中 `ix_run_trace_spans_kind_name`，因此抓取频率不会随 span
> 总量线性劣化。

Prometheus 默认 15 秒抓一次。如果这条 GROUP BY 要全表扫描，span 攒到几十万行之后每次抓取都会变成一次
慢查询——**观测系统本身成为负载来源**。索引让它变成一次索引扫描。

### 11.11.1 `count().filter(...)` 算错误数

```python
func.count().filter(RunTraceSpanRecord.status != TraceSpanStatus.ERROR.value),
...
error_count=int(count) - int(ok_count),
```

`FILTER (WHERE ...)` 是 SQL 标准的聚合过滤子句。这里数的是**非错误**的 span，然后在 Python 里用总数减
出错误数。为什么绕这一圈，不直接 `count().filter(status == ERROR)`？

因为 `status` 除了 `ok` / `error` 还可能有别的值（比如 `cancelled`）。直接数 error 得到的是"error 的
数量"，而 `总数 - 非error` 得到的是"**不是明确非错误**的数量"。当未来加一个新的 status 值时，前者会把
它算成正常，后者会把它算成异常。对错误率这个指标来说，**把未知归到异常**是更安全的方向——一个新增的
未处理状态大量出现时，你希望面板报警，而不是静默地把它当成成功。

`duration_ms_sum` 和 `duration_ms_max` 用 `or 0.0` 兜住 NULL：`SUM` 在分组内所有值都是 NULL 时返回
NULL 而不是 0。span 的 `duration_ms` 在"已开始未结束"的行上是 NULL（表上有对应的 CheckConstraint 允许
这种中间态），所以这个兜底是必要的。

### 11.11.2 runtime 未装配时返回 503

`trace_and_metrics_routes_return_503_when_runtime_is_disabled` 和
`diagnosis_resource_routes_return_503_when_runtime_is_disabled` 守的是同一条规则：模型 disabled 或
PostgreSQL 缺失时，这些接口返回 503，**不返回全零**。

全零和"没数据"在监控上是两件完全不同的事。一个返回 `run_counts={}` 的 `/metrics` 会让 Prometheus 记录
一个合法的零值样本，面板显示"零错误、零延迟、系统健康"。返回 503 让抓取失败，`up` 指标掉到 0,
面板显示"目标不可达"——这才是真相。

这条规则在 CLAUDE.md 里被写成硬约束："runtime 未装配时两者都返回 503 而不是全零。"它跟 §11.5.5 的
"区分 run 不存在和无 span"、§11.8.3 的"区分未知 run 和暂无事件"是同一类判断：**空和不存在必须可区分**。

## 11.12 Alembic：线性单 head 与两个真实的坑

十次迁移，一条直线：

```text
0001 → 0002 → 0003 → 0004 → 20260716_0005(session_checkpoints)
     → 20260716_0006(diagnosis_worker) → 20260716_0007(run_cancellation)
     → 20260716_0008(documents) → 20260716_0009(run_trace_spans)
     → 20260716_0010(remediation_risk_level)
```

**线性单 head 是刻意的。** Alembic 支持分支（多个 head 再 merge），团队并行开发时很常见。这个项目
一个人写，分支只会带来"`alembic upgrade head` 报 Multiple head revisions"这种纯粹的自找麻烦。

### 11.12.1 文件名和 revision 不一致的陷阱

`20260716_0005_diagnosis_worker.py` 这个文件里写的是：

```python
revision = "20260716_0006"
```

文件名说 0005，内容说 0006。**Alembic 只认 `revision` 变量，完全不看文件名。**所以实际顺序里
`session_checkpoints` 是 0005，`diagnosis_worker` 是 0006——跟文件名的直觉相反。

CLAUDE.md 里专门为这件事留了一句："注意 `20260716_0005_diagnosis_worker.py` 的文件名与它内部的
`revision = "20260716_0006"` 不一致，按 revision 值而不是文件名判断顺序。"

这是那种"知道就没事、不知道就浪费一小时"的坑。改名会破坏已经跑过这条链的数据库里
`alembic_version` 表的记录吗？不会——那张表存的是 revision 值，不是文件名。但改名的收益只是消除困惑，
而任何改动都有风险，所以选择记录它而不是修它。

### 11.12.2 `env.py` 里那两条约束

`env.py` 的 docstring 有一段特别的说明——它解释的不是自己的代码，而是**为什么这段说明写在这里**：

> 两条约束记录在这里而不是 alembic.ini：
> 1. 数据库 URL 刻意不写进 ini。凭据只经 `DATAOPS_DATABASE_URL` 进入进程，因此不会被提交进版本控制，
>    也不会出现在迁移日志或 `alembic history` 输出里。
> 2. alembic.ini 必须保持纯 ASCII。Alembic 自身用 `encoding="locale"` 读取该文件，`fileConfig` 也再读
>    一遍，所以在中文 Windows（cp936）终端下，ini 里任何 CJK 字节都会让 `alembic upgrade head` 在连接
>    数据库之前就抛 UnicodeDecodeError；本文件是 Python 源码，永远按 UTF-8 解码，才是放中文说明的正确
>    位置。

第一条是标准做法：`sqlalchemy.url` 从配置读，不写 ini。

```python
settings = get_settings()
if settings.database_url is None:
    raise RuntimeError("DATAOPS_DATABASE_URL is required for migrations")
```

它的收益不止"不进 git"。`alembic history` 和迁移日志都会打印配置里的 URL——如果 ini 里有密码，
**每一次迁移的 CI 日志里都有一份明文凭据**。

第二条是这个项目实际踩过的坑，而且极难自己想到。链条是这样的：

1. Python 的 `configparser` 默认用 `locale` 编码读文件；
2. 中文 Windows 的 locale 编码是 cp936（GBK）；
3. `alembic.ini` 如果用 UTF-8 保存了中文注释，那些字节在 cp936 下解不出来；
4. `UnicodeDecodeError` 发生在 `fileConfig(config.config_file_name)` 这一行——**在任何数据库连接之前**。

表现出来的现象是 `alembic upgrade head` 抛一个跟数据库完全无关的编码错误，很容易被误诊为"数据库连不上"
或者"编码环境坏了"。解决办法不是改编码声明（configparser 不读 ini 里的编码声明），而是**不在 ini 里
写中文**。`env.py` 是 `.py` 文件，Python 3 永远按 UTF-8 解码源码，所以中文说明放这里是安全的。

### 11.12.3 在线模式用 `NullPool` 和 `run_sync`

```python
engine = create_async_engine(
    settings.database_url.get_secret_value(),
    poolclass=pool.NullPool,
)
try:
    async with engine.connect() as connection:
        # Alembic API 是同步的，run_sync 在同一异步连接上下文中完成安全桥接。
        await connection.run_sync(_run_migrations)
finally:
    # 即使迁移 SQL 失败也释放引擎，避免测试或容器重试遗留连接。
    await engine.dispose()
```

两个细节：

- **`NullPool`**：迁移是一次性任务，注释说"无需长期池化，NullPool 让每个连接在使用后立即关闭"。
  默认的 `QueuePool` 会保留空闲连接，而迁移进程马上就要退出——那些连接在 PostgreSQL 侧要等 TCP 超时
  才释放。在容器启动脚本 `alembic upgrade head && python -m app.persistence.seed` 里，这意味着 seed
  阶段要跟迁移遗留的连接抢配额。
- **`run_sync`**：Alembic 的 API 是同步的（`context.run_migrations()` 里全是同步调用），但引擎是异步的。
  `run_sync` 是 SQLAlchemy 提供的桥：它在 greenlet 里跑同步函数，把里面的同步 I/O 转成外层的 `await`。
  这是 §11.2.1 那个 `MissingGreenlet` 的**正向用法**——那个异常正是"不在 greenlet 里却需要 I/O"的报错。

`finally: await engine.dispose()` 保证迁移 SQL 失败也释放引擎。容器会重试启动，一次泄漏的连接乘以
重试次数就是连接数耗尽。

离线模式（`alembic upgrade head --sql`）保留了生成 SQL 的能力，`literal_binds=True` 让参数直接内联成
字面量。docstring 说它的用途是"便于审阅部署 SQL"——生产环境的 DBA 想在执行前看一遍 DDL 时用得上。
两种模式共享同一个 `target_metadata`，所以不会出现"离线生成的 SQL 和在线执行的不一样"。

`compare_type=True` 在两个模式里都开着。它让 `alembic revision --autogenerate` 能检测出列类型变化
（比如 `String(50)` 改成 `String(100)`）。默认是关的，因为不同数据库方言的类型比较容易误报——但这个项目
只支持 PostgreSQL，所以开着的收益（类型漂移能被发现）大于成本。

### 11.12.4 迁移 0007：为什么必须先 drop 再 create

给 `agent_runs` 加一个 `cancelled` 状态，直觉上是"改约束"。但 PostgreSQL 没有 `ALTER CHECK CONSTRAINT`，
只能删了重建。注释指出了顺序为什么关键：

```python
# 先移除旧约束，随后一次性安装新语义；否则 PostgreSQL 会在 UPDATE 阶段先拦截取消行。
op.drop_constraint("ck_agent_runs_status", "agent_runs", type_="check")
op.drop_constraint("ck_agent_runs_terminal_payload", "agent_runs", type_="check")
```

**两条约束都要先删。** 只删 `ck_agent_runs_status` 是不够的——`ck_agent_runs_terminal_payload` 的五支
里没有 `cancelled` 那一支，所以任何 `status='cancelled'` 的行都会被它拦住。两条约束都在描述状态，删一条
留一条会让升级后的第一次取消操作直接 `IntegrityError`。

这也说明了 §11.2.3 那条长约束的一个隐性成本：**它跟状态枚举耦合，每次加状态都要重写整条**。0007 的
`upgrade` 里那 18 行字符串就是重写的结果。这个成本是值得付的（它挡住了"completed 但没有 result"这类
故障），但要知道它存在。

### 11.12.5 `downgrade` 不删数据

回退到旧 Schema 时，那些 `cancelled` 行怎么办？旧约束不允许这个值，所以必须处理。最省事的写法是
`DELETE FROM agent_runs WHERE status='cancelled'`。这里没这么做：

```python
# 旧版本无法表达 cancelled；将其显式转换为失败而不是静默删除，保留审计语义。
op.execute(
    sa.text(
        "UPDATE agent_runs SET status='failed', error_code='cancellation_migration_downgrade', "
        "error_message='取消状态因数据库版本回退被转换为失败。', "
        "started_at=COALESCE(started_at, created_at), "
        "completed_at=COALESCE(completed_at, now()), "
        "attempt_count=GREATEST(attempt_count, 1), updated_at=now(), "
        "lease_owner=NULL, lease_expires_at=NULL WHERE status='cancelled'"
    )
)
```

docstring：

> 旧版 Schema 无法表达 cancelled，回退时显式保存迁移错误码和结束时间，避免删除用户操作记录或留下违反
> 旧约束的 queued/running 行。

三点值得学：

- **`error_code='cancellation_migration_downgrade'`** 是一个专用错误码，不是复用 `user_cancelled`。
  回退之后看到这个码的人立刻知道"这条 run 的真实状态是取消，是版本回退把它变成失败的"。信息没丢，
  只是换了表达。
- **`COALESCE` 和 `GREATEST`** 处理的是 §11.7.2 那两种 cancelled 形态。一个 queued-cancel 的行
  `started_at IS NULL` 且 `attempt_count=0`，但旧约束的 `failed` 那一支要求
  `started_at IS NOT NULL AND attempt_count >= 1`。`COALESCE(started_at, created_at)` 和
  `GREATEST(attempt_count, 1)` 把它补成合法形态。**如果不补，重建约束那一步会失败，整个 downgrade
  回滚**——一个"回退脚本本身跑不了"的死局。
- **`WHERE status='cancelled'`** 让这条 UPDATE 只碰需要碰的行。它也让 downgrade 可重复执行：第二次跑
  没有 cancelled 行，UPDATE 影响 0 行。

写一个真的能跑的 `downgrade` 是很多项目省略的一步（直接 `pass` 或者 `raise NotImplementedError`）。
这里写全的价值不在于真的会回退，而在于**写 downgrade 的过程会强迫你想清楚新状态和旧状态的映射关系**——
0007 的这段 SQL 实际上是对"cancelled 到底是什么"的一次形式化回答。

## 11.13 引擎与会话：四个函数里的三个决定

`app/persistence/database.py` 只有 64 行、四个函数，但每一个都有一个明确的取舍。

### 11.13.1 `pool_pre_ping=True`

```python
return create_async_engine(database_url, pool_pre_ping=True)
```

docstring：

> `pool_pre_ping` 可在容器重启或空闲连接失效后先执行轻量探测，减少把断连暴露为业务查询错误。

连接池里的连接会失效——PostgreSQL 重启、`docker compose restart db`、网络中断、
`idle_session_timeout` 生效。没有 pre-ping 时，池子把一个已死的连接借出去，第一条业务 SQL 收到
`ConnectionDoesNotExistError`。用户看到的是"诊断失败"，而实际情况是"这次借到了一个坏连接，重试就好"。

pre-ping 让池子在借出前先发一个极轻量的探测，失败就丢弃这个连接、换一个新的。代价是每次借出多一次
往返（本地数据库通常 <1ms），收益是数据库重启不会造成一批业务错误。对一个会被 `docker compose up`
反复重启的演示项目，这个交换明显值得。

### 11.13.2 `expire_on_commit=False` 与 §11.2.1 是同一件事

```python
return async_sessionmaker(engine, expire_on_commit=False)
```

docstring：

> `expire_on_commit=False` 让提交后已加载字段仍可用于响应组装，避免离开事务后触发隐式异步查询。

SQLAlchemy 默认在 commit 之后把所有 ORM 对象标记为过期，下次属性访问会重新 SELECT。同步栈里这只是
一次额外查询；异步栈里它是 `MissingGreenlet`——跟 §11.2.1 的 `eager_defaults` 完全相同的失败模式，只是
触发时机从"flush 之后"变成"commit 之后"。

这两个设置合起来才完整：

- `eager_defaults=True` 处理 **INSERT 之后**读 `server_default` 列（用 `RETURNING` 取回）；
- `expire_on_commit=False` 处理 **commit 之后**读任何列（不标记过期）。

`complete_run` 返回 `_run_from_record(record)`，而调用方 `_execute_traced_run` 在 `async with begin()`
块**结束之后**（也就是 commit 之后）还要用这个快照构造 API 响应。没有 `expire_on_commit=False`，那次
使用就会崩。

顺便注意：这也是为什么仓储方法返回**冻结的 Pydantic 领域对象**而不是 ORM 行（§11.9）。领域对象跟
session 生命周期完全解耦，即使这两个设置被人改回默认值，返回值本身也不会突然需要 I/O。

### 11.13.3 `session_scope` 刻意不自动提交

```python
# 只管理资源生命周期，不隐式提交；事务语义必须留在了解业务原子性的调用层。
async with factory() as session:
    yield session
```

很多项目的 `get_db()` 依赖长这样：`try: yield session; session.commit() except: rollback()`。这里不
这么写，docstring 给了理由：

> 调用方显式决定 commit 或 rollback，避免通用基础设施把部分失败写入数据库。

"部分失败"是关键词。一个请求处理器做了三件事，第二件抛了异常但被上层某处捕获并转成了一个降级响应。
自动提交的版本会把第一件事的写入提交进数据库——一个只完成了三分之一的操作。基础设施层不知道这三件事
是不是必须原子，只有业务代码知道。

真正需要原子性的地方都用显式的 `async with self._session_factory.begin()`（§11.3.2、§11.5.2）。
`begin()` 的语义是明确的：正常退出 commit，异常退出 rollback。而 `factory()`（不带 `begin`）的语义是
"给我一个会话，事务我自己管"。两个入口对应两种意图，不混。

### 11.13.4 `check_database_connection` 的边界声明

```python
async with engine.connect() as connection:
    await connection.execute(text("SELECT 1"))
```

docstring 里有一句自我限定值得注意：

> 它不验证迁移和种子完整性，后续图计数查询承担那部分检查。

`SELECT 1` 能证明的只有"能连上、能执行"。它证明不了表存在、迁移跑过、种子写进去了。把这个限制写出来
是为了防止有人看到 `/health` 返回 ok 就以为数据库是完整的——lifespan 里紧跟着的图计数查询才是那道检查。

## 11.14 seed：幂等、单事务、从数据库回数

`seed_database` 是容器启动链的第二步（`alembic upgrade head && python -m app.persistence.seed`）。
90 行里有四个决定。

### 11.14.1 连接数据库之前先校验文件

```python
# 在连接数据库前完成文件与图引用校验，让坏种子以更清晰、低成本的错误提前失败。
bundle = load_knowledge_seed(settings.knowledge_seed_file)
library = load_document_library(settings.document_manifest_file)
```

顺序是：读 JSON/Markdown → 过 Schema 校验 → 校验图引用（边的两端节点必须存在）→ 生成 embedding →
才连数据库。

如果反过来先连库，一个 JSON 里的拼写错误会在事务中间被发现，错误信息混着 SQLAlchemy 的堆栈。更实际的
问题是**顺序决定了失败成本**：embedding 是付费的远程调用，而图引用校验是免费的本地检查。把免费的检查
放前面，意味着一个坏种子文件不会先烧掉一轮 embedding 配额。

### 11.14.2 知识图和文档语料在同一个事务

模块 docstring 里这段是本节的核心：

> 知识图与文档语料在同一个事务里提交，避免出现"图已就绪但文档缺失"的中间状态——那种状态下检索仍会返回
> 结果，只是永远少了一条通道，而这在演示时几乎不可能被发现。

这是全章最好的一个"部分成功比彻底失败更危险"的例子。GraphRAG 有两条检索通道：知识图谱和文档 RAG
（`document-retrieval:v1`）。如果图写成功了、文档写失败了：

- 检索**不报错**——图通道正常返回节点；
- 报告**能生成**——有引用、有根因、格式完全正确；
- 只是**永远少一条通道**的证据。

演示的时候你看不出来。评测的时候你会看到 `fault_path_completeness` 之类的指标偏低，然后开始怀疑
是不是模型不行、是不是阈值配错了——第 10 章 §10.10 那个 `evidence_bundle` 事故就是这个形状。同一个
事务把这种状态变成不可能：要么两者都在，要么 API 启动失败。

```python
# 节点必须先于边写入，整个 Bundle 只提交一次以保证图结构原子可见。
await repository.upsert_seed_bundle(embedded_bundle)
await document_repository.upsert_document_library(embedded_library)
await session.commit()
```

一次 `commit()`，两个仓储。注释还提了内部顺序：节点先于边——边有外键指向节点，反过来会直接违反外键。

### 11.14.3 提交后从数据库回数

```python
# 提交后计数验证数据库实际状态，而不是简单回报输入文件中的元素数量。
node_count, edge_count = await repository.count_graph()
document_count, chunk_count = await document_repository.count_documents()
return node_count, edge_count, document_count, chunk_count
```

`len(bundle.nodes)` 是现成的，为什么要多查一次数据库？

因为 upsert 是幂等的。第二次启动时，`upsert_seed_bundle` 写的是同样的 20 个节点，返回的输入长度还是
20——但数据库里可能有 25 个（比如上一版种子有 5 个节点后来被删了，upsert 不会删除它们）。**输入长度
描述的是"我打算写什么"，数据库计数描述的是"现在实际有什么"。**容器日志和健康检查要的是后者。

docstring 补了一句边界：**"返回计数用于容器日志和健康验证而不暴露知识正文。"**计数是安全的可观测量，
节点内容不是。

### 11.14.4 显式释放 embedding provider 和引擎

```python
# 远程 Provider 持有 httpx 连接池；种子是短进程，向量生成完成后立刻释放而不是等解释器退出。
if hasattr(embedding_provider, "aclose"):
    await embedding_provider.aclose()
```

`hasattr` 检查是因为 provider 有多个实现——确定性替身（评测和测试用）没有 HTTP 连接池，不需要
`aclose`。用 `hasattr` 而不是 `isinstance` 是鸭子类型的正确用法：关心的是"能不能关"，不是"是哪个类"。

```python
finally:
    # 命令行脚本是短进程，显式 dispose 可让失败路径也干净关闭 asyncpg 连接。
    await engine.dispose()
```

跟 §11.12.3 的 `env.py` 是同一个模式。这两个都是短进程、都在容器启动链里、都会因为失败被重试——
泄漏的连接会累积。

`main()` 的 docstring 点明了退出码的作用：

> 任何异常保持非零退出，让 Docker 启动链在迁移或种子失败时停止，而不是继续启动一个知识图不完整的 API。

`alembic upgrade head && python -m app.persistence.seed && uvicorn ...` 里的 `&&` 依赖退出码。
`asyncio.run` 让异常正常传播、进程非零退出、`&&` 短路——API 不会启动。这比"启动一个知识图空着的 API
然后在 `/health` 里报告不健康"更好：后者会让一个坏部署看起来是活的。

## 11.15 本章的取舍清单

| 决定 | 放弃了什么 | 换到了什么 | 出处 |
|---|---|---|---|
| PostgreSQL 作为唯一状态服务 | 专用队列/向量库/图库的性能上限 | 跨领域写入可以放进同一事务 | 本章开头 |
| 数据库约束重复 Pydantic 契约 | 一份规则维护两遍 | 绕过应用代码的写入也被挡住 | §11.2 |
| `eager_defaults=True` | 无（PostgreSQL 用 RETURNING，不多一次往返） | 异步栈不会因读 `server_default` 列抛 `MissingGreenlet` | §11.2.1 |
| 所有 `updated_at` 不用 `onupdate` | 写入方必须每次显式传 `now` | 审计时间戳由注入时钟决定，租约校验与 JSONB 比对可复现 | §11.2.2 |
| 把五状态机写进 CheckConstraint | 每次加状态要重写整条约束 | "completed 但 result 为 NULL"这类行根本写不进去 | §11.2.3 / §11.12.4 |
| 部分唯一索引限制单 session 活跃 run | 一个 session 无法并行诊断 | checkpoint 版本单调、追问顺序确定，冲突只花一次 409 | §11.2.4 |
| 数据库队列 + `FOR UPDATE SKIP LOCKED` | 跨机器扩展能力、优先级队列等高级特性 | 零额外中间件，入队与业务写入同事务 | §11.3.1 |
| 领取事务与执行严格分离 | 执行期间 run 行不受锁保护（靠租约） | 连接不被长占、行锁不阻塞取消、无 idle-in-transaction 风险 | §11.3.2 |
| 允许领取过期 running（限 2 次） | 极端情况下同一 run 被执行两次的窗口 | Worker 崩溃不会让 session 永久卡在 409 | §11.3.3 |
| `started_at` 只在首次领取写 | 无法直接得到"最后一次尝试耗时" | `completed_at - started_at` 就是用户端到端等待 | §11.3.4 |
| 心跳必须 < 租约一半（构造期校验） | 配置自由度 | 单次心跳失败可由下一次补救，不产生偶发重复执行 | §11.4.1 |
| `asyncio.wait` 而非 `wait_for` | 没有执行超时上限 | 诊断可跑任意长，心跳独立于执行时长 | §11.4.2 |
| 条件 UPDATE 续租（看 rowcount） | 无法区分"被接管"和"已终态" | 检查与写入原子，两个 Worker 之间无竞态 | §11.4.3 |
| 心跳不写 `run_events` | 无法从时间线看出续租历史 | 用户看到的四五条业务事件不被基础设施噪声淹没 | §11.4.3 |
| reaper 放在每次 `run_once` 开头 | 每轮多一条 UPDATE | 不需要额外调度器，Worker 活着就持续修复卡住的 run | §11.4.4 |
| `_run_loop` 吞掉非 `CancelledError` 异常 | 单次故障的细节只在进程日志里 | 一次数据库抖动不会杀掉 Worker；traceback 不进 API | §11.4.5 |
| 终态 + 事件 + checkpoint + trace 同事务 | 一次提交的事务更大 | 轮询者永不看到"completed 但没有时间线" | §11.5.2 |
| 根 span 在最终提交**之前**关闭 | trace 里少了 commit 本身的耗时 | trace 与 run 终态严格同事务，不会出现"有 span 没终态" | §11.5.2 |
| `fail_run` 要求 `sequence=1` 的 system 事件 | 失败 run 无法保留部分时间线 | 阻止把部分成功的时间线伪造成失败 | §11.5.3 |
| span 归属校验放 Python 而非只靠外键 | 多一次显式判断 | 外键证明不了"A 的 span 没被记到 B 名下" | §11.5.4 |
| checkpoint 用显式字段清单 | 每加一个要恢复的字段都得改代码 | 未来给 `AgentState` 加敏感字段不会被自动持久化 | §11.6.2 |
| checkpoint 是有界滚动窗口（六个上限） | 很老的证据会被丢弃 | JSONB 行、检索查询、恢复校验都有确定上限 | §11.6.1 |
| 恢复时归零七个瞬态字段 | 追问无法"接着上一轮的步数继续" | 预算、终止原因、审计裁决、记忆候选都不污染新 run | §11.6.3 |
| checkpoint 版本必须恰好 +1 | 基于旧快照完成的并发 run 会失败 | 失败信息精确指出"你基于过期快照在写" | §11.6.6 |
| JSONB 与关系列冗余存储并每次比对 | 存两份、读时多几次判断 | 只改一边的污染无法把错误上下文恢复到下一轮 | §11.6.7 |
| 取消先返回终态快照而不抛异常 | 客户端要自己判断 status | Worker 已完成时用户拿到的是报告，不是"取消失败" | §11.7.1 |
| resume 是 run 级不是节点级 | 被取消那部分工作真的白做 | 恢复语义完全确定，不存在"半个状态被恢复" | §11.7.3 |
| 序号连续性检查三层 | 同一条规则写三遍 | 缺口、重复、替身漂移各有一层能挡 | §11.8.1 |
| `list_events_after` 返回裸元组 | 增量路径没有列表模型包装 | 全量接口保留最强的"1..N"约束 | §11.8.2 |
| 每次读都重过 Pydantic / 枚举 | 每次读多一点 CPU | 契约升级后的旧 payload 显式失败而不是静默残缺 | §11.9.1 |
| `get_run` 不加载事件 | 想同时拿两者要发两个请求 | 最高频的轮询接口只搬一行；失败面独立 | §11.9.4 |
| advisory lock 用事务级变体 | 锁范围不能跨事务 | commit/rollback 自动释放，异常路径不泄漏锁 | §11.10.1 |
| 先查精确签名再算向量 | 多一条 SQL | 最高频的复发故障完全不碰付费 embedding | §11.10.2 |
| 图分数 = 种子相似度 × 边权 | 图扩展无法逆转排序 | 互相相似的旧案例不能凭结构获得高排名 | §11.10.6 |
| 指标聚合放数据库 | 每次抓取一条 GROUP BY | 进程重启不会让"错误率突然下降" | §11.11 |
| 错误数 = 总数 − 非错误数 | 多一次减法 | 未来新增的未知 status 被算成异常而不是成功 | §11.11.1 |
| Alembic 保持线性单 head | 无法并行开发迁移 | 永远不会遇到 multiple heads | §11.12 |
| 数据库 URL 不写 `alembic.ini` | 每次迁移都依赖环境变量 | 凭据不进版本控制、不进 `alembic history` 输出 | §11.12.2 |
| `alembic.ini` 保持纯 ASCII | 中文说明只能放 `env.py` | cp936 终端下 `alembic upgrade head` 不会因编码先崩 | §11.12.2 |
| `downgrade` 转换而非删除 cancelled 行 | 回退脚本更长 | 用户操作记录不丢，且回退本身不会因违反旧约束失败 | §11.12.5 |
| `session_scope` 不自动提交 | 每个调用点都要写 commit | 基础设施层不会把部分失败写进数据库 | §11.13.3 |
| 知识图与文档语料同事务 | 种子事务更大 | 不会出现"检索能跑但永远少一条通道"的隐性缺陷 | §11.14.2 |
| 计数从数据库读而非用输入长度 | 多两条 COUNT | 日志反映数据库实际状态，不是"我打算写什么" | §11.14.3 |

## 11.16 遗留问题

诚实记录这一层还没解决的东西。

1. **单 Worker，没有真正验证过多副本分工。** `SKIP LOCKED` 的语义保证多个 Worker 能分工，
   `postgres_diagnosis_resources_persist_success_failure_and_events` 也在真库上跑过，但从来没有真的
   同时起过三个 Worker 进程去抢队列。理论正确和实测正确之间还差一次实验。

2. **崩溃恢复只在逻辑上成立。** §11.3.3 那条"过期 running 可被领取"的路径没有被真实的进程 kill 测试
   覆盖过——测试用的是注入的合成时钟把租约推到过期，而不是真的 `docker kill` 一个 Worker。两者的差别
   在于真实崩溃可能发生在任何一条语句之间，包括 `complete_run` 事务提交的瞬间。

3. **`max_attempts=2` 是猜的。** §11.3.3 讲的推理（一次可能是抖动、两次就该认定任务本身有问题）是合理
   的，但这个数字没有任何实测支撑。真实系统会根据"崩溃原因中基础设施抖动占比"来定，这个项目没有那个
   数据。

4. **root span 缺少提交耗时。** §11.15 表里那一行是个已知的、被文档化的不准确：trace 显示的总耗时不含
   最后那次事务提交。对一个 60–120 秒的诊断来说这点误差无关紧要，但如果将来要用 trace 精确归因 P95，
   得先修这个。

5. **checkpoint 的六个上限没有基于真实会话长度调过。** 16/16/64/64/32/128 这组数字是"看起来够用"的量级。
   没有数据说明真实追问会话平均积累多少证据，所以也不知道这些上限是过紧（丢了有用上下文）还是过松
   （JSONB 白占空间）。

6. **`hashtext` 碰撞概率没有量化。** §11.10.1 说碰撞只导致多一点串行、不影响正确性——这个论断是对的，
   但"多一点"具体是多少取决于实际组件组合数。当前只有三个组件（7 种非空子集），碰撞概率可以忽略；
   如果组件数增长到几十个，值得换成一个真正的分配式锁键。

7. **没有归档策略。** `run_events`、`run_trace_spans`、`agent_runs` 只增不减。一个长期运行的实例会让
   §11.11 的 GROUP BY 越来越慢，即使有索引。生产系统会有分区表或定期归档，这里没有。

## 11.17 小结

这一层的核心论点只有一句：**把状态放进一个支持事务的数据库，然后让约束表达业务规则。**

从这句话展开出来的东西比看起来多：

- 队列不需要中间件（§11.3），因为 `SKIP LOCKED` 已经解决了多消费者竞争，而事务性是外部队列给不了的；
- 租约不需要分布式协调服务（§11.4），因为条件 UPDATE 的 rowcount 就是一次原子的 compare-and-swap；
- 状态机不需要一个"状态机框架"（§11.2.3），因为一条 CheckConstraint 能把五个状态各自的合法字段组合
  完整表达出来，而且对绕过应用的写入同样生效；
- 上下文恢复不需要序列化整个执行状态（§11.6），因为只在 run 边界恢复的语义是确定的，而显式字段清单
  同时是一道防止未来泄露的门禁。

反过来，代价也集中在一处：**所有并发正确性都压在 SQL 上**。这一章反复出现的机制——`FOR UPDATE`、
`SKIP LOCKED`、部分唯一索引、advisory lock、CheckConstraint、条件 UPDATE 的 rowcount——每一个都需要
知道它精确的语义边界。`FOR UPDATE` 和 `FOR UPDATE SKIP LOCKED` 差一个词，行为差一个惊群；
`pg_advisory_lock` 和 `pg_advisory_xact_lock` 差三个字母，差一次锁泄漏。这些知识没法靠"框架帮我处理"
绕过。

还有一条贯穿全章的判断，值得单独记住：**空和不存在必须可区分**。它出现了四次——
`list_trace_spans` 区分"run 不存在"和"无 span"（§11.5.5）、`list_events` 区分"未知 run"和"暂无事件"
（§11.8.3）、`/metrics` 在 runtime 未装配时返回 503 而不是全零（§11.11.2）、`seed` 的计数从数据库读
而不是用输入长度（§11.14.3）。每一次的错误形态都一样：一个合法的空值让调用方以为系统正常，然后基于
错误前提继续。这跟第 10 章 §10.10 的"指标读到 0 先看分母是不是空的"是同一条经验的不同侧面。

**第 12 章转向对外接口**：`app/api/` 的路由与鉴权（`api-auth:v1` 那个 ASGI 前缀中间件、限流为什么必须
先于鉴权、三种失败为什么共享逐字相同的 401）、`app/observability/` 的两个出口（进程内的
`model-call-metric:v1` 和落库的 `run-trace:v1` 有什么区别）、`run-stream:v1` 的 SSE 推流如何用标准
`id` 字段复用 `Last-Event-ID`，以及那条被公开声明的限制——浏览器 `EventSource` 不能带请求头，所以
bearer 模式下推流必然 401。
