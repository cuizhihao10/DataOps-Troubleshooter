# 第 1 章 领域契约：先把不可协商的数据形状钉死

## 1.1 你会验证什么

```bash
.venv/Scripts/python -m pytest -q tests/unit/test_domain_models.py tests/unit/test_planner_contract.py
```

这一章读完，你要能回答三个问题：为什么这个项目的"报告"不是一段文本而是一棵强类型树；为什么
`AgentState` 里**故意没有** `thought` 字段；为什么 Planner 的停止原因必须是枚举而不是自由文本。

## 1.2 为什么从契约开始，而不是从"跑起来"开始

多数 Agent 教程的入口是"让模型调用一个函数"。那种写法能跑，但一旦要回答"这条结论凭什么"，就没有
地方可查——模型返回的是字符串，字符串里没有引用，引用不存在就没法审计。

本项目反过来：先规定所有节点之间**只能**传递哪些 Pydantic 模型，且这些模型自带跨字段校验。于是
"无来源的结论"在数据结构层就构造不出来，不需要靠 Prompt 提醒模型守规矩。

给 Java 读者的对照：Pydantic 的 `BaseModel` 相当于带校验的 DTO/Record，`model_validator(mode="after")`
相当于构造完成后自动执行的不变量检查（类似 Bean Validation 的 `@AssertTrue`，但它抛异常而不是收集
错误）。`ConfigDict(extra="forbid")` 相当于反序列化时遇到未知字段直接失败——Jackson 默认是忽略，
这里刻意选择失败。

## 1.3 九个只读工具的白名单：`app/domain/tooling.py`

第一个契约是"系统到底能做什么"。它不是文档里的一句话，而是一个枚举：

```python
class ToolName(StrEnum):
    LTS_GET_TASK_STATUS = "lts.get_task_status"
    LTS_GET_TASK_LOG = "lts.get_task_log"
    LTS_GET_DEPENDENCY_TOPOLOGY = "lts.get_dependency_topology"
    BDS_GET_TASK_STATUS = "bds.get_task_status"
    BDS_GET_TASK_LOG = "bds.get_task_log"
    BDS_GET_TABLE_INFO = "bds.get_table_info"
    FLASHSYNC_GET_SYNC_DELAY = "flashsync.get_sync_delay"
    FLASHSYNC_GET_SYNC_LOG = "flashsync.get_sync_log"
    FLASHSYNC_CHECK_CONSISTENCY = "flashsync.check_consistency"
```

`StrEnum` 是 Python 3.11 引入的枚举基类：成员既是枚举又是 `str`，因此可以直接进 JSON、直接拼进
Prompt、直接写进数据库列，不需要在边界上手工 `.value`。

这九个名字是**同一个来源**，同时约束四层：Planner 的 Action、Fixture 数据、MCP 服务端注册表、集成
测试。任何一层想改名或加工具，都会在另外三层立刻失败。这是本项目最常用的一种手法——**把"约定"变成
"唯一定义 + 多处比对"**，后面第 2 章的契约 ID 门禁是同一手法的放大版。

注意工具名的动词全是 `get`/`check`：**没有任何写操作**。整个系统不实现自动重跑、扩容、删表或修复。
这不是能力不足，是范围声明：只读工具让"Agent 出错"的最坏后果限制在"给出错误建议"，而不是"改坏
生产"。

## 1.4 错误分类决定重试策略

```python
class ToolErrorCode(StrEnum):
    INVALID_REQUEST = "INVALID_REQUEST"
    EMPTY_RESULT = "EMPTY_RESULT"
    TIMEOUT = "TIMEOUT"
    PERMISSION_DENIED = "PERMISSION_DENIED"
    SERVICE_UNAVAILABLE = "SERVICE_UNAVAILABLE"
    INTERNAL_ERROR = "INTERNAL_ERROR"

RETRYABLE_TOOL_ERRORS: frozenset[ToolErrorCode] = frozenset(
    {ToolErrorCode.TIMEOUT, ToolErrorCode.SERVICE_UNAVAILABLE}
)
```

只有两类错误可重试。判断标准写在模块 docstring 里，值得抄下来当面试答案：

> 只有超时和暂时不可用属于瞬时错误，权限拒绝、空结果和非法请求不会因重复调用而增加信息。

这句话把"重试"从一个体力活变成了一个语义判断：重试的意义是**获得新信息**。`EMPTY_RESULT` 重试一百
次还是空，`PERMISSION_DENIED` 重试只会浪费预算并给对端制造压力。很多生产事故来自对 4xx 类错误
无脑重试。

把可重试集合定义成 `frozenset` 常量而不是写在执行器里的 `if err in (...)`，好处是执行器、评测和测试
读的是同一个集合，不会各写一份。

## 1.5 请求外壳：为什么九个工具共用一个参数模型

```python
class McpToolRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")

    resource_id: str = Field(min_length=1, max_length=200)
    time_range: TimeRange
    scenario_id: str = Field(pattern=r"^[a-z0-9][a-z0-9_-]{2,79}$")
    trace_id: str = Field(min_length=3, max_length=100)
```

四个字段各有明确职责：`resource_id` 指定调查对象，`time_range` 限制观察窗口，`scenario_id` 选择合成
数据快照，`trace_id` 把一次诊断的所有调用串起来。

统一外壳的收益在 Planner 侧：模型只需要学一种参数形状，九个工具都能调。如果每个工具一套参数，
Structured Outputs 的 Schema 会变成九选一的 union，模型出错率和 Schema 复杂度同时上升。

`scenario_id` 用正则约束成小写标识符（首字符必须是字母数字，长度 3–80）。这既是数据校验，也是安全
边界：它会被用来定位 Fixture 文件，宽松的字符集会带来路径穿越风险。

## 1.6 时间必须带时区：一条小校验背后的大问题

```python
class TimeRange(BaseModel):
    start: datetime
    end: datetime

    @model_validator(mode="after")
    def validate_range(self) -> TimeRange:
        # 时区完整性属于可审计性约束，应在任何大小比较前明确验证。
        if self.start.tzinfo is None or self.end.tzinfo is None:
            raise ValueError("time_range values must include a timezone")
        if self.end <= self.start:
            raise ValueError("time_range.end must be later than time_range.start")
        return self
```

顺序很讲究：**先查时区，再比大小**。两个 naive datetime（无时区）当然可以比较，但比较结果无法映射到
统一时间线——容器用 UTC、宿主用 Asia/Shanghai，同一个字符串代表不同瞬间。项目的 Golden 案例里正好
有一条真实的时区故障（`WATERMARK_TIMEZONE_MISMATCH`：源事件时间是 UTC、水位线按 Asia/Shanghai 解释、
偏移 480 分钟、静默跳过 900 条），所以这条校验不是洁癖，是被案例逼出来的。

`end <= start` 被拒绝而不是被容忍：零长度窗口会让工具返回"空结果"，而空结果在诊断里是一个**有含义
的事实**（"这段时间确实没有日志"）。如果参数错误也表现为空结果，两者就分不开了。

## 1.7 响应外壳：`ok` 是唯一分支开关

```python
class McpToolResponse(BaseModel):
    ok: bool
    data: dict[str, Any] = Field(default_factory=dict)
    evidence: list[ToolEvidencePayload] = Field(default_factory=list)
    error_code: ToolErrorCode | None = None
    error_message: str | None = Field(default=None, max_length=1000)
    observed_at: datetime

    @model_validator(mode="after")
    def validate_success_or_error(self) -> McpToolResponse:
        if self.observed_at.tzinfo is None:
            raise ValueError("observed_at must include a timezone")
        # `ok` 是唯一分支开关，错误字段必须与它保持严格互斥才能安全自动化。
        if self.ok and (self.error_code is not None or self.error_message is not None):
            raise ValueError("successful responses cannot include error fields")
        if not self.ok and (self.error_code is None or not self.error_message):
            raise ValueError("failed responses require error_code and error_message")
        return self
```

这条校验保证了两件事：

1. **失败响应不可能携带 Evidence。** 因为失败必须有 `error_code`，而执行器对失败响应不生成 Evidence
   （第 3 章会看到）。错误消息不是业务事实——"查询超时"不能作为"任务失败的原因"被引用。项目里有
   一条 Golden 案例专门测这个：三个工具中日志工具返回不可重试的 `EMPTY_RESULT`，报告必须保留另外两个
   成功来源、以 `evidence_insufficient` 停止、根因留空。
2. **执行器只看 `ok` 和 `error_code` 就能决定重试**，不需要解析文本、也不需要处理"既成功又失败"的
   矛盾状态。

一个容易被忽略的点：`ok=true` 只代表**协议传输成功**，不代表业务读取成功。项目里那条源端授权过期的
跨组件案例，六个 MCP 响应全部 `ok=true`，因为 FlashSync 确实正常回答了"我读不到源端"。把业务失败
塞进协议失败会让"协议是否健康"和"业务是否健康"两个信号混在一起。

## 1.8 `ToolEvidencePayload` 与 `Evidence`：为什么要两个模型

服务端返回 `ToolEvidencePayload`：只有 `source_id`、`content`、`metadata`。

领域层的 `Evidence` 多了三个字段：`evidence_id`、`source_type`、`reliability`。

```python
class Evidence(BaseModel):
    evidence_id: str = Field(min_length=1, max_length=100)
    source_type: EvidenceSourceType
    source_id: str = Field(min_length=1, max_length=200)
    content: str = Field(min_length=1, max_length=4000)
    observed_at: datetime
    reliability: float = Field(ge=0, le=1)
    metadata: dict[str, Any] = Field(default_factory=dict)
```

差别是刻意的：**可靠性和引用 ID 是审计属性，不能由被审计方自己声明。** 如果 MCP 服务端可以自己说
"我这条证据可靠性 0.99"，那么可靠性就失去了意义。这些字段由客户端的 Observation 适配器按确定性
规则补齐（第 3 章）。

`EvidenceSourceType` 有五档：

```python
TOOL = "tool"
KNOWLEDGE_NODE = "knowledge_node"
GRAPH_PATH = "graph_path"
DOCUMENT_CHUNK = "document_chunk"
CASE_MEMORY = "case_memory"
```

区分来源类型是为了让 Auditor 能按"时效性"审查引用：`TOOL` 是本次实时观察，`CASE_MEMORY` 是历史。
第 9 章的审计规则里有一条"关键结论必须至少有一条实时支撑引用"，它就是靠这个枚举实现的——否则模型
只要复述知识库就能拿满引用分。

`DOCUMENT_CHUNK` 单独成类而不并入 `KNOWLEDGE_NODE`，源码注释给了理由：两者核查方式不同，节点要核对
`source_span`，切片要核对"哪份文档的哪一节"。

## 1.9 报告不是文本，是一棵带引用的树

这是本项目最值得学的契约设计。`DiagnosisReport` 的每个字段都是结构化的：

```python
class DiagnosisReport(BaseModel):
    summary: str = Field(min_length=1, max_length=4000)
    fault_chain: list[FaultChainStep] = Field(default_factory=list)
    root_causes: list[RootCauseConclusion] = Field(default_factory=list)
    evidence_refs: list[str] = Field(default_factory=list)
    remediation_steps: list[RemediationStep] = Field(default_factory=list)
    risks: list[str] = Field(default_factory=list)
    uncertainties: list[str] = Field(default_factory=list)
    similar_cases: list[SimilarCaseReference] = Field(default_factory=list)
```

关键在于叶子节点。根因不是字符串：

```python
class RootCauseConclusion(BaseModel):
    root_cause: str = Field(min_length=1, max_length=1000)
    confidence: float = Field(ge=0, le=1)
    evidence_refs: list[str] = Field(min_length=1)
```

`min_length=1` 加在 `evidence_refs` 上，意味着**无引用的根因在 Python 层就构造不出来**。这比"Prompt 里
要求模型给引用"强一个数量级：前者是不变量，后者是建议。

链路同理：

```python
class FaultChainStep(BaseModel):
    description: str = Field(min_length=1, max_length=2000)
    evidence_refs: list[str] = Field(min_length=1)
```

源码注释解释了它替换掉了什么：

> 旧的自由文本列表无法判断某一段链路是否有依据；本模型把描述与至少一个 evidence_id/path_id 绑定。

也就是说，`fault_chain: list[str]` 是这个项目**曾经的**写法，被换掉的原因是无法验证。

## 1.10 高风险建议的三重保护

`RemediationStep` 是唯一带条件校验的报告子模型：

```python
class RemediationStep(BaseModel):
    order: int = Field(ge=1)
    action: str = Field(min_length=1, max_length=2000)
    risk_level: RiskLevel
    evidence_refs: list[str] = Field(default_factory=list)
    prerequisites: list[str] = Field(default_factory=list)
    rollback: str = Field(min_length=1, max_length=2000)
    verification: str = Field(min_length=1, max_length=2000)

    @model_validator(mode="after")
    def validate_high_risk_controls(self) -> RemediationStep:
        # 高风险操作对错误根因更敏感，因此必须先证明必要性，再说明执行前置条件。
        if self.risk_level is RiskLevel.HIGH:
            if not self.evidence_refs:
                raise ValueError("high-risk remediation requires evidence references")
            if not self.prerequisites:
                raise ValueError("high-risk remediation requires prerequisites")
        return self
```

`rollback` 和 `verification` 对**所有**等级都强制非空（字段级 `min_length=1`），`evidence_refs` 和
`prerequisites` 只对 `high` 强制。这个不对称是有理由的：低/中风险大多是只读检查（"看一眼配额"），
要求它引用证据没有意义；而 high 操作（比如"按缺失窗口小批量回补数据"）一旦根因判断错误，代价是
不可逆的。

`validate_remediation_order` 要求 `order` 从 1 连续编号：

```python
orders = [step.order for step in self.remediation_steps]
if orders and orders != list(range(1, len(orders) + 1)):
    raise ValueError("remediation order must be consecutive starting at one")
```

空列表被允许——这是**降级报告**的形状（证据不足时没有建议）。`if orders and ...` 这个短路很重要：
如果写成无条件校验，所有降级报告都会构造失败。

## 1.11 历史案例引用：相似不等于等价

`SimilarCaseReference` 的校验器是全项目最"啰嗦"的一个，但每条都有来由：

```python
    @model_validator(mode="after")
    def validate_confirmed_explanation(self) -> SimilarCaseReference:
        if not self.confirmed:
            raise ValueError("similar case references must be confirmed")
        for field_name in (
            "common_points", "differences", "reference_actions",
            "pitfall_warnings", "evidence_refs",
        ):
            values = getattr(self, field_name)
            if len(values) != len(set(values)):
                raise ValueError(f"similar case {field_name} must not contain duplicates")
        if self.case_id not in self.evidence_refs:
            raise ValueError("similar case evidence_refs must include case_id")
        return self
```

三条不变量：

1. **`confirmed=False` 不是可展示的降级值，而是上游污染。** 召回本身就是 confirmed-only 搜索，所以
   一个未确认案例出现在报告里说明检索层出了 bug，应该炸而不是显示。
2. **五个解释列表都至少一项且不许重复**（`min_length=1` 在字段上，去重在校验器里）。强制 `differences`
   非空是关键设计：它逼着系统说出"这次和那次哪里不一样"，而不是把相似度当等价。
3. **`case_id` 必须出现在 `evidence_refs` 里**，这样"我参考了历史"这件事本身也是可追溯引用，而不是
   只引用本次 Observation 就把历史结论搬过来。

## 1.12 `AgentState`：LangGraph 唯一的共享状态

```python
class AgentState(BaseModel):
    model_config = ConfigDict(extra="forbid")

    run_id: str
    session_id: str
    user_query: str
    session_context: SessionTurnContext | None = None
    intent: str | None = None
    active_capabilities: list[str] = Field(default_factory=list)
    plan: list[str] = Field(default_factory=list)
    hypotheses: list[FaultHypothesis] = Field(default_factory=list)
    evidence: list[Evidence] = Field(default_factory=list)
    tool_events: list[ToolEvent] = Field(default_factory=list)
    retrieved_paths: list[RetrievedPath] = Field(default_factory=list)
    react_step: int = Field(default=0, ge=0)
    next_action: PlannerDecision | None = None
    observation_refs: list[str] = Field(default_factory=list)
    stop_reason: str | None = None
    draft_report: DiagnosisReport | None = None
    audit_result: AuditResult | None = None
    retry_count: int = Field(default=0, ge=0, le=1)
    memory_candidate: CaseMemory | None = None
```

先说**没有什么**：没有 `thought`、没有 `reasoning_process`、没有 `messages`、没有 Prompt、没有供应商
原始响应。模块 docstring 把这写成了设计目标：

> 模型刻意不包含 Thought 或 reasoning_process，从数据结构层阻止原始思维链进入日志、API 和长期记忆。

这是"绝不外泄推理过程"这条硬边界的**结构性实现**。LangGraph 的 checkpoint 会序列化整个 state，API
会投影它，SSE 会推它，`run_events` 会存它。如果 state 里有 thought，那么要在四个出口分别做脱敏；
state 里没有 thought，四个出口就都不需要脱敏。**用类型系统消除一类风险，而不是在每个出口打补丁**。

两个"预算"字段值得注意：

- `react_step: int = Field(ge=0)` —— ReAct 步数计数器，第 8 章会看到它是有界循环的核心。
- `retry_count: int = Field(ge=0, le=1)` —— 返工次数，`le=1` 直接把上限写进类型。模型无法通过输出
  一个大数字来给自己争取更多返工机会，因为 state 装不下。

`extra="forbid"` 在这里的作用是**暴露契约漂移**：某个节点如果想偷偷塞一个字段传给下游，会在构造时
失败，而不是让下游读到一个不在契约里的键。

## 1.13 Planner 决策契约：`app/domain/planner.py`

Planner 每轮输出一个 `PlannerDecision`。三个状态：

```python
class PlannerStatus(StrEnum):
    CALL_TOOL = "call_tool"
    FINISH = "finish"
    NEED_USER_INPUT = "need_user_input"
```

跨字段校验把"状态"和"字段组合"绑成唯一合法组合：

```python
    @model_validator(mode="after")
    def validate_actions_and_stop_reason(self) -> PlannerDecision:
        # 先处理唯一会继续执行外部动作的分支，确保批次和 stop_reason 互斥。
        if self.status is PlannerStatus.CALL_TOOL:
            if not self.actions:
                raise ValueError("call_tool decisions require at least one action")
            if len(self.actions) > MAX_PARALLEL_TOOL_ACTIONS:
                raise ValueError(
                    f"call_tool decisions accept at most {MAX_PARALLEL_TOOL_ACTIONS} actions"
                )
            if self.stop_reason is not None:
                raise ValueError("call_tool decisions cannot include stop_reason")
            return self

        # 结束类分支不允许携带“顺便执行”的工具调用，以保持一次决策只有一种副作用。
        if self.actions:
            raise ValueError("non-call_tool decisions must not include actions")
        if not self.stop_reason:
            raise ValueError("finish and need_user_input decisions require stop_reason")
        return self
```

"一次决策只有一种副作用"是这段校验的中心思想。允许 `finish` 同时带 Action，会出现"报告已经生成、
但还有工具在跑"的竞态；允许 `call_tool` 带 `stop_reason`，路由就要决定谁优先。禁掉这两种组合，
LangGraph 的条件边只读 `status` 就够了。

上限 3 写在**校验器**里而不是 `Field(max_length=3)`，注释解释了原因：

> Structured Outputs 的 strict Schema 不接受 `maxItems`，把上限留在校验器可以同时保住"模型必须遵守
> 上限"和"Schema 能被兼容端点接受"两件事。

这是一个非常具体的工程妥协，也是"读源码才能学到"的东西：Pydantic 的 `max_length` 会生成 JSON Schema
的 `maxItems`，而 OpenAI 兼容的 strict Structured Outputs 不支持这个关键字，会整个拒绝 Schema。

并行上限本身也有理由（`MAX_PARALLEL_TOOL_ACTIONS = 3`）：

> 每个 MCP 调用都会拉起一个独立 stdio 子进程，无界并行会把"省下的等待"换成子进程风暴；三个恰好
> 覆盖"状态 + 日志 + 拓扑"这类真实互不依赖的取证组合。

## 1.14 停止原因为什么必须是枚举——一条实测教训

```python
class PlannerStopReason(StrEnum):
    EVIDENCE_SUFFICIENT = "evidence_sufficient"
    EVIDENCE_INSUFFICIENT = "evidence_insufficient"
    EVIDENCE_CONFLICT_REQUIRES_MANUAL_REVIEW = "evidence_conflict_requires_manual_review"
    TOOL_UNAVAILABLE_DEGRADED = "tool_unavailable_degraded"
    PERMISSION_DENIED_REQUIRES_ACCESS = "permission_denied_requires_access"
    MISSING_RESOURCE_ID = "missing_resource_id"
    NEED_USER_INPUT = "need_user_input"
```

这个枚举的 docstring 记录了一次真实的评测失败，值得完整引用：

> 这里必须是枚举而不是自由文本：停止原因会进入 `run_events`、`run-trace:v1` span 和 Golden 评测的
> `stop_reason_hit`，自由文本会同时造成三件事——公开事件里出现接近思维链的长篇叙述、span 属性白名单
> 直接拒绝非 ASCII 值、以及"期望 evidence_sufficient"的评测项恒不命中。首次真实模型冒烟评测三个案例
> 的 `stop_reason_hit_rate` 就是这样实测为 0：模型给出的是一整段中文理由，而不是可比较的分类。

三个后果分属三个不同子系统（可观测性、安全、评测），却由同一个类型选择引发。解释性文字并没有被
删掉，而是搬到了 `decision_summary`（限长 500 字符）——**职责分离**，而不是二选一。

## 1.15 假设更新为什么能"创建"假设——另一条实测教训

`HypothesisUpdate` 的 docstring 记录了第二个实测缺陷：

> `status=new` 必须同时给出症状与候选根因，否则控制器无法把它投影成 `FaultHypothesis`——这正是首次
> 真实模型评测里假设集合恒为空、确定性草稿因此永远拿不到根因的原因：契约只能"更新"假设，却没有
> 任何字段能"创建"假设。

原来的契约里 `HypothesisUpdate` 只有 `hypothesis_id` 和 `status`，逻辑上假定假设已经存在。但假设是
谁创建的？没人。于是模型每轮都在"更新"一个不存在的假设，投影时被丢弃，报告永远没有根因。

修法是给 `new` 状态补上内容字段，并强制校验：

```python
    @model_validator(mode="after")
    def validate_new_hypothesis_content(self) -> HypothesisUpdate:
        symptom = (self.symptom or "").strip()
        root_cause = (self.candidate_root_cause or "").strip()
        if self.status is HypothesisUpdateStatus.NEW and not (symptom and root_cause):
            raise ValueError("new hypothesis updates require symptom and candidate_root_cause")
        return self
```

`.strip()` 那两行不是多余的：不做 strip，模型可以用一个空格通过校验，然后投影出一个内容为空白的
假设。注释也点明了为什么选择"失败"而不是"静默丢弃"——静默丢弃会重现"模型说了根因、报告里没有
根因"的结构性缺陷。

另外注意这个契约**没有** `components` 字段，docstring 说明了原因：组件范围由能力路由的已批准组件
决定，避免模型自述把未获批组件写进结论。这是"模型不能自己扩大权限"的一个具体例子。

## 1.16 审计契约：两态 + 有限问题码

```python
class AuditStatus(StrEnum):
    ACCEPT = "accept"
    REVISE = "revise"

class AuditIssueCode(StrEnum):
    INVALID_EVIDENCE_REF = "invalid_evidence_ref"
    UNSUPPORTED_CLAIM = "unsupported_claim"
    EVIDENCE_CONFLICT = "evidence_conflict"
    MISSING_RISK_CONTROL = "missing_risk_control"
    UNCONFIRMED_CASE = "unconfirmed_case"
    REPORT_INCOMPLETE = "report_incomplete"
    AUDITOR_UNAVAILABLE = "auditor_unavailable"
```

Auditor 只有两个出口，没有"部分通过"。`AuditResult` 的校验器把状态和内容绑死：

```python
        if self.status is AuditStatus.ACCEPT:
            if self.issues or self.revision_instructions:
                raise ValueError("accepted audit cannot contain issues or revision instructions")
            return self
        if not self.issues:
            raise ValueError("revise audit requires at least one issue")
        if not self.revision_instructions:
            raise ValueError("revise audit requires revision instructions")
```

这消除了"口头接受但仍列出阻断问题"的矛盾状态——LangGraph 只读枚举即可安全路由。

`AuditIssue` 用了 `frozen=True`：

```python
class AuditIssue(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    code: AuditIssueCode
    claim_path: str = Field(min_length=1, max_length=300)
    message: str = Field(min_length=1, max_length=1000)
    evidence_refs: tuple[str, ...] = ()
```

不可变（相当于 Java 的 final 字段 + 无 setter）加上 `tuple` 而不是 `list`，是因为审计问题会被
去重、比较、放进集合。可变对象不可哈希，也可能在返工流程里被下游节点悄悄改写。

`claim_path` 是问题定位方式：它是报告字段路径（比如 `root_causes[0].evidence_refs`），不是自然语言
描述。第 12 章会看到 `run_events` 和前端裁决卡**只暴露问题码与 `claim_path`，不暴露
`issues[].message`**——因为 message 可能包含模型的推理痕迹。

## 1.17 `ToolEvent`：每次尝试都是一条独立事件

```python
class ToolEvent(BaseModel):
    event_id: str
    trace_id: str
    tool_name: ToolName
    request: McpToolRequest
    response: McpToolResponse
    attempt: int = Field(default=1, ge=1, le=2)
    retryable: bool = False
    started_at: datetime
    completed_at: datetime
```

`attempt` 的上界是 2，直接对应"瞬时错误最多重试一次"这条边界。docstring 说明了为什么重试成功也要
保留首次失败：

> 每次尝试独立成事件，即使重试成功也保留首次失败，便于计算真实延迟和失败率。

这条选择在评测里有直接后果：`tool_attempt_success_rate` 的分母是**尝试数**而不是逻辑 Action 数，
所以一次"失败后重试成功"会让成功率低于 1.0。同时 `duplicate_action_rate` 必须排除合法的 `attempt=2`，
否则重试会被误记成重复调用。两个指标读同一份事件流，靠 `attempt` 字段区分。

## 1.18 `CaseMemory`：长期记忆默认不可信

```python
class MemoryStatus(StrEnum):
    PENDING = "pending"
    CONFIRMED = "confirmed"
    REJECTED = "rejected"
```

`CaseMemory.status` 默认 `PENDING`。docstring 给出理由：

> 默认待确认保证 Auditor 通过的报告仍不会自动污染默认召回；只有 confirmed 案例可参与常规历史匹配。

这是"审计通过"和"可作为知识复用"之间的一道额外闸门。审计通过只说明这份报告**自身**证据自洽；把它
变成会影响未来所有诊断的知识，需要人确认。第 10 章会看到 `stage_case_memory` 节点如何实现这一点。

## 1.19 `SessionTurnContext`：多轮追问只带公开信息

```python
class SessionTurnContext(BaseModel):
    source_run_id: str
    previous_user_query: str
    report_summary: str
    root_causes: list[RootCauseConclusion] = Field(default_factory=list)
    remediation_steps: list[RemediationStep] = Field(default_factory=list)
    risks: list[str] = Field(default_factory=list)
    uncertainties: list[str] = Field(default_factory=list)
    evidence_refs: list[str] = Field(default_factory=list)
    report_degraded: bool = False
```

多轮对话最常见的实现是把历史 `messages` 全塞回去。本项目不这么做：追问上下文**只复制用户已经能通过
run API 看到的内容**。docstring 明确：它不保存 Prompt、供应商原始输出、Thought 或隐藏推理。

作用是让 Planner 理解"这个操作"这类省略指代，同时保证"多轮"不会成为思维链泄漏的后门。而且实时
Evidence 仍以独立字段进入状态，保持更高事实优先级——上一轮的结论不能压过这一轮的观察。

## 1.20 本章小结

这一章其实只讲了一件事：**把边界写成类型，而不是写成纪律。**

| 边界 | 类型层实现 |
|---|---|
| 只能调九个只读工具 | `ToolName` 枚举 |
| 无来源结论不许存在 | `evidence_refs: Field(min_length=1)` |
| 高风险建议必须有依据和回滚 | `validate_high_risk_controls` |
| 思维链绝不外泄 | `AgentState` 里没有该字段 |
| 返工最多一次 | `retry_count: Field(le=1)` |
| 重试最多一次 | `attempt: Field(le=2)` |
| 记忆默认不可信 | `MemoryStatus.PENDING` 默认值 |
| 停止原因可评测 | `PlannerStopReason` 枚举 |

下一章看这些契约如何在进程启动时被逐项核对——如果代码、配置、文档三方对不上，服务会拒绝启动。
