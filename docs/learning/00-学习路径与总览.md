# 第 0 章 学习路径与总览

## 0.1 这份文档是给谁看的

读者只需要具备 Java 或 Python 的语法基础：会读类、函数、循环、异常，知道什么是接口与继承。
不需要事先了解 LLM Agent、LangGraph、MCP、RAG、pgvector、FastAPI 或 Alembic——每一项都会在第一次
出现的地方从"它解决什么问题"讲起，然后直接读本项目的源码。

文档的讲法是**以源码为主**：每一节先给出该功能落在哪个文件、哪个类、哪个函数，再逐段解释这段代码
为什么这样写、它保证了什么边界、如果写成常见的另一种写法会坏在哪里。凡是项目里能跑的命令都给出
可复制的命令行，最后两章专门讲部署验证与 Agent 评测的完整做法。

## 0.2 项目一句话定位

用户用自然语言描述 LTS（调度）/ BDS（计算）/ FlashSync（同步）三个模拟大数据组件的故障，系统通过
真实 MCP 协议调用九个只读工具收集证据，用 PostgreSQL 里的知识图 + 向量做 GraphRAG 溯源，由
Planner（ReAct 决策）和 Auditor（独立审计）两个 Agent 产出**每条结论都带引用**的结构化报告，审计
通过的案例写入长期记忆。

全部数据是脱敏、合成或 Mock 的，不接入任何生产系统。工具全部只读：不实现自动重跑、扩容、删表或
修复。

## 0.3 为什么按这个顺序学

真实的开发顺序是"从里向外"的：先把不可协商的数据契约钉死，再实现协议边界，然后是检索、模型调用，
最后才是编排、API 和评测。倒过来学（先看 API）会看到一堆已经成型的对象，却不知道它们为什么长这样。

本文档因此按下面的顺序推进，每章都对应一个可独立验证的垂直切片：

| 章 | 主题 | 主要源码 |
|---|---|---|
| 1 | 领域契约：工具、证据、假设、报告、审计 | `app/domain/tooling.py`、`app/domain/models.py` |
| 2 | 配置与契约 ID 门禁 | `app/core/settings.py`、`app/api/main.py` 的 lifespan |
| 3 | MCP 真协议边界：九个只读工具 | `mcp_server/server.py`、`app/mcp/client.py`、`app/mcp/executor.py` |
| 4 | 能力配置层：不是 Agent 的"能力" | `app/capabilities/` |
| 5 | GraphRAG：向量 + 全文 + 图扩展 + 精排 | `app/retrieval/` |
| 6 | 文档 RAG 与证据预算 | `app/retrieval/documents.py`、`chunking.py`、`document_service.py`、`budget.py` |

## 0.4 三层嵌套的 LangGraph（先建立地图）

整个系统的核心是三个真实的 `StateGraph`，外层复用内层，不是一条扁平函数链。学完第 8–10 章你会
自己写出这张图；现在只需要记住它的形状：

```text
AuditedDiagnosisWorkflow (audited-diagnosis-workflow:v2)
  recall_case_memories → run_react → explain_case_matches → run_report → stage_case_memory
                            │                                  │
                            │                                  └─ 内嵌 AuditedReportWorkflow
                            │                                       draft_report → audit_report
                            │                                         →（revise ⇄ audit | degrade | accept）
                            └─ 内嵌 BoundedReactLoop
                                 select_capabilities → planner_react ⇄ execute_tools（有界循环）
```

三条必须记住的规则，后面每章都会回到它们：

1. **实时 Observation 永远优先于历史案例**：历史只能作参考证据，冲突时报告必须突出差异。
2. **记忆入库必须在审计之后**，且只接收 accepted 且含根因的报告，且默认 pending 等用户确认。
3. **确定性规则对模型有非对称否决权**：规则说有问题就必须返工，模型的"通过"覆盖不了它。

## 0.5 先把环境跑起来

后面每章都会让你运行一小段验证命令，因此建议现在就把环境准备好。Windows 仓库，bash 下用
`.venv/Scripts/python`：

```bash
.venv/Scripts/python -m pip install -r requirements-dev.lock

# 静态检查（ruff，line-length 100，规则集 E/F/I/UP/B/ASYNC）
.venv/Scripts/python -m ruff check .

# 快速测试：pyproject 的 addopts 已含 -m 'not postgres'，默认跳过需要数据库的用例
.venv/Scripts/python -m pytest -q

# 本地起服务；访问 /health 与 /demo
.venv/Scripts/python -m uvicorn app.api.main:app --reload
```

第 13 章会补上 PostgreSQL、Docker、迁移与知识种子；在那之前，不带数据库的快速测试足够验证前面
所有章节的内容。

## 0.6 阅读本文档的两个建议

- **每章先看"你会验证什么"，再读源码。** 这个项目的每个边界都有对应的测试，测试名就是这条边界的
  自然语言表述；先跑一次测试，再去读它保护的实现，理解速度会快很多。
- **注意"为什么不那样写"。** 项目里大量注释解释的是被放弃的写法（例如"截断"而不是"整批拒绝"、
  "静默降级"而不是"明确 503"）。这些取舍才是本项目区别于教学 Demo 的地方，也是面试里真正会被追问
  的部分。

## 0.7 生成 Word 版本

十五份章节 Markdown 可以合成一份带封面和目录的 Word 文档：

```bash
.venv/Scripts/python docs/learning/build_docx.py --code-revision "$(git rev-parse --short HEAD)"
# 输出：docs/learning/dist/DataOps-Troubleshooter-项目学习文档.docx
```

`build_docx.py` 只解析章节实际用到的 Markdown 子集（标题、围栏代码块、管道表格、列表、引用块、
行内 `代码` 与粗体），不引入 pandoc 或通用 Markdown 库——章节里的代码块混着中文注释和全角标点，
通用转换器经常把缩进和字体回退处理坏，而这些缩进本身就是要讲的内容。两个刻意的选择：

- **输出目录是 `docs/learning/dist/`，不能是 `docs/` 根目录。** `tests/unit/test_documentation_policy.py`
  的 `test_learning_constraint_is_synchronized_to_formal_docx` 用 `next(Path("docs").glob("*.docx"))`
  定位正式产品设计 DOCX，多放一个 docx 会让那条门禁指向错文件。
- **目录页写的是 Word 的 TOC 域，不是脚本生成的页码列表。** 页码只有排版引擎知道，脚本自己算出来
  的页码一定是错的；打开文档后右键"更新域"即可。

需要 PDF 时用 Word 或 LibreOffice 导出（`soffice --headless --convert-to pdf`），脚本不做这一步：
无头转换依赖本机字体，缺字体时中文会静默变成方框，这种失败不该藏在构建脚本里。
