# 第 9 章 报告草稿、确定性规则、独立审计与四级阶梯

第 8 章结束时，系统手里有一个停止了的 `AgentState`：一批 Evidence、一批 ToolEvent、一组已投影的
`hypotheses`、一个 `stop_reason`。本章要把它变成一份能给人看的报告，并且回答一个所有多 Agent 系统都
必须回答的问题：**谁有权说"这份结论可以发出去"？**

本项目的答案是：**没有任何单一方有权放行。** 确定性规则和独立 Auditor 都同意才能 accept，而两者中只要
规则说不行，模型的 accept 就无效。这条非对称性是本章的核心。

## 9.2 为什么报告层要拆成四个组件

先看模块的职责划分，因为它决定了后面所有代码的形状：

| 组件 | 是不是模型？ | 能不能新增内容？ | 出错时 |
|---|---|---|---|
| `DeterministicReportBuilder` | 否 | 只能从状态投影 | 抛异常（实现缺陷） |
| `ReportPolicyValidator` | 否 | 不改报告，只产 `AuditIssue` | 抛异常（契约损坏） |
| `AuditorAgent` | **是**（第二个 LLM） | 只能指出问题，不能补事实 | 立即降级 |
| `SafeReportReviser` | 否 | **只删不加** | 抛异常 |

四个组件里只有一个是模型，而且那个模型**只有否决权，没有生成权**。

### 9.2.1 为什么草稿不让模型写

最直觉的设计是"把证据丢给模型，让它写报告"。本项目没这么做，`draft.py` 的模块 docstring 第一句就是理由：

> 草稿只使用现有假设、实时 Evidence、GraphRAG Bundle 和已确认案例元数据，**不请求模型补写事实**。
> 证据不足时宁可保留 uncertainties 和只读检查步骤，也不会为了报告完整度编造根因或解决方案。

三个具体后果：

1. **同一输入必然产生同一份报告。** `DeterministicReportBuilder` 的 docstring：
   "同一输入始终产生相同字段顺序和文本，便于 Golden Case 回放"。第 14 章的 Golden 基线能做逐字段断言，
   就是因为草稿没有随机性。
2. **"证据不足"是一个可以正常产出的结果，而不是失败。** 让模型写报告时，一个必然出现的行为是它会
   把报告的空白填满——这是训练目标决定的，不是 Prompt 能可靠约束的。确定性 Builder 在证据不足时产出
   的是一份**带 `uncertainties` 的降级报告**，而不是一段听起来完整的推测。
3. **模型的贡献被前移到了第 8 章。** 报告里的根因来自 `AgentState.hypotheses`，而那些假设是 Planner
   在 ReAct 循环里逐轮提交、被确定性规则打折之后的产物（§8.9）。**模型的判断确实进了报告，但它进的是
   "假设"这个受约束的通道，而不是"报告正文"这个自由文本通道。**

这也是第 8 章 §8.9.1 那个事故的另一半：草稿**只认** `AgentState.hypotheses`，绝不去读
`decision_summary` 的自由文本。当时 `hypothesis_updates` 被丢弃，模型在 `decision_summary` 里说对了根因，
报告的 `root_causes` 却恒为空。**很多人会把修法选成"那就让草稿也读一下 decision_summary"——那会立刻毁掉
上面三个性质。** 正确的修法是把 `hypothesis_updates` 接回状态，让结论继续走受约束的通道。

### 9.2.2 Schema 是第一级门禁，不是第四级

四级阶梯（9.6 节）之前还有一级：Pydantic 本身。`RemediationStep` 的 validator：

```python
@model_validator(mode="after")
def validate_high_risk_controls(self) -> RemediationStep:
    # 高风险操作对错误根因更敏感，因此必须先证明必要性，再说明执行前置条件。
    if self.risk_level is RiskLevel.HIGH:
        if not self.evidence_refs:
            raise ValueError("high-risk remediation requires evidence references")
        if not self.prerequisites:
            raise ValueError("high-risk remediation requires prerequisites")
    return self
```

docstring 点明了为什么不靠 Prompt：

> 低/中风险的只读检查可以没有证据引用，但 high 操作若缺少任一保护就会在报告构造阶段失败，
> **而不是只依赖 Prompt 提醒 Auditor**。

`AuditResult` 的 validator 是同一种做法：

```python
if self.status is AuditStatus.ACCEPT:
    if self.issues or self.revision_instructions:
        raise ValueError("accepted audit cannot contain issues or revision instructions")
    return self
if not self.issues:
    raise ValueError("revise audit requires at least one issue")
if not self.revision_instructions:
    raise ValueError("revise audit requires revision instructions")
```

docstring 讲了它买到了什么：

> accept 必须没有问题或返工内容；revise 必须同时说明至少一个问题和一条修订指令。这样 LangGraph
> **只读取枚举即可安全路由**，不会出现"口头接受但仍列出阻断问题"的矛盾状态。

这是第 8 章 §8.10 那条"路由只读枚举"的前置条件。路由之所以敢只看 `AuditStatus`，是因为 Schema 已经保证
了 `accept` 和"没有阻断问题"是同一件事。**如果模型能返回 `accept` 却附带三个 issue，那么只读枚举的路由
就是不安全的**——它会放行一份模型自己都指出了问题的报告。

`DiagnosisReport` 还有一条：

```python
orders = [step.order for step in self.remediation_steps]
if orders and orders != list(range(1, len(orders) + 1)):
    raise ValueError("remediation order must be consecutive starting at one")
```

编号必须是 1..N 连续。这条看起来是格式洁癖，但 9.7.4 会看到它逼出了修订逻辑里一个真正重要的细节。

测试 `domain_schema_rejects_uncontrolled_high_risk_and_contradictory_audit_payloads` 一次覆盖这两组
Schema 断言——**它们在同一个用例里，是因为它们是同一个决定：把能在类型层拦住的东西拦在类型层。**

### 9.2.3 `evidence.py`：可引用宇宙只定义一次

73 行，两个函数，但它是整个证据链条的地基。模块 docstring：

> 同一规则同时被草稿、策略校验和修订使用，避免三个节点各自解释 Evidence/GraphRAG/案例来源。

```python
def collect_reference_sources(...) -> dict[str, EvidenceSourceType]:
    sources: dict[str, EvidenceSourceType] = {}
    for evidence in state.evidence:
        _insert_source(sources, evidence.evidence_id, evidence.source_type)
    for path in state.retrieved_paths:
        _insert_source(sources, path.path_id, EvidenceSourceType.GRAPH_PATH)
    if evidence_bundle is not None:
        for node in evidence_bundle.selected_nodes:
            _insert_source(sources, node.evidence_id, EvidenceSourceType.KNOWLEDGE_NODE)
        for path in evidence_bundle.selected_paths:
            _insert_source(sources, path.evidence_id, EvidenceSourceType.GRAPH_PATH)
        for chunk in evidence_bundle.selected_documents:
            _insert_source(sources, chunk.evidence_id, EvidenceSourceType.DOCUMENT_CHUNK)
    for memory in confirmed_case_memories:
        _insert_source(sources, memory.memory_id, EvidenceSourceType.CASE_MEMORY)
    return sources
```

五类来源：实时 Evidence、旧式 `retrieved_paths`、Bundle 的节点/路径/文档切片、已确认案例。
`collect_valid_reference_ids` 只是它的 `set(...)` 包装。

**这个函数是第 8 章那五处引用门禁的共同定义**：Planner 决策引用（§8.8.5）、假设引用（§8.8.5）、草稿投影
（9.4.3）、规则校验（9.5.2）、修订过滤（9.7）。五个调用点，一份定义——第 8 章 §8.8.5 记录的那次
`invalid_evidence_reference` 事故，起因正是渲染层和门禁层各算了一遍。

两个细节：

**`_insert_source` 在来源冲突时抛 `ValueError`。**

```python
current = sources.get(reference_id)
if current is not None and current is not source_type:
    raise ValueError(f"conflicting evidence source for {reference_id}")
sources.setdefault(reference_id, source_type)
```

同一个 ID 既是知识节点又是文档切片，说明稳定 ID 生成规则撞了。docstring："来源冲突表示 ID 命名或上游
持久化契约损坏，必须显式失败而不能依靠字典覆盖继续生成报告。" 这与第 8 章 §8.14 的
`_merge_evidence` 是完全相同的判断：**同一个标识符对应两份不同事实，是数据系统坏了，不能降级掩盖。**

**案例只贡献 `memory_id`，不把内部的 `evidence_refs` 摊平进来。** 注释说明了原因：

> 案例本身是可审计历史来源；其内部 evidence_refs 没有随原 Evidence 内容注入时不能伪装成本次可直接核对
> 的证据。报告应引用 memory_id，再由案例对象追溯其历史引用。

也就是说报告里写的是"参考案例 `mem_xxx`"，而不是"参考证据 `ev_yyy`"（后者是那个历史案例当时看到的
Observation，本次运行根本没取回来）。**引用必须指向读者真的能打开的东西。**

## 9.3 拓扑：四个节点、一条条件边

```python
graph = StateGraph(ReportGraphState, context_schema=ReportGraphRuntime)
graph.add_node("draft_report", traced_node("report.draft")(_draft_report))
graph.add_node("audit_report", traced_node("report.audit")(_audit_report))
graph.add_node("revise_report", traced_node("report.revise")(_revise_report))
graph.add_node("degrade_report", traced_node("report.degrade")(_degrade_report))
graph.add_edge(START, "draft_report")
graph.add_edge("draft_report", "audit_report")
graph.add_conditional_edges(
    "audit_report",
    _route_after_audit,
    {"revise": "revise_report", "degrade": "degrade_report", "end": END},
)
graph.add_edge("revise_report", "audit_report")
graph.add_edge("degrade_report", END)
return graph.compile(name="dataops_audited_report_v2")
```

```text
START → draft_report → audit_report ─┬─ "end"     → END
                            ↑        ├─ "revise"  → revise_report ─┐
                            │        └─ "degrade" → degrade_report → END
                            └──────────────────────────────────────┘
```

结构和第 8 章的 ReAct 图同源：Pydantic 状态 schema、`context_schema` 装不可序列化依赖、条件边、
`compile(name=...)`。三处差异值得说。

**差异一：用 `ainvoke` 而不是 `astream`。**

```python
raw_state = await self._graph.ainvoke(initial_state, context=self._runtime, config={"recursion_limit": 10})
```

第 8 章之所以要 `astream` + `latest_state`，是因为 ReAct 循环需要"超时了也保留已经取到的证据"（§8.6）。
报告图没有这个需求：**它的中间态没有独立价值**。一份修订到一半的报告不能返回给用户，所以要么走完，
要么让异常传播。没有 per-node 超时，也没有 `asyncio.timeout`——单次 Auditor 调用的超时已经由
`auditor_timeout_seconds`（默认 90，第 7 章 §7.11.3）覆盖，而节点数量是固定的。

**差异二：`recursion_limit=10` 是硬编码常量，不是公式。** 对比第 8 章的 `max_steps * 2 + 6`。这里能写死
是因为路径是**穷举可数的**：`draft → audit → revise → audit → degrade → END` 最长 5 个节点访问，
10 留了一倍余量。docstring 也把它讲清楚了："LangGraph recursion_limit 只覆盖草稿、两次审计、一次修订
和降级。" 而 ReAct 图的循环次数依赖配置，所以必须是公式。

**差异三：节点用 `traced_node` 装饰器，不在函数体里写 `with`。**

```python
graph.add_node("audit_report", traced_node("report.audit")(_audit_report))
```

`traced_node` 的 docstring 解释了这个分工：

> 节点的价值信息是"哪一层慢、哪一层抛错"，用装饰器在注册处包一层即可，既不用给每个节点缩进一个
> with 块，也不会让节点逻辑与遥测耦合。需要写属性的地方仍然直接用 `trace_span`，因此本装饰器**刻意不
> 暴露 handle**：节点内部真正想标注的往往是模型调用而不是整个节点。

所以本章有两层 span：`report.draft` / `report.audit` / `report.revise` / `report.degrade`（装饰器自动，
`kind=node`）和 `auditor.review`（节点内手写，`kind=model_call`，带属性）。**装饰器负责"每层多久"，
手写 span 负责"模型往返多久 + 结论是什么"**——后者需要 handle 才能 `annotate`，这就是装饰器不暴露
handle 的分界线。

装饰器用 `@wraps(node)`，docstring 说了为什么：

> 用 `wraps` 而不是新建函数名，是因为 LangGraph 的错误信息与调试快照会显示被包装对象的名字；丢掉原名
> 会让"哪个节点抛错"这类问题需要额外一次源码定位。

`ReportGraphRuntime` 与第 8 章的 `ReactGraphRuntime` 同构（`frozen=True, slots=True`），装五样东西：
auditor、builder、validator、reviser、config。**四个组件里三个是确定性服务，但它们同样通过 Protocol
注入**——因为测试需要注入一个"故意产出无依据报告"的 Builder 来证明规则门禁真的能否决。
`ReportDraftBuilder` 的 docstring 直接把这个用途写了出来：

> 协议便于测试故意注入无依据报告，证明确定性门禁能否决错误的 Auditor accept。

**这就是为什么确定性组件也要有 Protocol：不是为了"将来换实现"，是为了能构造出坏输入。**

## 9.4 `DeterministicReportBuilder`：投影，而不是写作

299 行里没有一次模型调用。`build` 的参数就是它能看到的全部世界：

```python
def build(
    self,
    state: AgentState,
    *,
    evidence_bundle: GraphEvidenceBundle | None = None,
    confirmed_case_memories: tuple[CaseMemory, ...] = (),
    history_case_matches: tuple[SimilarCaseReference, ...] = (),
) -> DiagnosisReport:
```

四个输入，第一件事就是算出可引用宇宙：

```python
valid_refs = collect_valid_reference_ids(state, evidence_bundle, confirmed_case_memories)
uncertainties: list[str] = []
```

注意 `history_case_matches` **没有**进 `collect_valid_reference_ids`。这两个案例参数长得很像，但角色完全
不同：`confirmed_case_memories` 是已确认的历史案例，它的 `memory_id` 是合法引用；`history_case_matches`
是本次召回的相似案例展示项（§10 会讲 `explain_case_matches`），只进 `similar_cases` 字段。

### 9.4.1 根因升级的三道过滤

```python
for hypothesis in state.hypotheses:
    if hypothesis.status not in {HypothesisStatus.SUPPORTED, HypothesisStatus.CONFIRMED}:
        continue
    supporting_refs = _stable_valid_refs(hypothesis.supporting_evidence, valid_refs)
    contradicting_refs = _stable_valid_refs(hypothesis.contradicting_evidence, valid_refs)
    if contradicting_refs:
        uncertainties.append(f"假设 {hypothesis.hypothesis_id} 同时存在反对证据，未提升为根因结论。")
        continue
    if not supporting_refs:
        uncertainties.append(f"假设 {hypothesis.hypothesis_id} 缺少当前上下文中的有效支持引用。")
        continue
    root_causes.append(
        RootCauseConclusion(
            root_cause=hypothesis.candidate_root_cause,
            confidence=hypothesis.confidence,
            evidence_refs=supporting_refs,
        )
    )
```

三道过滤，每一道被拒都写一条 `uncertainty` 而不是静默丢弃：

1. **状态门**：只有 `supported` / `confirmed` 能升。行内注释："candidate/rejected 不能仅凭置信度越级。"
   这句话回答了一个很容易犯的错：既然置信度是数字，为什么不写 `if hypothesis.confidence >= 0.7`？因为
   置信度本身是**从状态查表得来的**（第 8 章 §8.9.4 的 `_HYPOTHESIS_CONFIDENCE`），拿它当门槛等于把
   已经做过的判断绕回去一遍，还多了一个可以被调参偷偷放宽的旋钮。
2. **反对证据门**：只要还有**任何一条合法的**反对证据，就不升。注意是先过滤再判断——反对证据里那些
   已经悬空的 ID 不算。这与 9.5 的规则校验是同一口径，两边必须一致，否则草稿升了根因、规则又否决，
   系统会稳定地走进"必然返工"的死循环。
3. **支持证据门**：过滤后必须还剩至少一条。

第三道门的存在意义要单独说：假设是 Planner 在**某一轮**提交的，`supporting_evidence` 引用的是当时那一轮
看到的 `evidence_id`。而报告是在循环停止之后生成的。如果中间发生过状态合并冲突或 Bundle 重算，这些 ID
可能已经不在可引用宇宙里。**"引用曾经有效"不等于"引用现在有效"，而报告只能承诺后者。**

三道门的共同点是：**被拒的假设不会消失，它变成一条 `uncertainty`。** 读者能看到"系统考虑过这个假设、
因为什么没敢下结论"，而不是看到一份干净但沉默的报告。这与第 8 章 §8.8.6 的"整批拒绝并告知"是同一
个价值观：**沉默的丢弃是最难排查的故障形态。**

### 9.4.2 三条常驻 uncertainty

根因循环之后还有三条与假设无关的：

```python
if not root_causes:
    uncertainties.append("当前证据不足以形成可审计根因，报告保持降级结论。")
if evidence_bundle is not None and evidence_bundle.truncated:
    uncertainties.append("GraphRAG 上下文受到预算裁剪，省略候选不能解释为知识库不存在。")
if history_case_matches:
    uncertainties.append("历史案例解释仅作参考；差异与本次实时 Observation 冲突时以后者为准。")
```

中间那条是第 6 章证据预算的收尾。第 6 章讲过 Bundle 会因为 token 预算截断候选，并把 `truncated=True`
记进 Bundle。**那个布尔值不是内部统计，它必须一路走到读者眼前**：否则读者看到"报告没提到 X"，会自然
推断"知识库里没有 X"，而真相是"X 排在预算之外"。这两个结论会导向完全不同的下一步行动。

第三条是 §0.4 那条"实时 Observation 永远优先于历史案例"在报告层的落地。它是无条件写入的——只要召回
到了历史案例就写，不判断是否真的存在冲突。**因为"是否冲突"需要语义判断，而这里是确定性层。**

### 9.4.3 报告级引用是并集，不是新一批引用

```python
# 报告级引用是所有已采纳结论的并集，便于 API 快速展示和 Auditor 检查遗漏。
evidence_refs = _stable_unique(
    [
        *(ref for cause in root_causes for ref in cause.evidence_refs),
        *(ref for step in fault_chain for ref in step.evidence_refs),
        *(ref for step in remediation_steps for ref in step.evidence_refs),
        *(ref for item in history_case_matches for ref in item.evidence_refs),
    ]
)
```

`DiagnosisReport.evidence_refs` 是一个**派生字段**：它等于四类子结论引用的并集，不含任何独立信息。
这个性质在 9.7.3 会变得很关键——修订时它必须被重算而不是被删。

`_stable_unique` 按首次出现顺序去重，docstring 说明了为什么不排序：

> 该工具不排序 ID，避免改变 Planner 或检索已确定的时间/相关性顺序。

把 ID 排序看起来更"整洁"，但那会把"最相关的证据在最前面"这个已经花了精排代价（第 5 章）拿到的顺序
洗掉。**ID 的字典序不携带任何语义。**

### 9.4.4 summary 的两个分支

```python
summary = (
    f"基于 {len(evidence_refs)} 个可追溯引用形成 {len(root_causes)} 项根因结论。"
    if root_causes
    else "现有调查已停止，但证据不足以安全确认根因；请按只读步骤继续核验。"
)
```

只有两句模板，且两句都不复述任何结论内容——只报数量和状态。这里可以看出确定性投影的取舍：**摘要
质量明显不如模型写的**，但它换来两件事：不会出现"摘要里说的根因跟 root_causes 字段不一致"，以及
Golden 回放可以逐字断言。9.7.5 会讲到 Auditor 实测确实抱怨过修订稿的摘要，那是另一个位置的问题。

### 9.4.5 `_build_fault_chain`：不从节点名推因果

```python
if evidence_bundle is not None:
    for path in evidence_bundle.selected_paths:
        chain.append(FaultChainStep(
            description=_path_description(path.node_ids, [item.value for item in path.relation_types]),
            evidence_refs=[path.path_id],
        ))
        seen_paths.add(path.path_id)
for path in state.retrieved_paths:
    if path.path_id in seen_paths:
        continue
    ...
```

Bundle 优先、`retrieved_paths` 兜底，`seen_paths` 去重。docstring 里那句是重点：

> 函数不从相邻节点名称推断额外因果，只把已有节点/关系顺序格式化。

而 `_path_description` 把这条守得很死：

```python
if len(node_ids) != len(relation_types) + 1:
    raise ValueError("fault path requires exactly one relation between adjacent nodes")
parts = [node_ids[0]]
for relation, node_id in zip(relation_types, node_ids[1:], strict=True):
    parts.extend([f"-[{relation}]->", node_id])
return " ".join(parts)
```

输出形如 `lts_scheduler -[depends_on]-> bds_cluster`：只有原始 ID 和原始关系名，没有一个字是这里生成的。

`N` 个节点必须对应 `N-1` 条边，这个不变量被检查了**两次**：显式的 `if` 一次，`zip(..., strict=True)` 一次。
显式检查在前，所以 `strict=True` 实际上永远不会触发。这不是冗余：显式检查负责给出领域语言的错误消息
（"fault path requires exactly one relation between adjacent nodes"），`strict=True` 负责在未来有人重构掉
上面那个 `if` 时不让错误变成静默截断。docstring 把选择讲明了：

> 不变量破坏表示上游 GraphRAG 模型或旧状态损坏，函数显式失败，不用截断 zip 掩盖悬空节点。

**如果这里用默认的 `zip`，一条 3 节点 1 关系的坏路径会安静地渲染成 2 节点链路**——报告看起来完全正常，
只是少了一跳。这与第 8 章 §8.11.4 的 `zip(..., strict=True)` 是同一个判断。

### 9.4.6 风险等级的来源：声明，不是猜

`_build_remediation_steps` 有两类来源，风险等级的处理方式不一样：

```python
for order, node in enumerate(solution_nodes, start=1):
    # Bundle 的模型校验保证 solution/sop 一定带声明，因此这里不需要（也不应该）兜底默认值：
    # 一旦出现 None 就说明证据来源绕过了校验，宁可 Pydantic 立刻拒绝也不要静默降成 medium。
    steps.append(RemediationStep(
        order=order,
        action=node.content,
        risk_level=node.remediation_risk_level,
        ...
    ))
for order, chunk in enumerate(document_chunks, start=len(steps) + 1):
    steps.append(RemediationStep(
        order=order,
        action=chunk.content,
        risk_level=RiskLevel.MEDIUM,
        ...
    ))
```

**知识节点用自己声明的 `remediation_risk_level`；文档切片固定 `MEDIUM`。** docstring 解释了这个不对称：

> 知识节点内容保持原文并引用自身 evidence_id，风险等级直接采用该节点声明的 `remediation_risk_level`；
> 文档切片补充"步骤写在哪一节"的可执行细节并引用 `dc_*`，因为切片是原文摘录而没有声明字段，只能固定
> 为 medium。

这条设计是最近一次提交（`4e5e1b4 feat: 处置风险等级改由知识节点显式声明`）才定型的。**之前的写法是
把两类来源都硬编码成 `RiskLevel.MEDIUM`。** 提交说明记录了它造成的三个后果：

> 报告层原来把每条处置建议硬编码为 medium，导致 `RiskLevel.HIGH` 在生产路径上永远不可达、
> `derive_report_risks` 的 high 分支是死代码，`risk_level_hit_rate` 被实现方式而不是模型质量封顶在 0.667。

这三条值得逐条看，因为它们是三种不同层次的伤害：

1. **`RiskLevel.HIGH` 不可达。** §9.2.2 那个 `validate_high_risk_controls`（要求 high 必须有证据引用和
   前置条件）在生产路径上从来没有被触发过——它只在测试里活着。**一道永远不会执行的门禁，等于没有门禁。**
2. **`derive_report_risks` 的 high 分支是死代码。** 那句"必须完成证据复核、审批、备份和回滚演练"永远
   不会出现在任何报告里。
3. **评测指标被实现封顶。** `risk_level_hit_rate` 卡在 0.667，而这个数字与模型好坏无关——它测的是
   "报告的风险等级是否等于期望值"，而报告永远只会说 medium。**这是最危险的一条：一个看起来在测模型的
   指标，实际上在测一行硬编码常量。**

修复方式是让 `remediation_risk_level` 由三层共同保证（提交说明原话）：`app/retrieval/models.py` 的共享
校验器（`KnowledgeNode` 与 `BundledKnowledgeNode` 复用）、数据库的
`ck_knowledge_nodes_remediation_risk_level` 约束，以及**全链路没有任何默认值**。种子数据同步从
`graph-seed:v11` 升到 v12（8 个 solution 节点新增声明：3 high / 5 medium）。

那条行内注释还回答了另一个常见写法：`risk_level=node.remediation_risk_level or RiskLevel.MEDIUM`。
加上 `or` 之后代码"更健壮"了，但它买到的是：一个绕过了校验的高风险方案会被静默降级成 medium，然后
跳过 §9.2.2 的 `validate_high_risk_controls`（因为它只对 HIGH 生效），最终一个没有前置条件、没有证据
引用的高风险操作会出现在报告里。**兜底默认值在这里正好把最重要的一道门给关掉了。**

这次提交里还有两个诚实性细节值得学：

- Prompt 渲染器用 `model_dump` 且**不排除 `None`**，所以新字段的 `null` 真实进入 Prompt，固定查询的
  字节快照从 5658 变成 5876。提交说明写的是"照实提升，而不是为保住旧数字在计费里排除 null"。
- `docs/live-golden-eval-results.md` **保留 0.667 作为最后一次实测值**，理由是"解除实现约束不是一次新的
  测量"。这正是 CLAUDE.md 那条评测诚实性要求的执行样例：**修好了瓶颈不等于测到了更好的数字。**

测试 `declared_high_risk_solution_node_reaches_the_report_risk_level` 断言声明的 high 原样到达报告；
`bundle_rejects_missing_or_out_of_scope_remediation_risk_declaration` 断言这个声明在 Bundle 层就是必填且
受枚举约束的——**两条测试一起才构成"声明式风险"这条链的完整证明**：值必须存在（Bundle 层），且必须
原样传递（报告层）。

### 9.4.7 `_is_remediation_chunk`：只认标题路径

```python
_REMEDIATION_SECTION_KEYWORDS = ("处置步骤", "确认步骤", "恢复步骤")
_REMEDIATION_DOCUMENT_TYPES = frozenset({DocumentType.RUNBOOK, DocumentType.SOP})

def _is_remediation_chunk(chunk: BundledDocumentChunk) -> bool:
    if chunk.doc_type not in _REMEDIATION_DOCUMENT_TYPES:
        return False
    section = chunk.heading_path.rsplit(" > ", maxsplit=1)[-1]
    return any(keyword in section for keyword in _REMEDIATION_SECTION_KEYWORDS)
```

两道过滤，各有一句 docstring 解释：

**文档类型门**："只认 Runbook/SOP 的步骤小节：复盘的'改进项'是长期治理动作而非本次处置，FAQ 是判断
依据而非操作，把它们混入建议会让报告把'以后要改流程'和'现在要做什么'混为一谈。" 第 6 章的四种文档类型
（RUNBOOK / SOP / POSTMORTEM / FAQ）里，只有前两种能产出建议。

**标题路径门**：`rsplit(" > ", maxsplit=1)[-1]` 取的是**最后一段标题**，也就是切片所在的那一节的名字。
docstring 说明了为什么不搜正文：

> 匹配标题路径而不是正文关键词，因为标题由文档作者显式声明，正文里出现"步骤"二字往往只是叙述。

这一条和 9.4.6 的风险声明是同一个模式：**能用作者声明的元数据，就不要用文本匹配去猜。** 一段写着
"上述步骤不适用于跨机房场景"的正文里含"步骤"二字，按正文匹配会把一句禁止性说明变成一条待执行建议。

模块顶部的注释还讲了第三层理由：

> Runbook 同样包含"禁止操作""升级条件"这类正文，把它们当成待执行动作会让报告建议运维去做一件文档明确
> 禁止的事。关键词集合显式声明而不是靠模型判断，才能在 Golden 回放里稳定复现同一份建议。

测试 `only_runbook_and_sop_step_sections_become_remediation_steps` 守这条；
`document_chunks_alone_can_carry_remediation_without_solution_nodes` 守的是另一件事——**没有知识节点时
文档切片可以独立承载处置**。两条一起说明文档 RAG 不是知识图的附属品，它是一条独立的证据通道（第 6 章
`document-retrieval:v1` 的存在意义）。

### 9.4.8 没有方案证据时的兜底：一条只读步骤

```python
if not solution_nodes and not document_chunks:
    return [
        RemediationStep(
            order=1,
            action="继续通过已批准的只读 MCP 工具补齐状态、日志或一致性证据。",
            risk_level=RiskLevel.LOW,
            evidence_refs=[],
            prerequisites=["确认资源标识、时间范围、scenario_id 与 trace_id 均属于本次运行。"],
            rollback="只读检查不修改系统状态；若查询异常，停止并保留已有 ToolEvent。",
            verification="新增 Observation 必须生成稳定 evidence_id，并在下一轮重新审计。",
        )
    ]
```

这是"证据不足是一个正常结果"（§9.2.1 第 2 点）的具体形态。注意三个细节：

- **`evidence_refs=[]` 是合法的**，因为 §9.2.2 的 validator 只对 HIGH 要求引用。低风险只读检查本来就没有
  证据支撑——它是在承认"我不知道"，不需要引用来支撑一个不存在的结论。
- **它仍然填了 `rollback` 和 `verification`。** 一条只读步骤为什么要写回滚？因为 `RemediationStep` 的
  Schema 要求所有步骤都有，而**统一格式意味着读者不需要判断"这一条有没有回滚说明"**。这里写的是
  "只读检查不修改系统状态"——它明确回答了这个问题而不是留空。
- **`action` 描述的是"继续取证"而不是"修复"。** docstring："避免编造具体写操作。"

### 9.4.9 `derive_report_risks`：不从动作文本猜风险

```python
levels = {step.risk_level for step in remediation_steps}
if not remediation_steps:
    return ["当前未形成可审计修复步骤，不应执行生产变更。"]
if RiskLevel.HIGH in levels:
    return ["包含高风险人工操作，必须完成证据复核、审批、备份和回滚演练。"]
if RiskLevel.MEDIUM in levels:
    return ["知识方案仅供人工评审，先在隔离环境验证后再决定是否实施。"]
return ["当前仅建议只读核验，不执行生产写操作。"]
```

四个分支，取的是所有步骤风险等级的**最大值**（用 `in` 而不是排序，因为只有三档）。docstring 两句都重要：

> 函数不从动作文本猜风险，防止自然语言关键词改变控制语义。

也就是说 `action` 字段里写着"删除"或"重启"不会改变 `risks` 的措辞——**风险只来自枚举字段**。这是
9.4.6 那条链的下游：声明 → 枚举字段 → 报告级风险摘要，全程没有一次文本匹配。

> 修订路径共享同一函数，否则修订稿会写出"只允许人工只读核验"却同时保留中风险变更步骤这种自相矛盾的组合。

这句是提前说 9.7.3。**`risks` 是 `remediation_steps` 的函数**，所以任何改动步骤的地方都必须重算它，
而重算必须用同一个函数——两处实现必然漂移。

## 9.5 `ReportPolicyValidator`：五组规则，一次收集

模块 docstring 就是本章开头那条非对称性的原文：

> 这些规则不替代 Auditor 的语义判断，但拥有最终否决权：即使模型返回 accept，任何客观不变量失败仍必须
> 进入 revise。规则只产生 `AuditIssue`，不修改报告，保持验证与修订职责分离。

`validate` 的主体只有八行：

```python
valid_refs = collect_valid_reference_ids(state, evidence_bundle, confirmed_case_memories)
issues: list[AuditIssue] = []
# 按存在性、语义支撑、风险、案例和完整性顺序收集，便于返工从基础引用开始处理。
issues.extend(_invalid_reference_issues(report, valid_refs))
issues.extend(_root_cause_issues(report, state, valid_refs))
issues.extend(_risk_control_issues(report))
issues.extend(_case_issues(report, confirmed_case_memories, history_case_matches))
issues.extend(_completeness_issues(report))
return tuple(_deduplicate_issues(issues))
```

### 9.5.1 为什么不早退

docstring 明确：

> 函数不会因首个错误提前返回，也不会把模型 accept 当作豁免。

类 docstring 给了理由："Validator 不调用模型或数据库；它把所有客观问题一次性收集，**减少返工往返**。"

这是一条被返工预算逼出来的设计。`max_revisions ≤ 1`（§9.6.4），也就是说**只有一次机会修**。如果规则
在第一个错误就返回，一份有三个问题的报告需要三轮返工才能干净——而预算只有一轮，它会直接降级。
**一次收集全部问题，是"只给一次返工机会"这个约束的必要配套。**

顺序的作用是可读性而不是短路：引用存在性 → 语义支撑 → 风险 → 案例 → 完整性，从最基础的错误排到最
派生的。注释说"便于返工从基础引用开始处理"——因为一个悬空引用往往会连带产生"根因引用未命中假设"
和"报告级汇总漏项"，先看第一条更容易定位。

### 9.5.2 `_invalid_reference_issues`：存在性 + 汇总完整性

它做两件事。第一件是按字段分组检查存在性：

```python
groups: list[tuple[str, list[str]]] = [("evidence_refs", report.evidence_refs)]
groups.extend((f"root_causes[{index}].evidence_refs", item.evidence_refs) for index, item in enumerate(report.root_causes))
groups.extend((f"fault_chain[{index}].evidence_refs", item.evidence_refs) for ...)
groups.extend((f"remediation_steps[{index}].evidence_refs", item.evidence_refs) for ...)
groups.extend((f"similar_cases[{index}].evidence_refs", item.evidence_refs) for ...)
for path, refs in groups:
    invalid = tuple(ref for ref in refs if ref not in valid_refs)
    if invalid:
        issues.append(AuditIssue(code=AuditIssueCode.INVALID_EVIDENCE_REF, claim_path=path, ...))
```

**`claim_path` 是这里最重要的产出**，不是错误消息。`root_causes[2].evidence_refs` 这个字符串会一路传到
`SafeReportReviser`，让修订能精确删掉第 3 项根因而不是清空整个 `root_causes`（§9.7.1）。docstring 说得
很直白："每个字段单独报告 `claim_path`，便于安全修订精确删除问题项。"

**所以这个函数为什么要分组而不是一次性检查所有引用？** 一次性检查更短，但它只能报告"报告里有非法
引用"，无法定位。**能定位的错误才能被精确修复；不能定位的错误只能被整批删除。**

第二件是汇总完整性：

```python
if path != "evidence_refs":
    claim_refs.extend(refs)
missing_from_summary = tuple(ref for ref in _stable_unique(claim_refs) if ref not in report.evidence_refs)
if missing_from_summary:
    issues.append(AuditIssue(code=AuditIssueCode.REPORT_INCOMPLETE, claim_path="evidence_refs", ...))
```

检查的是 9.4.3 那个派生关系：报告级 `evidence_refs` 必须**覆盖**所有子结论引用。注意它是单向的——
子项引用必须都在汇总里，但汇总里可以有子项没用到的（例如 §9.8 降级稿保留的引用）。docstring 的理由：
"否则 API 汇总会误导用户。" 第 12 章的 `/demo` 前端直接渲染 `evidence_refs` 作为"本次报告的证据清单"，
漏项等于对用户隐瞒了一条已被采纳的证据。

注意 `if path != "evidence_refs"` 这行：报告级字段自己不进 `claim_refs`，否则就是拿自己检查自己。

### 9.5.3 `_root_cause_issues`：精确匹配把根因钉回状态

```python
hypotheses = {
    item.candidate_root_cause: item
    for item in state.hypotheses
    if item.status in {HypothesisStatus.SUPPORTED, HypothesisStatus.CONFIRMED}
}
for index, conclusion in enumerate(report.root_causes):
    path = f"root_causes[{index}]"
    hypothesis = hypotheses.get(conclusion.root_cause)
    if hypothesis is None:
        issues.append(AuditIssue(code=AuditIssueCode.UNSUPPORTED_CLAIM, claim_path=path,
                                 message="根因未对应当前状态中的 supported/confirmed 假设。", ...))
        continue
    valid_supporting = set(hypothesis.supporting_evidence) & valid_refs
    if not valid_supporting.intersection(conclusion.evidence_refs):
        issues.append(AuditIssue(code=AuditIssueCode.UNSUPPORTED_CLAIM, claim_path=path,
                                 message="根因引用未命中对应假设的有效 supporting_evidence。", ...))
    conflicts = tuple(ref for ref in hypothesis.contradicting_evidence if ref in valid_refs)
    if conflicts:
        issues.append(AuditIssue(code=AuditIssueCode.EVIDENCE_CONFLICT, claim_path=path,
                                 message="该根因仍存在有效反对证据，不能以确定结论放行。", ...))
```

三层检查，对应 9.4.1 的三道门——**这不是重复，这是双向验证。** 9.4.1 是 Builder 自己保证的性质；这里
是在**不信任 Builder** 的前提下重新验证一遍。回想 §9.3 那句"协议便于测试故意注入无依据报告"：如果规则
校验只是复述 Builder 的逻辑，注入一个坏 Builder 就能骗过整个系统。

**用 `dict` 做精确字符串匹配**，key 是 `candidate_root_cause` 全文。docstring 解释：

> 根因文本用精确匹配连接 `FaultHypothesis`，避免模糊字符串把不同故障合并。

这里很容易想到"用模糊匹配更友好"——毕竟报告文本和假设文本可能只差几个字。但模糊匹配的失败方式是
致命的：`"LTS 调度器时钟漂移"` 和 `"LTS 调度器时钟漂移不是根因"` 的相似度极高。**一个把否定句匹配成
肯定句的门禁，比没有门禁更糟。**

精确匹配也解释了 Builder 里那行 `root_cause=hypothesis.candidate_root_cause` 为什么必须是**原样赋值**、
不能有任何格式化（加句号、去空格、加前缀）。**这两处代码构成一个隐式契约：Builder 原样搬，Validator
原样比。** 任何一边动一下，所有根因都会被判为 `UNSUPPORTED_CLAIM`。

第二层的 `valid_supporting.intersection(...)` 要求**交集非空**而不是子集关系。为什么不要求报告引用是假设
引用的子集？因为报告可以额外引用图路径或文档切片来支撑同一个根因，那些 ID 不在假设的
`supporting_evidence` 里但完全合法。**要求"至少有一条来自假设"，是在防止根因被完全无关的引用包装。**

第三层用的是 `EVIDENCE_CONFLICT`，docstring 那句是本节最值得记的：

> `contradicting_evidence` 一旦仍有效，就**要求 revise 而非比较分数**。

也就是说系统拒绝做"支持证据 3 条 vs 反对证据 1 条，所以结论成立"这种加权。理由是那个权重没有任何
客观依据——它只会变成一个可以调到让结论通过的旋钮。**在证据系统里，一条有效的反证足以阻止一个
确定性结论；要下结论，必须先解释掉那条反证。**

测试 `policy_vetoes_valid_but_semantically_unsupported_root_cause` 守的正是第一层：**所有引用都合法存在，
但根因文本对不上任何 supported 假设。** 这是一份"引用检查全绿、语义无支撑"的报告——纯存在性检查会
放行它。

### 9.5.4 `_risk_control_issues`：故意与 Schema 重复

```python
for index, step in enumerate(report.remediation_steps):
    missing_controls = not step.prerequisites
    if step.risk_level is RiskLevel.HIGH and not step.evidence_refs:
        missing_controls = True
    if missing_controls:
        issues.append(AuditIssue(code=AuditIssueCode.MISSING_RISK_CONTROL, claim_path=f"remediation_steps[{index}]", ...))
```

这与 §9.2.2 的 `validate_high_risk_controls` 检查的是同一件事。docstring 直接承认并给了理由：

> Schema 已强制 rollback/verification 非空并在 high 时要求引用；此处再次检查前置条件和报告级语义，
> **防止从旧 checkpoint 或未来迁移绕过当前模型**。

两个绕过途径都是真的：第 11 章的 `session_checkpoints` 会把报告 JSON 存进数据库，`resume` 时反序列化——
**一个在旧 Schema 下合法写入的报告，在新 Schema 下 validator 可能已经改了。** Pydantic 校验发生在构造时，
而 checkpoint 恢复出来的对象是用当时的规则构造的。规则层每轮都跑，所以它能拦住这种时间旅行。

另外注意这里比 Schema 更严：**所有等级都要求 `prerequisites` 非空**，而 Schema 只对 HIGH 要求。
9.4.8 那条兜底只读步骤是带 `prerequisites` 的，所以它能过。

### 9.5.5 `_case_issues`：`confirmed=True` 不算证明

```python
confirmed_ids = {memory.memory_id for memory in confirmed_case_memories}
expected_by_id = {item.case_id: item for item in history_case_matches}
for index, item in enumerate(report.similar_cases):
    if not item.confirmed or item.case_id not in confirmed_ids:
        issues.append(AuditIssue(code=AuditIssueCode.UNCONFIRMED_CASE, ...))
        continue
    expected = expected_by_id.get(item.case_id)
    if expected is None or item != expected:
        issues.append(AuditIssue(code=AuditIssueCode.EVIDENCE_CONFLICT, ...))
```

两层，docstring 把两层的必要性都写了：

> `confirmed` 布尔值不足以证明来源，`case_id` 必须命中同批 memory；报告项还必须与 matcher 的完整强类型
> 结果相同，防止后续节点提高 similarity、删除冲突差异或改写历史方案。

**第一层：不信自称。** `SimilarCaseReference.confirmed` 是报告里的一个字段，任何写报告的代码都能把它设成
`True`。真正的证明是"这个 `case_id` 出现在本轮注入的 `confirmed_case_memories` 里"。这与第 8 章那条
"组件不让模型自述"（§8.9.7）是同一个模式：**自我声明的字段只能当索引，不能当凭证。**

**第二层：`item != expected` 是整对象相等比较。** 不是比 `case_id`，不是比 `similarity` 的容差，而是
Pydantic 模型的全字段相等。它防的是三件被点名的事：提高 similarity、删除冲突差异、改写历史方案。

这一层为什么必要，要结合第 10 章的拓扑看：`explain_case_matches` 是一个**确定性**节点，它算出
`history_case_matches`；然后这批结果被 `run_report` 拿去投影进报告。中间没有模型。**那为什么还要防止
被改？** 因为"中间没有模型"是当前实现的性质，不是被强制的不变量。这条规则把它变成了不变量：任何未来
在这两步之间插入的加工都会被立刻发现。**审计规则的价值之一，就是把"目前恰好如此"钉成"必须如此"。**

### 9.5.6 `_completeness_issues`：不许用空字段假装完整

```python
if not report.root_causes and not report.uncertainties:
    issues.append(AuditIssue(code=AuditIssueCode.REPORT_INCOMPLETE, claim_path="uncertainties",
                             message="无根因报告必须明确证据缺口或无法判断原因。"))
if not report.remediation_steps and not report.uncertainties:
    issues.append(AuditIssue(code=AuditIssueCode.REPORT_INCOMPLETE, claim_path="remediation_steps",
                             message="没有修复建议时必须解释为什么只能安全降级。"))
```

docstring 一句话概括：

> 证据不足是合法结果，但空 `root_causes` 不能同时用空 `uncertainties` 假装完整……规则不要求虚构根因，
> 只要求**降级语义可见**。

这是 §9.2.1 那条"证据不足是正常结果"的强制执行形式。一份 `root_causes=[]` 且 `uncertainties=[]` 的报告
在技术上通过所有 Schema 校验，但它对读者说的是"没什么问题"——而真相是"什么都没查出来"。**这两句话
的差别，就是这条规则的全部价值。**

注意这两条是唯一不带 `evidence_refs` 的 `AuditIssue`（`AuditIssue.evidence_refs` 默认空元组）。因为
问题不是"某条引用不对"，而是"某个字段该有内容却是空的"。

### 9.5.7 去重键不含 `message`

```python
key = (issue.code.value, issue.claim_path, issue.evidence_refs)
```

docstring：

> `message` 不参与键，避免同一客观问题因措辞差异重复消耗上下文；首次问题保留，输出顺序与校验阶段一致。

"客观问题的身份"由三元组定义：**什么错、在哪个字段、涉及哪些引用**。措辞不是身份的一部分。

这条在 9.5.3 里就会用到：同一个 `root_causes[0]` 可能既触发 `UNSUPPORTED_CLAIM` 又触发
`EVIDENCE_CONFLICT`——`code` 不同，两条都留。而如果 `_invalid_reference_issues` 和某条未来的新规则用
不同措辞报了同一个 `(INVALID_EVIDENCE_REF, "evidence_refs", ("ev_1",))`，只留一条。

为什么要在意"重复消耗上下文"？因为这些 `issues` 会进 `_merge_audit_result` 交给 Auditor 的下一轮
（§9.6.1）和 `SafeReportReviser` 的 `revision_instructions`。**重复的问题会让模型误以为某个字段错得更严重，
也会挤掉 Prompt 里其他问题的位置。**

顺便注意 `_stable_unique` 在这个文件里被重新实现了一次（`list(dict.fromkeys(items))`），draft.py 里也有
一份。docstring 说明了这不是遗漏：

> 与报告 Builder 保持相同顺序语义，但局部实现避免策略模块依赖 Builder 私有函数。

这跟 §9.2.3 把可引用宇宙抽成共享模块的判断看起来矛盾，其实是同一条标准：**共享的必须是"规则"，不是
"工具"。** 引用宇宙的定义是一条业务规则，三处漂移会造成安全漏洞；"按首次出现顺序去重"是一个两行的
标准库用法，抄一遍的代价远小于让 `policy.py` 依赖 `draft.py` 的私有函数（那会让两个模块的修改互相牵连）。

## 9.6 四级阶梯与非对称否决权

现在把四个组件接起来。CLAUDE.md 把这套机制叫"四级阶梯"，四级是：

| 级 | 谁在判 | 判什么 | 不通过的后果 |
|---|---|---|---|
| 0 | Pydantic Schema | 类型、枚举、字段间不变量 | 构造失败，异常传播（§9.2.2） |
| 1 | `ReportPolicyValidator` | 客观不变量：引用、支撑、风险、案例、完整性 | 强制 `revise`，**模型无法豁免** |
| 2 | `AuditorAgent` | 语义：自然语言是否真的支持结论 | 请求 `revise` |
| 3 | 工作流预算 | 返工次数是否还有 | 转 `degraded` |

放行需要 1 和 2 **同时**同意；而 1 说不行时，2 说行不算。

### 9.6.1 `_merge_audit_result`：非对称性只有九行代码

```python
if not deterministic_issues:
    return model_result
combined_issues = _deduplicate_issues([*deterministic_issues, *model_result.issues])
instructions = list(model_result.revision_instructions)
instructions.append("先修复全部确定性引用、冲突和风险问题，再重新提交独立审计。")
return AuditResult(
    status=AuditStatus.REVISE,
    issues=combined_issues,
    revision_instructions=list(dict.fromkeys(instructions)),
)
```

**只要 `deterministic_issues` 非空，返回的 `status` 就写死是 `REVISE`——不看 `model_result.status`。**
这就是整章标题里那条"非对称否决权"的全部实现。反过来，`deterministic_issues` 为空时原样返回模型结果，
模型的 `revise` 照样生效。所以：

- 规则 revise + 模型 accept → **revise**（规则赢）
- 规则 accept + 模型 revise → **revise**（模型赢）
- 两边都 accept → accept

**没有任何组合能让"一方通过"覆盖"另一方拒绝"。** 这不是投票，是逻辑与。

三个细节：

**确定性问题排在前面。** `[*deterministic_issues, *model_result.issues]`，配合 `_deduplicate_issues` 的
"首个对象保留"，意味着 code/path/refs 相同时**保留规则版本的 message**。docstring：
"保留确定性问题在前的优先顺序。" 规则的措辞是固定文本，模型的措辞每次不同——保留固定的那份，让下游
（`revision_instructions`、`run_events`）稳定可测。

**模型的指令保留，但要追加一条通用指令。** docstring：
"模型 revision instruction 可保留为公开修订要求，但确定性问题只追加通用指令，不让模型覆盖。"
为什么不用规则指令替换模型指令？因为模型可能同时发现了真实的语义问题，那些指令有价值。但规则问题
必须有自己的一句话，否则一份"模型 accept + 规则 revise"的结果会变成 `revision_instructions=[]`——
而 §9.2.2 的 `AuditResult` validator 要求 revise 必须至少有一条指令，**构造会直接抛异常**。
所以这行 `instructions.append(...)` 不是提示语，是**让非对称否决在 Schema 层合法**的必要条件。

**`list(dict.fromkeys(instructions))` 去重。** 如果模型恰好也说了同一句话，不重复。

`_deduplicate_issues` 在这里被又实现了一遍（`policy.py` 里已有一份）。判断标准和 9.5.7 那段一样：这是
一个"稳定去重"工具，不是业务规则；两份实现的键完全相同，且各自 docstring 都写明了键的构成。

### 9.6.2 `_audit_report` 每轮都重新校验

```python
report = graph_state.agent_state.draft_report
if report is None:
    raise RuntimeError("audit node requires a draft report")
# 每轮审计都重新校验当前草稿，不能沿用首次 issues 误判修订后的引用状态。
deterministic_issues = runtime.context.validator.validate(report, graph_state.agent_state, ...)
```

`_draft_report` 已经算过一次 `deterministic_issues` 并写进了状态，但 `_audit_report` **不读它**，重新算。

原因就是那条注释：修订之后引用状态变了。设想第一轮发现 `root_causes[0]` 引用非法，`SafeReportReviser`
把这条根因删了——那么第二轮的正确 `issues` 应该是空的。如果沿用首轮结果，**这份已经修好的报告会被自己
的旧问题永久否决**，必然走到 degraded。

测试 `deterministic_policy_vetoes_model_accept_then_allows_one_safe_revision` 断言的正是这条：

```python
assert [issue.code for issue in auditor.contexts[0].deterministic_issues] == [AuditIssueCode.UNSUPPORTED_CLAIM]
assert auditor.contexts[1].deterministic_issues == ()
```

两轮注入 Auditor 的上下文不同：第一轮带一个 `unsupported_claim`，第二轮为空。这个测试用的是
`ScriptedAuditor([_accept(), _accept()])` + `UnsupportedReportBuilder()`——**模型两次都说 accept，但第一次
被规则否决了**。最终 `outcome=ACCEPTED`、`retry_count=1`、`root_causes == []`。

事件序列也被逐项断言：

```python
assert [event.event_type for event in result.events] == [
    ReportEventType.DRAFT_CREATED,
    ReportEventType.AUDIT_COMPLETED,
    ReportEventType.REVISION_APPLIED,
    ReportEventType.AUDIT_COMPLETED,
]
```

**四个事件，`REVISION_APPLIED` 恰好一次。** 这条断言同时守住了"发生了返工"和"没有发生第二次返工"。

那么既然重新算了，`_draft_report` 写进状态的那份 `deterministic_issues` 有什么用？它是**给公开事件用的**：
`summary=f"确定性草稿已生成，规则预检发现 {len(issues)} 个问题。"`，让读者在第一个事件就知道草稿的
客观质量，而不用等审计结束。

`_draft_report` 还有一处值得看：

```python
agent_state = graph_state.agent_state.model_copy(update={"draft_report": report, "audit_result": None})
```

**报告和 `audit_result: None` 在同一次 `model_copy` 里写入。** docstring："报告和 issues 在一个 state copy 中
原子写入，Auditor 不会看到'有报告但规则未计算'的中间态。" 显式清空 `audit_result` 是因为
`AgentState` 可能是从 checkpoint 恢复的（第 11 章），带着上一次运行的审计结论——**一份新草稿配一份旧
审计，是最危险的中间态。**

### 9.6.3 `_route_after_audit`：只读三个结构化字段

```python
if graph_state.status is ReportWorkflowStatus.COMPLETED:
    return "end"
audit_result = graph_state.agent_state.audit_result
if audit_result is None:
    raise RuntimeError("audit routing requires AuditResult")
if audit_result.status is AuditStatus.ACCEPT:
    raise RuntimeError("accepted audit must mark report workflow completed")
return "revise" if graph_state.agent_state.retry_count < graph_state.max_revisions else "degrade"
```

docstring 的最后一句是本章最该背下来的一句：

> 函数**不读取 revision instruction 自然语言**。

路由只看三个字段：`status`（工作流级）、`AuditStatus`（枚举）、`retry_count` vs `max_revisions`（整数）。
这是第 8 章 §8.10 那条"路由只读枚举"的同一条纪律，也是 §9.2.2 那些 Schema validator 的兑现——正因为
`accept` 在类型层就不可能带 issue，这里才敢只看枚举。

**注意第一个 `if` 同时处理了两条完全不同的路径**：模型 accept（`_audit_report` 里已写
`COMPLETED/ACCEPTED`）和 Auditor 异常降级（同样已写 `COMPLETED/DEGRADED`）。两者都返回 `"end"`。
节点自己决定终态，路由只负责发现"已经终了"——这个分工让 `AuditorAgentError` 的处理完全留在节点内部，
路由不需要知道"审计不可用"这个概念存在。

那句 `raise RuntimeError("accepted audit must mark report workflow completed")` 是一条**不变量断言**，
不是错误处理：能走到这里说明 `_audit_report` 判了 accept 却忘了写 `status=COMPLETED`。如果不抛，
`retry_count < max_revisions` 会把一份已被接受的报告送进返工——一个"审计通过反而被删结论"的极隐蔽 bug。
**在两个节点分别维护同一个状态转换时，用断言把它们的一致性钉住。**

最后一行还有一个容易忽略的细节：预算比较用的是 `graph_state.max_revisions`（状态里的副本），而
`_revise_report` 的守卫用的是 `runtime.context.config.max_revisions`。两份值都在 `run()` 里从同一个
config 赋出：

```python
initial_state = ReportGraphState(..., max_revisions=self._runtime.config.max_revisions)
```

为什么要在状态里放一份副本？因为**LangGraph 的条件边函数只接收 state，拿不到 runtime**——
`_route_after_audit(graph_state)` 的签名里没有 `Runtime` 参数。这是把配置塞进状态的合法理由之一，与
第 8 章"依赖不能进状态"（§8.5）不冲突：`max_revisions` 是一个可序列化的整数，不是 Agent 实例。

### 9.6.4 返工预算属于工作流，模型碰不到

```python
class ReportWorkflowConfig(...):
    max_revisions: int = Field(default=1, ge=0, le=1)
```

`le=1`。**类型层就写死了"最多一次返工"**，配置改不了，模型更改不了。构造函数的 docstring：

> 返工预算由 Pydantic config 限制为零或一，**不允许节点用魔法数字扩张循环**。

这与第 8 章的 `max_steps` 是同一类东西，但上限严格得多。为什么报告层只给一次？`AuditedReportWorkflow`
的类 docstring 回答了：

> 图不会重新执行 MCP，报告级返工若需要新证据只能降级，后续切片再接回 Planner 调查边。

**报告层的返工不可能带来新证据。** `SafeReportReviser` 只删不加（§9.7），所以第二轮审计看到的报告一定是
第一轮的子集。如果第一轮的问题是"证据不足"，删掉更多内容不会让它变充分——**再给第二次、第三次机会，
唯一的效果是多花两次 Auditor 调用然后得到同一个降级结论。** 一次返工够用，是因为它能修的只有"报告里
有不该有的东西"这一类问题。

测试 `second_revise_degrades_and_removes_unaccepted_claims` 用 `ScriptedAuditor([_revise(), _revise()])`
证明第二次 revise 不会触发第二次返工：Auditor 恰好被调用两次、`REVISION_APPLIED` 恰好一次、最终
`degraded`，且 `audit_result` 仍保留 `revise` 以明确"未通过"。**降级稿不会把 `audit_result` 改成 accept
来让终态看起来漂亮。**

`_revise_report` 里那条守卫是同一条不变量的第二道锁：

```python
if graph_state.agent_state.retry_count >= runtime.context.config.max_revisions:
    raise RuntimeError("revision node entered after revision budget exhausted")
```

路由已经保证不会进来，这里再断言一次——因为节点是可以被单元测试直接调用的（第 8 章 §8.10 提过同样的
理由），而**一个只由调用方保证的前置条件，在直接调用时就没人保证了**。

### 9.6.5 `AuditorAgentError`：立即降级，不消耗预算，不重跑报告

```python
except AuditorAgentError as exc:
    unavailable_issue = AuditIssue(
        code=AuditIssueCode.AUDITOR_UNAVAILABLE,
        claim_path="auditor",
        message=exc.public_summary,
    )
    audit_result = AuditResult(
        status=AuditStatus.REVISE,
        issues=[unavailable_issue],
        revision_instructions=["Auditor 不可用，禁止放行并返回安全降级报告。"],
    )
    degraded = runtime.context.reviser.degrade(report, tuple(audit_result.issues), graph_state.agent_state, ...)
    agent_state = graph_state.agent_state.model_copy(update={"draft_report": degraded, "audit_result": audit_result})
    stopped = graph_state.model_copy(update={
        "agent_state": agent_state,
        "deterministic_issues": tuple(audit_result.issues),
        "status": ReportWorkflowStatus.COMPLETED,
        "outcome": ReportWorkflowOutcome.DEGRADED,
    })
    return _append_report_event(stopped, event_type=ReportEventType.SAFE_DEGRADED,
                               summary=f"Auditor 失败（{exc.stop_reason}），报告未放行并已安全降级。", ...)
```

这段代码里最重要的东西是**它没有做什么**：

- **没有 `retry_count + 1`。** 返工预算是给"报告有问题"用的，而这里报告没问题——是审计服务挂了。
  扣掉预算等于让一次基础设施故障永久剥夺这次运行的返工机会。
- **没有回到 `draft_report`。** 重跑确定性草稿必然产出一模一样的报告（§9.2.1 第 1 点），毫无意义。
- **没有重试 Auditor。** 重试已经在第 7 章的 Provider 层做完了（`AuditorAgentError` 是重试之后仍然失败）。
  编排层再重试一次，就变成了嵌套重试——总耗时不可预测。
- **没有把它当成 accept。** 这是整段的核心。CLAUDE.md 那句话是最精确的表述：**"审计不可用"不等于
  "审计通过"。**

`claim_path="auditor"` 也值得注意：它不指向报告里的任何字段，因为问题不在报告里。而 `message` 用的是
`exc.public_summary`——第 7 章那个刻意构造的、**不含 URL、模型名、凭据、Provider 原始响应**的摘要
（§7.9）。异常穿过编排层进入公开事件，中间没有任何一处需要重新做脱敏，因为**脱敏在异常被构造的那一刻
就完成了**。

`degrade` 里那份 `AuditResult` 还有一个 Schema 层的巧合值得看：它的 `revision_instructions` 必须非空
（§9.2.2），而这个"降级"路径根本不会执行修订。写下"Auditor 不可用，禁止放行并返回安全降级报告。"
既满足了 Schema，也让 `run_events` 里出现一句人能读懂的话。

测试 `auditor_provider_failure_degrades_without_report_revision_retry` 逐条断言了上面那些"没做"：

```python
assert result.outcome is ReportWorkflowOutcome.DEGRADED
assert result.state.retry_count == 0
assert result.state.audit_result.issues[0].code is AuditIssueCode.AUDITOR_UNAVAILABLE
assert [event.event_type for event in result.events] == [
    ReportEventType.DRAFT_CREATED,
    ReportEventType.SAFE_DEGRADED,
]
```

**只有两个事件**——没有 `AUDIT_COMPLETED`（审计没完成）、没有 `REVISION_APPLIED`（没返工）。
用例 docstring 还提到一条："异常公开摘要不包含 URL 或凭据。"

### 9.6.6 `max_revisions=0`：完全关掉返工

```python
return "revise" if graph_state.agent_state.retry_count < graph_state.max_revisions else "degrade"
```

`max_revisions=0` 时 `0 < 0` 为假，第一次 revise 就直接 `degrade`。测试
`zero_revision_budget_degrades_after_first_revise_without_incrementing_counter`：

```python
assert result.outcome is ReportWorkflowOutcome.DEGRADED
assert len(auditor.contexts) == 1
assert result.state.retry_count == 0
assert ReportEventType.REVISION_APPLIED not in {event.event_type for event in result.events}
```

用例 docstring 说明了这个配置的意义："该边界证明配置可以完全关闭报告返工，同时**仍要求 Auditor 审查并
安全删除未放行内容**。" 也就是说 `max_revisions=0` 关掉的是"修一次再试"，不是"审计"——审计仍然跑，
未放行的结论仍然被删。

`retry_count` 保持 0 这条断言的意思是：**系统不假装执行过一次返工。** 一个很容易写出的实现会在降级时
把 `retry_count` 设成 `max_revisions` 以表示"预算用完了"，那会让第 12 章的 `/demo` 和 `run_events` 显示
"已修订 0 次"变成"已修订 1 次"——一次不存在的返工。

## 9.7 `SafeReportReviser`：只删不加

返工是整个系统里最容易被写成安全漏洞的地方。原因很简单：**返工的输入包含 Auditor 的自然语言指令**，
而一个"根据指令修改报告"的实现，就是把自由文本重新接回了报告正文——第 8 章和 §9.2.1 费尽力气堵住的
那条通道，会在这里重新打开。

`SafeReportReviser` 的类 docstring 把边界写死了：

> Reviser 只收窄报告，不提升置信度或增加根因；**即使 Auditor 指令含有新事实，也只读取有限
> `AuditIssueCode` 决定保守动作。** 该边界保证返工不会成为绕过证据门禁的第二个生成通道。

注意"只读取有限 `AuditIssueCode`"——`revise()` 的参数里有完整的 `AuditIssue`（含 `message`），但实现
**从不读 `message`**。它只读 `code` 和 `claim_path`。**枚举和受限路径语法是可穷举的，自由文本不是。**

### 9.7.1 精确删除 vs 整类删除：一次实测事故

模块 docstring 用一段很长的话记录了这个决定，值得整段引用：

> 删除按 `claim_path` 定位到具体条目：修订器只会删内容，删除方向永远偏安全，而修订稿必须再过一遍
> 确定性规则与独立 Auditor 才可能被接受，因此"精确删除"不会成为放行不良结论的通道；**反过来把整类
> 根因一起删掉才会制造新问题——空报告与现有 Observation 自相矛盾，第二轮审计以 evidence_conflict
> 再否决一次，返工预算必然耗尽。**

这段话推翻的是一个看起来更保守的写法：*"审计说 `root_causes` 有问题？那就把 `root_causes` 全清空，
最安全。"* 测试 `safe_reviser_keeps_unflagged_claims_and_falls_back_when_path_is_unparseable` 的 docstring
记录了它在真实模型上的后果：

> 第一段构造两个根因、只否决第二个：修订稿必须保留第一个，否则模型给出的正确根因会被连带删掉，
> 第二轮审计再以 evidence_conflict 否决一次并耗尽返工预算（**首次真实模型评测的案例 1 就是如此**）。

**"删得更多"在这里不等于"更安全"。** 因为报告不是孤立的文本，它要和 `AgentState` 里的 Observation
一致：证据明明显示了 A 故障，报告却说"没有根因"，那是**一份自相矛盾的报告**，而自相矛盾会被
`EVIDENCE_CONFLICT` 否决。整类删除把"一个无支撑结论"这个可修的问题，换成了"报告与证据矛盾"这个
不可修的问题。

这条经验的一般形式值得记住：**降级的方向必须让报告仍然自洽。** 单向地"删更多"不保证自洽。

### 9.7.2 受限路径语法与兜底

```python
# 受限路径语法：可选 `$.` 前缀、字段名、可选 `[i]` 或 `[i:j]`。模型实际会写出 `$.root_causes[0]`、
# `summary`、`$.uncertainties[2:5]` 三种形态，无法解析时退回整类删除而不是猜测。
_CLAIM_PATH_PATTERN = re.compile(
    r"^\$?\.?(?P<field>[a-z_]+)(?:\[(?P<start>\d+)(?::(?P<stop>\d+))?\])?$"
)
```

这个正则**故意不支持嵌套路径**。`root_causes[0].evidence_refs[0]` 匹配不上——它会走兜底。
测试第二段就是用这个路径验证兜底的。

为什么不支持？因为支持它意味着要实现"删除某条根因的第 0 个引用"这个语义，而那是**修改**一条结论
（改变它的支撑证据），不是删除它。**Reviser 的能力边界只有"删条目"，路径语法就只应该能表达"哪个条目"。**
语法的表达力必须和实现的能力对齐——语法能说出实现做不到的事，就一定会出现"看起来处理了其实没处理"
的路径。

`_parse_claim_path` 的三个返回形态：

```python
matched = _CLAIM_PATH_PATTERN.match(claim_path.strip())
if matched is None:
    return (None, None)
field = matched.group("field")
start_text = matched.group("start")
if start_text is None:
    return (field, None)          # 整个字段
start = int(start_text)
stop_text = matched.group("stop")
if stop_text is None:
    return (field, frozenset({start}))   # 单个下标
stop = int(stop_text)
if stop <= start:
    return (None, None)           # 方向相反的切片视为不可解析
return (field, frozenset(range(start, stop)))
```

`stop <= start` 判成不可解析，而不是"空集合"。docstring 给的理由是本节最关键的一句：

> 语法不符或切片方向相反都返回 `(None, None)`，由调用方退回整类删除——**猜测下标会删错条目，而删错的
> 方向不一定偏安全。**

如果 `[5:2]` 被解释成空集合，效果是"什么都不删"，那份被审计否决的结论会**原样进入第二轮审计**，再被
否决一次，预算耗尽。**面对无法理解的输入，"什么都不做"往往不是安全的选择。**

`_removal_targets` 把 issues 翻译成删除计划：

```python
for issue in issues:
    if issue.code not in _CLAIM_REMOVING_CODES:
        continue
    field, indices = _parse_claim_path(issue.claim_path)
    if field in _DERIVED_FIELDS:
        continue
    if field is None or field not in _LIST_FIELDS:
        wholesale = True
        continue
    if indices is None:
        targets[field] = None
        continue
    existing = targets.get(field, frozenset())
    # 已经决定整类删除的字段不必再累加下标，否则会把 None 覆盖成更宽松的集合。
    if existing is None:
        continue
    targets[field] = existing | indices
```

注意那条行内注释守的坑：`targets[field]` 的 `None` 表示"整类删除"，而 `frozenset` 表示"删这几个下标"。
如果先来一条整类删除的问题、后来一条带下标的，不加这个判断就会把 `None` 覆盖成一个小集合——
**从"删全部"退化成"删一个"，正好是不安全的方向。** 这是"用 `None` 表示特殊语义"这种设计必然要付的税：
每一处读写都要先判 `None`。

兜底的具体动作是：

```python
if wholesale:
    targets["root_causes"] = None
    targets["fault_chain"] = None
    targets.setdefault("similar_cases", None)
```

前两个用 `=` 直接覆盖，第三个用 `setdefault`。这不是笔误：`similar_cases` 如果已经有精确的下标计划，
就保留那个计划（因为 `_case_issues` 给出的路径一定带索引，是可信的）；而根因和链路必须无条件清空。
行内注释也说明了兜底是异常路径而非常态：

> 这是兜底而不是常态路径，确定性规则给出的路径始终带索引，模型路径也覆盖了受限语法的三种形态。

### 9.7.3 四个删除码，三个不删

```python
# 只有这些代码代表"某条声明不能留"；invalid_evidence_ref 由引用过滤处理，report_incomplete 表示
# 缺内容，再删只会让报告更空，auditor_unavailable 根本不进入修订路径。
_CLAIM_REMOVING_CODES = frozenset({
    AuditIssueCode.UNSUPPORTED_CLAIM,
    AuditIssueCode.EVIDENCE_CONFLICT,
    AuditIssueCode.UNCONFIRMED_CASE,
    AuditIssueCode.MISSING_RISK_CONTROL,
})
```

七个 `AuditIssueCode` 里只有四个触发删除，另外三个各有各的处理方式：

| 未列入的 code | 为什么不删 | 怎么处理 |
|---|---|---|
| `INVALID_EVIDENCE_REF` | 问题在引用不在结论 | 由 `_valid_refs` 统一过滤；引用全丢的结论自然被淘汰 |
| `REPORT_INCOMPLETE` | 表示"缺内容" | 删更多只会更空；由重算 `evidence_refs` 和补 `uncertainties` 解决 |
| `AUDITOR_UNAVAILABLE` | 不进修订路径 | §9.6.5 直接 `degrade()` |

第一条的机制值得展开。`revise` 不针对 `INVALID_EVIDENCE_REF` 做定向删除，而是对**每一条保留下来的结论**
都重新过滤引用：

```python
root_causes = [
    item.model_copy(update={"evidence_refs": _valid_refs(item.evidence_refs, valid_refs)})
    for item in _survivors(report.root_causes, targets, "root_causes")
    if _valid_refs(item.evidence_refs, valid_refs)
]
```

**`if _valid_refs(...)` 这个条件是关键**：过滤后引用为空的根因直接被淘汰。行内注释："先按定位删除，
再清理引用；任何引用为空的根因/链路都不能继续存在。" 也就是说"悬空引用"这类问题**不需要 claim_path
也能被正确处理**——因为处理方式是无条件的、作用于全体的。这比逐条定位更可靠。

`remediation_steps` 的处理不一样：

```python
retained_steps = [
    item
    for item in _survivors(report.remediation_steps, targets, "remediation_steps")
    if item.risk_level is not RiskLevel.HIGH or _valid_refs(item.evidence_refs, valid_refs)
]
```

**只有 HIGH 风险的步骤在失去全部引用后被淘汰**，low/medium 保留。这和 §9.2.2 的
`validate_high_risk_controls` 是同一条口径：低风险只读检查本来就允许没有引用（9.4.8 那条兜底步骤就是
`evidence_refs=[]`），把它删掉会让报告失去"下一步做什么"。而 HIGH 步骤没有引用**在 Schema 层就非法**，
留着它 `DiagnosisReport` 会直接构造失败。**这个条件不只是安全考虑，它是让修订稿能被构造出来的必要条件。**

### 9.7.4 派生字段：重算，不删

```python
# summary、risks 与报告级 evidence_refs 全部由保留内容重新推导，指向它们的问题靠重算解决；
# 若把它们当成删除信号，一句被判为无支撑的摘要就会连带删光本来有引用支撑的根因。
_DERIVED_FIELDS = frozenset({"summary", "risks", "evidence_refs"})
```

这三个字段就是 9.4.3、9.4.4、9.4.9 讲的那三个派生量。它们在 `_removal_targets` 里被 `continue` 跳过，
然后在构造新报告时无条件重算：

```python
evidence_refs = _aggregate_refs(root_causes, fault_chain, remediation_steps, similar_cases)
...
return DiagnosisReport(
    summary=_revision_summary(root_causes, fault_chain),
    ...
    # 风险文本与草稿共享同一推导规则：写死"只允许人工只读核验"会与保留下来的中风险步骤
    # 直接矛盾，而这正好构成 Auditor 的 evidence_conflict，把一次本可放行的修订推向降级。
    risks=derive_report_risks(remediation_steps),
    ...
)
```

`risks` 那条注释是 9.4.9 那句 docstring 的另一半，两处互相引用。这里的教训是：**派生字段一旦被写死或
单独修改，就会与它的来源矛盾，而矛盾是会被审计发现的。**

那条 `_DERIVED_FIELDS` 注释描述的失败路径也值得想一遍：Auditor 判"summary 无支撑"，`claim_path="summary"`。
如果不跳过，`_parse_claim_path` 返回 `("summary", None)`，而 `summary` 不在 `_LIST_FIELDS` 里 → `wholesale=True`
→ **根因和链路全被清空**。一句摘要的措辞问题，会连带删掉所有有证据支撑的结论。测试第三段专门验证
这条："指向 summary 的问题只触发重算。"

### 9.7.5 `order` 重编号与"摘要必须复述结论"

`order` 重编号：

```python
# order 在删除之后重新编号：沿用原下标会留下 1、3、4 这样的空洞，人工执行时无法判断
# 中间那一步是被删了还是漏渲染了。
remediation_steps = [
    item.model_copy(update={"order": order, "evidence_refs": _valid_refs(item.evidence_refs, valid_refs)})
    for order, item in enumerate(retained_steps, start=1)
]
```

这就是 §9.2.2 那条"编号必须 1..N 连续"逼出来的细节。**Schema 的那条约束不只是格式洁癖：它强迫修订逻辑
必须重编号，从而消除了"1、3、4"这种会让执行者误判的输出。** 如果 Schema 允许空洞，这里就会有人写
`item` 原样保留，然后运维在凌晨三点对着缺了第 2 步的 runbook 猜测那一步是什么。

**一个好的 Schema 约束的价值不在于它拒绝了什么，而在于它逼出了什么实现。**

删空之后还有一条兜底：

```python
if not remediation_steps:
    remediation_steps = [_readonly_follow_up_step()]
```

`_readonly_follow_up_step()` 与 9.4.8 那条兜底步骤是两个不同的函数（一个在 `draft.py`、一个在
`revision.py`），措辞也不同："停止生产变更，仅通过白名单只读工具补齐 Auditor 指出的证据缺口。" 后者
明确提到了 Auditor，因为它只在审计之后出现。docstring 强调"每次调用返回新对象避免共享可变列表"——
`RemediationStep` 有 `prerequisites` 这样的列表字段，模块级常量会被多份报告共享。

然后是 `_revision_summary`，它的 docstring 记录了一次真实模型实测：

```python
if root_causes:
    head = root_causes[0].root_cause.strip()
    if len(root_causes) > 1:
        return f"修订后保留 {len(root_causes)} 项有引用支撑的根因，其中首要根因为：{head}"
    return f"修订后保留唯一有引用支撑的根因：{head}"
if fault_chain:
    head = fault_chain[0].description.strip()
    return (f"修订后保留 {len(fault_chain)} 段可追溯的传播链路，但尚不能收敛到单一根因；"
            f"链路起点为：{head}")
return "当前引用集合不足以支撑根因或传播链路结论，修订稿只保留只读补证步骤。"
```

> 摘要是 Auditor 逐项核对的字段之一：只写流程状态会被判为 `report_incomplete`（**实测评语是"摘要仅描述
> 报告修订状态，没有回答用户要求判断的问题"**），因此这里必须复述保留下来的根因或链路。

之前的实现写的是"报告已按审计要求修订"这类过程陈述。它在逻辑上无可指责，但 Auditor 说得对：**用户问的
是"我的系统为什么坏了"，摘要回答的是"这份报告经历了什么"。** 这是一次模型审计发现了确定性代码缺陷的
真实案例——很值得记住，因为它说明第二个 Agent 的价值不只是"多一道保险"。

### 9.7.6 自我否决回路：审计问题码不能写进报告正文

这是本章最值得单独学的一个事故。代码里那段注释就是它的全部记录：

```python
# 审计问题码刻意不再写进 uncertainties：它们已经通过 audit_completed / revision_applied 公开
# 事件对外暴露，而"首次审计要求修订：unsupported_claim"这类句子本身不是本轮证据支持的事实。
# 第二轮审计会以 unsupported_claim 指向 uncertainties 把修订稿自己写的这几句话再否决一次，
# 于是返工预算必然耗尽——首次真实模型评测三个案例全部 safe_degraded 就有这条自我否决回路。
uncertainties = _survivors(report.uncertainties, targets, "uncertainties")
```

**原来的实现把审计问题码写进了 `uncertainties`**，动机完全正当：让用户看到"审计发现了什么"。后果是一个
闭环：

```text
第一轮审计 → unsupported_claim
    ↓
修订：删掉根因，并在 uncertainties 里写"首次审计要求修订：unsupported_claim"
    ↓
第二轮审计：uncertainties 里这句话本身没有任何证据支撑 → unsupported_claim
    ↓
预算耗尽 → safe_degraded
```

**修订稿被自己写的修订说明否决了。** 而且这个回路是稳定的、必然发生的——所以首次真实模型评测的三个
案例全部落到 `safe_degraded`。

修好之后 `uncertainties` 写什么？三个分支，全部描述**报告本身的状态**而不是审计过程：

```python
if not root_causes and not fault_chain:
    uncertainties.append("当前引用集合不足以支撑可审计的根因与传播链路，相关结论已移除。")
elif len(root_causes) < len(report.root_causes) or len(fault_chain) < len(report.fault_chain):
    uncertainties.append("审计否决的结论已按定位删除，保留部分只覆盖仍有引用支撑的判断。")
if not uncertainties:
    uncertainties.append("修订稿只保留现有引用可支持的内容，其余判断需要补充只读取证。")
```

差别很微妙但很关键："审计否决的结论已按定位删除"是一条**关于这份报告的事实**（读者可以对照
`root_causes` 长度自行验证）；"首次审计要求修订：unsupported_claim"是一条**关于审计过程的断言**，报告
里没有任何东西能支撑它。

那么用户怎么知道审计发现了什么？注释给了答案：**通过 `audit_completed` / `revision_applied` 公开事件**
（§9.9）。**信息没有丢失，只是换了出口。** 报告正文回答"你的系统怎么了"，事件流回答"这个结论是怎么被
审出来的"——两个问题分别有自己的通道。

这条经验的一般形式：**在一个"每条陈述都必须有证据"的系统里，元陈述（关于系统自身运行的陈述）没有
证据可引。** 所以它们必须走另一条通道，否则它们会被系统自己的规则判为违规。

测试断言得很彻底：

```python
assert any("按定位删除" in item for item in revised.uncertainties)
assert not any("审计要求修订" in item for item in revised.uncertainties)
assert not any(code.value in item for item in revised.uncertainties for code in AuditIssueCode)
```

第三行遍历**全部七个** `AuditIssueCode`，断言没有任何一个的字符串值出现在任何一条 `uncertainty` 里。
这是一条会随枚举扩展自动生效的断言——**新增一个 code 不需要改测试，它自动被覆盖。**

同一个用例还断言了 9.7.1 的精确删除和 9.7.4 的派生重算：

```python
assert revised.root_causes == []
assert revised.fault_chain == initial.fault_chain
assert revised.risks == derive_report_risks(revised.remediation_steps)
```

第二行是精确删除的证明（只否决了 `root_causes[0]`，链路一条不动）；第三行不是断言某个具体字符串，而是
断言**与共享函数的输出相等**——这样 `derive_report_risks` 将来改措辞，测试不会假失败，但两处实现漂移
一定会被抓到。

## 9.8 `degrade`：终态，不是"更狠的修订"

```python
retained_refs = _valid_refs(report.evidence_refs, valid_refs)
issue_codes = sorted({issue.code.value for issue in issues})
uncertainties = ["Auditor 未能放行报告，所有根因、链路和历史案例结论均已移除。"]
uncertainties.extend(f"未解决审计问题：{code}。" for code in issue_codes)
return DiagnosisReport(
    summary="本次诊断返回安全降级报告：保留证据索引，但不确认根因或生产修复方案。",
    fault_chain=[],
    root_causes=[],
    evidence_refs=retained_refs,
    remediation_steps=[_readonly_follow_up_step()],
    risks=["不得依据本降级报告执行生产写操作或自动修复。"],
    uncertainties=uncertainties,
    similar_cases=[],
)
```

**`root_causes`、`fault_chain`、`similar_cases` 全部清空，无条件。** 不做定位、不看 `claim_path`。

有意思的是：**降级稿反而写了 issue codes**（`f"未解决审计问题：{code}。"`），而 9.7.6 刚说修订稿不能写。
这不矛盾，因为**降级稿是终态，不会再进审计**。9.7.6 那个自我否决回路的成立条件是"还有下一轮审计"；
降级稿没有下一轮，所以这些信息可以直接写给用户。`degrade` 的 docstring 也点了这个终态性质："该结果
明确未获审计接受。"

**`evidence_refs=retained_refs` 是唯一被保留的东西。** 为什么清空了所有结论还留引用？因为引用是**读者
继续排查的入口**：一份说"我不知道原因，但这是我查到的 12 条证据"的报告，比一份完全空白的报告有用得多。
docstring："降级稿仅保留仍可寻址的原始报告引用。" 注意仍然过了 `_valid_refs`——降级不是放宽引用要求的
借口。

这也解释了 9.5.2 那条"汇总覆盖检查是单向的"：降级稿的 `evidence_refs` 里有一堆没被任何子结论使用的
引用，如果检查是双向的，降级稿自己就过不了规则校验。

`sorted(...)` 是为了确定性输出（`set` 的迭代顺序不稳定），这样降级稿也能被 Golden 回放逐字断言。

docstring 最后一句是它与 §0.4 第 2 条规则的接口：

> 它不会把 Auditor 消息原文或模型响应写给用户，也**不会生成 memory candidate**。

第 10 章的 `stage_case_memory` 只接收 accepted 且含根因的报告。降级稿两个条件都不满足——`outcome` 是
`DEGRADED`，`root_causes` 是空的。**两道独立的门，任一道都足以拦住它。**

测试断言：

```python
assert degraded.root_causes == []
assert degraded.similar_cases == []
assert degraded.remediation_steps[0].risk_level is RiskLevel.LOW
assert "不得依据本降级报告" in degraded.risks[0]
```

注意这个用例是先 `revise` 再 `degrade`，用同一个 issue 连续调用两次——**验证 `degrade` 不依赖"输入是原始
草稿"这个前提**，它对任何报告都产出同一种终态。

## 9.9 公开面：只有 code，没有 message

`_append_report_event` 是本章唯一的对外投影入口：

```python
sequence = len(graph_state.events) + 1
event_id = _stable_event_id(graph_state.agent_state.run_id, str(sequence), event_type.value)
issue_codes = tuple(dict.fromkeys(issue.code for issue in issues))
event = ReportPublicEvent(
    event_id=event_id,
    sequence=sequence,
    event_type=event_type,
    summary=summary,
    audit_status=audit_status,
    issue_codes=issue_codes,
    revision_number=graph_state.agent_state.retry_count,
)
return graph_state.model_copy(update={"events": [*graph_state.events, event]})
```

**`issues` 进来，只有 `issue.code` 出去。** `message` 一个字都不投影。CLAUDE.md 那条边界的原话是：
"`run_events` 与 `/demo` 裁决卡只暴露问题码与 `claim_path`，不暴露 `issues[].message`。"

为什么？因为 `AuditIssue.message` 有两种来源：规则给的固定文本（安全），和**Auditor 模型生成的自由文本**
（不安全）。模型的 message 可能包含它对 Prompt 内容的复述——而 Prompt 里有证据原文、能力片段，甚至
（如果实现有缺陷）思维链。`ReportPublicEvent` 的类 docstring 说得很准：

> `issue_codes` 不复制模型消息，既可解释又**避免把未验证自然语言当作事实**。

七个枚举值足够解释"哪一类问题"，而它们是**闭集**——第 12 章的 `/demo` 前端可以为每个 code 准备固定的
中文说明和图标，永远不会遇到未知内容。这与第 8 章 §8.13 的 `ReactPublicEvent` 是同一套做法：
`ConfigDict(extra="forbid", frozen=True)` + 有限枚举 + 定长 ID 模式。

`ReportPublicEvent` 的字段约束：

```python
event_id: str = Field(pattern=r"^report_evt_[a-f0-9]{16}$")
sequence: int = Field(ge=1)
event_type: ReportEventType
summary: str = Field(min_length=1, max_length=500)
audit_status: AuditStatus | None = None
issue_codes: tuple[AuditIssueCode, ...] = ()
revision_number: int = Field(ge=0, le=1)
```

`revision_number` 的 `le=1` 又出现了一次——**返工上限这条约束在四个地方被独立表达**：
`ReportWorkflowConfig.max_revisions`（`le=1`）、`ReportGraphState.max_revisions`（`le=1`）、
`ReportPublicEvent.revision_number`（`le=1`）、`_revise_report` 的运行时守卫。多处重复不是冗余，
是**让"预算被绕过"这个 bug 在最早的位置暴露**：如果某天有人把 config 上限改成 3，事件模型会立刻在
第二次返工时构造失败。

`_stable_event_id` 与第 8 章的 `_stable_id` 同构，只是前缀不同：

```python
digest = sha256("|".join(parts).encode("utf-8")).hexdigest()[:16]
return f"report_evt_{digest}"
```

docstring 讲了前缀的作用："前缀隔离 ReAct 与报告事件命名空间"，以及截断的边界："截断只用于本作品审计
引用，**不承担认证或密码学唯一性**。" 后半句很重要：16 位十六进制 = 64 bit，作为可读 ID 够用，但任何
人不应该拿它当安全凭证。**明确写出"这个哈希不是为安全设计的"，比让读者自己猜要好。**

输入是 `(run_id, sequence, event_type)`——**不含任何模型文本**，所以同一次运行、同一条控制流重放会得到
同一批 ID。这是 Golden 回放能逐字段断言事件的前提。

## 9.10 `ReportRunResult`：终态的四条不变量

`run()` 的最后一段和 `ReportRunResult` 的 validator 一起，构成本章最后一道门：

```python
final_state = ReportGraphState.model_validate(raw_state)
if final_state.status is not ReportWorkflowStatus.COMPLETED:
    raise RuntimeError("report graph ended without completed status")
if final_state.outcome is None:
    raise RuntimeError("completed report graph requires outcome")
```

第一条挡的是"图因为边配置错误提前结束"；第二条挡的是 `COMPLETED` 但没写 `outcome`。注意
`ReportGraphState.model_validate(raw_state)` 这一步——LangGraph 返回的是 dict，**重新过一遍 Pydantic**
是防止节点通过 `model_copy(update=...)` 写进了不符合 schema 的东西。

然后 validator 又检查四条：

```python
if self.state.draft_report is None or self.state.audit_result is None:
    raise ValueError("completed report workflow requires report and audit result")
if self.outcome is ReportWorkflowOutcome.ACCEPTED:
    if self.state.audit_result.status is not AuditStatus.ACCEPT:
        raise ValueError("accepted outcome requires accepted audit")
elif self.state.audit_result.status is AuditStatus.ACCEPT:
    raise ValueError("degraded outcome cannot contain accepted audit")
if self.events[-1].event_type not in {ReportEventType.AUDIT_COMPLETED, ReportEventType.SAFE_DEGRADED}:
    raise ValueError("report workflow requires a terminal public event")
```

1. **报告和审计结论都必须存在。** 一个 `outcome=ACCEPTED` 但 `audit_result=None` 的结果毫无意义。
2. **`ACCEPTED` ⟹ `AuditStatus.ACCEPT`。**
3. **`DEGRADED` ⟹ 不是 `ACCEPT`。** 这条是第 2 条的逆向，docstring 说得直接："degraded 不得伪装为
   accept。" 两条一起把 `outcome` 和 `AuditStatus` 变成**双向等价**，任一方向的漂移都会被抓到。
4. **最后一个事件必须是 `AUDIT_COMPLETED` 或 `SAFE_DEGRADED`。** docstring："防止图因边配置错误在修订
   中途静默结束。" 如果 `revise_report → audit_report` 这条边某天被误删，图会在 `REVISION_APPLIED` 之后
   结束——`status` 可能还是 `RUNNING`（被第一条 `RuntimeError` 抓住），但如果同时有人手滑写了
   `COMPLETED`，这条断言是最后一张网。

再加上 `events: list[ReportPublicEvent] = Field(min_length=2)`：至少两个事件（草稿 + 终态）。
§9.6.5 那条 Auditor 失败路径恰好产出两个，是这个下限的来源。

`ReportRunRequest.validate_post_react_boundary` 是同一种思路，在**入口**方向：

```python
if not self.state.stop_reason:
    raise ValueError("report workflow requires a completed ReAct state")
if self.state.intent != self.capabilities.intent.value:
    raise ValueError("report workflow intent must match capability selection")
if self.state.active_capabilities != expected_names:
    raise ValueError("report workflow capabilities must match state")
if any(memory.status is not MemoryStatus.CONFIRMED for memory in self.confirmed_case_memories):
    raise ValueError("report workflow can include only confirmed case memories")
if [item.memory_id for item in self.confirmed_case_memories] != [
    item.case_id for item in self.history_case_matches
]:
    raise ValueError("report history explanations must match confirmed memory order")
```

五条，每条都在**构造图状态之前**就失败，docstring："任一失败都不会调用 Builder 或 Auditor。"
这是第 7 章那条"免费的门放在付费调用之前"（§8.8.1 的同一原则）在跨层边界上的应用。

最后那条列表相等断言值得注意：`confirmed_case_memories` 的 ID 序列必须**逐位等于** `history_case_matches`
的 `case_id` 序列——不是集合相等，是顺序相等。它把 §9.5.5 那条"案例解释不能漂移"的检查提前到了入口：
两个参数必须是同一批案例的两种视图。**如果它们能不一致，`_case_issues` 的 `expected_by_id` 查表就会
稳定漏项。**

## 9.11 本章的设计取舍清单

| # | 决定 | 被放弃的写法 | 放弃的理由 | 位置 |
|---|---|---|---|---|
| 1 | 草稿由确定性代码投影 | 把证据丢给模型写报告 | 模型会填满空白；无法 Golden 回放 | §9.2.1 |
| 2 | 模型贡献走"假设"通道 | 草稿兼读 `decision_summary` 自由文本 | 会毁掉确定性、可引用性和降级语义 | §9.2.1 |
| 3 | high 风险缺保护在 Schema 层失败 | 只在 Prompt 里提醒 Auditor | Prompt 不是门禁 | §9.2.2 |
| 4 | `accept` 不许带 issue | 允许"口头接受但仍列问题" | 只读枚举的路由会放行有问题的报告 | §9.2.2 |
| 5 | `order` 必须 1..N 连续 | 允许编号空洞 | 逼出修订重编号，消除"第 2 步去哪了" | §9.2.2 / §9.7.5 |
| 6 | 可引用宇宙只定义一次 | 五个调用点各算一遍 | 已发生过 `invalid_evidence_reference` 事故 | §9.2.3 |
| 7 | ID 来源冲突抛 `ValueError` | 字典覆盖继续生成 | 同一 ID 对应两份事实是数据系统坏了 | §9.2.3 |
| 8 | 案例只贡献 `memory_id` | 摊平历史 `evidence_refs` | 引用必须指向读者真能打开的东西 | §9.2.3 |
| 9 | 报告图用 `ainvoke` | `astream` + 保留中间态 | 修订到一半的报告没有独立价值 | §9.3 |
| 10 | `recursion_limit=10` 写死 | 用公式算 | 路径穷举可数，5 个节点访问封顶 | §9.3 |
| 11 | 节点用 `traced_node` 装饰 | 每个节点体内写 `with` | 遥测不与节点逻辑耦合；装饰器不暴露 handle | §9.3 |
| 12 | 确定性组件也走 Protocol | 直接 new 具体类 | 为了能注入坏 Builder 证明门禁有效 | §9.3 |
| 13 | 被拒假设转 `uncertainty` | 静默丢弃 | 沉默的丢弃是最难排查的故障形态 | §9.4.1 |
| 14 | 状态门用枚举不用置信度阈值 | `confidence >= 0.7` | 置信度本身是查表来的，会多一个可调松的旋钮 | §9.4.1 |
| 15 | `truncated` 一路走到读者眼前 | 当内部统计 | "没提到"会被读成"不存在" | §9.4.2 |
| 16 | 引用不排序 | 按字典序整理 | 会洗掉精排买来的相关性顺序 | §9.4.3 |
| 17 | 路径 N/N-1 不变量显式失败 | 默认 `zip` 截断 | 坏路径会安静地少渲染一跳 | §9.4.5 |
| 18 | 风险等级由知识节点声明 | 报告层硬编码 medium | HIGH 不可达、高风险门禁从未触发、指标被实现封顶在 0.667 | §9.4.6 |

## 9.12 本章遗留的缺口

和第 7、8 章一样，把没做到的写出来。以下五条是核对源码与 `tests/unit/test_reporting.py`、
`tests/unit/test_report_workflow.py` 之后确认的（用 `grep` 在 `tests/` 下搜过对应字面量，均无命中）：

1. **`_revise_report` 的 docstring 与代码不一致。** docstring 写着"`max_revisions=0` 时不调用 Reviser，
   直接由本节点生成降级准备状态"，但实际代码在 `retry_count >= max_revisions` 时**抛 `RuntimeError`**；
   而 `max_revisions=0` 时 `_route_after_audit` 根本不会路由到这个节点（`0 < 0` 为假 → `"degrade"`）。
   行为是对的（§9.6.6 的测试证明了终态正确），错的是这句 docstring——它描述的是一个更早的实现。
   **这是本章唯一一处文档与代码矛盾。**
2. **`_route_after_audit` 的两条 `RuntimeError` 分支没有测试。**
   `"audit routing requires AuditResult"` 和 `"accepted audit must mark report workflow completed"` 都是
   不变量断言，而正常控制流走不到它们。要覆盖需要直接调用这个纯函数并喂一个手工构造的
   `ReportGraphState`——它是同步纯函数，写起来很便宜，只是还没写。
3. **`recursion_limit=10` 这个常量没有测试。** 与第 8 章 §8.17 那条完全同类：如果哪天有人给图加了第五个
   节点或第二条返工边，10 可能不够，而没有任何测试会告诉你。
4. **`claim_path` 的切片形态 `[i:j]` 没有测试。** 注释声称模型实际会写出 `$.uncertainties[2:5]`，
   `_parse_claim_path` 也实现了 `frozenset(range(start, stop))` 和 `stop <= start` 的兜底，但现有用例只覆盖了
   `$.root_causes[1]`（单下标）、`root_causes[0].evidence_refs[0]`（不可解析）、`summary`（派生字段）三种。
   **一个声称"实际出现过"的输入形态没有对应断言，是最容易在重构中失效的那类代码。**
5. **`_insert_source` 的来源冲突分支和 `_path_description` 的 N/N-1 断言都没有测试。** 两条都是"数据系统
   坏了就显式失败"的路径（§9.2.3、§9.4.5），构造输入很容易（同一 ID 给两种 `source_type`；节点数与关系数
   不匹配），但目前只有实现和注释，没有断言。

另外两条不算缺口、但要标清楚现状：

- **`MISSING_RISK_CONTROL` 这条规则（§9.5.4）在本章两个测试文件里没有直接触发的用例。** 它被覆盖的方式
  是间接的——`_CLAIM_REMOVING_CODES` 包含它，`domain_schema_rejects_...` 覆盖了 Schema 层的同名约束。
  规则层自己那条"所有等级都要求 `prerequisites` 非空"（比 Schema 更严的部分）目前没有断言。
- **`risk_level_hit_rate` 的实测值仍是 0.667**，来自 `4e5e1b4` 之前的那次真实模型评测。如 §9.4.6 所说，
  那次提交解除了实现层的封顶，但**没有重新测量**。按 CLAUDE.md 的诚实性要求，文档里保留旧实测值并
  标注它是"最后一次实测"，而不是把"瓶颈已解除"写成新数字。

## 9.13 小结与下一章

本章把一个停止了的 `AgentState` 变成了一份可以发出去（或明确不发出去）的报告。回过头看，整章只在
回答一个问题的不同侧面：**"谁有权说这份结论可以发出去？"**

- 没有单一方有权。规则和 Auditor 都同意才 accept（§9.6.1）。
- 规则的否决不可被覆盖，模型的通过可以被覆盖。**非对称，且非对称的方向偏保守。**
- 模型只有否决权，没有生成权。草稿是投影（§9.2.1），修订只删不加（§9.7）。
- 审计不可用时不放行（§9.6.5）。**系统的默认答案是"不"。**

三条最值得带走的经验，都来自真实事故而不是设计文档：

1. **"删得更多"不等于"更安全"。** 降级必须让报告仍与证据自洽，否则会撞上 `evidence_conflict`（§9.7.1）。
2. **元陈述在证据系统里没有证据可引。** 关于"这份报告被审计过"的句子，必须走事件通道而不是报告正文，
   否则会被系统自己的规则否决（§9.7.6）。
3. **一行硬编码常量可以让一个指标看起来在测模型，实际在测那行常量。** `risk_level_hit_rate` 封顶在 0.667
   两个月，直到有人去问"HIGH 分支到底跑过吗"（§9.4.6）。

至此第 8、9 两章覆盖了两段内层 LangGraph。**第 10 章接上最外层**：`AuditedDiagnosisWorkflow` 怎么把
`recall_case_memories → run_react → explain_case_matches → run_report → stage_case_memory` 串起来，
`explain_case_matches` 为什么只做确定性解释而不重新搜索，以及长期记忆为什么必须在审计之后写、且默认
`pending` 等用户确认。§9.8 那句"降级稿不会生成 memory candidate"到时候会有第二道门。
