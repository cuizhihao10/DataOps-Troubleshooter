# 第 12 章 对外接口与可观测性

前面十一章都在往里走：从 Fixture 到 MCP 协议，从 GraphRAG 到双 Agent，从有界循环到四级审计，最后落到 PostgreSQL 的表和队列。这一章往外走一步，看这套东西怎么变成一个能被浏览器、`curl`、Prometheus 和容器探针一起使用的服务。

外层看起来"只是几个路由"，但它恰好是三个容易做错的地方同时汇合的位置：

- **鉴权**。保护得不够，端口一暴露就等于把整套排障接口送出去；保护得太散，新增一个路由忘写依赖就悄悄裸奔。
- **可观测性**。生产多 Agent 系统必须回答"这一次 run 的 30 秒花在哪一层"。答不出来，性能优化就只能靠猜。但遥测又是最容易把 Prompt、Thought、凭据顺手带出去的地方。
- **推流**。轮询能用但体验差；一旦为了体验把"推流"做成第二条执行路径，就会出现"轮询看到的结论"和"流里看到的结论"不一致，这种 bug 极难查。

这一章的三个答案分别是：`api-auth:v1` 用一个 ASGI 前缀中间件做 fail-closed 保护；`run-trace:v1` 把 span 落库并用正则把自然语言挡在类型层之外；`run-stream:v1` 的推流只持有两个只读方法，结构上无法推进 run。

## 12.2 鉴权：为什么是前缀中间件而不是逐路由 `Depends`

FastAPI 的官方写法是依赖注入：给每个需要保护的路由加一个 `dependencies=[Depends(verify_token)]`。这个项目没这么做。`app/api/security.py:1` 的模块 docstring 和 `app/api/main.py:751` 的中间件一起说明了原因。

先看保护范围是怎么定义的：

```python
PROTECTED_PATH_PREFIXES = ("/api/v1", "/metrics")
```

保护的是**前缀**，不是路由列表。差别在于失败方向：

- 逐路由 `Depends`：默认不保护。今后有人加一个 `/api/v1/admin/reset`，忘了写依赖，这个路由就是裸奔的，而且没有任何测试会失败——它本来也不在任何鉴权测试的清单里。
- 前缀中间件：默认保护。新增的 `/api/v1/...` 自动落在保护内。要让某条路由公开，必须显式把它挪出前缀，这是一个看得见的动作。

这就是 **fail closed**（失败时关闭）与 fail open 的区别。安全边界要选前者：写漏了导致"用不了"是可以立刻发现的；写漏了导致"没保护"可能几个月都发现不了。

`/health` 与 `/demo` 刻意留在前缀之外。`/health` 是容器存活探针要调的，如果它需要凭据，`docker compose` 的 healthcheck 就得带令牌，令牌于是出现在 compose 文件里——为了保护接口反而多了一处凭据泄露面。`/demo` 是一个只调用公开 API 的静态页面，它自己不含任何数据。

### 12.2.1 中间件在异常处理器之外，所以拒绝是"数据"不是"异常"

这是本章第一个需要理解 ASGI 的地方。如果你只写过 Java 的 Spring MVC，可以把 ASGI 中间件类比成 Servlet Filter：它在框架的路由分发**之前**执行，所以框架内部的异常映射（Spring 的 `@ControllerAdvice`、FastAPI 的 exception handler）对它不生效。

FastAPI 的 `HTTPException` 之所以能变成一个漂亮的 JSON 响应，是因为 FastAPI 注册了一个异常处理器。在中间件里 `raise HTTPException(401)`，这个处理器根本轮不到执行，结果是一个 500 或者一个裸的 ASGI 异常。

所以 `ApiSecurityGuard.authorize` 不抛异常，它**返回一个值**：

```python
@dataclass(frozen=True)
class ApiSecurityRejection:
    status_code: int
    error_code: str
    message: str
    headers: dict[str, str]
```

`None` 表示放行，非 `None` 表示拒绝。中间件自己把它翻成 `JSONResponse`（`app/api/main.py:751`）：

```python
if not is_protected_path(request.url.path):
    return await call_next(request)
guard = getattr(request.app.state, "api_security", None)
if guard is None:
    return JSONResponse(
        status_code=503,
        content={
            "detail": {
                "error_code": "security_unavailable",
                "message": "api security guard is not initialised",
            }
        },
    )
```

三个细节值得单独看：

1. **未受保护路径零开销**。第一行就 `return await call_next(request)`，`/demo` 的每个静态资源不会去碰限流表。
2. **守卫缺失按 503 拒绝而不是放行**。`getattr(..., None)` 会在 lifespan 还没跑完（或者跑失败了）时拿到 `None`。这时候放行等于"因为没装锁，所以门开着"。
3. **`detail` 是对象而不是字符串**。`{"error_code": ..., "message": ...}` 与 409 冲突响应的结构一致，前端的错误分支只写一套解析逻辑就够了。字符串 `detail` 需要前端做字符串匹配，那是最脆的一种耦合。

## 12.3 限流必须先于鉴权

`ApiSecurityGuard.authorize` 的顺序不是随手写的：

```python
retry_after = self._limiter.check(self.identify(client_host))
if retry_after is not None:
    return ApiSecurityRejection(
        status_code=429,
        error_code="rate_limited",
        message="request rate limit exceeded for this client",
        headers={"Retry-After": str(retry_after)},
    )
if self._mode == "disabled":
    return None
if self._token_matches(authorization_header):
    return None
```

限流在最前面。如果反过来先鉴权、只对通过鉴权的请求计数，那么**猜令牌这件事本身就不受配额约束**：攻击者可以每秒发几千个错误令牌，每一个都在鉴权环节被拒、都不计数，于是限流对暴力破解完全无效。把限流放在最前面，未认证请求也吃配额，猜令牌的速率就被压到 120 次/分钟（默认值，见 `app/core/settings.py:74`）。

### 12.3.1 身份用 IP 而不是令牌

`identify` 返回的是 `ip:<host>`，即使请求带着合法令牌也一样。理由是配额的归属对象：如果用令牌当 key，而这个部署只有一个共享令牌（这正是本项目的情况），那么所有客户端共用一个配额桶，一个写死循环的脚本能把其他所有人的配额吃光。用 IP 当 key，一个客户端跑飞只影响自己。

拿不到客户端地址时用常量兜底：

```python
UNKNOWN_CLIENT_IDENTITY = "ip:unknown"
```

这条兜底本身是个已知妥协：所有拿不到 IP 的请求会共享同一个桶。在这个项目的部署形态（单机 Docker、宿主端口直连）里 `request.client` 基本不会是 `None`，但如果将来放到某些代理后面，需要改成读 `X-Forwarded-For`——而那要求代理可信，否则请求方可以随便伪造这个头来绕过限流。这一点记在 §12.17。

### 12.3.2 滑动窗口，以及"超限时不写入时间戳"

限流器的核心只有几行（`SlidingWindowRateLimiter.check`）：

```python
if len(window) >= self._max_requests:
    retry_after = self._window_seconds - (now - window[0])
    return max(1, math.ceil(retry_after))
window.append(now)
self._evict_cold_identities()
return None
```

`window` 是这个身份最近一批请求的时间戳（超出窗口的会先被清掉）。三个决定：

**为什么是滑动窗口而不是固定窗口。** 固定窗口（"每分钟计数器，到点归零"）在边界上允许两倍突发：59.9 秒发满 120 个，60.1 秒又发满 120 个，两秒内实际通过了 240 个。滑动窗口看的是"最近 60 秒内",这个漏洞不存在。代价是要保存时间戳列表而不是一个整数。

**为什么超限时不 `append`。** 这是最容易写错的一行。如果超限时也把当前时间追加进窗口，那么一个不停重试的客户端会不断把窗口的右端往后推，`window[0]` 永远不过期，结果是**永久封禁**——用户停手 60 秒本该恢复，但只要客户端有自动重试，它就再也进不来了。限流应该是"减速带"而不是"路障"。

**`Retry-After` 向上取整且至少 1。** `math.ceil` 保证不会告诉客户端"再等 0 秒"（等 0 秒回来还是超限，客户端会陷入紧密循环）；`max(1, ...)` 兜住取整后仍为 0 的情况。

### 12.3.3 两个防 OOM 与防时钟的细节

```python
MAX_TRACKED_IDENTITIES = 4096
```

限流表按身份增长。如果不设上界，一个伪造源 IP 的请求流（每个包一个新 IP）会让这张字典无限膨胀，最终把进程 OOM 掉——**限流器自己变成了拒绝服务的载体**。`_evict_cold_identities` 在超过上界时淘汰最久未活动的身份。这是有意的取舍：极端情况下淘汰掉某个身份的历史会让它的配额被重置，但"配额偶尔宽松一次"远好过"进程被打死"。

另一个是时钟：限流器接收注入的单调时钟（默认 `time.monotonic`）而不是直接读 `time.time()`。墙钟会被 NTP 校正，向后跳会让 `now - window[0]` 变成负数（永远不超限、限流失效），向前跳会让所有窗口瞬间过期。单调时钟只增不减，不受校正影响。这和 §11.5 里 `duration_ms` 用单调时钟测量是同一个理由，也和第 5 章的水位线时区案例同源：**时间只要有两种口径，就一定会有人比较错**。

## 12.4 三种 401 为什么逐字相同

令牌校验只有三行：

```python
digest = hashlib.sha256(candidate.encode("ascii")).digest()
return hmac.compare_digest(digest, self._token_digest)
```

两个决定叠在一起：

**只保存摘要，不保存明文。** `ApiSecurityGuard` 构造时就把令牌哈希掉，明文不留在实例字段里。这样即使进程崩溃转储、或者有人打印了 `guard.__dict__`，拿到的也只是摘要。这不是强防护（摘要能被离线爆破），但它消除了最常见的一类泄露：日志和异常里意外带出对象状态。

**用 `hmac.compare_digest` 而不是 `==`。** Python 的字符串 `==` 是短路比较：第一个字节不同就返回，用时极短；前十个字节相同才会比第十一个。攻击者能测量响应时间，就能逐字节地把令牌"猜"出来（时序攻击）。`compare_digest` 是恒定时间比较。比较的是固定长度的摘要而不是变长明文，也顺带消除了"长度本身泄露信息"。

然后是共享响应。三种失败——完全没带 `Authorization`、带了但方案不是 `Bearer`、带了正确方案但令牌错误——返回**逐字相同**的响应体：

```python
# 缺失、方案错误和令牌错误共享同一响应：任何差异都会告诉探测者"这个实例配了令牌"，
# 甚至帮助他确认令牌前缀是否正确。
return ApiSecurityRejection(
    status_code=401,
    error_code="unauthorized",
    message="a valid bearer token is required for this endpoint",
    headers={"WWW-Authenticate": 'Bearer realm="dataops-api"'},
)
```

为什么这重要？假设"没带令牌"返回 `missing_credentials`、"令牌错误"返回 `invalid_token`。探测者不带令牌请求一次，看到 `missing_credentials`，就知道这个实例**确实配了令牌**（而不是 disabled 模式），值得继续攻。更糟的是，如果错误码能区分"格式对但值错"和"格式都不对"，就等于给了一个可以逐步逼近的反馈信号。逐字相同意味着探测者从响应里学不到任何东西。

从学习角度看，这是"信息泄露"这个漏洞类别最小的一个例子：**泄露的不是数据，是关于系统配置的事实**。

### 12.4.1 两个方向的启动期拒绝

```python
MINIMUM_API_TOKEN_CHARS = 32
```

`ApiSecurityGuard.__init__` 会直接拒绝构造，不给"先跑起来再说"的机会：

- `bearer` 模式却没给令牌 → 拒绝。否则每个请求都 401，服务等于不可用，而运维要排查很久才发现是配置问题。
- `disabled` 模式却配了令牌 → 也拒绝。这一条更重要：部署者配了令牌，以为接口已经受保护，于是放心把端口暴露出去，实际上守卫是 disabled 的。这是**最危险的一种半配置**，因为它的表现是"一切正常"。
- 令牌短于 32 字符、或包含空格/非可打印 ASCII → 拒绝。

`app/core/settings.py:265` 的 `_validate_api_security` 也检查前两条。两处重复不是冗余失控：Settings 层能在读配置时立刻报错，守卫层持有唯一的策略常量（32 这个数字只写在 `security.py` 里），所以最小长度不会漂移成两份。

由于守卫在 lifespan 里**先于**任何 Provider、MCP 子进程和数据库连接构造（`app/api/main.py:520`），弱配置会让进程在开放端口前就退出。

## 12.5 lifespan：在开放端口之前把所有假设验完

`app/api/main.py:453` 的 `lifespan` 是这个项目最长的一个函数，但结构非常规整。它是一个 `@asynccontextmanager`：`yield` 之前是启动，`yield` 之后（在 `finally` 里）是停机。FastAPI 保证 `yield` 之前抛异常时**端口不会被开放**。

这个"要么全好，要么不启动"的姿态是整章的基调。它的顺序是按成本从低到高排的：

```python
# 先验证完全本地且成本最低的资产，让路径或 Schema 错误在启动早期给出清晰反馈。
fixture_registry = FixtureRegistry.from_directory(settings.fixture_directory)
golden_cases = load_golden_cases(settings.golden_case_file)
scenario_ids = set(fixture_registry.scenario_ids)
missing_scenarios = sorted({case.scenario_id for case in golden_cases} - scenario_ids)
if missing_scenarios:
    raise ValueError(f"golden cases reference unknown scenarios: {missing_scenarios}")
```

顺序是：本地文件 → 契约 ID 逐项比对 → 安全守卫 → capability 注册表 → Provider 工厂 → 真实 MCP 握手 → 可选数据库 → 两个模型角色 → 组装 runtime → 发布 `app.state` → 启动 Worker。免费的检查先做，付费的（embedding、模型 SDK）和慢的（stdio 子进程、数据库）后做。一个拼错的文件路径不该等到 MCP 子进程起完才报错。

### 12.5.1 三类"这个字段拼错了会静默失效"的校验

**Golden Case 引用的 scenario 必须存在。** 上面那段。否则评测会拿一个不存在的场景跑，结果不是报错而是一个空证据的诊断。

**根因锚点必须真的是图里的 `root_cause` 节点：**

```python
# 根因锚点必须真的是知识图里的 root_cause 节点：锚点一旦拼错就永远不可能被任何报告引用命中，
# 于是 `root_cause_anchor_hit_rate` 会静默退化成恒为 0 的假指标——那正是这条契约要修掉的毛病。
root_cause_node_ids = {
    node.node_id
    for node in load_knowledge_seed(settings.knowledge_seed_file).nodes
    if node.node_type is KnowledgeNodeType.ROOT_CAUSE
}
```

这段代码是一个具体的教训被固化下来的样子。锚点命中率这个指标的定义是"报告引用的节点里有没有 Golden Case 声明的根因锚点"。锚点拼错一个字符，分母照旧、分子恒为 0，指标看起来像是"模型找不到根因"，实际是"锚点不存在"。第 14 章会再回到这个指标；这里只记住：**任何"按 ID 匹配"的指标都需要一个启动期的 ID 存在性校验，否则它随时可能变成恒零的假指标。**

**向量必须是全有或全无：**

```python
if knowledge_nodes_embedded != knowledge_nodes_loaded:
    raise ValueError(
        "all knowledge nodes must be embedded in the configured provider space"
    )
```

文档切片有一份完全对称的检查，注释解释了为什么：

```python
# 与知识节点同样是全有或全无：部分切片缺向量时语义通道只会少召回而不报错，
# 那种"看起来正常但永远查不到某份 Runbook"的状态在演示中几乎不可能被发现。
```

这是第 10 章 `evidence_bundle` 事故、第 11 章 seed 单事务的同一个形状：**部分成功的检索通道不会报错，只会少给结果**，而"少给结果"和"这份资料确实不相关"从外部完全无法区分。

### 12.5.2 契约 ID 逐项比对：为什么值得写二十个 `if`

lifespan 里有一长串形状完全相同的检查：

```python
if settings.planner_prompt_id != PLANNER_PROMPT_ID:
    raise ValueError("configured planner prompt ID does not match the packaged prompt")
if not load_planner_prompt().strip():
    raise ValueError("planner prompt must not be empty")
...
if settings.run_stream_contract_id != RUN_STREAM_CONTRACT_ID:
    raise ValueError("configured run stream contract ID does not match the package")
```

看起来很笨。为什么不写个循环遍历一个 `(setting_name, module_constant)` 列表？

因为这些检查的价值在于**改代码时会被强制想起**。契约 ID 是"这一版的 Prompt / Schema / 工作流拓扑长什么样"的标签，它出现在四个地方：`settings.py` 的默认值、模块常量、`docs/prompt-contracts.md`、以及 `tests/unit/test_documentation_policy.py` 的字面量断言。升版本时如果只改了模块常量，lifespan 会拒绝启动，报错信息直接指出是哪一个契约。如果写成循环 + 数据表，新增契约时容易漏加一行表项，而漏加不会失败——**又回到了 fail open**。

同时注意 Prompt 检查是成对的：`ID 匹配` 加 `文本非空`。只校验 ID 会让"ID 对但文件是空的"通过，那么评测记录的版本号就不代表实际执行内容——这正是评测诚实性最底层的一块砖。

### 12.5.3 `app.state` 必须整批发布

```python
# 只有全部检查完成后才发布共享状态，避免路由观察到半初始化的依赖集合。
app.state.settings = settings
app.state.api_security = api_security
...
if diagnosis_worker is not None:
    # Worker 在所有 app.state 依赖发布后再启动，避免后台 task 观察到半初始化的 runtime。
    diagnosis_worker.start()
yield
```

`app.state` 是 FastAPI 给应用挂共享对象的地方（可以类比 Spring 的 ApplicationContext，只是没有类型）。如果边构造边赋值，路由就可能在某个中间时刻读到"数据库有了但 Planner 还没有"的组合。更实际的问题是 Worker：它是后台协程，`start()` 之后立刻就会去领任务，如果此时 `app.state.diagnosis_runtime` 还没赋值，第一个任务就会撞 `AttributeError`——而这个错误会表现为一次莫名的 run 失败。

`yield` 之后的 `finally` 是对称的关闭顺序：

```python
if diagnosis_worker is not None:
    # 先停止领取新任务；未完成 run 的 lease 会自然过期并由新 Worker 接管。
    await diagnosis_worker.stop()
if auditor_runtime is not None:
    await auditor_runtime.aclose()
if planner_runtime is not None:
    await planner_runtime.aclose()
if reranker is not None and hasattr(reranker, "aclose"):
    await reranker.aclose()
if hasattr(embedding_provider, "aclose"):
    await embedding_provider.aclose()
if database_engine is not None:
    await database_engine.dispose()
```

先停 Worker（不再领新活），再关模型 HTTP 池，最后释放数据库池——反过来会让还在执行的 run 撞上已关闭的连接池。每一个都判空，因为 `finally` 也要覆盖"构造到第三步就抛异常"的路径：那时后面几个对象还是 `None`。

`hasattr(reranker, "aclose")` 这种鸭子类型判断和第 11 章 `seed.py` 里的写法一致：离线确定性实现和测试替身不必为了通过关闭路径而实现一个空的 `aclose`。

## 12.6 `/health` 不是"活着吗"，而是一份可机器验证的契约快照

大多数项目的健康检查返回 `{"status": "ok"}`。这个项目的 `HealthResponse` 有 20 多个字段，嵌套 8 个子模型。理由是它服务三类消费者：

- Docker healthcheck / 存活探针：只看 HTTP 200。
- 集成测试：断言 `contracts.*` 的每个 ID、`limits.*` 的每个预算。
- 演示者：在打开 `/demo` 之前就能回答"这个实例配了模型吗、装了几个知识节点、推流能不能用"。

关键是路由**完全不做 I/O**：

```python
settings = request.app.state.settings
fixture_registry = request.app.state.fixture_registry
...
```

全部读 lifespan 已经验完并缓存在 `app.state` 的值。所以探针可以每秒调用而不会给数据库和 MCP 加压。代价是这些数字是启动时的快照，不会随运行变化——唯一的例外是 `memory_counts`，`decide_memory` 和 `delete_memory` 在改动后会主动刷新它（`app/api/main.py:1213`），这样 `/health` 仍然不用自己开数据库连接。

### 12.6.1 几个字段的存在本身就是设计声明

`RuntimeLimits` 里并列公开两个上限，注释说明了原因：

```python
max_react_steps: int
# 并行上限和步数上限一起公开：只看 max_react_steps 无法判断这个实例是"六步串行"还是
# "两轮各三个并行"，而这两者的 P95 延迟完全不同。
max_parallel_tool_actions: int
```

同一节里 `tool_retry_count` 和 `chat_transient_retry_attempts` 也是并列的，因为两者是**互相独立的预算**：只看工具侧的重试次数，会误判一个模型侧的 429 是否会被直接判成 `planner_provider_error` 终态。

`status` 字段一律用 `Literal["disabled", "configured"]` 而不是布尔：

```python
class PlannerConfiguration(BaseModel):
    status: Literal["disabled", "configured"]
    provider: str
    model: str
    endpoint_host: str
```

`configured` 的语义是"本地配置可构造"，**不是**"远端连接已探测成功"。lifespan 里构造 Provider 时刻意不发探测请求（那会是一次付费调用，而且启动时的一次成功也不保证下一次成功）。用两个明确的词而不是 `available: true`，就不会让人以为服务端已经确认过模型可用。

注意所有配置模型都只暴露 `endpoint_host` 而不是完整 URL：`settings.chat_base_url.host or ""`。完整 URL 可能带 userinfo（`https://user:pass@host/...`），主机名不会。API key 从头到尾没有任何字段承载。

`DiagnosisApiConfiguration.execution_mode` 是 `Literal["postgres-worker"]`——一个只有一个取值的字面量类型。它的作用是**声明当前的执行模式，并让改动这件事必须同时改契约**。早期版本这里是同步执行，改成 Worker 队列时这个字面量强制被修改，于是文档和测试的断言一起被拖着改。

### 12.6.2 `extra="forbid"` 在响应模型上的意义

每一个响应模型都是 `model_config = ConfigDict(extra="forbid")`。在请求模型上这好理解（拒绝客户端塞未知字段）。在**响应**模型上它防的是另一件事：服务端自己写错字段名。

`HealthResponse(..., knowledge_nodes_loded=12)` 拼错一个字母，如果不 forbid，Pydantic 会安静地把它当额外字段接受，而真正的 `knowledge_nodes_loaded` 用默认值——如果它有默认值的话。forbid 让这变成一个立刻抛出的 `ValidationError`。

`RetrievalConfiguration` 的 docstring 记了一条相关的判断：图通道权重和文档通道权重**分开公开而不合并**。

```python
score_weights: HybridScoringWeights
document_score_weights: DocumentScoringWeights
```

两者的因子集合本来不同（文档没有 path/freshness 这两个因子）。合并成一个字段会让人以为文档片段也参与了关系路径打分。这是一个很小的字段设计决定，但它决定了演示时能不能准确解释"名次为什么这样排"。

## 12.7 两个观测出口，以及它们为什么不能合并

这是本章的核心。`app/observability/` 有两个出口，名字都带 metric，但用途完全不同：

| | `model-call-metric:v1` | `run-trace:v1` |
| --- | --- | --- |
| 存储 | 进程内 `ContextVar` 上的列表 | PostgreSQL `run_trace_spans` 表 |
| 生命周期 | 由评测 CLI 显式绑定/释放 | 与 run 终态同事务提交 |
| 覆盖范围 | 只有 Planner/Auditor 的 Chat 调用 | 七类 span，覆盖工作流/节点/工具/检索/模型/持久化 |
| 消费者 | 离线评测报告（token、成本、修复次数） | `GET /api/v1/runs/{run_id}/trace`、`/metrics` |
| 进程重启后 | 全丢 | 保留 |

为什么不合并成一个？因为**它们回答的问题不同**。

评测 recorder 要回答"跑完 28 个案例一共花了多少 token、有几次 `output_invalid` 被修复"。它需要按调用完成顺序保留每一条记录，而且只在评测 CLI 的作用域内存在——生产 API 进程如果也维护这个列表，那就是一个只增不减的隐式全局调用历史，长期运行必然吃内存。

trace 要回答"这一次 run 的 30 秒花在哪一层"。它必须落库（Worker 重启、API 与 Worker 分进程），必须覆盖所有层（模型调用只是其中一层），而且必须能按 run 回放。

`ModelCallMeasurement.finish` 是两者唯一的交汇点，注释把分工写得很清楚：

```python
# trace 与 recorder 是两套用途不同的出口：recorder 服务离线评测聚合，span 服务单次 run 的
# 时间轴，因此即使没有绑定 recorder（普通 API 请求）也要落 span，否则生产 trace 会缺模型层。
record_completed_span(
    TraceSpanKind.MODEL_CALL,
    "model.chat_completion",
    duration_ms=duration_ms,
    status=(
        TraceSpanStatus.OK
        if status is ModelCallStatus.SUCCEEDED
        else TraceSpanStatus.ERROR
    ),
    ...
)
# 未绑定是普通 API 的预期路径；直接返回可避免在长期进程中建立隐式全局调用历史。
if self._recorder is None:
    return
```

span 无条件写，recorder 只在绑定时写。这个顺序不能反：如果先判断 recorder 为空就 `return`，生产 trace 里会永远缺少 `model_call` 这一层——而那一层恰好是最慢的一层。

### 12.7.1 `finish` 恰好一次，以及"未知不能伪装成零"

```python
if self._finished:
    raise RuntimeError("model call measurement cannot be finished twice")
self._finished = True
```

Provider 的 `complete` 有六个结束分支（成功、Schema 无效、被拒、超时、连接错误、HTTP 错误），每个分支都要调 `finish`。重复调用会让同一次请求被计两次 token，成本数据直接失真。抛 `RuntimeError` 而不是静默忽略，是因为这属于 Provider 的分支设计错误，应该在测试里立刻暴露。

同样重要的是 token 缺失时的处理：

```python
if any(value is None for value in (prompt_tokens, completion_tokens, total_tokens)):
    return None
```

某些 OpenAI 兼容端点不返回 `usage`。这时整个 `token_usage` 对象是 `None`，而**不是**三个 0。docstring 写得直白："空快照表示绑定范围内没有到达模型 Provider，不能被解释为零 token 的成功运行。"

这条和 §11 的"空和不存在必须可区分"是同一件事，也和评测诚实性直接相关：如果把未知记成 0，评测报告里的 token 总数会偏低，而看报告的人无从知道有多少次调用其实没数据。

`ModelTokenUsage` 还有一条不变量：

```python
if self.total_tokens != self.input_tokens + self.output_tokens:
    raise ValueError("model token total must equal input plus output")
```

如果将来某个兼容服务引入了额外 token 类别（比如缓存命中的 token 单独计），这个断言会立刻失败，逼着升级契约而不是让它静默混入当前指标。

### 12.7.2 `ContextVar` 而不是实例字段

recorder 通过 `ContextVar` 绑定，而不是存在 Provider 实例上：

```python
_CURRENT_RECORDER: ContextVar[InMemoryModelCallRecorder | None] = ContextVar(
    "dataops_model_call_recorder",
    default=None,
)
```

这是异步代码里最容易踩的一类坑。Provider 是可复用对象（持有 HTTP 连接池），如果在它上面存一个 `self.last_usage`，两个并发请求会互相覆盖——第二个请求读到的是第一个的 usage。`ContextVar` 的语义是"每个 asyncio task 各看到自己的值"，`asyncio.gather` 派生的子任务会复制当前上下文，所以并发天然隔离。

`ModelCallMeasurement.__init__` 里还有一个细节：

```python
self._recorder = _CURRENT_RECORDER.get()
```

recorder 在**网络请求之前**就捕获好，而不是在 `finish` 里现取。这样即使调用过程中上下文发生切换，这条记录也只会写进发起它的那次运行。

绑定/恢复是显式成对的（`bind_model_call_recorder` / `reset_model_call_recorder`），调用方必须在 `finally` 里恢复。写成两个函数而不是让调用方直接操作 `ContextVar`，是为了让这一对在代码搜索里成对出现——漏掉恢复会让长期运行的 API 进程把普通用户请求计入一次已经结束的评测。

## 12.8 span 契约：把"不得泄露 Prompt"变成类型层的不可能

整个仓库有一条贯穿的硬规则：API 响应、`run_events`、trace span、SSE 帧、`/metrics` 曝光和 `/demo` 前端都不得包含 Thought、原始思维链、Prompt、embedding、凭据或 Provider 原始响应。

在大多数项目里这条规则靠代码评审执行。这个项目把它变成了正则：

```python
_SPAN_NAME_PATTERN = re.compile(r"^[a-z][a-z0-9_.]{2,63}$")
_ATTRIBUTE_KEY_PATTERN = re.compile(r"^[a-z][a-z0-9_.]{1,39}$")
#: 属性值只允许 ASCII 标识符、路径与版本号常用字符。空格与 CJK 被排除，因此自然语言正文
#: （Prompt、Thought、日志原文）无法通过校验，敏感面由类型系统保证而不是靠代码评审。
_ATTRIBUTE_VALUE_PATTERN = re.compile(r"^[A-Za-z0-9_.:\-/+]+$")
```

关键在于**空格不在白名单里**。任何一句自然语言——中文、英文、日志原文、Prompt 片段——都含空格或 CJK 字符，因此在写入时就会抛 `ValueError`。这不是"约定不要这么做"，而是"这么做会崩"。

这种"用类型系统承载安全约束"的思路值得单独记住。对比两种写法：

- 写在文档里："span 属性不要放 Prompt。" → 依赖每个人每次都记得。
- 写成正则白名单：不合规的值进不去。 → 违规变成一个测试失败或启动失败。

第二种的成本是灵活性：想在 span 上记一句人话的说明就不行了。这个项目认为这个代价可以接受——span 是给机器聚合的，人话应该放在 `run_events` 的问题码里（那里有独立的脱敏规则）。

`normalize_span_attributes` 是遥测层**唯一**的写入口，所有属性都必须过它：

```python
if len(attributes) > MAX_ATTRIBUTES_PER_SPAN:
    raise ValueError(f"span accepts at most {MAX_ATTRIBUTES_PER_SPAN} attributes")
normalized: dict[str, AttributeValue] = {}
for key, value in attributes.items():
    if not _ATTRIBUTE_KEY_PATTERN.fullmatch(key):
        raise ValueError(f"invalid span attribute key: {key!r}")
    if value is None or isinstance(value, bool):
        normalized[key] = value
        continue
    if isinstance(value, int | float):
        normalized[key] = value
        continue
```

有一个 Python 语言层面的陷阱在这里被显式处理：**`bool` 是 `int` 的子类**。`isinstance(True, int)` 返回 `True`。如果不先判断 `bool`，`True` 会走进数字分支，被当成 `1` 写入，语义就丢了（"是否降级 = 1" 和 "重试了 1 次" 在聚合视图里无法区分）。

`None` 被保留为显式的"未知"，不折叠成 0。又是同一条原则。

### 12.8.1 为什么 span 名不能包含动态信息

`TraceSpan.validate_name` 的 docstring 说明了这条约束的真实成本来源：

```python
if not _SPAN_NAME_PATTERN.fullmatch(value):
    raise ValueError("span name must be a lowercase dotted identifier")
```

span 名是**聚合维度**。`/metrics` 按 `(kind, name)` 分组。如果名字里带了 run_id 或表名，每次 run 都会产生一组全新的时间序列——这在 Prometheus 里叫"标签基数爆炸"，是监控系统最经典的自伤方式：几万个只有一个样本的序列，占满内存，而且没有任何两次 run 能对齐比较。

动态信息应该放属性。属性同样受 ASCII 约束，所以两条路径都不会承载自由文本。

`TraceSpanKind` 只有七个固定值，对应真实的架构边界：

```python
WORKFLOW = "workflow"
NODE = "node"
REACT_STEP = "react_step"
TOOL_CALL = "tool_call"
RETRIEVAL = "retrieval"
MODEL_CALL = "model_call"
PERSISTENCE = "persistence"
```

docstring 里有一条容易忽略的判断：`persistence` **单列**而不是混进 `node`。理由是"数据库往返常常是首个可优化项，混进 node 会被工作流耗时掩盖"。这是把优化经验编码进了枚举设计。

### 12.8.2 span_id 是派生的，不是随机的

```python
def make_span_id(run_id: str, sequence: int) -> str:
    if sequence < 1:
        raise ValueError("span sequence must start at 1")
    digest = sha256(f"{run_id}|{sequence}".encode()).hexdigest()[:16]
    return f"span_{digest}"
```

用 `sha256(run_id|sequence)` 而不是 `uuid4()`。三个好处：

1. **重放稳定。** 同一次 run 重新导出，span 引用不变。Golden 评测可以逐字比对报告。随机 UUID 会让每次导出的引用都不同，报告没法做字符串比较。
2. **可重新验证。** `TraceSpan.validate_consistency` 会检查 `span_id == make_span_id(run_id, sequence)`。任何一条从数据库读回来的记录都能被重新推导一遍，错误关联或篡改立刻暴露。
3. **不需要额外的 trace ID 体系。** OpenTelemetry 有 trace_id + span_id 两级。这里 run_id 本身就是 trace 标识，省掉一层。

`validate_consistency` 里还有一条防死循环的检查：

```python
if self.parent_span_id == self.span_id:
    raise ValueError("span must not be its own parent")
if self.ended_at < self.started_at:
    raise ValueError("span ended_at must not precede started_at")
```

自引用的父指针会让前端的树形渲染进入无限递归。docstring 说这必须"在契约层拒绝而不是在 UI 里防御"——防御性代码写在最外层意味着每个消费者都要写一遍。

时间戳必须带时区：

```python
if value.tzinfo is None:
    raise ValueError("span timestamps must be timezone-aware")
```

docstring 直接引用了第 5 章的水位线时区案例："这类错误只表现为'结果看起来正常但结论错误'。" naive datetime 在容器（UTC）和本机开发（东八区）之间会静默偏移 8 小时，而 trace 的全部价值依赖时间轴可比。

### 12.8.3 `total_duration_ms` 取根 span，不能求和

```python
@property
def total_duration_ms(self) -> float:
    return self.spans[0].duration_ms if self.spans else 0.0
```

这个 property 只有一行，但它防的错误很致命。子 span 在时间上被父 span **包含**：`workflow` span 覆盖整个 run，里面的 `node` span 覆盖一个节点，里面的 `model_call` span 覆盖一次 API 调用。三层的耗时是嵌套关系，不是并列关系。

如果把所有 span 的 `duration_ms` 加起来当端到端时长，一个真实 30 秒的 run 会被报成上百秒。而 P95 延迟目标（≤30 秒）正是拿这个数字衡量的——口径错了，整个性能结论就是废的。

`RunTrace.validate_structure` 的四条断言里，"父必须先出现"这条最有意思：

```python
for index, span in enumerate(self.spans, start=1):
    if span.run_id != self.run_id:
        raise ValueError("all spans must belong to the trace run")
    if span.sequence != index:
        raise ValueError("span sequences must be consecutive starting at 1")
    if span.parent_span_id is None:
        roots += 1
    elif span.parent_span_id not in seen:
        raise ValueError("span parent must appear before the child span")
    seen.add(span.span_id)
if self.spans and roots != 1:
    raise ValueError("a non-empty trace must contain exactly one root span")
```

序号在 span **开始**时分配，所以父一定比子小——"父先出现"是这个事实的自然推论。把推论写成断言的价值在 docstring 里："可以在插桩把 ContextVar 传播搞错时立刻失败；否则错误只会表现为火焰图层级看起来'有点怪'。"

这是一类很实用的测试思路：**把你相信为真的推论写成断言**，它就变成了对上游逻辑的免费监控。

## 12.9 采集器：并行工具调用为什么必须用 ContextVar 存父指针

这是整个遥测模块最精妙的一处，而且它直接对应第 8 章的并行工具调用。

先看两个 `ContextVar`：

```python
_CURRENT_COLLECTOR: ContextVar[RunTraceCollector | None] = ContextVar(
    "dataops_run_trace_collector", default=None
)
#: 当前父 span 也放在 ContextVar 里而不是采集器内部的栈：``asyncio.gather`` 会为每个协程复制上下文，
#: 因此并行工具调用天然共享同一个父 span，而共享栈会被并发的 push/pop 互相破坏。
_CURRENT_PARENT: ContextVar[str | None] = ContextVar("dataops_run_trace_parent", default=None)
```

传统的 trace 实现用一个栈：进入 span 时 push、退出时 pop、栈顶就是当前父。串行代码里这完全正确。

但 `execute_tools` 节点会用 `asyncio.gather` 并发执行 1–3 个工具调用。用共享栈会发生什么？

```
时刻 1: 工具 A 开始 → push(A)，栈 = [root, A]
时刻 2: 工具 B 开始 → push(B)，栈 = [root, A, B]   ← B 的父被算成 A！
时刻 3: 工具 A 结束 → pop()，弹掉了 B
时刻 4: 工具 B 结束 → pop()，弹掉了 A
```

结果是父子关系错乱，而且栈状态被破坏。火焰图会显示"工具 B 是工具 A 的子调用"——完全错误的因果关系，而且会让人以为串行执行了。

`ContextVar` 的语义解决了这个问题：`asyncio.gather` 为每个协程**复制**当前上下文。三个工具协程各自拿到一份 `_CURRENT_PARENT = <execute_tools 的 span_id>`，各自 `set` 自己的值时互不影响。三个 `tool_call` span 于是正确地并列挂在同一个父下面。

`trace_span` 的实现体现了这一点：

```python
collector = _CURRENT_COLLECTOR.get()
if collector is None:
    yield _INERT_SPAN
    return
parent_span_id = _CURRENT_PARENT.get()
with collector.open_span(kind, name, parent_span_id=parent_span_id, **attributes) as handle:
    if handle.span_id is None:
        yield handle
        return
    token = _CURRENT_PARENT.set(handle.span_id)
    try:
        yield handle
    finally:
        # 必须在 span 结束前恢复父指针，否则同级后继 span 会错误地挂到刚结束的兄弟节点下。
        _CURRENT_PARENT.reset(token)
```

`finally` 里的 `reset` 是必须的：没有它，同一层的下一个 span 会把刚结束的兄弟当成父。

### 12.9.1 未绑定采集器时是零成本 no-op

```python
_INERT_SPAN = SpanHandle()
```

`SpanHandle` 的三个参数全缺省时构造出一个"惰性句柄"：`span_id is None`，`annotate` 和 `mark` 都直接 `return`。

这个设计的价值是**插桩可以无条件写**。检索模块、MCP 客户端、Agent 节点里到处是 `with trace_span(...)`，但离线评测脚本和单元测试根本不绑定采集器。如果没有 no-op 路径，这些代码就得到处写 `if collector is not None:`，或者测试就得准备一套遥测环境。

`is_recording` 属性给少数需要跳过昂贵取值的地方用：

```python
@property
def is_recording(self) -> bool:
    return self.span_id is not None
```

docstring 明确说"绝大多数调用点不必检查"——只有当属性值本身需要额外计算（比如统计字节数）时才值得先看这个标志。

### 12.9.2 句柄可写、span 不可变

`SpanHandle` 允许补属性和改状态，但不允许改名和改父。`TraceSpan` 是 `frozen=True` 的 Pydantic 模型。这个分界很有讲究。

**为什么必须允许后补属性。** 多数有价值的属性只有执行完才知道：工具是否命中缓存、召回了几条、报告是否降级。所以 `annotate` 必须存在：

```python
def annotate(self, **attributes: AttributeValue) -> None:
    if self.span_id is None:
        return
    merged = {**self._attributes, **attributes}
    self._attributes = dict(normalize_span_attributes(merged))
```

合并后**重新走一遍** `normalize_span_attributes`，所以后补的属性不能绕过白名单。

**为什么句柄不暴露耗时和时间戳。** docstring 说得直接："避免调用方'帮忙'写入自己测的数字导致口径不一致。" 如果某个节点自己 `time.time()` 测了一遍再写进 span，就会出现同一个 run 里有两套计时口径。

**`mark` 为什么必要。**

```python
def mark(self, status: TraceSpanStatus) -> None:
    if self.span_id is None:
        return
    self._status = status
```

有一类失败**不抛异常**：重排降级、Auditor 否决、run 被取消。如果状态只由异常决定，这些路径全部记成 `ok`，错误率指标就失去意义了。回想第 9 章：审计预算耗尽转 `degraded` 是一条完全正常的返回路径，但它在 trace 上应该是可见的。

`__slots__ = ("_attributes", "_status", "sequence", "span_id")` 是一个纯性能决定：span 数量可能上百，`__slots__` 省掉每个实例的 `__dict__`。

### 12.9.3 三个状态分支与"遥测绝不吞控制流"

```python
try:
    yield handle
except CancelledError:
    # 取消是外部中断而不是缺陷，单独归类才能让错误率指标只反映真实故障。
    self._finish(
        handle, kind, name, parent_span_id, started_at, started_perf, cancelled=True
    )
    raise
except Exception:
    self._finish(handle, kind, name, parent_span_id, started_at, started_perf, failed=True)
    raise
else:
    self._finish(handle, kind, name, parent_span_id, started_at, started_perf)
```

两点：

**`CancelledError` 单独接。** 在 Python 3.8+ 里 `CancelledError` 继承 `BaseException` 而不是 `Exception`，所以 `except Exception` 抓不到它——必须显式写。而且它在语义上确实不同：用户点了取消、或者到了超时，这不是缺陷。如果和真实错误混在一起，`/metrics` 的错误率会被"用户主动取消"污染，告警阈值就没法定了。

**两个分支都 `raise`。** 遥测记完就把异常原样重抛。这条规则值得放大：**观测层永远不能改变控制流。** 如果这里吞掉异常，一个 span 记录失败会伪装成业务节点执行成功——这比完全没有 trace 危险得多，因为它是错误的信息而不是缺失的信息。`traced_node` 装饰器的 docstring 也重复了这一点。

耗时的测量方式：

```python
duration_ms = max((perf_counter() - started_perf) * 1000, 0.0)
```

`perf_counter()` 是单调时钟，墙钟只用于时间轴展示。`max(..., 0.0)` 是纯防御——单调时钟理论上不会倒退，但 `duration_ms` 字段有 `ge=0` 约束，一个负值会让整个 span 构造失败，进而毁掉这次 run 的 trace。

### 12.9.4 为什么用字典按序号存放，而不是 append

```python
self._completed: dict[int, TraceSpan] = {}
```

序号在 span **开始**时分配，记录在 span **结束**时写入。并发工具调用的完成顺序和开始顺序不同：A 先开始（序号 2）但慢，B 后开始（序号 3）但快，B 先结束。

如果用 `list.append`，`_completed` 会是 `[B, A]`——序号 3 排在序号 2 前面。导出时 `RunTrace` 的"父先于子"和"序号连续"两条断言会同时触发，一次 run 的 trace 直接报废。

用 `dict[序号]` 存，导出时 `sorted(self._completed)` 恢复开始顺序。

还有一个"孤立 span 挂到根"的兜底：

```python
effective_parent = parent_span_id
if effective_parent is None and handle.sequence != 1:
    effective_parent = make_span_id(self._run_id, 1)
```

序号不为 1 却没有父指针的 span，一律挂到根。docstring 说明了原因：这种情况说明某处插桩漏了传父指针，而它会让 trace 变成"互不相连的森林"，直接违反唯一根约束——**一次插桩小错误会连带毁掉整个 trace 接口**。挂到根虽然不精确，但保住了可读性。

### 12.9.5 上限与丢弃计数

```python
MAX_SPANS_PER_RUN = 512
```

```python
def _reserve_sequence(self) -> int | None:
    if self._next_sequence > self._max_spans:
        self._dropped_span_count += 1
        return None
    sequence = self._next_sequence
    self._next_sequence += 1
    return sequence
```

有界 ReAct 循环的 span 数量本身就有上界，正常永远碰不到 512。碰到了只可能意味着插桩递归失控。这时候丢弃并计数，而不是让一次诊断把无界数据写进数据库。

`dropped_span_count` 通过 `RunTrace` 一路暴露到 `GET /api/v1/runs/{run_id}/trace` 的响应里。这条链子的意义在 `RunTraceResponse` 的 docstring：

> `dropped_span_count` 非零表示插桩超过上限被截断，必须原样暴露而不是让残缺 trace 看起来完整。

**丢弃是有意的保护动作，但必须可见。** 否则使用者会把一份被截断的火焰图当成完整的执行过程，得出"系统只做了这些步骤"的错误结论。这和 §12.7.1 的"未知不能伪装成零"是同一条原则的第三次出现。

计数器只增不减也是刻意的："即使某个 span 因异常提前结束，序号也不会被复用——复用会让两个 span 派生出同一个 `span_id`，前端的父子关联随之错乱。"

## 12.10 `snapshot`：导出阶段的序号压实

这是采集器里最不显眼但最必要的一段。

问题：序号在开始时分配、记录在结束时写入。如果一个 span 被强制中断且没走完 `finally`（比如整个事件循环被杀），它就永远不会进 `_completed`，于是留下一个**空洞**：`_completed` 的键是 `{1, 2, 4, 5}`。

空洞直接违反"序号从 1 连续"的契约。后果不是"少一个 span"，而是 `RunTrace` 构造失败 → **整个 trace 接口对这次 run 报错**。

解法是导出时压实：

```python
ordered = [self._completed[key] for key in sorted(self._completed)]
remapped: dict[str, str] = {}
compacted: list[TraceSpan] = []
for index, span in enumerate(ordered, start=1):
    new_span_id = make_span_id(self._run_id, index)
    remapped[span.span_id] = new_span_id
    parent = span.parent_span_id
    # 父 span 一定先被压实，因此映射必然已经存在；缺失说明父 span 未完成，此时挂到根。
    if parent is not None:
        parent = remapped.get(parent, make_span_id(self._run_id, 1))
    if index == 1:
        parent = None
    compacted.append(
        span.model_copy(
            update={
                "sequence": index,
                "span_id": new_span_id,
                "parent_span_id": parent,
            }
        )
    )
```

逐行看：

1. `sorted(self._completed)` 恢复开始顺序。
2. 重新按新序号派生 `span_id`——因为 `span_id` 是从序号推导的，改序号就必须改 ID。
3. `remapped` 记录旧 ID → 新 ID 的映射，用来修正每个父指针。**这一步是压实的全部难度所在**：如果只改序号不改父指针，所有父指针都会指向旧 ID，全部悬空。
4. `remapped.get(parent, 根)` 的兜底覆盖"父 span 本身就是那个未完成的空洞"这种情况。
5. `if index == 1: parent = None` 强制第一个 span 成为根。

**正常路径下这个映射是恒等的**，压实不产生任何差异。它是一段只在异常情况下起作用的代码——但没有它，异常情况的代价是整个接口 500 而不是一份稍微残缺的 trace。

### 12.10.1 `record_completed_span`：为遥测让路的一个妥协

大部分 span 用 `with trace_span(...)`。但有一个例外：

```python
def record_completed_span(
    kind: TraceSpanKind,
    name: str,
    *,
    duration_ms: float,
    status: TraceSpanStatus = TraceSpanStatus.OK,
    **attributes: AttributeValue,
) -> None:
```

它接受**外部已经测好的耗时**。docstring 说明了分工和理由：

> 模型 Provider 的计时器跨越 `__init__` 与多个 `finish` 分支，无法改写成一个 with 块；与其为遥测重构可靠性关键的异常分支，不如接受外部耗时。

这是一个诚实的工程妥协。`ModelCallMeasurement` 有六个结束分支，每个分支都有自己的错误处理和重试判断。为了让它变成一个 `with` 块，需要重构这段可靠性关键代码——风险大于收益。所以遥测层退一步，多提供一个入口。

代价写在同一段 docstring 里：开始时间由结束时间**回推**（`ended_at - timedelta(milliseconds=duration_ms)`），只用于时间轴展示，真正参与聚合的仍是调用方测的 `duration_ms`。所以模型调用 span 在火焰图上的横向位置是近似的。这个精度损失被接受了，但被写清楚了。

`traced_node` 装饰器是另一头的便利：

```python
def decorator(node: NodeCallable) -> NodeCallable:
    @wraps(node)
    async def wrapper(*args: object, **kwargs: object) -> object:
        with trace_span(kind, name):
            return await node(*args, **kwargs)
    return wrapper
```

`@wraps` 保留原函数名，因为 LangGraph 的错误信息和调试快照会显示被包装对象的名字。丢掉原名会让"哪个节点抛错"这种问题需要额外一次源码定位。

装饰器刻意**不暴露 handle**。docstring 解释："节点内部真正想标注的往往是模型调用而不是整个节点。" 需要写属性的地方直接用 `trace_span`。

`NodeCallable = TypeVar("NodeCallable", bound=Callable[..., Awaitable[object]])` 用 TypeVar 绑定而不是重写签名，因为 LangGraph 节点的签名各不相同（`state`、`runtime`、可选 `writer`），包装后的类型需要与原节点保持一致。

## 12.11 `/metrics`：为什么自己拼曝光文本

`app/observability/metrics.py` 的模块 docstring 开门见山地说不用 `prometheus_client`：

> 模块刻意不依赖 `prometheus_client`：需要暴露的只是若干计数器和一个 max gauge，自己拼字符串比引入一个带全局注册表的库更可控——全局注册表在多 Worker、多次 lifespan 的测试里会出现重复注册错误。

这是一个"不引入依赖"的合理案例。`prometheus_client` 的设计前提是**进程内计数器**：你在代码里 `counter.inc()`，库把它累加到一个全局注册表，`/metrics` 读注册表。但这个项目的指标全部来自数据库聚合（§11.11），所以库的核心功能用不上，剩下的只是字符串拼接。而它的全局注册表会在测试里反复重启 lifespan 时抛"这个指标已经注册过了"。

### 12.11.1 三个渲染细节

**标签白名单与 span 契约同源：**

```python
_LABEL_VALUE_PATTERN = re.compile(r"^[a-z][a-z0-9_.]{1,63}$")
```

`SpanMetric.validate_label` 在构造期就拒绝非法值。docstring 说明了为什么校验必须前移：

> 渲染函数因此可以无条件拼接字符串；如果非法值能进到渲染阶段，抓取端会得到一份语法损坏的曝光文本，整个 job 的所有指标都会被丢弃，故障范围远大于拒绝单条记录。

Prometheus 的曝光格式解析是全文件级别的：一行语法错误会让这次抓取的**全部**指标作废。所以宁可拒绝一条记录。因为 span 名和 kind 已经被遥测契约限制成同一字符集，这里的重复校验实际上永不触发——它防的是"有人绕过 ORM 手工写库"。

**错误数不得超过总数：**

```python
if self.error_count > self.count:
    raise ValueError("span error count cannot exceed total count")
```

这个不变量在数据库层**没有**对应约束（错误数由 SQL 的 `FILTER` 子句派生），所以必须在契约边界兜住。失败率一旦超过 1，看板和告警阈值会同时失去意义。

**单位写进指标名：**

```python
"# HELP dataops_span_duration_ms_sum Total span duration in milliseconds.",
```

`_ms` 后缀是刻意的。Prometheus 生态默认用秒，如果指标名不带单位，某天有人写了一条 `rate(dataops_span_duration_sum[5m]) > 30` 的告警，实际比较的是毫秒和秒，差三个数量级。docstring 说这是"这类自制 exporter 最常见且最难察觉的错误"。

**末行换行：**

```python
# 曝光格式要求以换行结尾；缺少末行换行会让部分抓取端丢弃最后一个样本。
return "\n".join(lines) + "\n"
```

**顺序稳定：**每个指标族只写一次 HELP/TYPE，样本按 `(kind, name)` 排序。所以两次抓取的文本差异只来自数值变化，测试可以逐行比对。

`RuntimeMetricsSnapshot` 刻意**不携带时间戳**："Prometheus 以抓取时间为准，自带时间戳反而会在补抓时产生乱序样本。"

### 12.11.2 503 而不是全零

```python
runtime = _require_diagnosis_runtime(request)
snapshot = await runtime.get_runtime_metrics()
return PlainTextResponse(
    render_prometheus_text(snapshot),
    media_type="text/plain; version=0.0.4; charset=utf-8",
)
```

`_require_diagnosis_runtime` 在 runtime 未装配时抛 503。docstring 给出了原因：

> 诊断 runtime 未装配（无数据库）时返回 503 而不是一份全零文本，避免监控面板把"未部署"显示成"零错误"。

这是本章第四次遇到同一条原则。全零文本会被 Prometheus 当成一次成功抓取，记录下 `error_count=0`，看板显示"一切健康"。503 会被记成抓取失败（`up=0`），这是一个能触发告警的信号。

**"没有数据"和"数据是零"必须用不同的机制表达。** 前者是抓取失败，后者是一个正常样本。

## 12.12 SSE 推流：一条只读的读法

先说什么是 SSE（Server-Sent Events）。它是 HTTP 上最简单的服务端推送：响应的 `Content-Type` 是 `text/event-stream`，服务端保持连接不关，一帧一帧地写纯文本：

```text
id: 3
event: run_event
data: {"contract_id":"run-stream:v1","cursor":3,...}

```

浏览器用内置的 `EventSource` 接收。比 WebSocket 简单得多（单向、纯文本、走普通 HTTP、自动重连），代价是只能服务端推客户端。对"看诊断进度"这个场景刚好够用。

`app/api/streaming.py:1` 的模块 docstring 定了基调："推流刻意不是'另一条执行路径'。" 这句话是整节的关键。

### 12.12.1 用 Protocol 让"无法推进 run"成为结构性事实

```python
class RunStreamSource(Protocol):
    async def get_run(self, run_id: str) -> AgentRunSnapshot | None: ...
    async def get_events_after(
        self, run_id: str, *, after_sequence: int
    ) -> tuple[RunEvent, ...] | None: ...
```

`iter_run_stream` 的参数类型是这个 Protocol，而不是 `DiagnosisApplicationRuntime`。Protocol 在 Python 里是结构化子类型（类似 Go 的 interface：不需要显式继承，方法齐了就算实现）。

实际传进去的确实是完整的 runtime 对象，它上面有 `submit_message`、`cancel_run` 这些能改状态的方法。但**类型签名只承诺两个只读方法**，所以：

- 类型检查器会拒绝在 `iter_run_stream` 里调用 `source.submit_message(...)`。
- 读代码的人看到签名就知道这个函数不可能推进 run。
- 测试可以传一个只有两个方法的假对象。

这就是"结构性保证"和"纪律要求"的区别。写一句注释说"不要在推流里改状态"是纪律；把类型窄化成两个只读方法，是让违规无法通过类型检查。

run 永远由 Worker 执行。轮询（`GET /api/v1/runs/{run_id}` + `/events`）是永久保留的等价回退路径——这不是"暂时还留着"，而是设计上的对等选项。

### 12.12.2 每跳必须先读 run 快照再读增量事件

推流循环的骨架：

```python
while True:
    run = await source.get_run(run_id)
    if run is None:
        # run 在推流期间消失只可能是外部清理，客户端不该按"诊断失败"处理，也不该无限重连。
        yield _end_frame(...RunStreamEndReason.RUN_DISAPPEARED).to_server_sent_event()
        return
    if run.status is not last_status:
        last_status = run.status
        yield RunStreamFrame(... kind=RunStreamFrameKind.RUN_SNAPSHOT ...).to_server_sent_event()
    events = await source.get_events_after(run_id, after_sequence=cursor)
    for event in events or ():
        cursor = event.sequence
        yield RunStreamFrame(... kind=RunStreamFrameKind.RUN_EVENT, event=event ...).to_server_sent_event()
    if run.status in TERMINAL_RUN_STATUSES:
        yield _end_frame(..., reason=RunStreamEndReason(run.status.value)).to_server_sent_event()
        return
    if monotonic() >= deadline:
        # 超时结束是连接级事件而不是 run 级事件：客户端应带最后游标重连，或退回轮询。
        yield _end_frame(..., reason=RunStreamEndReason.STREAM_TIMEOUT).to_server_sent_event()
        return
    await asyncio.sleep(config.poll_seconds)
```

顺序是 **先读快照 → 再读增量事件 → 再判终态**。反过来会漏事件，原因在第 11 章已经埋好了：`complete_run` 在**同一个事务**里提交终态和最后一批事件。

如果先读事件再读快照：

```
时刻 1: 读事件 → 拿到 1..7（此时事务还没提交）
时刻 2: complete_run 提交（终态 + 事件 8、9）
时刻 3: 读快照 → status=completed → 发终态帧 → return
```

事件 8、9 永远不会被发出。客户端看到 run 完成了，但时间线缺最后两条。

先读快照的情况：

```
时刻 1: 读快照 → status=running
时刻 2: complete_run 提交
时刻 3: 读事件 → 拿到 8、9 → 全部发出
时刻 4: 因为快照还是 running，不 return，继续下一跳
时刻 5: 下一跳读快照 → completed → 发终态帧 → return
```

多转一圈，但一条不漏。**这是把"事务原子性"翻译成"轮询顺序"的一个具体例子**，也是第 11 章 §11.5.1 那条规则在这一层的直接后果。

### 12.12.3 三种帧、五种结束原因

```python
class RunStreamFrameKind(StrEnum):
    RUN_SNAPSHOT = "run_snapshot"
    RUN_EVENT = "run_event"
    STREAM_END = "stream_end"
```

只有三种。`run_snapshot` 只在状态**变化**时发（`if run.status is not last_status`），所以一次正常的 run 大约是 `queued → running → completed` 三帧快照加上若干事件帧。不每跳都发快照，是为了不让 0.5 秒一跳的轮询把带宽浪费在重复内容上。

结束原因是本章最值得学的一个类型设计：

```python
class RunStreamEndReason(StrEnum):
    COMPLETED = "completed"
    FAILED = "failed"
    CANCELLED = "cancelled"
    STREAM_TIMEOUT = "stream_timeout"
    RUN_DISAPPEARED = "run_disappeared"
```

前三个是 **run 级终态**：诊断本身结束了。后两个是**连接级终止**：诊断可能还在跑，只是这条连接不再看了。

为什么必须区分？因为客户端的正确反应完全不同：

- `completed` / `failed` / `cancelled` → 渲染最终结果，不要重连。
- `stream_timeout` → run 可能还在跑。带最后的游标重连，或者退回轮询。
- `run_disappeared` → run 被外部清理了。**不要**当成"诊断失败"（那会给用户一个错误的结论），也**不要**无限重连（那会打服务端）。

如果把这五种情况合成一个 `{"done": true}`，客户端只能猜。而"流断了"和"诊断完成了"猜错的代价是：用户以为系统失败了，实际上诊断已经成功完成并写进了数据库。

前三个枚举值刻意等于 `AgentRunStatus` 的字符串值，所以可以直接 `RunStreamEndReason(run.status.value)` 转换。

### 12.12.4 游标放进标准 `id` 字段

```python
return ServerSentEvent(
    data=self.model_dump_json(exclude_none=True),
    event=self.kind.value,
    id=str(self.cursor),
)
```

SSE 协议本身就有 `id` 字段，而且浏览器的 `EventSource` 对它有内建行为：**记住最后收到的 `id`，断线自动重连时用 `Last-Event-ID` 请求头把它送回来**。

所以路由只要读这个头就实现了续传：

```python
cursor = resolve_stream_cursor(
    last_event_id=last_event_id,
    after_sequence=after_sequence,
)
```

对比一下自造协议的方案：在 `data` 的 JSON 里放一个 `cursor` 字段，前端自己存到变量里，重连时拼到 query string 上。功能一样，但要写前端逻辑、要处理"前端刷新后变量丢了"、而且浏览器的自动重连不会带上它（自动重连是 `EventSource` 内部行为，你无法插手）。

**复用协议的既有语义几乎总比自造更省事。** 这里的收益具体到：断线重连这件事完全不需要前端代码。

`resolve_stream_cursor` 有一个刻意的宽容：`Last-Event-ID` 损坏（不是数字、是负数）时**静默回退**到 `after_sequence` 参数，而不是返回 400。理由是这个头由浏览器自动发送、开发者无法控制其内容；因为一个损坏的头就拒绝整条连接，会让用户陷入"重连总是失败"而无从下手。回退到 0 的代价只是重发一遍已经收到的事件——而事件帧带序号，客户端能自己去重。

### 12.12.5 存在性检查必须在开流之前

```python
runtime = _require_diagnosis_runtime(request)
# 先确认 run 存在再开流，让 404 仍然是一个真正的 HTTP 状态码而不是流内的一帧。
if await runtime.get_run(run_id) is None:
    raise HTTPException(status_code=404, detail="diagnosis run not found")
```

这是一条 HTTP 层面的硬约束：**一旦响应体开始写，状态码就已经发出去了**。SSE 的响应状态是 200，之后无论发生什么都改不了。

所以如果不在开流前检查，未知 run 只能表达成"流内的一条错误帧"。而客户端（尤其是浏览器的 `EventSource`）几乎一定会把流的意外结束当成网络抖动去重连——于是变成对一个不存在的 run 无限重连。

多花一次数据库查询换一个真正的 404，非常值得。

心跳交给库：

```python
return EventSourceResponse(
    iter_run_stream(runtime, run_id, after_sequence=cursor, config=config),
    ping=int(config.keepalive_seconds),
)
```

`sse-starlette` 的 `ping` 参数会自动插入注释帧（`: ping`）。手写心跳需要处理"心跳和数据帧的交错"、"心跳算不算一次 yield"这些细节，而且容易和帧编码搞混。

## 12.13 三个时间预算的偏序，以及为什么它是启动期校验

`RunStreamConfig` 有三个数字（默认值来自 `app/core/settings.py:149`）：

```python
poll_seconds: float = 0.5      # 多久查一次数据库
keepalive_seconds: float = 15   # 多久发一次心跳
max_seconds: float = 300        # 单条连接最长活多久
```

`app/core/settings.py:250` 的 `_validate_run_stream` 强制它们满足一个偏序：

```python
if self.run_stream_poll_seconds >= self.run_stream_keepalive_seconds:
    raise ValueError("run_stream_poll_seconds must be shorter than the keepalive period")
if self.run_stream_keepalive_seconds >= self.run_stream_max_seconds:
    raise ValueError("run_stream_keepalive_seconds must be shorter than the max lifetime")
if self.run_stream_max_seconds <= self.react_total_timeout_seconds:
    raise ValueError("run_stream_max_seconds must exceed react_total_timeout_seconds")
```

前两条是内部一致性：轮询快于心跳、心跳短于寿命。否则这条连接根本等不到第一次心跳，中间的反向代理仍会按空闲超时把它掐断——**你以为配了心跳，实际上心跳从来没发出去过**。

第三条是**跨模块**的约束，也是最容易漏掉的一条。docstring 讲得很具体：

> 寿命必须超过 ReAct 总超时：否则一个完全正常、只是跑满预算的 run 会在结束前被推流强行截断，演示者看到的是"流断了"而不是"诊断完成"，只能退回轮询才能看到结论。

这类跨模块的数值约束在大多数项目里根本不存在——两个数字分属两个模块，各自看都合理，组合起来才出问题。而症状（"推流总是断"）和原因（"两个超时配反了"）之间隔了好几层，排查很贵。把它写成启动期校验，配错的实例直接起不来。

这和第 7 章 `_validate_react_budget`（ReAct 总超时必须覆盖一次 Planner 调用加它的瞬时重试）是同一个模式：**任何两个超时之间的关系都应该有一条显式断言。**

## 12.14 一个被写进健康接口的限制

浏览器的 `EventSource` **不能设置请求头**。这是规范层面的限制，不是实现缺陷，也没有办法绕过（只能换 `fetch` + 手写流解析，那就失去了自动重连）。

后果很直接：`api-auth:v1` 处于 bearer 模式时，前端的 `EventSource` 无法携带 `Authorization`，鉴权中间件必然把它挡在 401。**bearer 模式下推流一定不可用。**

处理这件事有三种态度：

1. 为推流开一个鉴权例外（比如允许 query string 带令牌）。→ 令牌会出现在浏览器历史、代理日志和 Referer 里。为了一个体验功能打穿安全边界，不做。
2. 只写在文档里。→ 演示时会出现"说好有流式却一直在轮询"，然后现场解释。
3. 写进健康接口。

选了第三种：

```python
class RunStreamConfiguration(BaseModel):
    contract_id: str
    poll_seconds: float
    keepalive_seconds: float
    max_seconds: float
    available_under_auth: bool
```

赋值就一行：

```python
available_under_auth=request.app.state.api_security.mode == "disabled",
```

`/health` 如实报告这个实例的推流能不能用，前端可以据此直接决定走推流还是走轮询，不用先试一次 401。

这一节想说的其实不是 SSE，而是**怎么对待一个无法修复的限制**。它既没有被藏起来，也没有被"修复"成一个安全漏洞，而是变成了一个可以被机器读取的事实。这比大多数项目做得都要干净：多数项目的做法是让它成为一个只有原作者知道的隐性知识。

`stream_diagnosis_run` 的 docstring 把这件事又写了一遍，因为读路由代码的人不一定会去看 `/health` 的模型定义：

> 注意浏览器 `EventSource` 无法设置请求头：`api-auth:v1` 处于 bearer 模式时这条路由会被鉴权中间件拒绝，前端必须退回轮询，`/health` 的 `stream.available_under_auth` 会如实报告这一点。

## 12.15 路由层的其余边界

剩下几处值得快速过一遍，它们都是"错误语义"的设计。

**202 而不是 200。** `POST /api/v1/sessions/{session_id}/messages` 返回 `202 ACCEPTED`，因为 run 只是入队了，还没执行。返回 200 会暗示"处理完了"。

**409 带上冲突对象的 ID：**

```python
except ActiveRunConflictError as exc:
    # 同一 session 只允许一个 queued/running run，客户端应轮询旧 run 后再提交追问。
    raise HTTPException(
        status_code=status.HTTP_409_CONFLICT,
        detail={"active_run_id": exc.active_run_id, "message": "session has an active run"},
    ) from exc
```

只回一个"有活跃 run"的消息，客户端还得再查一次才知道是哪个。带上 `active_run_id`，前端可以直接跳去轮询它。

**500 里带 run_id，但不带原异常：**

```python
except DiagnosisExecutionFailed as exc:
    raise HTTPException(
        status_code=500,
        detail={
            "run_id": exc.run_id,
            "error_code": exc.error_code,
            "message": exc.public_message,
        },
    ) from exc
```

`public_message` 和 `error_code` 是稳定的、脱敏的；原异常通过 `from exc` 留在进程日志里（它可能含数据库连接串、Provider 原始响应或 Prompt 片段）。而 `run_id` 让客户端仍然能去 `GET /api/v1/runs/{run_id}/events` 看已经持久化的安全时间线。

**`/demo` 静态资源的路径穿越防护：**

```python
candidate = (DEMO_ASSET_ROOT / asset_name).resolve()
if DEMO_ASSET_ROOT not in candidate.parents or not candidate.is_file():
    raise HTTPException(status_code=404, detail="demo asset not found")
```

`asset_name` 是路径参数（`{asset_name:path}`），所以浏览器能请求 `../../.env`。`resolve()` 把它展开成绝对路径，然后必须验证结果**仍在** demo 目录内。这是路径穿越（path traversal）最标准的防法：先规范化，再检查包含关系。反过来（先检查字符串里有没有 `..`，再拼接）会被各种编码变体绕过。

注意 `_resolve_demo_asset` 和 `_demo_index_available` 都是**同步** helper。这不是随手写的：文件系统调用是阻塞的，在 async 路由里直接遍历路径会占住事件循环。抽成同步函数让 Ruff 的 `ASYNC` 规则集（`pyproject.toml` 里启用了）能验证这一点。

**两个 `_require_*` helper 集中降级语义：**

```python
runtime = request.app.state.diagnosis_runtime
if runtime is None:
    raise HTTPException(
        status_code=503,
        detail="diagnosis resources require PostgreSQL and configured Planner/Auditor",
    )
```

七八个路由共用它。不集中的话，每个路由要么各写一遍（容易漂移），要么直接 `.something` 撞 `AttributeError` 变成 500——而 500 会让客户端以为是 bug，503 才是"这个实例没配这个功能"。docstring 还提到另一个更隐蔽的误判：把 disabled 模式误报成"未知 session/run"（404）。

## 12.16 本章的取舍清单

| --- | --- | --- | --- |
| 鉴权用 ASGI 前缀中间件 | 无法给单个路由做细粒度策略 | 新增 `/api/v1/...` 默认受保护（fail closed） | §12.2 |

| 提供 `mark` 显式改状态 | 调用方要记得调 | 降级/否决/取消不会被记成 `ok` | §12.9.2 |
| `CancelledError` 单独归类 | 多一个 `except` | 错误率不被用户主动取消污染 | §12.9.3 |
| 两个异常分支都 `raise` | 无 | 观测层不改变控制流 | §12.9.3 |
| `_completed` 用字典按序号存 | 导出时要排序 | 并发完成顺序不破坏父先于子 | §12.9.4 |
| 孤立 span 挂到根 | 层级不精确 | 一处插桩疏漏不毁掉整个 trace 接口 | §12.9.4 |
| 超限丢弃且公开计数 | trace 可能残缺 | 残缺是可读事实而非静默沉默 | §12.9.5 |
| 导出阶段压实序号并改父指针 | 一段只在异常时生效的代码 | 空洞不会让整个 trace 接口 500 | §12.10 |
| `record_completed_span` 接受外部耗时 | 开始时间由结束回推、横向位置近似 | 不为遥测重构六分支的可靠性关键路径 | §12.10.1 |
| 不用 `prometheus_client` | 自己拼曝光文本 | 无全局注册表、测试反复重启 lifespan 不冲突 | §12.11 |
| 标签值构造期校验 | 重复一次遥测已有的检查 | 一行语法错误不会作废整次抓取 | §12.11.1 |
| 单位写进指标名（`_ms`） | 指标名更长 | 不与 Prometheus 默认秒制静默混用 | §12.11.1 |
| `/metrics` 未装配返回 503 | 抓取端会报错 | "未部署"不显示成"零错误" | §12.11.2 |
| 推流类型窄化为 `RunStreamSource` Protocol | 多一个协议定义 | 结构上无法推进或修改 run | §12.12.1 |
| 每跳先读快照再读增量事件 | 终态多转一圈才发出 | 与 `complete_run` 的单事务配合，一条事件不漏 | §12.12.2 |
| 结束原因区分 run 级与连接级 | 枚举有五个值 | 客户端知道该重连、退回轮询还是渲染结论 | §12.12.3 |
| 游标放进标准 SSE `id` 字段 | 受限于协议格式（字符串） | 断线重连完全不需要前端代码 | §12.12.4 |
| `Last-Event-ID` 损坏时静默回退 | 可能重发已收事件 | 不因浏览器自动发的头拒掉整条连接 | §12.12.4 |
| 存在性检查在开流之前 | 多一次数据库查询 | 404 是真正的状态码而非流内一帧 | §12.12.5 |
| 三个时间预算的偏序写成启动期校验 | 配置灵活度降低 | 跑满 ReAct 预算的正常 run 不被推流截断 | §12.13 |
| bearer 模式下推流不可用、写进 `/health` | 前端要处理两种模式 | 不为体验功能打穿安全边界，限制可被机器读取 | §12.14 |
| 409/500 带上 ID 但不带原异常 | 响应结构更复杂 | 客户端能继续操作，敏感文本留在进程日志 | §12.15 |
| 静态资源先 `resolve()` 再检查包含关系 | 每次请求多一次路径规范化 | 路径穿越无法用编码变体绕过 | §12.15 |

## 12.17 遗留问题

按诚实性要求，这一层已知没做完的地方：

1. **限流是进程内的，多实例部署会失效。** `SlidingWindowRateLimiter` 的窗口存在进程内存里。API 只要横向扩到两个实例，每个客户端实际拿到的配额就是 `120 × 实例数`。要修需要把窗口挪到共享存储——但项目的硬边界是"PostgreSQL 是唯一状态服务，不引入 Redis"，用数据库做限流会给每个请求加一次写事务，代价不小。当前部署形态是单实例，所以这个问题还没到必须解决的时候，但它必须被写下来。

2. **`ip:unknown` 兜底桶与代理场景未处理。** 见 §12.3.1。放到反向代理后面时所有请求的 `request.client.host` 会是代理的地址，等于全局共享一个配额桶。改成读 `X-Forwarded-For` 需要先确立"代理可信"这个前提，否则请求方可以伪造该头绕过限流。这一步没做。

3. **单令牌、无角色、无过期。** `api-auth:v1` 只有一个共享 bearer 令牌。没有多用户、没有权限分级（谁都能 `DELETE /api/v1/memories/{id}`）、没有令牌轮换机制。对求职演示项目够用，但离生产的鉴权体系还差一整套。

4. **trace 只落库、不导出。** span 表结构和 `run-trace:v1` 契约在设计上是照着 OpenTelemetry 的概念做的，但没有 OTLP exporter，所以接不进 Jaeger / Tempo / Grafana。`RunTraceCollector` 的 docstring 提到"后续把 span 导出到 OTLP 时也只需要替换采集器实现"——这条路留着了，但没走。

5. **根 span 缺最终提交的耗时。** §11.5.2 记过：根 span 在最终事务提交**之前**关闭，换来的是严格原子性。代价是 `total_duration_ms` 不含那次提交的耗时。提交通常是毫秒级，但在数据库压力大时可能不是。

6. **`MAX_SPANS_PER_RUN = 512` 与六个 checkpoint 上限一样没有实测调优依据。** 都是按"有界循环的理论上界乘一个余量"估的，没有拿真实长会话的分布验证过。

7. **`/metrics` 没有直方图，算不出真正的分位数。** 只有 count / sum / max（§12.11 解释了为什么：分位数无法跨实例合并）。所以 P95 ≤ 30 秒这个目标目前只能靠离线评测逐案例统计，不能从 `/metrics` 直接读。

8. **推流未在真实反向代理后验证过。** 心跳周期是 15 秒，理论上够绕开常见的 60 秒空闲超时，但没有实测过 nginx / Cloudflare 之类会不会缓冲 `text/event-stream`（缓冲会让所有帧攒到最后一起到达，推流退化成一次性响应）。

9. **P95 ≤ 30 秒仍未达成。** 真实模型评测实测每案例 58–125 秒。并行工具调用已经落地（§8），但它只减少工具等待，模型调用本身的耗时是主要成本。这条是全项目最大的未达成目标，第 14 章会给出实测数字。

## 12.18 小结

这一章的三个契约各自解决一类问题，但共用同一种思路：**把纪律变成结构**。

- `api-auth:v1` 不靠"记得给新路由加依赖"，靠前缀判定让保护成为默认值；不靠"记得别泄露配置信息"，靠三种失败共享逐字相同的响应。
- `run-trace:v1` 不靠"记得别把 Prompt 写进 span"，靠正则白名单让含空格的文本在写入时崩掉；不靠"记得传对父指针"，靠 `ContextVar` 让并行任务自动继承。
- `run-stream:v1` 不靠"记得别在推流里改状态"，靠把类型窄化成两个只读方法。

回顾这一章反复出现的那条原则——**空、零和不存在必须可区分**——它在本章出现了四次：token usage 缺失时是 `None` 而不是 0（§12.7.1）；`dropped_span_count` 非零必须暴露而不是让残缺 trace 看起来完整（§12.9.5）；`/metrics` 未装配返回 503 而不是全零文本（§12.11.2）；`RunTrace.spans` 为空表示"插桩上线前执行或仍在队列"而不是零耗时（`RunTraceResponse` 的 docstring）。第 11 章的 §11.17 已经数过四次，第 10 章的"指标读到 0，先检查分母是不是空的"是同一件事的第一次出现。**这大概是整个项目最值得带走的一条工程直觉。**

另外值得记住的是三处"跨模块的数值约束"：推流寿命必须超过 ReAct 总超时（§12.13）、ReAct 总超时必须覆盖一次 Planner 调用加其重试（第 7 章）、心跳必须短于寿命（§12.13）。这类约束在代码里是两个各自合理的数字，只有组合起来才出问题，而症状与原因之间隔着好几层。把它们写成启动期断言，是这个项目里性价比最高的一类防护。

**第 13 章转向部署与验证**：`docker compose` 的两个服务、`Dockerfile` 的多阶段构建、启动命令里 `alembic upgrade head && python -m app.persistence.seed` 那个 `&&` 为什么必须是 `&&`、`.env` 里每个变量的作用与它们的安全边界，以及一份从零到 `/demo` 能跑通的完整验证清单——包括在没有模型凭据时哪些接口应该返回 503（那不是失败，那是正确行为）。第 14 章再回到评测：五层作品集评测的 20 个指标、GraphRAG 与记忆的消融方法、真实模型评测的实测数字与它们的限制说明。
