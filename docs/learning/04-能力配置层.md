# 第 4 章 能力配置层：为什么"五项能力"不是五个 Agent

## 4.1 你会验证什么

```bash
.venv/Scripts/python -m pytest -q tests/unit/test_capabilities.py
```

这一章读 `app/capabilities/`（五个文件，549 行）。它是全项目最容易被误解的一个包：名字叫
"capabilities"，很像插件系统或者子 Agent 目录，实际上**一行 I/O 都没有**——没有 LLM 调用、没有 MCP
调用、没有数据库访问。

包 docstring 把边界说得很清楚：

> 本包只描述 Planner 可复用的调查策略，不执行模型、MCP、数据库或工作流调用。调用方通过默认注册表
> 获得版本化选择结果，从而把 capability 与仓库级 Codex Skill、动态插件系统隔离。

## 4.2 常见的三种做法，以及本项目为什么都不选

要实现"系统支持五项能力"，主流写法有三种：

1. **五个子 Agent。** 每项能力是一个能自己调模型和工具的 Agent，由一个 Supervisor 分派。这是
   `AutoGen`/`CrewAI` 风格。
2. **五个工具（function calling）。** 把能力包装成工具交给模型选。
3. **五段 Prompt 模板 + if/else 拼接。** 最朴素的做法。

本项目选的是第三种的强类型版本：能力是**冻结的 Pydantic 数据**，由一个确定性注册表按规则合并。
理由分三层：

- **对第一种（子 Agent）的反对**：本项目已经有两个 Agent（Planner + Auditor），它们的分工是
  "生产"与"审计"，这是一条有意义的对抗关系。再加五个"领域 Agent"只会让同一份证据被反复重述，
  每加一个 Agent 就多一份 token 成本、多一个可能违反引用规则的输出源，而对"结论是否有据"没有任何
  帮助。`base.py` 的 docstring 直接写了这条：模型不提供执行钩子，因此 capability 不会演变成
  第三类 Agent。
- **对第二种（当工具给模型选）的反对**：能力的选择在本项目里是**确定性的**——单组件意图就用单组件
  策略，跨组件意图就用链路策略，风险与报告永远启用。让模型来选，等于把一个可以用 `if` 判断的事情
  变成一次可能出错、可能不稳定、还要花钱的模型调用。
- **对第三种朴素版的反对**：裸字符串拼接没法校验"每项能力恰好一段 Prompt"、没法保证工具优先级
  去重、没法在启动时审计能力集合完整。所以本项目把这些约束写成 Pydantic 模型和校验器。

CLAUDE.md 的表述是："`app/capabilities/` 是配置不是 Agent……别和 `.agents/skills/` 的开发 Skill
混淆。"后半句针对的是另一种混淆：仓库里 `.agents/skills/` 是**给开发工具用的**（指导怎么开发这个
项目），`app/capabilities/` 是**运行时的**（指导 Planner 怎么调查故障），两者同名不同物。

## 4.3 `CapabilityDefinition`：一项能力就是六个字段

```python
class CapabilityDefinition(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    name: CapabilityName
    summary: str = Field(min_length=20, max_length=500)
    prompt_fragment: str = Field(min_length=80, max_length=5000)
    tool_priority: tuple[ToolName, ...] = ()
    required_inputs: tuple[CapabilityInputField, ...] = Field(min_length=1)
    output_validation_rules: tuple[str, ...] = Field(min_length=1)
```

六个字段对应"一项能力需要说明的全部内容"：叫什么、干什么、给模型什么指令、优先用哪些工具、需要
哪些输入、输出要满足什么规则。**没有 `execute` 方法，也没有任何回调字段**——这是本章的核心。

几个约束值得单独说：

- **`frozen=True`**：定义是模块级常量，冻结之后任何"运行时改一下 prompt"的想法都会失败。
- **`prompt_fragment: min_length=80`**：一段少于 80 字符的能力指令基本等于没写。下限逼着维护者
  真的把约束写出来，而不是留个 `"诊断故障"` 占位。
- **`tool_priority` 默认为空元组**：`RISK_ASSESSMENT` 和 `STRUCTURED_REPORTING` 是横切输出策略，
  不需要工具。这个默认值让"不需要工具"成为合法状态，而不是被迫填一堆无关工具。
- **`required_inputs: min_length=1`**：反过来，任何能力都至少需要一项输入。一个不需要任何输入的
  "能力"说明它其实是常量文本。
- **全部用 `tuple` 而不是 `list`**：配合 `frozen=True` 使定义真正不可变，也让它们可哈希、可进集合。

### 4.3.1 三个去重校验

```python
    @model_validator(mode="after")
    def validate_unique_policy_items(self) -> CapabilityDefinition:
        # 分别比较序列长度与集合长度，保留原始顺序的同时检测维护者误复制的配置项。
        if len(self.tool_priority) != len(set(self.tool_priority)):
            raise ValueError("capability tool_priority must not contain duplicates")
        if len(self.required_inputs) != len(set(self.required_inputs)):
            raise ValueError("capability required_inputs must not contain duplicates")
        if len(self.output_validation_rules) != len(set(self.output_validation_rules)):
            raise ValueError("capability output rules must not contain duplicates")
        return self
```

`len(x) != len(set(x))` 是 Python 里检测重复的惯用法，它保留顺序（不像 `sorted(set(x))`）。

docstring 解释了为什么单项定义内部不允许重复，而注册表合并时又允许："注册表按声明顺序稳定去重，
但单项定义内部的重复通常代表维护错误而非组合需要。"**同一个操作（去重）在两个层次有不同语义**：
跨能力重复是正常的（两项能力都需要 `REALTIME_OBSERVATIONS`），单项内重复只能是复制粘贴的手滑。

这些校验在**模块导入时**就跑了——因为 `SINGLE_COMPONENT_DIAGNOSIS` 等是模块级常量。写错一个字，
`import app.capabilities` 直接失败，服务起不来。

## 4.4 三个枚举各自封住一类"自由输入"

```python
class CapabilityName(StrEnum):
    SINGLE_COMPONENT_DIAGNOSIS = "single_component_diagnosis"
    CROSS_COMPONENT_CHAIN_TRACING = "cross_component_chain_tracing"
    HISTORY_CASE_MATCHING = "history_case_matching"
    RISK_ASSESSMENT = "risk_assessment"
    STRUCTURED_REPORTING = "structured_reporting"
```

docstring 里有一句很直接的话：

> 拒绝任意字符串能防止新能力绕过产品审查，也明确这里是固定策略集合而不是可动态安装的插件目录。

"不是插件目录"是一个**产品决定**，写在类型里。想加第六项能力，必须改枚举 → 改 `_FIXED_DEFINITIONS`
→ 改文档 → 改测试，途中会经过评审。

```python
class DiagnosisIntent(StrEnum):
    SINGLE_COMPONENT_DIAGNOSIS = "single_component_diagnosis"
    CROSS_COMPONENT_DIAGNOSIS = "cross_component_diagnosis"
```

注意 `DiagnosisIntent` 和 `CapabilityName` **前两项字符串很像但不是一回事**：意图是"用户想查什么"，
能力是"系统用什么策略查"。docstring 说明这个枚举"复用 Golden Case 已有字符串，避免 capability
注册表自行解析自然语言"——也就是意图不是这里判定的，是上游给的（第 8 章会看到 `select_capabilities`
节点怎么拿到它）。

为什么意图只有两个、而历史案例不是第三种意图？docstring 回答了："历史案例是调查中的可选增强而非
第三种诊断主流程，因此由独立 `HistoryTrigger` 控制。"

```python
class HistoryTrigger(StrEnum):
    NOT_REQUESTED = "not_requested"
    USER_REQUESTED = "user_requested"
    PLANNER_VALIDATION = "planner_validation"
    REUSABLE_SIGNATURE = "reusable_signature"
```

`NOT_REQUESTED` 是**安全默认值**，docstring 明说：显式来源便于事件审计，也防止每轮 ReAct 无条件
召回旧案例。

这是一条很实际的设计：如果历史召回无条件执行，那么每次诊断都会把一批旧案例塞进上下文，模型很容易
顺着旧结论走（这在文献里叫 anchoring）。三个非默认值各自对应一种**有理由**的召回：用户明确要求、
Planner 想验证先例、症状签名可复用。触发原因会进 run 事件，所以"这次为什么看了历史"是可审计的。

第四个枚举 `CapabilityInputField` 列出十种输入类别，docstring 强调："输入名描述上游工作流必须提供
的数据，不绑定具体存储或函数参数。"也就是它是**需求声明**而不是函数签名——编排层可以在调用 Planner
之前统一检查缺口，而不是让 Prompt 在运行中猜。

## 4.5 五项能力的 Prompt 片段里藏着全部产品立场

这一节值得慢读：五段 `prompt_fragment` 是整个系统"价值观"最集中的表述。

### 4.5.1 单组件诊断：不许扩大范围

```text
仅调查 components 中唯一的组件。先选择最能确认当前状态的只读工具，
再按证据缺口读取日志或组件特有元数据；每轮只能提出一个结构化 Action。不得把相似文本、
工具失败或其他组件的历史现象当成本次实时事实。若白名单工具无法取得关键证据，
应降低置信度并明确缺失项，而不是扩大组件范围或编造 Observation。
```

四条约束，每条都对应一种典型失败：扩大调查面（成本失控）、把工具失败当事实（第 3 章那条不变量的
Prompt 侧呼应）、把相似文本当证据（RAG 系统的经典毛病）、证据不足时硬凑结论。

最后一句"降低置信度并明确缺失项"是本项目反复出现的姿态：**允许说"我不知道"，并且要说清不知道
什么。** 对应契约层的 `uncertainties` 字段和 `evidence_insufficient` 停止原因。

注意这段文本里写着"每轮只能提出一个结构化 Action"——而系统现在支持单轮 1–3 个并行 Action。这不
矛盾：并行批次上限由控制器在运行时注入（第 8 章会看到 `min(配置并行度, 剩余步数)`），能力片段
只表达"不要在一个 Action 里塞多件事"的最保守基线。

### 4.5.2 跨组件链路：图路径只能提候选

```text
围绕 components 中的多组件范围调查传播关系。优先确认上游状态和依赖拓扑，
再沿 LTS、BDS、FlashSync 的候选链逐段取得实时 Observation，并用 retrieved_paths 补充
可引用关系。故障链中的每个节点和边都必须有 evidence_id 或 path_id；图路径只能提出候选连接，
不能覆盖冲突的实时工具结果。缺少某一段证据时应明确标记链路不完整。
```

"图路径只能提出候选连接，不能覆盖冲突的实时工具结果"就是第 0 章那条规则一（实时 Observation 永远
优先于历史/检索）在 Prompt 层的落点。它在三处出现：这里（Prompt）、`output_validation_rules`
（校验规则）、以及第 9 章确定性规则（真正的强制）。**Prompt 负责引导，规则负责强制**——只写 Prompt
不写规则等于只有建议。

工具优先级顺序也变了：

```python
# 单组件
LTS_GET_TASK_STATUS, LTS_GET_TASK_LOG, LTS_GET_DEPENDENCY_TOPOLOGY, ...
# 跨组件
LTS_GET_TASK_STATUS, LTS_GET_DEPENDENCY_TOPOLOGY, LTS_GET_TASK_LOG, ...
```

第二、三位对调了：跨组件调查里"依赖拓扑"比"日志"更重要，因为你先要知道链路形状才知道下一步查谁。
源码注释写着：跨组件顺序先建立 LTS 拓扑，再沿 BDS 和 FlashSync 观察验证传播链，而非按文本相似度
拼链。

`required_inputs` 也比单组件多了 `CURRENT_HYPOTHESES` 和 `RETRIEVED_PATHS`——跨组件推理必须带着
已有假设和图路径走，否则每一步都是孤立观察。

### 4.5.3 历史案例：差异比相似更重要

```text
只使用 confirmed 的历史案例，并保留案例 ID、确认状态、相似度和引用。
逐项比较本次组件、症状、候选根因、故障路径和关键 Observation，分别列出共同点与差异点；
历史方案只能作为参考和风险提示，不能直接确认本次根因。任何历史记录与实时 Observation
冲突时，必须突出差异并以本次实时证据为准。
```

对照第 1 章 `SimilarCaseReference` 的校验器：`differences` 字段 `min_length=1`。Prompt 要求"分别
列出共同点与差异点"，类型层强制"差异点非空"。**同一条约束两层实现**——模型忘了写，构造报告时就
会失败。

`HISTORY_CASE_MATCHING` 的 `tool_priority` 是空的（用默认值）：历史匹配不需要调工具，它消费的是
`CONFIRMED_CASES`。而它的 `required_inputs` 里同时有 `REALTIME_OBSERVATIONS`——因为"比较"这件事
必须两边都有。

模块 docstring 还交代了职责边界：本模块只定义策略，实际的召回由顶层诊断图按 trigger 执行，
比较由 `app.memory.matcher` 确定性生成（第 10 章）。**能力层描述"要什么"，实现层负责"怎么做"。**

### 4.5.4 风险评估：不许声称已执行

```text
对每项修复建议独立评估 low、medium 或 high 风险，并给出执行前置条件、
失败回滚和结果验证。建议只能描述人工可审查的处理方案，不能声称已经执行生产写操作；
高风险建议必须引用支持其必要性的证据。证据不足时优先提出只读检查或降低建议强度，
不得用确定语气掩盖不确定性。
```

"不能声称已经执行生产写操作"这条约束的必要性很容易被低估。工具全是只读的，模型**不可能**执行写
操作，但它完全可能在报告里写"已重启同步任务"——语言模型描述一个动作和执行一个动作在文本上没有
区别。而一份写着"已重启"的报告会让值班工程师跳过真正的处理步骤。所以这条既在 Prompt 里，也在
`output_validation_rules` 里。

"优先提出只读检查或降低建议强度"和第 1 章 `RemediationStep` 的风险不对称校验对应：低风险步骤
（只读检查）不要求证据引用，所以"降级为只读检查"是一条**成本低、总是可行**的退路。

### 4.5.5 结构化报告：不许用一段自由文本代替字段

```text
输出必须分别填写故障摘要、传播链、根因与置信度、证据引用、分步修复、
风险与回滚、证据不足项、后续检查和相似案例，不得用一段自由文本替代结构化字段。
每项根因与故障链关键边必须引用有效证据；无法确定时保留 uncertainties 并说明下一步，
而不是为了完整性编造结论。不要输出或保存原始 Thought。
```

最后一句是"绝不外泄推理过程"边界的 Prompt 侧。它和第 1 章 `AgentState` 里**没有** `thought` 字段
构成两道防线：Prompt 让模型不要输出，类型让它即使输出也无处存放。

`RISK_ASSESSMENT` 与 `STRUCTURED_REPORTING` 的 `required_inputs` 里都**没有** `SCENARIO_ID` /
`TRACE_ID`——它们不调工具，不需要定位数据。这种"只声明真正需要的输入"让编排层的缺口检查更精确。

## 4.6 `CapabilitySelectionRequest`：意图与组件数必须匹配

```python
    @model_validator(mode="after")
    def validate_component_scope(self) -> CapabilitySelectionRequest:
        # 先拒绝重复值，否则两个相同组件可能错误满足跨组件的长度要求。
        if len(self.components) != len(set(self.components)):
            raise ValueError("components must not contain duplicates")
        if self.intent is DiagnosisIntent.SINGLE_COMPONENT_DIAGNOSIS and len(self.components) != 1:
            raise ValueError("single-component diagnosis requires exactly one component")
        if self.intent is DiagnosisIntent.CROSS_COMPONENT_DIAGNOSIS and len(self.components) < 2:
            raise ValueError("cross-component diagnosis requires at least two components")
        return self
```

那条注释指出了一个真实的绕过路径：如果不先去重，`components=(LTS, LTS)` 的长度是 2，**满足**跨
组件的 `>= 2` 检查，于是系统会用链路追溯策略去查一个组件的传播关系——链路空间是空的，模型只能编。
**校验顺序有语义**，这和第 1 章 `TimeRange` 先查时区再比大小是同一类问题。

单组件用 `!= 1`（精确等于一个）而不是 `<= 1`：零个组件也不合法，而 `Field(min_length=1)` 已经拦了
零，这里再精确一次是为了让"单组件"名副其实。

## 4.7 注册表：构造期审计 + 确定性合并

### 4.7.1 构造函数拒绝外部注入

```python
    def __init__(self) -> None:
        definitions_by_name = {definition.name: definition for definition in _FIXED_DEFINITIONS}
        expected_names = set(CapabilityName)
        # 字典会覆盖重复键，因此先比较长度，才能同时识别重复定义和缺失定义。
        if len(definitions_by_name) != len(_FIXED_DEFINITIONS):
            raise ValueError("runtime capability definitions contain duplicate names")
        if set(definitions_by_name) != expected_names:
            raise ValueError("runtime capability definitions must match the fixed product baseline")
        self._definitions = MappingProxyType(definitions_by_name)
```

三个设计点：

1. **`__init__` 不接参数。** docstring 说明了目的："避免把 registry 误用为插件注入点。"能接受
   `definitions` 参数的注册表，早晚会有人从配置文件加载它。
2. **先比长度再比集合。** 注释解释了原因：字典推导会静默覆盖重复键，所以只比 `set(...)` 相等的话，
   "同一个能力写了两遍、另一个漏了"这种情况可能被漏掉。两条检查合起来才能同时抓重复和缺失。
3. **`MappingProxyType`** 是 Python 的只读字典视图（类比 Java 的
   `Collections.unmodifiableMap`）。`self._definitions[x] = y` 会抛 `TypeError`。加上定义自身
   `frozen=True`，这个注册表在运行期是彻底不可变的。

第 2 章讲过 lifespan 会构造它——那次构造就是这段审计的执行时机。误删一项能力，服务拒绝启动。

### 4.7.2 `select`：五项能力如何组合成三到四项

```python
        if request.intent is DiagnosisIntent.SINGLE_COMPONENT_DIAGNOSIS:
            primary_name = CapabilityName.SINGLE_COMPONENT_DIAGNOSIS
        else:
            primary_name = CapabilityName.CROSS_COMPONENT_CHAIN_TRACING

        active_names = [primary_name]
        if request.history_trigger is not HistoryTrigger.NOT_REQUESTED:
            active_names.append(CapabilityName.HISTORY_CASE_MATCHING)
        # 风险与报告是每次诊断都必须执行的横切约束，顺序固定在调查策略之后。
        active_names.extend((CapabilityName.RISK_ASSESSMENT, CapabilityName.STRUCTURED_REPORTING))
```

整个"路由"就是这几行 if。所以 `CapabilitySelection.active_capabilities` 的
`Field(min_length=3)` 才成立：主策略 1 项 + 风险 + 报告 = 至少 3 项，带历史时 4 项。

顺序不是随意的：调查策略在前、横切约束在后。Prompt 拼接时（见下）片段按这个顺序排列，最后出现的
是"输出必须结构化、不要泄漏 Thought"——**约束越硬越靠后**，因为靠后的指令在长上下文里通常权重
更高。这是一个经验性的 Prompt 工程细节，但它在代码里是确定的顺序，不是随机的。

`RISK_ASSESSMENT` 和 `STRUCTURED_REPORTING` 永远启用，正是第 0 章说的"风险与报告是横切关注点"。
如果它们也可选，就会出现"这份报告没有风险评估因为路由没选它"这种无法解释的差异。

### 4.7.3 工具优先级要按已批准组件裁剪

```python
        tool_priority = _stable_unique(
            tuple(tool for definition in definitions for tool in definition.tool_priority)
        )
        # 无论单组件还是跨组件，都裁剪到路由已经批准的范围，避免优先级诱导 Planner 越界调查。
        allowed_components = set(request.components)
        tool_priority = tuple(
            tool
            for tool in tool_priority
            if any(_tool_belongs_to_component(tool, component) for component in allowed_components)
        )
```

两个定义都列出了全部九个工具，裁剪发生在这里。注释里"避免优先级诱导 Planner 越界调查"点明了必要
性：如果只查 LTS 却把九个工具都按优先级递给模型，模型很可能顺手调 BDS——即使 Prompt 说了"仅调查
唯一组件"。**减少诱惑比增加禁令有效。**

注意这只是"优先级列表"的裁剪，真正的越界拦截在 ReAct 循环的门禁（第 8 章：capability 范围校验，
整批拒绝）。这里是第一道，那里是最后一道。

组件归属判断用前缀比较：

```python
def _tool_belongs_to_component(tool: ToolName, component: Component) -> bool:
    return tool.value.startswith(f"{component.value}.")
```

docstring 解释了为什么不维护一张映射表：

> 工具名契约固定为 `<component>.<operation>`，因此前缀比较可复用九个枚举且无需维护第二张易漂移
> 映射表。

这是第 1 章"唯一定义"的又一次应用：`lts.get_task_status` 属于 `lts` 这件事已经写在名字里了，
再建一张 `{ToolName: Component}` 字典就是把同一个事实存两遍，两遍就会漂移。代价是命名规则变成了
隐式契约——docstring 因此点明"若未来命名规则改变，工具契约测试和本函数测试会共同失败"。

### 4.7.4 `_stable_unique`：为什么不能排序

```python
def _stable_unique(items: tuple[_Item, ...]) -> tuple[_Item, ...]:
    seen: set[_Item] = set()
    result: list[_Item] = []
    for item in items:
        # 只有第一次出现时才保留，既合并共享输入又不改变前一个能力声明的优先级。
        if item not in seen:
            seen.add(item)
            result.append(item)
    return tuple(result)
```

docstring 里那句"该函数不排序，因为排序会破坏调查优先级"是重点。用 `set()` 或
`sorted(set(...))` 去重是最常见的写法，但工具顺序**是策略的一部分**（4.5.2 那个二三位对调）。
一次 `sorted()` 会把"先看拓扑再看日志"变成字母序。

`TypeVar("_Item")` 让它对工具、输入枚举、规则字符串三种类型复用而不丢类型信息。

### 4.7.5 Prompt 片段带标签拼接

```python
        prompt_fragments = tuple(
            f"[{definition.name.value}]\n{definition.prompt_fragment}" for definition in definitions
        )
```

每段前面加 `[capability_name]` 标签。这不只是好看：`CapabilitySelection.validate_aligned_fragments`
要求 `active_capabilities` 与 `prompt_fragments` **位置一一对应**：

```python
        if len(self.active_capabilities) != len(self.prompt_fragments):
            raise ValueError("each active capability requires exactly one prompt fragment")
        if len(self.active_capabilities) != len(set(self.active_capabilities)):
            raise ValueError("active capabilities must not contain duplicates")
```

docstring 说明了价值："位置对齐使审计者能把合并 Prompt 追溯到具体能力。" 也就是说，当模型输出
了一个奇怪的结论，你可以从最终 Prompt 里的标签反查是哪项能力的指令在起作用——**Prompt 也需要
可追溯性**。

第二条（不许重复）的理由同样有意思："重复能力会改变权重感知却没有业务含义。"同一段指令出现两次，
模型会认为它更重要，而这个权重变化没有任何人有意为之。

## 4.8 `CapabilitySelection` 是一个可写进状态的快照

```python
class CapabilitySelection(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    contract_id: str = Field(pattern=r"^runtime-capabilities:v\d+$")
    intent: DiagnosisIntent
    components: tuple[Component, ...]
    history_trigger: HistoryTrigger
    active_capabilities: tuple[CapabilityName, ...] = Field(min_length=3)
    ...
```

它把"这次诊断用了什么策略"完整记录下来：契约版本、路由输入（意图、组件、历史触发）、结果（能力
顺序、Prompt 片段、工具顺序、输入需求、输出规则）。

`contract_id` 用正则约束成 `runtime-capabilities:v\d+`，而值由 `registry.contract_id` 提供，也就是
`CAPABILITY_CONTRACT_ID = "runtime-capabilities:v1"`。第 2 章讲过 lifespan 会把它和 Settings 里的
期望值比对。**为什么选择结果里要带契约版本？** 因为合并语义可能变（比如将来风险能力改成可选），
带版本的评测记录才能说明"这一批数字是在哪套合并规则下测出来的"。

`frozen=True` 加 `tuple` 让它可以安全地写进 `AgentState`：LangGraph 会在节点之间传递状态，
不可变对象不可能被某个下游节点就地改写。docstring 写着："后续工作流可安全写入状态而不会被就地
修改或混入执行对象。"

## 4.9 `get_capability_registry`：又一个 `lru_cache`

```python
@lru_cache(maxsize=1)
def get_capability_registry() -> CapabilityRegistry:
    return CapabilityRegistry()
```

和第 2 章的 `get_settings` 同一个手法。docstring 给了两个理由：避免 lifespan 与路由重复审计同一组
定义；确保各节点观察一致契约。

最后一句是给测试写的："测试若需验证全新构造，可直接实例化 `CapabilityRegistry` 而不修改缓存对象。"
——**提供一条不污染全局状态的测试路径**，比在测试里 `cache_clear()` 更干净。

## 4.10 本章小结

| 设计选择 | 实现 | 拒绝的替代方案 |
|---|---|---|
| 能力是数据不是执行体 | `CapabilityDefinition` 无回调字段 | 五个子 Agent |
| 能力选择是确定性的 | `select` 里几行 `if` | 让模型选工具/能力 |
| 能力集合固定 | `CapabilityName` 枚举 + 构造期审计 | 插件目录、动态加载 |
| 历史召回必须有理由 | `HistoryTrigger` 默认 `NOT_REQUESTED` | 每轮无条件召回 |
| 优先级顺序是策略 | `_stable_unique` 不排序 | `sorted(set(...))` |
| 工具范围随组件裁剪 | `_tool_belongs_to_component` 前缀过滤 | 全量递给模型 |
| Prompt 可追溯 | `[name]` 标签 + 位置对齐校验 | 一大段拼接文本 |
| 选择结果可审计 | 冻结快照 + `contract_id` | 只把 Prompt 传下去 |

一句话：**这一层的价值在于把"策略"从"执行"里剥出来。** 策略是数据，可以被审计、被版本化、被
测试；执行只发生在两个 Agent 和一个执行器里，出口数量固定。很多 Agent 项目的复杂度失控，恰恰是
因为每加一个"能力"就多一个能自己调模型和工具的执行体。
