# FlashSync checkpoint 回退导致同步延迟的复盘

本复盘描述合成环境中的一次故障演练，用于说明"同步延迟持续增长但任务并未失败"这一形态的判定路径。时间、数值与组件均为演示用途。

## 故障概述

FlashSync 增量同步任务在一次进程重启后恢复到了一个较早的 checkpoint，随后同步位点虽然持续推进，但与源端最新位点的差距不断扩大。任务状态始终为 `running`，没有产生任何失败告警，因此延迟在约四十分钟后才被下游发现。

## 影响

- 下游 BDS 聚合任务读到的增量数据窗口不完整，产出结果口径偏小。
- 依赖该结果的 LTS 报表任务按时完成，但报表数值偏低，属于"成功但错误"的最危险形态。

## 时间线

1. 同步任务因所在节点资源回收被重启，重启本身符合预期。
2. 恢复时使用的 checkpoint 比最后一次成功提交的位点更早，重放了已同步过的区间。
3. 重放期间源端仍在持续写入，位点差距因此单向扩大。
4. 下游聚合结果异常后人工介入，才定位到 checkpoint 回退。

## 根因

checkpoint 提交与位点推进不是同一个原子操作：最后一次成功的位点推进没有对应的 checkpoint 落盘，重启后只能从更早的 checkpoint 恢复。这不是数据错误，而是恢复语义与提交语义之间的缝隙。

## 判定要点

出现"任务健康但延迟持续增长"时，应优先检查以下三项，而不是先看资源水位：

- 当前 checkpoint 时间戳与任务启动时间的关系：若 checkpoint 明显早于上次正常运行的结束时间，即为回退。
- 同步位点差距的变化趋势：单向扩大说明消费速度低于生产速度，与瞬时抖动不同。
- 目标端记录是否出现重复写入痕迹：重放区间可能与已同步区间重叠。

## 改进项

1. 恢复流程增加一步显式确认：重启后核对 checkpoint 时间戳与上次成功位点，差距超过一个批次窗口即人工介入。
2. 为"任务健康但延迟增长"单独建立观测视角，不再只依赖任务失败告警。
3. 下游聚合任务在读取增量数据前校验窗口完整性，避免不完整数据被当成正常输入。
